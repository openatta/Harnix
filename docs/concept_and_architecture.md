## 1. 定位

**Harnix 是 Agix 应用的公共底座。**

引擎负责「跑一个 agent 会话」：装配提示词、调模型、执行工具、管理上下文与历史。Harnix 负责把一台或
几台引擎变成一个**应用**：会话的持有与追赶、实例的组织、界面的外壳、身份与授权、部署形态，以及让
应用作者把自己的代码接进来的契约。一个应用（Helm、IPDrun、Grabix）是一个二进制加一份编在里面的界面产物，由
`harnix::App::builder()` 加上应用自己的模块组成，不 fork、不留补丁。

**Harnix 本身是三部分：**

| 部分 | 是什么 | 在哪讲 |
|---|---|---|
| **框架** | 骨架（传输、授权、中枢、装配）、实例层、模块契约、外壳与贡献点、插件 APP 的宿主 | 本文 |
| **Harnix app** | 会话 space 与项目 space：新建会话、按时间看会话、按项目管理会话。用框架自己的公开接口做的一个小应用 | [Harnix app](harnix-app.md) |
| **系统 space** | 始终在的调试面：按进程、实例、会话、任务看见并操作一切；应用开发的工具链（流程）也在这里 | §5.5、[系统 space](system-space.md) |

Harnix 自己发布的二进制 `harnix` 就是这三部分，再注册了流程模块。一个产品是框架上的另一个应用，和 Harnix app 同一种做法，
只是更大；它用 `[shell] spaces` 决定留不留 Harnix app 的两个 space 和系统 space。

这条分工是硬的，两个方向都是：

- **Harnix 不含任何引擎逻辑。** 会话怎么跑、工具怎么派发、上下文什么时候压缩，一律是 Agix 的事。
  缺的能力去给 Agix 提，不在这边补一个平行实现——一个平行实现意味着同一件事有两处真相，而它们会分叉。
- **Agix 不知道有界面、space、应用这回事。** 客户端面的协议、贡献点、身份、space、插件 APP，全部止步于 Harnix。

### 1.1 它不是什么

| 不是 | 因为 |
|---|---|
| 一个 agent 框架 | 框架是 Agix。Harnix 是它的宿主 |
| 一个多租户服务 | 一个进程服务一个用户（多个会话、多台设备、可以多台实例）。多租户是另一个系统，不是这个系统的配置项 |
| 一个「什么都能换」的内核 | 骨架不可插拔，见 §2.1 |
| 应用的功能仓库 | 应用独有的东西（领域服务、产品面板、批准策略）不进 Harnix，见 §1.3 |

### 1.2 三个目标，按优先级

1. **可定制。** 不 fork 就能做出一个形态不同的产品。这是首要目标，其余两条服务于它。
2. **可在边缘部署。** 一个后端二进制，无运行时依赖，冷启动以毫秒计，空载内存以十兆计。
3. **安全边界清楚。** 每一处约束要么是强制的，要么被明说成不是强制的。没有第三种。

落地它们的方式：应用以子仓引入 Harnix（Harnix 带着 Agix）、用编译期模块装配，产品可以再让别人装插件 APP（目标 1）；一个 Harnix
可以组织多台互相隔离的实例，进程内的、独立 daemon 进程的都行（目标 1、2）；插件 APP 跑在 WASM 里、按清单拿能力，自带一个能看见一切的
系统 space（目标 3：看得见才谈得上清楚）；每个功能都对着真的二进制测（§8）。

### 1.3 什么进 Harnix：判据

> **只有在公开契约之上做不出来，或者做出来会破坏 Harnix 不变量的东西，才进 Harnix。**

满足下面任一条才进：

- 它要碰中枢、授权、传输、装配的内部（例如无头会话：要和客户端共用排队与 `seq`）；
- 应用各写一份会破坏一条不变量（例如会话与 space 的对应关系）；
- 它本身就是契约的一部分（模块 trait、贡献点、宿主 API）。

「第二个应用也会要」不够：那样几乎什么都能塞进来。其余的，即使两个应用都要，也先由应用在模块契约上
实现；等两份实现证明是同一个形状，再考虑收进来。Helm、IPDrun 的需求是**输入**，不是必须满足的清单。

背后是维护者定下的一条：**Harnix 自己保持薄、容易改造。** 一个什么都带的底座，每个应用都要先学会
关掉它不要的那些；一个薄的底座，应用只学它要的那些。内建的东西因此也都做成可以去掉的：Harnix app 的
两个 space 与系统 space（`[shell] spaces`，§5.3、§5.5）、Agix 插件的界面模块（`[ui] runtime_modules`，§5.8）、插件 APP（cargo feature
`apps` 与 `[apps] enabled`，§4.3）都有开关。

## 2. 设计原则

### 2.1 骨架不可插拔

Harnix 的骨架是四件事：**传输、授权、中枢、装配**。它们不是扩展点，没有替换入口。

理由和引擎把轮次循环的步骤顺序写死是同一个：**顺序与所有权本身就是定义**。一个能被插件换掉的会话
中枢等于没有中枢——追赶不变量一旦可以被第三方重写，「打开一个跑到一半的会话会看到什么」就不再有
答案，而这是产品最基本的动作。

骨架之上的每一个判断都可插拔。分界线画在「这件事的形状」和「这件事怎么做」之间。

**「不可插拔」约束的是语义，不是实现形式。** 传输承载什么、保证什么是写死的，用几条连接承载不是
（§3.3）；中枢的语义是写死的，它对面的实例在本进程里还是在另一个进程里不是（§3.1.1）。

### 2.2 扩展按出身分：模块、插件、Agix 插件

扩展 Harnix 产品的代码有三种出身，各自的信任与能力不同，也各有自己的名字：

| 出身 | 什么时候进来 | 谁写的 | 跑在哪 | 信任从哪来 | 能加 space | 能加后端方法 |
|---|---|---|---|---|---|---|
| **编译期模块**（`Module`） | 应用构建时链接 | 应用作者本人 | 原生，Harnix 进程内 | 出身：它就是应用本身，内核级 | 能 | 能，在 `app.<模块 id>.*` |
| **插件**（插件 APP，代码里叫 `apps`） | 运行期安装 | 第三方也可以 | 后端与工具在 Harnix 的 WASM 沙箱里；Agent 部分在 Agix 里；界面在隔离的 iframe 里（受信发布者可进页面） | 签名（商店副署、受信发布者），加清单声明、装前披露、人同意的能力 | 能，id 是应用 id 或 `<应用 id>.<名字>`，照清单 | 能，在 `app.<应用 id>.*`，照清单 |
| **Agix 插件**（运行期包） | 运行期安装 | 第三方 | Agix 里：QuickJS 脚本、skill、agent 类型；`[[ui]]` 段的界面模块在页面里 | 引擎的能力门控与披露；界面模块与页面同级 | 不能 | 不能 |

**模块不是插件。** 编译期模块是应用作者链接进来的 Rust 源码，和内建模块同级，没有运行期加载、没有包、没有签名，
所以不叫插件。它的信任来自出身，不来自声明（§2.3）。应用要做的领域能力（后端方法、space、原生工具）写成模块。

**插件就是插件 APP。** 一个插件是一个应用包（`.hxapp`）：清单、一个 WASM 组件、一个 Agix 插件、界面，各部分可选，
从商店下载、验签、装上就能用，不改产品、不重新编译（§4.3，[插件](harnix-plugin.md)）。它能做的是编译期模块的一个子集，而且
**每一样都要在清单里写出来**：方法、主题、space、能调的 hub 方法、联网的主机、环境变量、存储。

**Agix 插件是引擎的。** 包格式、取包、校验、manifest、能力声明、披露、沙箱、生命周期，整件事都在引擎那边；Harnix 只把文件送过去、
读它引擎不关心的那一段 `[[ui]]`（§4.4）。插件 APP 的 Agent 部分就是一个 Agix 插件，Harnix 替它装进声明的实例。

一件事只有一处真相。插件 APP 的后端与工具是 Harnix 的事，因为 Agix 不再承接 WASM（它只留 Rust 插件与 QuickJS）；它的 Agent 部分
仍然是 Agix 的事，Harnix 不另起一套 Agent 侧的扩展。

#### 2.2.1 只在 WASM 沙箱里执行包里的代码，QuickJS 按签名信任

> **Harnix 只在 WASM 沙箱里执行包里的代码。包里的 QuickJS 在引擎里跑，按签名信任。**

- **WASM**：插件 APP 的后端与工具是 WASM 组件，跑在 Harnix 自己的 wasmtime 里（`harnix-wasm`）。它是隔离边界：内存安全，没有环境里的文件与网络，
  能碰到的只有宿主函数，而每个宿主函数都按清单的能力检查（`net` 精确主机、`env` 名单、`storage_mb` 上限、`hub` 方法名单、`fs` 预开目录）。
- **QuickJS**：插件 APP 的 Agent 部分可以带 QuickJS 脚本，它们挂在 Agix 的扩展点上、在引擎里跑、没有 I/O。Agix 明说 QuickJS 只限资源、
  **不是隔离边界**，所以它的信任来自签名：商店审核时按「脚本即代码」对待。
- **不执行的**：原生动态库、包里的任意进程、Harnix 自己的脚本解释器。Harnix 侧没有一个能跑包里脚本的地方：扩展 Agent 的脚本是 Agix 的。

由 `crates/harnix/tests/layering.rs` 盯着：整个 crate 树里不许出现任何解释器；wasmtime 只许出现在 `harnix-wasm` 里，外面经它的 API 碰组件，
那个 API 叫不出 wasmtime 的类型。

**为什么不是更宽的规则。** 早先有过一个例外：Agix 包的 `[[host]]` 段里的投影，一个折叠会话事件流的纯函数，由 Harnix 执行。它让规则必须写成
「Harnix 执行包里的代码，但只执行什么都做不了的那种」，而**一条带例外的规则是会被人加宽的**，所以它被撤掉了。今天的规则也不带例外：
包里的代码要在 Harnix 这边跑，只有一种跑法，就是 WASM 沙箱；要的每一项能力都在清单里、在宿主函数里查。编译期模块不受这条约束——
它不是包里的东西，是应用本身。

#### 2.2.2 为什么是今天的形状

这一节改过几次方向。留下来的理由是：

- **Agent 侧的扩展归引擎。** 一件事两处真相，它们就会分叉，而分叉之后往往只有一处是真正拦得住的。所以 Harnix 不做 Agent 侧的第二套插件，
  Agix 插件的包方案、能力与披露都留在引擎；Harnix 只补引擎有意不做的那一步（收文件，§4.4）。
- **应用的领域能力要原生。** 应用要在 Harnix 上做产品，就要能加后端方法、space、原生工具，这些运行期包给不了，也不该给。答案是
  **另开一种出身**：编译期模块，应用作者本人的源码，信任级与内核相同，编译期链接。
- **第三方的后端逻辑要隔离。** 应用要让别人往产品里加东西（模式 2），而第三方代码不能是内核级的。答案是 WASM：一个能对恶意代码也成立的
  边界，加上清单里逐项的能力。WASM 载体原来在 Agix 里，和脚本载体互斥；它搬到 Harnix 之后，Agix 只留 Rust 与 QuickJS 插件，
  WASM 只有一处，在 Harnix。

写下来是因为 §2.5：一份反复改过又没说为什么的设计，读的人无从判断哪一版是当前的。

### 2.3 信任按出身定，不按声明定

一个来自外面的扩展要撒谎，撒的正是「我需要什么」这种声明。所以级别由它**从哪儿来**决定：应用作者
编进来的模块、运维本人写在项目里的东西、装上的插件、远端连上来的设备，天然不同级。声明的作用是在已定
的级别内**进一步收窄**，不是用来晋级的。

插件 APP 是这条的直接用法：它的出身由签名定（商店副署、受信发布者、未签名），出身定了它的界面进页面还是进 iframe、能不能在非开发模式下跑；
清单里的能力只在这个级别里收窄——一个清单写得再宽，也拿不到 WASM 沙箱之外的东西。

### 2.4 失败的扩展只让它自己那份贡献消失

抛异常、超时、配额耗尽、答出一个用不了的形状——这个点保持原样，别的什么都不受影响。每个适配器先把
改动完整算出来再施加，所以不存在「施加了一半」的状态。

这条对每一种出身都成立：

- 一条界面贡献渲染出错，只有它消失；形状不对或 id 重复，这一条被拒，记进诊断。
- 一个包的界面模块照旧版贡献点 API 写的，**那一条**报「不生效」，包的其余部分照常（§5.8）。
- 一个编译期模块注册冲突、`migrate` 或 `start` 失败，只停用这个模块和它的方法、主题、路由、space、
  实例，进诊断页；别的模块照常启动。
- 一个插件 APP 装到一半失败，整体回滚，只停这一个；它的后端超时只换掉它的实例，崩溃两次只把它置于一旁；它的一个界面面板
  崩了，外壳只在那一块画「出错了，重试」，连续失败的面被置于一旁。

而且**「它什么也没做」是可查询的**：哪个点、谁、什么原因，都记下来并且能问（`harnix.diagnostics`、
设置与系统 space 的诊断）。否则「我的插件为什么不工作」只能靠猜。插件 APP 的这些在系统 space 的应用页签里（§5.5）。

### 2.5 每一条承诺都可检查

贡献点目录由代码生成；层与层之间的依赖方向由测试断言而不是由文档描述；性能预算进 CI 门禁；内建界面
走的就是公开的那批贡献点，而且有测试盯着「外壳真的去问了」；功能覆盖表由用例标签生成，一行在某一层是
零就失败。**一份没人检查的承诺，下一次改动就变成谎话。**

## 3. 内核

骨架是四件事：装配、中枢、传输、授权（§2.1）。先看它们管着的东西。

**运行时四层。** Harnix 里一切和 Agent 有关的东西都落在这四层之一：

```text
Harnix 进程
 ├─ 实例 system           （进程内）  ← 隔离单位：数据根、设置、provider、MCP、Agix 插件、场景
 │   ├─ 会话 a            ← 一条轮次循环；同一时刻至多一轮
 │   │   ├─ 任务：子 Agent "explore"     ← 属于会话，跟着会话的权限、项目根、生命周期
 │   │   ├─ 任务：后台 Bash `npm run dev`
 │   │   └─ 任务：定时任务 0 9 * * *
 │   └─ 会话 b
 ├─ 实例 helm-l1          （进程内，Helm 的模块按自己的模板建的）
 └─ 实例 ci-runner        （daemon，本机另一个进程）
```

| 层 | 是什么 | 拥有什么 | 隔离到什么程度 | 谁建 | 身份 |
|---|---|---|---|---|---|
| **Harnix 进程** | 一个二进制，一个用户 | 中枢、授权、传输、实例登记表、账本 | — | 运维 | — |
| **实例** | 一台 Agix 引擎，一个会话池 | 数据根（设置三层、transcript、记忆、技能、录像）、provider 路由与凭据、MCP 连接、插件、场景、原生扩展 | **彼此完全隔离**。daemon 载体还隔离了崩溃和资源 | profile 声明；模块、界面按模板建 | `instance` |
| **会话** | 实例里的一条轮次循环 | transcript、场景（创建时定，决定工具集）、项目根、模型、权限规则 | 共享所属实例的配置；彼此的上下文互不可见 | 客户端、模块（无头）、模型（子 Agent 的侧链） | `(instance, session)` |
| **任务** | 属于某个会话、在会话之外继续跑的工作 | 子 Agent、团队成员、执行中的 Shell 与监视器、定时任务 | 跟着所属会话：同一套权限、项目根；会话删了，任务一起没 | 会话里的模型（经工具） | `(instance, session, task)` |

由这张表直接推出来的规则：

- **隔离只在实例这一层承诺。** 要两套互不相干的配置（不同的 MCP、凭据、场景），就建两台实例，不在
  一台实例里靠会话区分。进程内实例的隔离由 Agix 承诺（同一进程里的几台会话池互不可见，有守护测试；
  唯一共享的是 OTel 导出器）。
- **任务是 Agix 的东西，Harnix 只看、只转发停止。** 子 Agent 的侧链在 Agix 里也是一个会话，在 Harnix
  里它是父会话的任务，不出现在会话列表的顶层，不进中枢的键，不进账本。
- **会话不跨实例，也不跨 space。** 要跨就用 `@session` 引用或分叉（§5.4）。
- **轮不一定由 Harnix 发起。** 定时任务会让一个会话自己开始一轮。实例在 `daemon.event` 上报每一轮的
  开始与结束（带 `initiator`），中枢据此知道，不假定「我没发起的轮就不存在」。

**结构。** 装配分实例层与应用装配两层（§3.1）；中枢下面不是「一个引擎」，而是一张实例登记表，中枢只认 `EngineLink`（§3.1.1）；
内建功能全部是内建模块；插件 APP 的运行时是 `apps` feature 才链进来的一组 crate，接在模块这一层（§4.3）。

```text
 浏览器（同一份产物；Tauri 只是装它的窗口）
 ┌──────────────────────────────────────────────────────────────────┐
 │ @harnix/shell  外壳：固定外框、space 切换、设置；Harnix app 与系统 space     │
 │ 应用的 space    应用自己的 React 组件，只依赖 @harnix/react              │
 │ 插件 APP 的界面 隔离 iframe 里的页面，经桥（@harnix/app-sdk）借外壳的手   │
 │ @harnix/react  贡献注册表、useNest()、i18n、令牌；对话组件 ChatPanel 等     │
 │ @harnix/core   不依赖框架：协议类型（生成）、协议客户端、会话状态            │
 └──────────────────────────────┬───────────────────────────────────┘
                                │ 五种通道语义（拓扑可选）· /apps/<id>/ 自有链接
 ┌──────────────────────────────▼───────────────────────────────────┐
 │ harnix 进程（应用的二进制 = App::builder() + 模块）                      │
 │  传输 harnix-transport  通道、TLS、静态面、模块路由、启动链接              │
 │  授权 harnix-authz      唯一准入点：主体 × 方法 / 路由，默认拒绝            │
 │  中枢 harnix-hub        会话持有者：订阅、缓冲、turn、队列；两类调用方      │
 │  实例 harnix-instance   模板、两种载体，一个 EngineLink                   │
 │  模块 harnix-module     编译期模块契约、注册表、贡献点目录                  │
 │  装配 harnix-app        App::builder()、profile、启动顺序、诊断            │
 │  插件 APP harnix-apps…  应用宿主、harnix-wasm（每应用一台虚拟机）；可选     │
 └────────────┬──────────────────────────────┬──────────────────────┘
              │ 进程内调用                     │ JSON-RPC（unix socket / 回环 ws）
      ┌───────▼────────┐             ┌───────▼──────────────────┐
      │ Agix 实例       │  ……         │ Agix daemon 进程          │ ……
      │（作为库链接）    │             │（由 Harnix spawn 或 attach）│
      └────────────────┘             └──────────────────────────┘
```

依赖是单向的，每一层不认识它上面那层的概念，由 `crates/harnix/tests/layering.rs` 断言：

| 层 | 不许知道 |
|---|---|
| 传输 | 会话、实例是什么 |
| 授权 | 帧长什么样、走的哪条通道、实例在哪 |
| 中枢 | HTTP、TLS、连接、拓扑、**实例的载体** |
| 实例层 | 客户端面协议、space、模块 |
| 模块契约 | 中枢、`EngineLink` |
| 协议类型（`harnix-contract`） | 任何一层 |

内建功能（会话与工作区、文件、搜索、设置、Agix 插件、设备、系统 space、录像，以及代管插件 APP 的 `apps`）全部是**内建模块**，只走公开的
模块 API，同一个测试盯着。如果内建的东西不能用公开契约写出来，这份契约就不值得相信。

### 3.1 装配：应用装配与实例层

装配拆成两层：**应用装配**（`harnix-app`：这个进程由哪些模块组成、按什么顺序起来）和**实例层**
（`harnix-instance`：怎么建或连上一台引擎）。

装配是**声明式的**，并且在启动时定：

> **装配在启动时定：有哪些模块、哪些模板、哪些载体。运行期能新建的只有会话、模板允许的实例，以及经 `apps` 内建模块
> 登记的插件 APP 的方法、主题与 space。模板与模块本身不能在运行期新增或改写。**

本意是「运行期没有东西能决定这个进程是什么」。运行期建出来的每台实例，在启动时就已经能被枚举（模板 × 允许的参数）。插件 APP 登记的东西
也不改写装配：它们只在 `app.<应用 id>.*` 与 `<应用 id>.*` 这两个命名空间里，照装前披露过的清单，可撤；名字和任何编译期模块重叠就拒，
编译进来的优先；内核只把登记的接口给 `apps` 一个模块。`[apps] enabled` 关着时这条路不存在，授权表就是启动时装配出来的那张。

启动顺序：

1. 读 profile。
2. **注册**：按顺序调每个模块的 `manifest` 与各注册函数。模块 API 版本不符**编译不过**；id、方法、路由
   冲突时后注册的那个停用。
3. **迁移**：按顺序调 `migrate`，失败只停用这个模块。
4. **建实例**：`system`（带上仍启用的模块给它的原生贡献）、profile 的 `[[instances]]`、账本里按模板建过的。
5. **启动**：按顺序调 `start`，失败只停用这个模块和它的一切；它已经交给 `system` 的场景摘不掉，留到下次
   启动，诊断页写明。
6. 开始服务。

引擎的根**显式传进去**，不改本进程的环境变量：那样一个进程才可能服务几台实例，状态也不会藏在调用者
看不见的地方。

#### 3.1.1 实例层：载体、模板、EngineLink

**实例只从声明来**：profile 里声明的固定实例，或者按模板建的。

| | 进程内 | daemon |
|---|---|---|
| 是什么 | Agix 的会话池建在本进程里 | 本机另一个 Agix daemon 进程，经 JSON-RPC（unix socket 优先，其次回环 ws） |
| 怎么来 | Harnix 建 | **spawn**：Harnix 起子进程并做最小看护（等它开始监听；stdin 一断它就退出，所以随 Harnix 退出；退出了就重启，连续几次刚起来就退出则不再重启——重启循环只会掩盖问题），默认起本二进制的 `harnix daemon`，版本按构造就对得上；**attach**：连一台只给这个 Harnix 用的 daemon |
| 原生 Rust 贡献 | 能：场景、原生工具、`SessionCustomizer`、凭据源 | 不能，只有那个 daemon 自己的配置与插件 |
| 隔离 | 状态隔离；崩溃与资源共用进程 | 状态、崩溃、资源都隔离；断了是「实例降级」，不是 Harnix 挂掉 |
| 版本 | 必然是这次构建链接的那版 Agix | 握手比对协议版本，不匹配就拒绝并说清楚 |

**模板**（`InstanceTemplate`）是建实例的规格：载体、场景、数据根规则、允许调用方填的参数、能不能由
界面用（`ui`）、最多几台。profile 里的模板只能是 spawn 或 attach（profile 拿不出原生贡献）；模块在
`templates()` 里声明的进程内模板可以带原生贡献。**界面永远给不出二进制路径、命令行参数、环境变量、
模型端点**——那些等于「装载子进程、改写模型端点」，不对设备开放（§3.4）。

每台实例有**拥有者**：`kernel`（profile 声明的）、`module:<id>`、`space:<id>`（界面建的，归发起时的前台
space）。账本记按模板建的实例；**重启后一律由 Harnix 按账本重建**：模板还在、拥有者启用着就照建；
否则这台实例显示为 `Down` 并写明原因，数据根不动。模块停用时，它拥有的实例和它的模板建出的实例一起停。
删除实例删的是登记，数据根默认保留。

**中枢与实例之间只有一个接口：`EngineLink`。** 一次调用、全部异步帧、一个屏障标记（中枢结算一轮前
在已收到的帧后面放一个标记，等它从事件流里出来——等的是「已经路由」，不只是「已经收到」，否则
`turn_settled` 会超车本轮最后的事件）、链接状态（`Starting / Ready / Degraded / Down`）。三种实现：
进程内、daemon、`DownLink`（建不起来的实例）。中枢的代码里不出现「是不是远程」的分支。

**`EngineLink` 不对模块开放。** 模块拿到的是只读的 `InstanceHandle`，所有会话调用仍然经过中枢和授权。
模块要是能直接对一台实例发 `session.run_turn`，「中枢先订阅」这条不变量就有了旁路。

**daemon 的语义。** daemon 对一条通过认证的连接完全信任，没有逐方法授权。所以：

- **一台 daemon 只服务一个 Harnix。** spawn 的天然如此：它的 unix socket 放在只有本用户能打开的私有
  目录里；attach 的由运维保证。中枢的排队、结算、「先答者生效」都假定它是这台 daemon 上会话的唯一调用方。
- **daemon 的凭据不出 Harnix**：经回环 TCP attach 时要的 token 在 profile 里只写凭据名，值由凭据源给，
  不发给任何客户端。
- 透传白名单对每台实例都一样，`config.setProvider`、`mcp.addServer` 这些对 daemon 实例同样拒绝。
- **断线**：实例变成 `Degraded`，daemon 那边的轮照跑。中枢重连后对每个在观看的会话重建缓冲，再推
  `harnix.session_resync`，客户端照刷新那条路重新 attach；这期间的发送进队列，不拒绝。daemon 丢订阅
  （`subscription_dropped`）走同一条路。这是中枢本来就有的恢复路径，不是新语义。

### 3.2 中枢

中枢是会话的持有者。它的存在理由是一条不变量：

> **中枢永远比任何客户端先订阅。**

会话第一次被打开时中枢立刻订阅并开始缓冲，此后任何观看者的追赶**只在中枢的缓冲区里进行**。由此得到：

1. **刷新页面不丢内容。** 一轮跑到一半刷新，前半段在缓冲里，不依赖引擎补发。
2. **turn 不挂在连接上。** 关掉标签页、切换设备、断网重连都不影响这一轮，最终结果广播给所有观看者。
3. **多设备一致。** 同一个会话可以被几个客户端同时看，任何一个都能回答权限提问，先答者生效。
4. **排队是产品行为，不是错误。** 引擎对同一会话同时刻只允许一个 turn；有 turn 在跑时新消息进中枢的
   队列，上一轮结束后自动发出，队列可撤销，整值快照推给所有客户端。

**turn 由中枢发起，调用方有两类：客户端和服务端（内核、模块），语义相同**——排队、中断、结算、广播
都一样。服务端调用方经 `ModuleContext.sessions` 建、开、发、中断、关闭会话（**无头会话**），用
`OnBusy { Queue, Reject, Interrupt, Steer }` 说忙的时候怎么办；客户端的 `harnix.send` 和服务端的发送走
同一条路径。无头会话照样出现在它所属 space 的会话列表里，界面随时可以 attach 旁观。

为什么是两类调用方而不是只有客户端：无头会话必须和客户端共用排队与 `seq`——在中枢之外另做一份，就是第二份会话状态。
插件 APP 的后端驱动会话也走这一条（经 `host.call` 调 `session.create`、`harnix.send`，以 `module:<id>` 准入）。

**tap** 是服务端的观看者，和客户端观看者同一套语义，不是一条特殊的无损通道：有界、按 `seq` 投递、
**不在中枢的锁里等待**；满了就标成落后，它下一次读到 `Lagged { last_seq }`，按客户端追赶那条路补齐。
**中枢永远不会因为一个慢的 tap 卡住会话。**

**推送一律整值。** 队列、会话列表、实例树、引擎健康这类状态推的是完整快照，客户端不做增量合并——增量
合并的错误只在特定顺序下出现，而那个顺序在测试里不容易造出来。宿主主题可以**带参数订阅**，值在有人
订阅时才算，短时间内的多次变化合成一次：

| 主题 | 参数 | 内容 |
|---|---|---|
| `harnix.instances` | — | 实例登记表：载体、模板、拥有者、链接状态、版本、会话数 |
| `harnix.instances.sessions` | `instance` | 这台实例的顶层会话 |
| `harnix.sessions.tasks` | `instance`、`session_id` | 这个会话的任务 |
| `harnix.sessions.status` | — | 所有会话的运行状态 |
| `harnix.process` | — | 进程：版本、运行时长、内存、线程、已连接的客户端（有人订阅时每 5 秒重算） |
| `harnix.apps` | — | 插件 APP 的快照：每个应用的状态、健康、调用与被拒的调用（`[apps] enabled` 时） |
| `app.<id>.<主题>` | 模块或插件 APP 声明 | 它推的整值快照；插件 APP 撤下时订阅者收到 `harnix.topic_ended` |

中枢的状态与语义**不可替换**（§2.1）。

#### 3.2.1 往对话里写东西：扩展条目

模块可以往会话时间线写**扩展条目**（例如「采集任务跑完，推一张任务卡」）：走 Agix 的扩展条目
（`session.appendEntry` / `session.entries`），由 `flow.block` 画出来。条目进入会话日志，刷新、重放、
分叉都看得到；**只给人看，不给模型看**；命名空间由中枢定为 `app.<模块 id>`，模块自己说不了算。
Harnix 不另存一份会话状态。

### 3.3 传输

传输是**一组通道语义**，不是一种连接拓扑。**语义写死，拓扑可选。**

理由很具体：不同的部署对连接的诉求不一样。边缘弱网下少开一条连接是省下的重连与心跳；放在反向代理后面
时，让请求走普通 HTTP 能直接吃到现成的中间件；一个只想看进度的只读客户端不该被迫开一条能发请求的
双向连接。**这些差异不该逼着中枢换一套语义。**

#### 3.3.1 五种通道语义

| 语义 | 干什么 | 谁发起 |
|---|---|---|
| **unary** | 一次请求一次应答的方法调用 | 客户端 |
| **会话事件流** | 某个会话的事件：流式正文、工具行、权限提问、子 Agent、扩展条目 | 服务端 |
| **宿主事件流** | 与具体会话无关的主题：实例树、会话状态、队列、模块主题 | 服务端 |
| **带外应答** | 对服务端发起的提问的回答（权限、澄清） | 客户端 |
| **大负载旁路** | 附件上传、导出下载 | 双向 |

会话事件与宿主事件从语义上就是两个订阅面：一个只看侧栏的客户端不该为了知道「哪个会话在跑」而接收所有
会话的正文。带外应答单列，是因为它在只下行的事件流拓扑里没有回程可用。

#### 3.3.2 三种参考拓扑

| 拓扑 | 映射 | 适合 |
|---|---|---|
| **单双向流** | 一条双向连接承载全部（大负载仍走旁路） | 单机、边缘弱网 |
| **分离流** | unary 与带外应答走 HTTP；两种事件流各一条只下行流 | 反向代理后面、多客户端、只读客户端 |
| **纯请求** | 只有 unary 与旁路，事件靠长轮询补上 | 脚本客户端、受限网络 |

三种拓扑的方法名、参数、错误码、事件形状完全一致。服务端配置支持哪几种，客户端在握手时选一种；不匹配
就拒绝并说清原因，不做静默降级。

分离流的一条事件流断了可以再开：再开就换掉前一个读者，浏览器的 `EventSource` 自己重连就能接上（断开期间的帧
不补发）。所以客户端库在两条流都重新开上之后，像重连之后那样追上：状态再报一次 `open`，看会话的重新 attach、
订阅的重新订阅。服务端拒了的流（不认识的凭据，比如进程重启过）浏览器不再重开：客户端重新握手，握手之前先取一次
当前的令牌，和单双向流重连失败时一样。两条流都关着、`/rpc` 也 5 分钟没来，这份握手就结束；在这之前它仍在
`harnix.process` 的连接里——分离流的客户端走的时候什么也不说，关掉的流和正在重开的流看起来一样。每个客户端的出站队列都有界（4096
帧）：读者不读、队列满了，这个客户端就算走了，连接关掉，重连后从中枢的缓冲追上，而不是让内存跟着它涨。

#### 3.3.3 跨拓扑的不变量

拓扑可选，但下面这些在任何拓扑下都成立，它们是传输真正写死的部分：

1. **`seq` 是唯一的追赶锚。** 每条会话事件带 `(instance, session_id, seq, turn_id)`，`seq` 由**中枢**
   按会话分配，与连接、载体都无关。
2. **一次握手，一次协商。** 协议版本、贡献点 API 版本、拓扑、能力位在握手里一次谈完；后开的通道携带
   握手换来的凭据，不各自再谈。
3. **权限提问的语义与通道无关。** 广播给所有观看者，任一可答，先答者生效，第二个回答是静默成功。
4. **大负载永远走旁路。** 一次性凭据换 URL，落盘后以路径引用。
5. **中枢与授权不感知拓扑。** 加一种拓扑不会改动这两层——**如果改动了，说明语义被拓扑污染了，那是要修的**。
   `layering.rs` 断言这两层的源码里叫不出拓扑、连接、HTTP 的类型。

#### 3.3.4 只提供 RPC 的形态

传输可以不提供任何静态资源（`--headless`）。界面在别处，或者根本没有界面（§5.1、§7.1）。

#### 3.3.5 模块自有链接

一个模块的前后端之间可以有自己的 HTTP 路由与 WebSocket，挂在 `/apps/<id>/` 下，由
Harnix 的传输层发出，与界面**同源**，准入走同一套（同一份凭据、按「主体 × 模块路由」判定、默认拒绝、有
审计）。前端经宿主 API 的 `space(id).fetch()` / `.socket()` 用它，模块代码不自己拼地址。它承载 Harnix
通道不适合的东西，代价是**不享受**拓扑无关和 `seq` 追赶这些保证——要这些保证，就用上面五种语义。

前后端之间用哪条：一问一答用 unary 调 `app.<id>.*`；状态更新用宿主主题推整值快照；长任务返回任务 id，
进度作为带参数的主题；大文件走旁路；剩下的才用自有链接。**不为模块加新的通道语义。**

### 3.4 授权

**这个进程只有一个准入点。** 加一个方法，默认是拒绝。

主体有三类：**内核**（这个二进制自己）、**模块**（`Module(id)`，一个编译期模块）、**设备**（配对过的
客户端，或本机带令牌的页面，代表一个人）。每个方法、每条模块路由声明给哪类主体用，进授权表。

- **插件 APP 是一个模块主体**：`module:<应用 id>`。它的后端调 hub 的方法、订 hub 的主题都以这个身份经同一个准入点，只到清单 `hub` 列出的
  （登记时像模块的 grant 一样写进授权表），被拒的记审计。没有另一类「插件」主体：那就是第二处决定扩展能做什么的地方。
- **Agix 插件不是这里的主体**——它跑在引擎里，受引擎的能力门控约束，够不到这个进程的方法面。
- **插件 APP 的 iframe 不是主体**：外壳先按清单查名字，再以页面的身份（一台设备）发出，所以它够得着的是设备能调的、又在清单里的那一小块。

单用户系统里「这个人能不能做」的答案几乎总是「能」，所以这一层真正在守的是：

- **引擎那些等价于接管进程的方法一个都不出去。** 改凭据、装载子进程、改写模型端点的方法，永远不出现在
  任何设备的可用集里——不是「未实现」，是明确拒绝，并且错误里写清原因。中枢独占的方法
  （`session.run_turn`、`session.subscribe`）同样拒绝，模块也不能 grant。
- **设备建实例只能按模板。** 模板集合在启动时定死，设备只能选模板、填模板放开的参数（§3.1.1）。
- **加一个方法默认是拒绝。** 设备能调到的引擎方法是一张透传白名单。

授权发生在**方法这一层**，不在连接那一层——多通道拓扑里同一个主体可能有好几条连接，把授权挂在连接上
会得到几份可能不一致的答案。`harnix.reachable` 告诉调用方它能调什么，界面据此决定画什么。

## 4. 扩展模型

### 4.1 三种做法

在 Harnix 上做应用有三种做法（[应用开发](app-development.md)）：

| | 模式 1 | 模式 2 | 模式 3 |
|---|---|---|---|
| 是什么 | 用 Rust 把 Harnix 装配成一个产品 | 插件 APP 嵌在产品进程里，每个插件一台 WASM 虚拟机 | 每个插件 APP 一个进程 |
| 状态 | 已有应用在用（IPDrun、Grabix） | 开发与测试中 | 只有设计 |
| 用什么写 | 编译期模块（§4.2）、原生工具与场景、编译期的界面 | 应用包（§4.3） | 同模式 2，同一个包 |

**一个产品开模式 2 或模式 3，不同时开**：两种模式对「插件的 Agent 在哪」答案不同，模式 2 的宿主要链 wasmtime、模式 3 的不链。
**包对模式中立**：同一个 `.hxapp` 在嵌入版、桌面版、各个应用里都能装，商店只有一种包。

由此有三种产品形态：**应用**一般是模式 1 + 2；**Harnix 嵌入版**是 Harnix app + 模式 2，给资源紧的设备与边缘；**Harnix 桌面版**是 Harnix app +
模式 3，我们自己的发布（只有设计）。资源、安全、目标市场的比较在 [应用开发](app-development.md) §3–§5。

### 4.2 编译期模块

一个模块实现 `Module` trait，应用在 `main.rs` 里显式列出，**顺序就是注册、迁移、启动的顺序**：

```rust
fn main() -> anyhow::Result<()> {
    harnix::App::builder()
        .profile_from_args()
        .with_builtins()
        .module(helm_home::Module::default())
        .run()
}
```

一个模块可以贡献：给 `system` 实例的原生贡献（`engine()`）、自己的实例模板（`templates()`）、后端侧的
space 声明（`spaces()`：默认实例、场景）、`app.<id>.*` 方法（带 schema 与主体声明）、宿主主题、
`/apps/<id>/` 路由，以及 `migrate` / `start` / `stop`。完整的接口见 [SDK](harnix-sdk.md) §17。

**原生贡献只有两条路**：给 `system` 的走 `engine()`，给自己实例的走进程内模板带的 `EngineContrib`。多个
模块的 `SessionCustomizer` 由 Harnix 按注册顺序组合，Agix 不用改。

`ModuleContext` 给模块：自己的配置段（profile 的 `[modules.<id>]`，密钥只写引用，值由凭据源提供）、自己
的数据目录、凭据、发布主题、以 `Module(<id>)` 身份调方法（和设备走同一个准入点）、服务端会话（§3.2）、
按自己的模板建实例。**拿不到中枢的内部状态，也拿不到 `EngineLink`。**

迁移：Harnix 只管**什么时候迁、失败了怎么办**（按顺序、失败只停用这个模块），不管**用什么迁**。数据库
选型、迁移工具都由模块自己定；Harnix 自己的账本与模块数据分开。

两个版本号各由拥有它的一侧检查：**模块 API 版本**在编译期检查，不匹配编译不过（模块是源码，错配在
运行期才发现没有任何好处）；**贡献点 API 版本**在握手与读包时检查（§5.8）。0.4.z 内协议与模块 API
只做加法。

### 4.3 插件 APP

一个插件 APP 是一个应用包：清单 `harnix-app.toml`、至多一个 WASM 组件、一个 Agix 插件（`agent/`）、界面（`ui/`）、签名（`SIGNATURES`），
各部分可选。怎么写见 [插件](harnix-plugin.md)；这里讲它为什么是这个形状。

**两道开关。** cargo feature `apps`（带 wasmtime，缺省不编）与 profile 的 `[apps] enabled`（缺省关）。都开着才有 `harnix.apps.*`、才有
内核给 `apps` 内建模块的应用宿主；任何一道关着，授权表就是装配出来的那张，二进制与没有这件事时一样。

**一个应用一台虚拟机，只在主进程里。** 「虚拟机」是一个边界，不是一个进程：后端是一个常驻实例（状态、订阅、定时器在这里，调用排队串行进入），
每次工具调用、每次事件另起一个临时实例、用完即弃。spawn 出来的 daemon 不起虚拟机，它的会话经这个应用的 MCP 端点回到主进程那一台。
所以在任何拓扑下，一个应用只有一份状态。超时的调用被放弃、后端实例换掉（停在半路的代码不能信它的状态）；后端崩了重建一次，再崩就置于一旁；
`on-demand` 的后端闲置时卸下，下一次调用冷启动。要留下的状态放 kv。

**它在内核里是谁。** 插件 APP 不是一个新的主体，它以 `module:<应用 id>` 行事：

- 它的方法、主题、space 由 `apps` 内建模块代管，照清单在启动时登记进授权表、方法路由与 space 表，停用时撤下（§3.1）。
  方法写明给哪类主体（设备、模块、内核），和编译期模块的方法同一个准入点、同一套审计。
- 它的后端 `host.call` / `host.subscribe` 以 `module:<id>` 经同一个准入点，只到清单 `hub` 列出的；被拒的记审计，也显示在系统 space 的应用页签。
- 它的工具由 Harnix 给 Agix 的 Rust 插件（`AppsPlugin`）在每个会话建起时登记，名字 `app__<id>__<工具>`；每次调用都先问人，
  能挡掉它的是 Agix 的权限。

**数据只走 Harnix 的通道。** 插件的界面和它的虚拟机之间没有自己的连接：iframe 经外壳的桥、外壳经页面那一条 Harnix 连接，到 hub、到后端；
后端推的主题原路回来。准入与审计一处管；断线重连、远程与桌面拓扑都由外壳已有的连接处理；iframe 不能联网，界面就没有绕过能力声明的路。

**编译放在商店。** 产品构建不带编译器，只反序列化商店为每个引擎指纹编好的产物：二进制小、攻击面小。反序列化只用于可信的产物，
所以先验签、再按签名里的 sha256 比对读进来的字节，才反序列化。产物绑 wasmtime 的版本，Harnix 与 Agix 一一对应地发布，wasmtime 只在
Harnix 发布时变，商店为每个 wasmtime 版本编一遍。

**代码按「共享核心 / 粘合」分层。** 分发与信任（`harnix-app-package`）、端口（`harnix-app-port`，可以搬上 RPC 的形状）、虚拟机（`harnix-wasm`）、
应用宿主核心（`harnix-app-host`）不依赖内核、hub、Agix 与 HTTP 框架；进程内的粘合（`harnix-apps`）单独一层。模式 3 的应用进程换的只是粘合。
分层与它的测试见 [应用开发](app-development.md) §11。

### 4.4 Agix 插件：一个包，装到引擎里；Harnix 只收文件

一个 Agix 插件（运行期包）装的地方是 Agix（以 Agix 的 `plugin_packages.md`、`extending_quickjs.md`、`extension_points.md` 为准）。
Harnix 不定义它的包格式、不校验、不解包、不判定能力。它做两件事：

1. **把文件送过去。** `plugin.install` 自己去取 URL，**没有上传通道**——这是引擎的选择，它在包已经躺在
   跑引擎那台机器上时完全够用；而当包在使用者的笔记本上、引擎在另一台机器上时，就没有路可走。那一步是
   宿主的活：`harnix.plugins.upload` 换一个一次性 URL（大负载旁路），`harnix.plugins.install` 把落盘路径
   交给引擎。插件 APP 的 `agent/` 也走 `plugin.install`，由 `apps` 模块替它装进声明的实例。
2. **读包里引擎不关心的那一段**——`[[ui]]`（§5.8）。**包在哪由引擎说**：`plugin.list` 的条目带 `root`，
   Harnix 只读那下面的 `plugin.toml`，自己不拼任何路径，引擎的缓存布局因此仍然是引擎的。
   插件 APP 的 `agent/` 另有一个读者：装包之前，`harnix-app-package` 从它的 `plugin.toml` 读 `[plugin]` 的 `name` 和
   `version`，是要请 `plugin.install` 装成的名字，此外一个键也不读（`layering.rs` 查这两处）。

**生命周期走 `harnix.plugins.*`，引擎自己那几个名字不开。** 装、卸、启、停都是引擎干的活，这一层不加判断
也不发明参数；它加的是后面那一步：任何改变「装了什么」的调用之后重读一遍，因为 Harnix 在服务每个包的
`ui/` 目录、并对外公布贡献集合。直接透传 `plugin.disable` 的后果是包停了而它的界面模块还在被服务，且没有
任何一侧会发现。

**披露在装完之后，因为引擎是那个顺序。** 引擎装完才回 `disclosure`（这个包会往模型上下文里塞的文本）。界面上就是：装好了，这是它会放到
模型面前的东西，留还是删。想在装之前看，就得在这一侧读包，而那正是这一节要避免的事。**沙箱管得住插件执行什么，管不住它说什么**，所以模型
可见文本必须被人看见。界面贡献占了哪些点是 Harnix 知道的，安装完的那一屏把两半拼起来，否则用户看到的披露是不全的。（插件 APP 不同：它的
清单是 Harnix 的，披露在装之前，人同意了才装，§4.3。）

**装 Agix 插件是这个人自己的决定。** `harnix.plugins.*` 对设备开放：一个进程服务一个用户，设备就是这个人本人。真正的强制边界在引擎：能力门控、
沙箱、它自己回的那份披露。`mcp.addServer` 保持拒绝，差别正在这里：它配出来的是一个能起子进程的工具，没有 manifest、没有能力声明、没有任何披露。

**包方案不跟着载体走。** 引擎的载体今天是 QuickJS 脚本与编译进宿主的 Rust 插件，带 `[[wasm]]` 段的包拒装（WASM 在 Harnix，§2.2.2）。
读 manifest、校验、解包、披露、启停不需要任何运行时。一个不带包方案的构建仍然合法，所以 `PLUGINS_DISABLED` **如实透传，不包装成
「没有已安装的插件」**：「这个构建里没有插件子系统」和「一个都没装」是两件事。

### 4.5 不进 Harnix、由应用自己做的

按 §1.3，下面这些应用在模块契约上就做得出来，不进 Harnix。做法写在 [SDK](harnix-sdk.md)：

- **批准**（「这个业务动作要不要人确认」）：只许设备调的 `app.<id>.*` 方法收回答、带参数的主题推待批事项、
  扩展条目记下决定、`flow.block` 画卡片。引擎权限管「这个工具能不能跑」，批准管「这个业务动作要不要人
  确认」，后者的策略本来就归应用。
- **MCP 服务端与角色令牌**：在那之前应用要给外部 Agent 开 MCP，就在自己的模块里起自己的监听，它不在
  Harnix 的授权与保证之内，由应用负责。
- **非 Rust 的 sidecar 服务**：走 Agix 的 MCP，或经模块路由转发。

### 4.6 流程：内置的应用开发工具链（`harnix-flow`）

流程是 Harnix 内置的应用开发工具链：让 Agent 按一套定义好的过程干活，判定只看结构化信号；流程本身也在它自己的对话里由 Agent 编写、试运行。
它不进骨架，是一个**按公开模块契约写的可选模块**（crate `harnix-flow`，界面 `@harnix/flow`）：应用注册它就有，不注册什么都不变；
Harnix 自己的二进制 `harnix` 注册了它。它的界面在系统 space 里（§5.5，[系统 space](system-space.md) §5）。

```
 流程包（内置层 + 可写层）     flows · skills · rules · policies · gates · hooks
          │ 校验、建运行时钉住定义与策略、门禁
          ▼
 内核（kernel/，纯）          站的有向无环图：进站、派工、租约、出站判定、返工、暂停；
          │                   只经宿主 trait 读写（RunStore、Packs、Authorizer、Tools）
          ▼ 工作项
 模块（module/）              会话任务交给会话（主会话 = 主 Agent；子 Agent；独立会话），
                              程序交给应用，命令 / 宿主门禁去跑，钩子去投递；
                              答流程会话的权限询问；app.flow.* 方法与主题
```

**分层**：内核不建会话、不碰磁盘、不知道谁是用户——存储、授权、应用的程序与检查都由应用以 trait 交进来，
所以同一个内核也跑在试运行的沙箱里（外面的一切模拟）。模块把内核接到 Harnix：会话、原生工具（`flow_submit`、
`flow_state`、`flow_propose`）、作者 scene `flow-author`、方法与主题、系统 space 里的流程界面。

**每个时间点只有一处能拦**：干活过程中是**权限**——流程会话对受限工具和权限提到的工具都 `ask`，模块按这一轮所属
任务的权限判（`deny` > `ask` > `allow`，`ask` 留给人）；出站时是**出站条件**——输出契约、门禁（`tool` / `command` /
`host`）、人的确认。**规则**与 skill 只告诉 Agent，不拦。**钩子**是旁观者：不写在流程里，从不阻塞运行。

**不进 Harnix 的**：审批策略（几个人批、批与做不能是同一人）归应用——流程把 `who` 交给应用的授权方。
对象与写法见系统 space 里流程的参考页（`crates/flow/docs/guide.*.md`）；构建器、方法与主题见 [SDK](harnix-sdk.md) §23。

## 5. 界面

### 5.1 界面在二进制里，可以被换掉

**安装物是一个文件。** 界面编译在里面，所以不存在「页面和后端对不上」这种状态。

| 形态 | 怎么来 | 用在哪 |
|---|---|---|
| 内嵌（默认） | 编译进二进制 | 单机、边缘节点。装一样东西 |
| `--ui-dir <目录>` / `[ui] dir` | 从磁盘读，整套替换 | 做另一个产品；开发前端时改完刷新 |
| `--headless` | 一张都不发 | 纯 RPC 节点 |
| `ui export <目录>` | 把内嵌的那份写出来 | 让 CDN 或代理去发。仍然只有一个安装物 |

**为什么编进去，而不是一个独立的界面产物。** 分开的唯一硬理由是运行期要 import 别人的界面模块，而那件事由包自己的
`ui/` 目录满足（Agix 插件的界面模块、插件 APP 的页面都由后端从包里发出），不需要界面本身是分离的。编进去对二进制大小几乎没有影响；
换一整套界面仍然是一个参数，不是一次重编译。

没有界面产物就直接 `cargo build` 会**明确失败并说该跑什么**，不悄悄嵌一份空界面。

#### 5.1.1 版本协商仍然要，使用者变了

界面在握手时声明协议版本、贡献点 API 版本与拓扑，后端回自己支持的；不匹配就拒绝并说清哪一边旧了，**不做
静默降级**——一个半兼容的界面产生的 bug 报告是无法处理的。

内嵌之后，内建界面不可能对不上，所以协商的使用者只剩这几个：`--ui-dir` 换进来的那一套；**包带的界面
模块**，在读包时逐条比对（§5.8）；插件 APP 的页面，它和外壳之间是另一份协议（桥 `harnix-ui-bridge@1`，§5.7）。界面**不假定拓扑**：它拿到的是一个客户端库，库把五种通道语义映射到
握手谈定的那种拓扑上。

### 5.2 技术栈与包

**React + TypeScript + Vite + Zustand，定死。** 用的人最多、后续好维护；Agent 类界面的生态基本都是 React 的；
IPDrun 已经有能对着 Harnix 协议跑的 React 对话组件，直接回流成了对话主干（`ChatPanel`）。代价是旧的原生 JS
界面整个换掉，以及运行期包的 v1 界面模块不再生效（§5.8）。

包的边界只画在「谁依赖谁」真正不同的地方：

| 包 | 依赖框架吗 | 职责 |
|---|---|---|
| `@harnix/core` | 否 | `/protocol`（从 `harnix-contract` 用 `ts-rs` **生成**的类型，漂移就失败）、`/client`（握手、拓扑与回退、追赶）、`/state`（会话事件归约、实例树、每个 space 的当前会话） |
| `@harnix/react` | React | 贡献注册表、`useNest()`、i18n、令牌、图标；对话组件。**应用写 space 界面只依赖它** |
| `@harnix/shell` | React | 外框、space 切换、设置、内建 space。应用的入口，不被 import |
| `@harnix/testkit` | 否 | LIVE 测试的启动器、API 客户端、Playwright 夹具 |
| `@harnix/flow` | React | 流程模块的界面：外壳在后端有流程模块时把它放进系统 space |
| `@harnix/app-sdk` | 否 | 插件 APP 的页面在 iframe 里的一侧：桥的协议与客户端、mock 宿主 |
| `@harnix/ui-kit` | 否 | 插件 APP 的页面用的外壳令牌与几样基础部件 |

框架只出现在 `@harnix/react` 及以上；`@harnix/core` 与后端一一对应（`/protocol` ↔ `harnix-contract`，
`/client` ↔ 传输，`/state` ↔ 中枢推的帧与快照），换框架也不动它。**内建 space 只用公开 API**：外壳里画
内建 space 的代码只许 import `@harnix/react`、`@harnix/core` 的公开导出——和后端「内建模块只用公开模块
API」是同一条。

应用的界面入口由构建脚本生成成一个虚拟模块，和外壳一起由 Vite 打成一份产物，顺序与 `main.rs` 里的模块
顺序一致。

### 5.3 外壳的框架

**固定外框，加上 space。** 外框里固定的只有：

- 左栏顶上：品牌（`[brand]` 的图标和名字）、新建对话、搜索；
- 左栏底下：系统 space 的入口（保留它时）和**头像**。头像就是设置入口，外圈颜色表示连接状态
  （已连 / 重连 / 断开），悬停说连到了哪。

其余都由 space 给。**一个 space 是三栏合在一起**：

| 栏 | 由什么给 | 不给时 |
|---|---|---|
| 左栏中段 | `sidebar()`：这个 space 的条目 | 这个 space 的会话列表 |
| 中区 | `center`：`chat`（默认）/ `minimized`（对话收成底部一条，可展开）/ `hidden`（用 `overview()` 画自己的视图） | 对话 |
| 右栏 | `tabs`：一组页签，**可以是当前选中项的函数**，每次绘制时读 | 只有详情抽屉 |

左右两栏都能拖宽并记在本地；窄屏时先把左栏收成图标栏，再把两侧都变成抽屉。一个 space 可以 `within` 另一个：不列在左栏，
由代码进入，在前台时点亮外层的入口（系统 space 里的流程就是这样）。

**Harnix 自带的 space 是 Harnix app 的两个加系统 space，都只是用例和默认值**，产品用 profile 的 `[shell] spaces` 选留哪几个（默认都留）：

| space | 属于 | 左 | 中 | 右 | 后端 |
|---|---|---|---|---|---|
| **会话** | Harnix app | 全部会话，按时间分组（`sidebar.group`，应用可以换），带搜索 | 对话 | 详情 | 后端的 `sessions` space |
| **项目** | Harnix app | 一棵树：项目（工作区）一次只展开一个，它的会话挂在下面 | 对话；新建的会话跑在展开的项目里 | 详情 | **同一个**后端 `sessions` space（`SpaceContribution.sessions = "sessions"`） |
| **系统** | 系统 space | 实例列表 | 控制台（`center: "hidden"`），不持有对话 | 选中项的检查器 | 后端的 `system` space（§5.5） |

去掉一个 space，它的入口就不注册；去掉「会话」，剩下的第一个成为默认；去掉「系统」，底部的入口和它的方法一起没了。Harnix app 怎么用框架
做出来的见 [Harnix app](harnix-app.md)。

**项目 space 是界面上的一个视图，不是第二个会话集合。** 「按时间看」和「按项目看」是同一批会话的两种排法；如果它们是两个后端 space，
同一个会话就得属于两个 space，而会话按 space 绑定是不变量（§5.4）。所以界面 space 可以用 `sessions` 指向另一个后端 space：两个界面视图，
一个后端归属。

**新建对话的空页**：问候、这个 space 的建议，下面是 `home.card` 的卡片。

为什么外框只有这些：

- **外框只留真正每个产品都要的东西，其余都可去掉。** 首页的问候、问一句、卡片，和新对话的空页是同一件事的两个入口；卡片放到新对话的
  输入框下面，首页就不需要是一个 space。`home.card` 这个点保留。
- **系统 space 是看进程的，不是又一个聊天的地方。** 它的中区是控制台；要在会话里继续说话，就「到所属 space 打开」。它因此不需要自己的会话。
- **一张表管所有内建 space。** `[shell] spaces` 一张表，内建 space 同等对待。profile 每一段都拒绝未知键，写了旧的开关会启动失败并说哪一行，
  而不是被悄悄忽略。

### 5.4 Space 模型

**space = 左栏 + 中区 + 右栏，一起注册，所以「成对」是原子的。** 一个 space 有三个**部分**，可以任意组合：

| 部分 | 在哪执行 | 来源 |
|---|---|---|
| 前端 | 浏览器 | 编译期（打进应用的界面产物）；或插件 APP 的面（iframe）与进页面的模块。Agix 插件的界面模块只能给已有的贡献点做贡献，不能新增 space |
| 后端 | Harnix 进程内 | 一个编译期模块；或插件 APP 的 WASM 后端（清单的 `[[space]]` 声明它的后端 space） |
| Agent | Agix 实例里 | 原生 Rust（模块的 `engine()` 或模板）或 Agix 插件（也可以是插件 APP 的 `agent/`） |

只有前端与 Agent 部分的 space 不用在后端声明，取默认（`system` 实例、实例的默认场景）。

中区缺省是对话；space 可以在对话旁边开一个**二级栏**（`secondary()`：标题、正文、能拖宽、能最大化、能关），放它右栏里
选中那一项的详情——列表留在右栏，详情不挤在列表下面。会话还空着时，space 可以给一段说明（`emptyConversation`）。

**会话规则：**

| 规则 | 内容 |
|---|---|
| 绑定 | 一个会话在创建时绑定一个 space 和一台实例，**不能挪**；要跨 space 延续，用 `@session` 引用（被引用会话说过的话作为附件交给这一轮——复制的是话，不是会话）或分叉 |
| 多会话 | 一个 space 可以有多个会话，可以分布在它能用的几台实例上 |
| 默认实例 | space 声明 `instance = "system"`（默认）、一台固定实例，或 `"template:<id>"`（第一次在这个 space 里建会话时按模板建一台，之后复用，归这个 space）。这就是「一个 space 要一台自己的、隔离的 Agent」的写法 |
| 切换 | 离开一个 space 时记住它当前的会话，切回来时恢复；那个会话没了就退到这个 space 的列表，**不退到别的 space 的会话** |

**硬理由**：Agix 的会话在创建时就定了场景，场景决定工具集。不同 space 的工具不同，它们的会话本来就不能
共用。所以按 space 绑定不是界面偏好，是引擎语义的直接结果。绑定是 Harnix 自己的账本数据（引擎不知道 space）。

**前台 space 与它的会话：对应关系不能错。** 哪个 space 在前台，中区、输入框、右栏看到和操作的就只能是这个
space 自己的会话。这件事错一次就是把消息发进了别的产品面、别的实例、别的工具集，所以它是不变量：

1. **前端没有全局的「当前会话」。** 状态里记的是「每个 space 的当前会话」，切换 space 就是切换取哪一项。
2. **会话总是带着实例一起出现。** 草稿、滚动位置、权限卡、队列的键都是 `(instance, session)`。
3. **服务端也核对。** 会话调用带上调用方声称的 `space`，中枢对着账本核对，不属于就拒绝
   （`SPACE_MISMATCH`，错误里写明它属于哪个 space）。**系统 space 是唯一的例外**，它可以观看、操作任何 space
   的会话，每一次跨 space 的操作都写审计。
4. **新建会话的去向只看前台 space。** 不存在「先建再挪」。
5. **在系统 space 里看别的 space 的会话是「观看」**，不改变归属，也不改写那个 space 记住的当前会话。

第 3 条是**防误，不是安全边界**：space 是调用方自己声称的，同页的任何代码都能声称任何 space，包括 `system`（§6.2）。

### 5.5 系统 space

开发调测用的基础面：**按四层（§3）看到这个 Harnix 管着的一切，并且能操作。** 它是 Harnix 三部分之一，始终在，除非产品在
`[shell] spaces` 里去掉它。它是内建模块加一个内建界面 space，只用公开 API，没有私有通道——这也让它成了「space 模型真能承载复杂面板」的
第一个内建证明。每个页签、每一列、每个数据来源见 [系统 space](system-space.md)。

| 栏 | 是什么 |
|---|---|
| 左 | 实例列表 |
| 中（控制台） | 指标条（版本、运行时长、内存、线程、连接、Agent、运行中的会话与任务、等人处理的）；页签：**活动**、**全部**（每行一个主 Agent，展开是子 Agent 与任务）、**流程**（有流程模块时）、**应用**（`[apps] enabled` 时）、**诊断** |
| 右（检查器） | 只出现适用于选中项的页签：实例的概况；会话的概况、调用、每轮、上下文、任务、原始帧 |

**流程在系统 space 里。** 流程是 Harnix 内置的应用开发工具链（§4.6）：控制台的「流程」页列出流程与运行，点一条就进了这条流程——左栏换成它的
上下文（返回系统、它的对话、它的运行），中区是它的会话，右栏是参考。它是一个嵌在系统 space 里的界面 space，id 仍是 `flow`；产品留 `flow`
去掉 `system` 时，退回一个单独的流程 space。

**插件 APP 在这里看得见。** 应用页签列每个插件 APP 的状态（运行中、休眠中、已搁置……）、虚拟机的健康（调用、故障、超时、换新与重建、内存、存储）、
最近被拒的调用、本页上它的界面面板与被拒的界面请求。只看，不操作：管理在设置 → 应用。

**设备够不着的引擎方法包在系统模块后面。** `inspectContext`、`dropMessages`、`editMessage`、`stopTask`、`messageTask`、`taskOutput`、`compact`、
目标那几个引擎方法不在设备的透传白名单里；系统模块把它们包成 `harnix.system.*`：设备调它，它以 `system` 模块的身份经授权调引擎，两次判定都进审计。
其余（`session.history`、`fork`、`interrupt`……）设备直接调，带上 `space: "system"`。会话的操作与实例的操作**全部写审计**。

**录像里有完整的系统提示词，敏感级别和 transcript 相同**（§6.4），所以只能经授权过的方法读，录像目录永不经 HTTP 暴露。产品不要系统 space，
就从 `[shell] spaces` 里去掉：系统模块不注册，它的方法连同授权一起没有，声称来自 `system` 的调用一律 `SPACE_MISMATCH`——**撤的是方法，不只是不画**。

**Agix 没给的，不画假的。** 页签或按钮在 Agix 补上之前不出现，而不是做成灰的或者在 Harnix 侧模拟。

### 5.6 贡献点与宿主 API

八个贡献点，数量本身是设计的一部分，加第九个是一个需要论证的决定。完整目录由 `harnix_module::catalog`
生成，见 [contribution_points.md](contribution_points.md)。

| 贡献点 | 贡献什么 |
|---|---|
| `space` | 一个 space：图标、标题、`sidebar()`、`center`、`overview()`、`tabs`、`sessions`、建议与提示 |
| `home.card` | 新对话空页上、输入框下的一张卡 |
| `tool.row` | 一次工具调用在流里的那一行 |
| `flow.block` | 流里的一种块（扩展条目就是用它画的） |
| `details.panel` | 右栏详情里的一页，由 `reveal(item)` 打开 |
| `sidebar.group` | 会话列表的分组与排序 |
| `command` | 一条 `/` 命令或 `@` 引用的补全候选（`trigger` 选哪个菜单） |
| `settings.section` | 设置里的一节 |

**这些是界面自己的接缝。** 它们存在的理由不是给第三方一个扩展面——扩展 agent 是引擎的事——而是让界面不是
一堆 switch：于是「换一整套界面」是换一批注册，而不是改一堆分支。**频率是约束**：没有一个点跟着流式分片求值。

**外壳必须真的去问。** 一个没人问的贡献点等于只存在于目录里，产品照旧自己直接画，而所有测试都还是绿的。这件
事真的发生过一次，七个点里的五个。判据因此不是「注册了」，是「被问过」，并且由测试盯着——点的名单本身也从
生成的目录里读，因为手抄的那份也漂过一次。内建界面走的就是这些点，没有一样有私有通道：**如果连工具行都是
这样画出来的，这些接缝就不需要谁来相信。** 例外要说出来：去掉 HOME 之后 `home.card` 没有内建注册了，外壳
照样在新对话的输入框下问它，`examples/hello-app` 注册了一张。

**令牌覆盖与语言包不是贡献点。** 注册表上的 `r.tokens({...}, owner)` 只许覆盖**已有的**令牌名，值只许是颜色或
长度；`r.strings(locale, {...}, owner)` 的 key 必须在 `<owner>.` 下面。不合规矩的那一条被拒并记进诊断。它们
不是点，因为它们不在任何时机被「问」——它们改的是主题和词典本身，所以点仍然是八个。

**宿主 API（`useNest()`）** 是前端代码拿到的全部能力：`call`（只放行 `harnix.reachable` 里的，包括
`app.<id>.*`）、`subscribe`（宿主主题，可带参数）、前台 space 的会话（`current / context / list / open /
create`，自动绑定前台 space）、实例（列、建、停，按可达方法过滤）、`composer.insert`、`reveal`、
`space(id).fetch / socket`、`t()`。**拿不到 Harnix 自己的连接**，所以同一份代码在任何拓扑下都能跑——这是
「语义写死、拓扑可选」在界面这一侧的体现。

### 5.7 插件 APP 的界面：面、桥、行内点

**受信的界面进页面，商店的界面进隔离的 iframe；外壳拥有一切，插件只能借外壳的手。** 会话、对话、连接、主题、快捷键、模态层都是外壳的；
插件的界面在外壳给的「面」里画自己的内容，所有数据经外壳那一条 Harnix 连接来回（§4.3）。

| 信任 | 界面怎么跑 |
|---|---|
| 商店副署（`store`）、未签名（`unsigned`，只在开发模式） | 隔离 iframe：清单的面与行内点；进页面的模块一个都不跑 |
| 受信发布者（`trusted`） | 进页面，和编译期的界面同权限；清单写 `isolate` 时也进 iframe |

**面与行内点分开。** iframe 适合整块的区域，不适合成百个的小部件（一个流块一个 iframe 养不起）。所以贡献点分成两类：

- **面**（8 个：space 的中区、左栏中段、右栏页签、二级栏，详情面板、设置节、新对话卡、模态框）给 iframe。外壳给每个面画外框（标题、加载、出错、
  重新加载），一个崩掉的插件看起来是「这一块出错了，重试」，而不是半张白页；连续失败的面被置于一旁。
- **行内点**（工具行、流块卡片、命令、侧栏分组）是**声明式**的：清单写模板，外壳用自己的组件照画，不跑插件的代码。要比模板更多的样子，
  就做成一个面，而不是在流里塞 iframe。

**对话始终是外壳的。** 商店的插件不能替换对话的画法，只能经声明给某种块、某个工具指定样子。一个 space 的左栏也只有一种：外壳的会话列表
（可以声明分组），或插件自己的面。

**iframe 的边界**：`sandbox="allow-scripts allow-forms"`，不给 `allow-same-origin`（不透明源，读不到页面的令牌、存储与 cookie），不给弹窗与顶层导航；
内容从 `/apps/<id>/ui/` 来，CSP `connect-src 'none'`：页面不能联网，数据只走桥。

**桥**（`harnix-ui-bridge@1`）：外壳经 `MessageChannel` 交给 iframe 一个端口（不是 `window.postMessage` 广播），页面一侧用 `@harnix/app-sdk`。
它能请外壳做的是宿主 API 的一个子集：调自己的 `app.<id>.*` 与清单 `[interface] hub` 列出的少数 `harnix.*` / `session.*`，开自己 space 的会话，
外壳的手（切 space、开右栏、二级栏、设置节、往输入框插字、角标、通知、复制、模态框、确认、外链、上传）。都是外壳去做：`confirm` 是外壳画的，
插件造不出假的确认；外链每次问人。被拒的请求记下来，系统 space 的应用页签看得到。**拿不到的**：页面的令牌、连接本身、别的应用的名字、DOM。

**看起来像原生的。** `@harnix/ui-kit` 是外壳的令牌加几样基础部件，主题与语言经桥推进来、即刻生效；外壳的快捷键在 iframe 里按下也交给外壳，
外壳的对话框开着时 iframe 收不到键：一个键只落在一处。

### 5.8 Agix 插件的界面模块

```toml
[[ui]]                          # 同源 ES 模块，浏览器 import
point       = "tool.row"
module      = "rows.js"         # 相对包里的 ui/，只在那底下解析
api_version = 2                 # 贡献点 API，与 [plugin] api_version 是两个数
```

**两个版本号，各由拥有它的一侧检查。** `[plugin] api_version` 是引擎的扩展 API，引擎校验；`[[ui]] api_version`
是贡献点 API，Harnix 校验。一个包可以在一边是新的、在另一边是旧的，所以它们不能是同一个数。

**v2 的模块是预编译好的 ES 模块**（JSX 已编译掉），**不带自己的 React**——页面上两份 React 会让 hooks 失效。
它按名字 import `react`、`react-dom`、`react-dom/client`、`react/jsx-runtime`、`@harnix/react`；外壳的构建
为这几个名字各出一个 facade，页面里一份**内联 import map** 把名字指到它们，外壳自己用的也是这几份，所以页面
上只有一个 React。React 的大版本因此是贡献点 API 的一部分，升 React 大版本就是升 `api_version`。

**import map 只能内联，而 CSP 是 `script-src 'self'`。** 办法是服务端在**发页面时**（`page_csp`）从要发的
`index.html` 算出 import map 的 `sha256`，写进这一页的 CSP：只放行这一段确定的文本，不算放宽，不需要
`unsafe-inline`、`unsafe-eval`。在发页面时算而不是构建时写死，是为了 `--ui-dir` 换进来的界面也对。

**照别的版本写的那一条不生效。** 版本不符（包括没声明 `api_version`，那被当作 v1）的条目在读包时就被拒，
报「这一条不生效」并写明哪一边旧了，包的其余部分照常。在读包时拒而不是 import 进来再失败，是因为后者的症状
是一个悄悄不出现的面板（§2.4）。v1 的模块是直接操作 DOM 的函数，React 外壳里没有办法让它们继续
工作，所以 v1 一律不生效，而不是拒装整个包。

`module` **只在 `ui/` 底下解析**——带 `..` 的直接拒，结构上就点不到包里别的文件。

**产品可以整个关掉：`[ui] runtime_modules = false`。** 关掉时既不提供、也不发任何包的界面模块，包就只剩引擎
那一半。需要「必须是人点的」的产品（例如交易）要关（§6.2）。

**信任级说清楚：界面模块与页面同级。** 它是同源模块，浏览器没有任何机制能把它关小；CSP 挡得住外部来源、
内联脚本与出网，挡不住一个已经被允许加载进来的同源模块去做页面本来就能做的事。所以这一层的约束是**披露、
准入检查、开关、可吊销与可审计**，不是强制隔离——一个被当成隔离来依赖的非隔离，比一个已知不隔离的地方危险
得多。一个界面模块能做的最坏的事，上限是「这个用户自己在这个页面上能做的事」。

受信发布者的插件 APP 进页面的 `[[ui]]` 模块是同一种东西，同样与页面同级；所以只给 `trusted`，商店与未签名的插件 APP 进 iframe（§5.7）。

### 5.9 界面产物的硬规矩

- **只用令牌，不写死颜色**——写死颜色的部件在另一种主题下不可读。
- **只用 key，不写死文案**——写死文案让整个界面在切换语言后变成两种语言。

由静态检查强制。**CSP 不放宽**：`script-src 'self'`（外加上面那一个 import map 的 hash）、`style-src 'self'`、
`connect-src 'self'`，无 `unsafe-inline`、无 `unsafe-eval`、无外部源。产物自包含，没有 CDN，没有运行期从网上拉
的依赖——所以断网时界面照常打开。

**出网是一项要披露的能力。** 界面这一侧没有第二条出网通道，CSP 挡住了。这是有意的：出网是一项要在安装时被
看见的能力，不该因为代码跑在浏览器里就绕过披露。要访问外部服务，走引擎侧声明了 `net` 能力的代码、模块的后端，或插件 APP
声明了 `net` 的后端。插件 APP 的 iframe 另有自己更严的 CSP（`connect-src 'none'`，§5.7）。

### 5.10 品牌与目录

profile 的 `[brand]`：`name`（页面标题、左栏产品名）、`icon`（SVG）、`product_id`。外观的其余部分（配色、文案）
由模块经 `r.tokens` / `r.strings` 贡献。应用不 fork 界面就能拥有自己的外观。

| 路径 | 是什么 |
|---|---|
| `~/.<product_id>/`（不配就是 `~/.harnix/`；`HARNIX_STATE_DIR` 能挪） | 程序自己的配置与状态：令牌、设备、工作区与偏好、space 账本、实例账本、按模板建的实例的数据根、各模块的数据目录、插件 APP（`apps/<id>/`：安装记录、解开的包、数据与 kv）、上传 |
| `~/.agix/`（`--agix-dir` / `AGIX_CONFIG_HOME`） | `system` 实例的引擎根：设置分层、transcript、记忆、技能、录像 |
| `~/Documents/`（`--data-dir` / `HARNIX_DATA_DIR`） | **只放项目**。选项目从这里开始，新建项目建在这里；里面没有隐藏目录 |
| `<项目>/.agix/` | 项目自己的数据与配置，**一律**放这里，不开 `<项目>/.harnix/` 之类 |

为什么这样分：状态目录按产品 id 命名，同一台机器上装两个产品不会抢令牌和账本；Documents 是用户的，不该
藏着程序的东西；项目里只有一个属于工具的目录，而它属于引擎。更早的版本把状态放在 `~/Documents/.harnix`，**旧目录
不迁移、不读**（维护者定）：升级后令牌、工作区分组、实例账本从空开始。

### 5.11 桌面：Tauri 只是外壳

`templates/desktop` 是一个 Tauri 2 壳，任何 Harnix 应用都能套上，只换品牌。**webview 直接加载服务端发的 HTTP
页面**，所有业务走页面自己的 HTTP/WS，和在浏览器标签页里一模一样——桌面版和浏览器版是同一个产品：同一份
界面、同一条准入路径、同一套测试。

| 模式 | 壳做什么 |
|---|---|
| **本地** | 以子进程启动应用二进制：回环、`--launch-link`、`--exit-with-stdin`（壳退出，应用跟着退）；读状态目录里的令牌文件，`POST /auth/link` 换一条一次性链接，让窗口打开它，链接种下 `HttpOnly`、`SameSite=Strict` 的 cookie |
| **远程** | 打开配置好的 `https://` 地址，走 TLS 与设备配对 |

**没有业务 IPC**：没有命令、没有 invoke handler、不用自定义协议发界面、不用本地 socket；令牌只经过一个文件和
一次回环请求，窗口只见到一条用过即废的链接。`check-no-ipc.mjs` 在离线检查层盯着。连不上服务端时只显示壳里
打包的「无法连接」页，壳里不放业务界面。理由：一条 IPC 就是一条不经授权表、不进审计、浏览器版没有的通道，
两个版本从此不是同一个产品。

唯一的例外属于窗口本身：macOS 上窗口没有标题栏（红绿灯浮在页面上），页面的顶栏就是拖窗口的地方，而网页自己
挪不动原生窗口。所以页面能对壳请求两件事——开始拖动、双击最大化——只给主窗口、只给回环上的页面
（`capabilities/window-drag.json`），`check-no-ipc.mjs` 对其余任何权限照样失败。它只动窗口，不经手应用的
任何数据。

## 6. 信任与安全

### 6.1 级别

| 级 | 是谁 | 能做什么 |
|---|---|---|
| **内核** | 这个二进制自己，**以及应用编进来的模块** | 全部（模块经授权表，但它是内核级的源码） |
| **运维本人** | 写在项目 / 配置目录里的脚本与设置 | 他本来就能亲手做的任何事 |
| **插件 APP** | 装上的应用包：后端与工具在 WASM 里，以 `module:<id>` 行事 | 清单里写了、装时披露了、人同意了的能力，别的什么也够不着 |
| **Agix 插件** | 装上的包的 Agent 段，含插件 APP 的 `agent/` | 默认什么也够不着；多要一分，安装时写下来一分（引擎判） |
| **页面** | 界面、Agix 插件的界面模块、受信发布者进页面的模块 | 这个用户在这个页面上能做的事 |
| **iframe** | 商店与未签名插件 APP 的界面 | 只有桥给的：自己的方法与主题、清单列出的少数名字、外壳的手 |
| **设备** | 远端连上来的客户端 | 授权表上的方法 |

级别按出身定（§2.3）。运维与 Agix 插件两级由**引擎**判定和强制——同一份 `.js`，放在项目里是运维本人写的，随插件下载来的就是插件，
判据是规范化之后的路径，不是它自称什么。Harnix 判定的是设备、模块与插件 APP。

**插件 APP 的三个信任等级**由签名定，写进安装记录，每次启动对盘上的文件再验：

| 等级 | 什么时候 | 界面 |
|---|---|---|
| `store` | 商店副署对 Harnix 内置的商店公钥验得过 | iframe |
| `trusted` | 发布者签全了每个文件，且它的公钥是 profile 为这个发布者写的 | 进页面（可选 iframe） |
| `unsigned` | 没有签名；只在 `[apps] dev = true` 时能装、能跑 | iframe |

### 6.2 强制、披露、防误

每一处约束标明是哪一种。**安全边界**对恶意代码也成立；**披露**是让人在装的时候看见；**防误**只防 bug、不防
恶意。后两种都是 §1.2 说的「明说不是强制的」那一类。不存在「大概安全」的地方。

| 约束 | 种类 | 防什么 | 不防什么 |
|---|---|---|---|
| 命令执行的权限判定与沙箱；出网策略 | **安全边界**（引擎的） | 插件、模型越权 | 运维配的端点不受出网策略约束 |
| 授权表：主体 × 方法 / 路由，默认拒绝；引擎的凭据 / 子进程 / 端点类方法不对设备开放 | **安全边界** | 未授权的主体调方法、访问模块路由；设备接管进程 | — |
| 设备配对与吊销；非回环必须 TLS + 配对 | **安全边界** | 网络上的其他人 | — |
| 设备建实例只能按启动时定下的模板、只能填模板放开的参数 | **安全边界** | 设备装载子进程、改写模型端点、指定任意数据目录 | — |
| daemon 的凭据不出 Harnix（spawn 的 socket 在私有目录里，attach 的 token 只在 Harnix 手里）；透传白名单对每台实例一样 | **安全边界** | 设备经 Harnix 拿到 daemon 的完全信任 | 本机上能读 Harnix 进程内存或环境的人 |
| 系统 space 去掉时它的方法从授权表撤掉 | **安全边界** | 产品里有人读录像、跨 space 操作 | — |
| 插件 APP 的 WASM 沙箱：宿主函数逐项按清单查（`net` 精确主机、`env` 名单、`storage_mb`、`hub`、`fs` 预开目录）；内存与单次调用时间封顶 | **安全边界** | 插件越权：联网到别处、读别的环境变量、调没列的方法、碰别的文件、吃光内存或 CPU | wasmtime 或宿主函数自己的 bug（同一个进程，波及整个产品；模式 3 才隔开） |
| 插件 APP 的签名：解包前验，每次启动再验，`.cwasm` 按签名的 sha256 比对后才反序列化；未签名的只在开发模式 | **安全边界** | 被篡改的包、来路不明的编译产物 | 签了名的发布者本人写的坏代码（那是 WASM 沙箱与披露的事） |
| 插件 APP 的界面进隔离 iframe：不透明源、`connect-src 'none'`、只经桥 | **安全边界** | 插件的界面读页面的令牌、自己联网、调清单之外的方法、伪造确认框 | 受信发布者进页面的模块（与页面同级）；iframe 自己导航外带数据（外壳当失败拆掉它，但挡不住那一次导航） |
| 「只有 `Device` 能回答」：权限提问，以及应用自己做的批准 | **安全边界，只对后端成立** | 引擎、模块、内核替人回答 | **区分不了人和同页的界面模块**：进页面的模块能替人点。需要「必须是人点的」的产品，设 `[ui] runtime_modules = false`，不信任发布者 |
| 插件 APP 包里的 QuickJS | **不是隔离边界**（按签名信任） | — | 脚本在实例共用的 Agix 里跑，看得到那个实例里其它会话的事件 |
| 插件 APP 的能力、行内点会知道什么、界面能调的名字 | **披露**（装前，人同意才装；升级多要能力时只列多出来的） | 人不知道插件要什么 | 插件在给了的能力之内做什么 |
| Agix 插件的模型可见文本 | **披露** | 人不知道包往模型面前放了什么 | 文本本身的内容 |
| 界面模块占了哪些贡献点 | **披露** | 人不知道包改了界面哪里 | 模块在页面里做什么（§5.8） |
| 模块拿不到 `EngineLink` 和中枢内部状态 | **结构约束**（编译期可见性） | 模块不小心绕过中枢 | 模块是内核级源码，真要绕可以；这一条防的是误用 |
| `SPACE_MISMATCH`：会话与声称的 space、实例对不上就拒绝 | **防误** | 界面或模块的 bug 把消息发进别的 space、别的实例 | 同页的代码：space 是调用方自己声称的，任何设备代码都能声称任何 space，包括 `system` |
| 设备在系统 space 之外只能用 `ui = true` 的模板 | **防误**（保留系统 space 时） | 界面 bug 在普通 space 里建出调试用的实例 | 声称 `system` 的设备代码能用任何模板（仍然只能是启动时定下的模板，上面那条安全边界不变）。要让 `ui` 标记成为边界，就去掉系统 space |

把这些讲清楚比藏起来有用。

### 6.3 远程访问

一个进程服务一个用户，但这个用户可能有几台设备。

- **配对**：一次性配对码换一份长期设备凭据（设备侧密钥对，挑战应答）。每台设备一条，可列出，可单独吊销。不需要
  CA，不需要身份提供方。配对过的设备存在状态目录的 `devices.json`（同令牌一样只有属主可读），重启后仍在。
- **凭据绑主体，不绑连接。** 多通道拓扑里所有通道共用握手换来的那一份凭据，吊销一台设备立即断掉它的全部通道：
  它的凭据当场作废（分离流的请求得 401），单双向流的连接以 1008 关掉，事件流结束。
- **准入只给一个答案。** 未知或已吊销的设备、过期或用过的挑战、对不上的签名，拒绝的理由是同一句；令牌按恒定时间比较；
  `/challenge` 同时最多 1024 个未答的挑战，超了回 429。
- **非回环绑定必须同时有 TLS 与已配对设备。** 没有裸 HTTP 的远程——不是默认关闭，是没有这条路径。
- **启动链接**：本机打开页面时令牌可以不进页面，浏览器凭一次性链接换一个 `HttpOnly` cookie（桌面壳的本地模式就
  走这条，§5.11）。
- 回环绑定同时监听 IPv4 与 IPv6：`localhost` 在多数系统上先解析到 `::1`，只绑一边会出现「curl 通了但页面打不开」。
- Origin 校验按部署形态取值：本地放行本地来源，远程只放行配置里写明的来源，**不提供通配**。

### 6.4 敏感数据

transcript、会话记忆、录像（每次模型调用的完整输入，含系统提示词）都是同一批内容，**敏感级别相同**，落在同一个
实例数据根、同一套文件权限下。

三条规则：录像默认开，因为没有它就无法回答「模型到底看见了什么」（系统 space 的「调用」页签就靠它）；录像目录
**永不经 HTTP 暴露**，只能通过授权过的方法读；删除会话连带删除它的录像，关闭会话不删——会话还能重开。

### 6.5 审计

授权的拒绝、设备配对与吊销、扩展的安装、权限回答、系统 space 的每次跨 space 操作、实例的新建停止重启，以及插件 APP 的登记、撤下、
它的 `hub` 能力写进与撤出授权表、它被拒的调用、清数据，都记下来。
进程里有一个有界的环，`harnix.audit` 与诊断能读；能归到一个会话上的，另以扩展条目写进那个会话的时间线（目前是
`system` 实例上的会话），与其余条目同序。不是每次放行都记：一秒几次的只读放行会把真正有人会去找的条目埋掉。

复用引擎的扩展条目而不是另建一套日志，有一个具体好处：**未知命名空间必须可跳过**，所以卸载一个 Agix 插件或插件 APP 之后，它留下
的旧条目仍然能被加载，历史不会因为少了一个插件而读不出来。

## 7. 边缘部署

### 7.1 形态

**一个进程、一个用户、多个会话、一个后端二进制、无运行时依赖。** 没有包管理器，没有 `node_modules`。安装物是这一个
文件；运行时不从安装目录读任何东西，状态在状态目录，所以升级就是换掉那个文件。要隔离崩溃与资源的那部分 Agent，
用 daemon 载体放到另一个进程里（默认就是同一个二进制的 `daemon` 子命令，不另外分发）。

| 形态 | 后端 | 界面 | 传输拓扑 |
|---|---|---|---|
| 单机 / 桌面 | 本机，回环 | 后端提供（桌面壳加载它） | 单双向流 |
| 边缘节点 + 远程使用 | 节点上，TLS + 配对 | 后端提供 | 单双向流 |
| 反向代理后面 | 内网，代理终结 TLS | 独立静态服务（`ui export`） | 分离流 |
| 一堆节点 / 自动化 | 每节点一个进程，`--headless` | 无，或一份共用界面 | 纯请求 |

**Harnix 嵌入版**就是为这一节做的：Harnix app 加系统 space，开模式 2，装少量受控的插件 APP。插件 APP 不多一个进程：每个应用一台虚拟机，
常驻开销是它后端实例的线性内存（清单的 `memory_mb` 封顶，通常几 MB），整个进程共用一个 wasmtime 引擎；`on-demand` 的后端闲置时卸下。
产品构建不带编译器，只反序列化商店编好的产物，所以带插件 APP 的二进制只比默认的大几 MB。资源与安全的取舍见 [应用开发](app-development.md) §3–§4。

### 7.2 预算

**一个不被测量的性能目标只是一句话。** 下面这些数进 CI 门禁（`tests/budget.mjs`），回归即失败。初值按「4 核 8G
小主机，也要能在 2 核 2G 的 arm64 单板上跑」定：

| 指标 | 上限 |
|---|---|
| 后端二进制大小（默认构建） | ≤ 48 MB |
| 后端二进制大小（带插件 APP 的 `apps` 构建） | ≤ 52 MB（只有运行时、没有编译器；编译器混进来就超） |
| 界面产物（gzip 后） | ≤ 300 KB（含 React） |
| 冷启动到可服务 | ≤ 300 ms |
| 空载常驻内存（只有 `system` 一台实例） | ≤ 80 MB |
| 每个空闲会话的内存增量 | ≤ 4 MB |
| 每多一台空载的进程内实例 | ≤ 4 MB（实测约 0.1–0.2 MB） |
| 一次 unary 往返 p99（同机） | ≤ 15 ms |
| 每条空闲连接的常驻开销（预热后的边际值） | ≤ 64 KB |
| 握着 100 条连接时的常驻内存 | ≤ 120 MB |
| 完全空闲时 CPU | < 0.5% |

**「每条空闲连接」测的是预热之后的边际值。** 冷测时头一百条连接看起来每条 145 KB；开完关掉再开一百条，边际不到
1 KB——差别是分配器第一次向操作系统要页然后一直留着。对冷数字设门禁等于对 malloc 设门禁。所以两个数都测：
**再开一条要多少**，以及**握着一百条时一共多少**；后者也是前者不能被悄悄换掉的原因。daemon 实例是另一个进程，不计入
Harnix 的内存预算。

调整这些数的前提是把新的数写进这张表并说明理由，不是让门禁静默放宽。

三个已知的取舍，摆在这里，不藏在实现里：

1. **QuickJS 每次调用建一个全新运行时**，这是「调用之间什么都不留」这条安全承诺的实现方式。是否为某些点复用
   运行时，是一个会削弱那条承诺的决定，要显式做。
2. **进程内实例意味着崩溃不隔离。** 换来的是没有 socket、没有握手、可以带原生工具。补偿措施是轮次级的故障隔离、
   随发布物提供的进程守护单元，以及需要时把那台实例换成 daemon 载体——是可选的，不是默认把进程拆开。
3. **拓扑的成本不一样，所以它是配置而不是常量。** 分离流在代理后面更好用，代价是多一条连接；单双向流在弱网下
   更省，代价是所有流量共享一条连接的队头。**边缘默认单双向流**，因为那里连接比中间件贵。

### 7.3 离线

- 模型走本地端点（OpenAI 兼容协议直连本地推理服务），并按任务分路由：主循环用大模型，压缩、子代理、记忆检索
  用小模型——这几类调用次数多、对质量要求低，是边缘设备上最值得省的地方。
- 界面产物自包含，无 CDN（§5.9），所以断网时界面照常打开。
- 插件安装可以完全离线：一个 Agix 插件是一个文件，从本地路径装与从市场装走同一条披露流程；插件 APP 也是一个文件，签了名的经
  `harnix.apps.installFile` 照样验签，商店也可以是本机的 `file://` 目录。
- 构建也能离线：Agix 随 `harnix/` 子仓一起检出，作为路径依赖，不经 git 源。

### 7.4 故障

- 引擎的持久化是 append-only 的日志，进程消失后重启即恢复到最后落盘的那一轮；按模板建的实例照账本重建。
- 被取消的轮次**不写终止标记**——取消是被打断，不是到达终点，所以会话必须保持可续。
- **断线不动 turn。** 任何通道断开只影响观看，中枢照跑；重连后按 `seq` 追赶。多通道拓扑里一条通道断了不牵连另一条。
- **daemon 断了是降级，不是挂掉**：那边的轮照跑，重连后 resync（§3.1.1）。
- **插件 APP 的陷阱、超时、内存超限被接住**，只动这一个应用（换实例、重建一次、再崩置于一旁）；健康运行一段时间后出错计数清零。
  wasmtime 或宿主函数自己的 bug 在模式 2 里会波及整个进程，这是模式 3 要用进程边界解决的。
- 上游长时间无响应要在界面上表现为可脱出的状态，不是无限「运行中」。

## 8. 改造它的层次

| 层次 | 做什么 | 代价 |
|---|---|---|
| **换 profile** | 一份声明式配置：场景、provider、实例与模板、拓扑、留哪几个内建 space、品牌、是否加载 Agix 插件的界面模块、是否开插件 APP | 不写代码 |
| **装 Agix 插件** | 引擎的脚本、skill、agent 类型改 agent 的行为；包的界面模块给已有的贡献点做贡献 | 不重编译 |
| **装插件 APP**（模式 2） | 一个应用包：后端方法、主题、space、给 Agent 的工具、Agix 插件、隔离的界面，照清单拿能力 | 不重编译；产品要带 `apps` 构建、开 `[apps] enabled` |
| **换界面** | 换掉 `--ui-dir` 指的那份产物，或者只换其中几个注册 | 不重编译后端 |
| **做一个应用：编译期模块**（模式 1） | 以子仓引入 Harnix，写自己的模块（后端方法、主题、路由、实例模板、原生工具）和 space 界面，`App::builder()` 装起来 | 重编译；不 fork Harnix |

最后一层是 §1.2 第一条目标真正落地的地方：一个形态完全不同的产品（Helm 的交易面板、IPDrun 的流程）不需要 fork，而是 Harnix 之上的一个应用。
应用仓库里只有一个子仓 `harnix/`，Agix 由它带进来（`harnix/agix`，版本就是 Harnix 钉的那一版）。应用只认 Harnix：代码只依赖 crate `harnix`，
Agent 侧的类型经 `harnix::agent`、`harnix::scenes` 取；问题与需求只提 Harnix 的 issue，落在哪一层由 Harnix 决定——这样应用只有一个版本
要跟，Harnix 也能改动自己与引擎之间的分界而不牵动应用。公共改动在应用的 `harnix/` 子仓里开分支回推上游，**应用里不许有长期补丁**
（`check-pins` 检查子仓指针只指向上游存在的提交）。怎么做见 [SDK](harnix-sdk.md)，从 `templates/app` 起步。

配套的两样，缺一不可：

- **贡献点目录由代码生成**，并有测试盯着它与代码一致。一份会过期的清单比没有更糟——它会被当成事实引用。
- **功能测试对着真的二进制跑（LIVE）**：后端走 API，前端走 Playwright 真浏览器，同一个运行器、同一套夹具；模型默认按位置回放引擎的录像，
  所以工具调用、权限提问、子 Agent 每次都一样，不花钱也不等网络；另有连真实模型的 live 模式刷新录像。覆盖表由用例标签生成，一个功能在
  某一层是零就要补或写明为什么。见 [testing.md](testing.md)。

为什么不用假 DOM、假后端：假后端还返回旧形状时，界面测试全绿而功能是坏的。在有录像回放之前，权限那条路**一次都没被真正跑到过**——
配置的模型不肯调工具，测试轮轮报「不确定」，而一切看上去是绿的。所以测试的结果有三种，不是两种：通过、失败、没结论。

## 9. 与 Agix 的边界

**依赖方式：**

> **进程内实例以库链接；daemon 实例经本机 JSON-RPC。两种载体对中枢是同一个 `EngineLink`，会话语义不因载体改变；
> 一台 daemon 只服务一个 Harnix，中枢仍是它上面会话的唯一持有者。**

这条原则的本意是两件事：中枢是会话的唯一持有者；Harnix 不因为连接方式不同而改变会话语义。daemon 载体保住了这两件事，换来了崩溃与资源的隔离。

**Harnix 一侧永远不做的事**：实现或复制任何引擎逻辑；绕过引擎直接操作 transcript；在引擎之外维护第二份会话状态
（中枢维护的是**观看状态**与队列，账本记的是会话归属，都不是会话本身）。

**Agix 必选，不做引擎可替换。** 抽象一层「任意引擎」，代价是每一处都只能用所有引擎的交集，而 Harnix 的价值恰恰在于把这一台引擎的语义完整地
交给应用。

**Agix 缺的，去补 Agix。** 缺口写成 Agix 的 issue，由它驱动 Agix 开发；Harnix 侧不绕过、不模拟（系统 space 的「Agix 没给的不画假的」是同一条）。
**Harnix 跟着 Agix 持续升级**：`agix/` 子仓的钉就是 Harnix 验证过的那一版，每个 Harnix 发布对应一个 Agix 发布；Agix 改自己的类型，对一个
不实现引擎逻辑的宿主不该有代价。

**WASM 在这一侧。** Agix 只留编译进宿主的 Rust 插件与 QuickJS 脚本，带 `[[wasm]]` 段的包拒装；插件 APP 的 WASM 组件跑在 Harnix 的 `harnix-wasm` 里，
经 Agix 的 Rust 插件接口进会话。所以 WASM 只有一处，Agent 侧的扩展也只有一处。

Harnix 依赖 Agix 提供的、并且已经由它提供的：

| Harnix 用来做什么 | Agix 给的 |
|---|---|
| 实例装配 | 装配的函数入口（`daemon::assemble::pool`）；同一进程里几台会话池互不可见 |
| daemon 载体 | `DaemonServer` 的库入口、协议版本与能力位、`subscription_dropped`、spawn 的就绪 |
| 中枢知道每一轮 | 会话与轮的生命周期进 `daemon.event`（带 `initiator`）；订阅冷会话 |
| 会话列表、改名、换模型 | 列表条目带场景与项目根；`session.rename`、`session.setModel` |
| 系统 space | 会话的任务可列、可停、可发话；上下文可查看、去掉或改写消息；目标；录像 |
| 扩展条目 | `session.appendEntry` / `session.entries` / `extension_entry` 帧；分叉带上条目 |
| Agix 插件 | 包方案与载体解耦；`plugin.list` 带包的 `root`、`script_faults`；装不上的包不会假装装上；manifest 里不认识的段只告警 |
| 插件 APP 进会话 | Rust 插件接口 `runtime::plugin::Plugin`：会话建起时登记工具、工具调用的中间件，子 Agent 带着父会话的插件构建 |

这些曾经一条条是给 Agix 提的 issue。

## 10. 明确不做的

| 不做 | 理由 |
|---|---|
| 多租户 | 一个进程一个用户。硬塞进来会让授权模型对单用户场景过度复杂 |
| 可替换的会话中枢、可替换的引擎 | §2.1、§9 |
| 让拓扑或载体差异渗进中枢、授权 | 传输可以有几种拓扑、实例可以有两种载体，但只能有一套语义 |
| 运行期新增或改写模板、模块 | 等于让别的东西决定这个进程是什么（§3.1）。插件 APP 不是模块：它在自己的命名空间里、照清单、可撤 |
| Agent 侧的第二套插件体系 | 同一件事两处真相，且只有一处真拦得住；Agix 插件的包方案、能力与披露留在引擎（§2.2） |
| 在 WASM 沙箱之外执行包里的代码 | 原生动态库、包里的进程、Harnix 侧的脚本解释器都不要；规则不需要例外才守得住（§2.2.1） |
| 给 Agix 插件贡献的 `harnix.*` / `app.*` 方法 | 它需要回调能力，给出能力就是在 Harnix 长出第二个能力模型。要后端方法，写编译期模块或插件 APP |
| 插件 APP 贡献 `harnix.*` 方法、往别人的 space 加东西 | 它的方法、主题、space、面都在它自己的 `app.<id>.*` 与 `<id>.*` 下 |
| 插件 APP 改宿主的单槽契约（权限判定、预算、提示组装器） | Agix 也只给 Rust；第三方代码不决定这些 |
| Agix 插件新增 space、往别的 space 加页签 | 要 space 的第三方代码写成插件 APP |
| dylib 形式的 Rust 模块 | 运行期的后端只有 WASM 的插件 APP；原生代码只走编译期模块 |
| 一个产品同时开模式 2 与模式 3 | 两种模式对「插件的 Agent 在哪」答案不同（[应用开发](app-development.md) §2） |
| 界面的运行期外部依赖（CDN、远程 import） | 断网即坏，且把供应链面开到系统之外 |
| 桌面壳的私有通道（IPC、自定义协议） | 一条不经授权、不进审计、浏览器版没有的通道（§5.11） |
| 把引擎的凭据 / 子进程 / 端点类方法开放给设备或插件 | 它们等价于接管这个进程 |
| 批准原语、角色令牌、MCP 服务端进内核 | 应用在模块契约上做得出来（§4.5）；两个应用的实现形状一致后再收 |
| 跨机器的 daemon 实例；几个宿主共用一台 daemon | 前者只做本机；后者破坏中枢的唯一持有（§3.1.1） |
| 宿主主题的「追加模式」 | 整值快照够用；出现真实的高频增量需求再说 |
| 迁移的备份钩子、`--dry-run` | Harnix 只管迁移的顺序与失败隔离（§4.2） |
| 协议层的投影子系统 | 派生视图不属于协议 |

这些里有「以后可能做」的，前提都是真实需求加 §1.3 的判据。

## 11. 与业界的位置

这一节说明哪些决定是共识、哪些是这套设计的选择。

近两年出现的几个 agent 宿主（DeepSeek Harness / dsh，以及围绕 MCP 生态生长出来的若干 IDE 与桌面宿主）在几件事上
给出了同样的答案，Harnix 也照做：**一切能力以插件形式接入**、**模型是可换的类别而不是硬编码**、**会话是可追加、
可回放的事件流**、**界面与内核分层**、**请求与事件流分开承载**、**界面用 React**。这些不是差异点，是这类系统的形状。

传输拓扑上没什么可争的：那类系统普遍采用「一条 unary 端点 + 若干只下行事件流 + 一条带外应答端点」的分法。Harnix
的做法是把这套分法**上升成语义、把连接数下降成配置**——同一套语义在边缘设备上更适合收敛成一条连接，在代理后面
更适合摊开成几条，这两种部署都在目标之内。

分歧在四处：

**一、内核边界。** 那类系统多把「一切皆插件」推到底——agent 循环、会话持久化、审批逻辑本身也是可换插件。代价是
这个系统不再保证任何东西：当循环本身可换时，「一轮是什么」没有答案。Harnix 反过来，骨架写死、判断开放（§2.1）。
这牺牲了一部分灵活性，换来的是可以对用户做出承诺。

**二、插件的运行方式与隔离。** 以 Node 为宿主的方案里，插件与内核同进程同权限，JS 的对象级隔离不是隔离；其沙箱通常只覆盖文件系统的几档模式。
这套设计里，Agent 侧的扩展在引擎里（QuickJS 没有 I/O、限内存限时；它限的是资源，不是对恶意代码的隔离边界，信任来自签名与安装时的披露）；
宿主这一侧的插件 APP 只跑在 WASM 里，那是一个对恶意代码也成立的边界，它要的每一项能力写在清单里、在宿主函数里逐项查；应用自己的代码是编译期
模块，不走插件。界面一侧，商店的插件进隔离的 iframe，受信的进页面、与页面同级，这一点明说，并且产品可以整个关掉（§5.7、§5.8）。差别不在
「更安全」这个形容词上，在于每一处都标明了自己是哪一种。

**三、模型可见文本的处理。** 这一类攻击面在多数方案里没有专门位置：沙箱管执行，而一段进入系统提示词的文字既不越权
也不出网。引擎把它当作一等的披露对象，从安装里回出来；宿主的活是把它摆到人面前，而不是自己再算一遍（§4.4）。系统
space 让人随时看到每一次调用实际带了什么（§5.5）。

**四、部署形态。** 以 Node 或容器为前提的宿主，安装物是一棵依赖树，冷启动以秒计，常驻内存以百兆计。Harnix 的后端
是一个二进制，预算写进 CI（§7.2）；带插件 APP 的构建另有一条体积上限，一个应用的常驻开销是它后端实例的线性内存。这条不是性能偏好，
它决定了这个系统能不能装在一台边缘设备上。

值得从那些系统里继续借的，是它们对**分层配置**的处理（插件 → 打包 → profile → 覆盖层，让「换一个形态」变成一次
配置而不是一次 fork）。Harnix 的改造层次（§8）就是这条思路，加上一层编译期的应用。
