## 1. 定位

**Harnix 是 Agix 应用的公共底座。**

引擎负责「跑一个 agent 会话」：装配提示词、调模型、执行工具、管理上下文与历史。Harnix 负责把一台或
几台引擎变成一个**应用**：会话的持有与追赶、实例的组织、界面的外壳、身份与授权、部署形态，以及让
应用作者把自己的代码接进来的契约。一个应用（Helm、IPDrun、Grabix）是一个二进制加一份编在里面的界面产物，由
`harnix::App::builder()` 加上应用自己的扩展组成，不 fork、不留补丁。

**Harnix 本身是两部分：**

| 部分 | 是什么 | 在哪讲 |
|---|---|---|
| **框架** | 骨架（传输、路由与准入、中枢、装配）、实例层、扩展接口与扩展宿主、两种 WASM 载体、外壳核心 | 本文 |
| **第一方扩展** | `harnix-app`（首页、会话 space 与项目 space）、`settings`、`plugins`、`observability`、`devices`、`flow`（流程 space）、`schedule`（定时），以及管扩展包的宿主组件 `packages`。每一个都是只用公开扩展接口写的原生扩展，界面在同名的 UI 包里 | §4、§5.5、[Harnix app](harnix-app.md) |

Harnix 自己发布的二进制 `harnix` 是框架加上全部第一方扩展、`packages` 与两个载体，profile 不写载体时跑模式 2。一个产品是框架上的另一组扩展，和
Harnix 自己的二进制同一种做法：链进自己的原生扩展，挑它要的第一方扩展，授予它们能力。

这条分工是硬的，两个方向都是：

- **Harnix 不含任何引擎逻辑。** 会话怎么跑、工具怎么派发、上下文什么时候压缩，一律是 Agix 的事。
  缺的能力去给 Agix 提，不在这边补一个平行实现——一个平行实现意味着同一件事有两处真相，而它们会分叉。
- **Agix 不知道有界面、space、应用这回事。** 客户端面的协议、贡献点、身份、space、扩展，全部止步于 Harnix。

### 1.1 它不是什么

| 不是 | 因为 |
|---|---|
| 一个 agent 框架 | 框架是 Agix。Harnix 是它的宿主 |
| 一个多租户服务 | 一个进程服务一个用户（多个会话、多台设备、可以多台实例）。多租户是另一个系统，不是这个系统的配置项 |
| 一个「什么都能换」的内核 | 骨架不可插拔，见 §2.1 |
| 应用的功能仓库 | 应用独有的东西（领域服务、产品面板、批准策略）不进 Harnix，见 §1.3 |

### 1.2 三个目标，按优先级

1. **可定制。** 不 fork 就能做出一个形态不同的产品。这是首要目标，其余两条服务于它。
2. **可在边缘部署。** 一个后端二进制，无运行时依赖，冷启动以毫秒计，空载内存以十兆计。
3. **安全边界清楚。** 每一处约束要么是强制的，要么被明说成不是强制的。没有第三种。

落地它们的方式：应用以子仓引入 Harnix（Harnix 带着 Agix）、用原生扩展装配，产品可以再让别人装扩展包（目标 1）；一个 Harnix
可以组织多台互相隔离的实例，进程内的、独立 daemon 进程的都行（目标 1、2）；扩展包跑在 WASM 里、按同意记录拿能力，模式 3 再加一层进程与
操作系统沙箱，每次调用实际带了什么、每个扩展在做什么都看得见（§5.5；目标 3：看得见才谈得上清楚）；每个功能都对着真的二进制测（§8）。

### 1.3 什么进 Harnix：判据

> **只有在公开契约之上做不出来，或者做出来会破坏 Harnix 不变量的东西，才进 Harnix。**

满足下面任一条才进：

- 它要碰中枢、路由与准入、传输、装配的内部（例如无头会话：要和客户端共用排队与 `seq`）；
- 应用各写一份会破坏一条不变量（例如会话与 space 的对应关系）；
- 它本身就是契约的一部分（扩展接口、贡献点、宿主 API）。

「第二个应用也会要」不够：那样几乎什么都能塞进来。其余的，即使两个应用都要，也先由应用在扩展接口上
实现；等两份实现证明是同一个形状，再考虑收进来。Helm、IPDrun 的需求是**输入**，不是必须满足的清单。

背后是维护者定下的一条：**Harnix 自己保持薄、容易改造。** 一个什么都带的底座，每个应用都要先学会
关掉它不要的那些；一个薄的底座，应用只学它要的那些。所以 Harnix 带的功能都是扩展，要不要一个功能就是要不要那个扩展：
不链它，或者 profile 写 `[extensions] off = ["<id>"]`。关掉时它的方法、主题、路由、space 连同授予一起从路由表撤下，
声称它的 space 的调用一律 `SPACE_MISMATCH`——**撤的是方法，不只是不画**。Harnix app 的后端也一样：不要自带会话模型的产品不链 `harnix-app`，
`harnix-app.*` 就不在。

## 2. 设计原则

### 2.1 骨架不可插拔

Harnix 的骨架是四件事：**传输、路由与准入、中枢、装配**。它们不是扩展点，没有替换入口。

理由和引擎把轮次循环的步骤顺序写死是同一个：**顺序与所有权本身就是定义**。一个能被插件换掉的会话
中枢等于没有中枢——追赶不变量一旦可以被第三方重写，「打开一个跑到一半的会话会看到什么」就不再有
答案，而这是产品最基本的动作。

骨架之上的每一个判断都可插拔。分界线画在「这件事的形状」和「这件事怎么做」之间。

**「不可插拔」约束的是语义，不是实现形式。** 传输承载什么、保证什么是写死的，用几条连接承载不是
（§3.3）；中枢的语义是写死的，它对面的实例在本进程里还是在另一个进程里不是（§3.1.1）。

**骨架也要薄。** 不可替换的东西越胖，「这一块动不得」覆盖的代码就越多。所以骨架里只留每个产品都离不开的：会话的持有、名字与调用的判定、
准入、装配与扩展宿主、实例登记表。Harnix app 的后端、设置、Agix 插件的管理、录像与用量、会话内部的观测、设备配对的管理、
进程统计、扩展包的安装与运行，都是骨架之外的扩展。**骨架里没有一个分支认某个扩展或 space 的 id**——没有 `"home"`、`"sessions"`、`"flow"`
这样的字面量；特权来自授予的能力（§2.3），由层次规则查（§2.5）。

### 2.2 一个扩展模型：三种载体

往一个 Harnix 产品里登记方法、主题、space、界面、工具的东西只有一个概念：**扩展**。一个扩展由一个描述（`ExtensionDescriptor`）说完它提供的一切，
经一个登记口进路由表，信任与能力写在它的登记里一处。扩展之间的区别只在**载体**，即它怎么跑：

| 载体 | 是什么 | 描述从哪来 | 能力从哪来 | 隔离 |
|---|---|---|---|---|
| **原生** | Rust，编进二进制 | 代码（`Extension::register`） | 装配时由产品授予 | 无：出身即信任 |
| **WASM 同进程**（模式 2，**缺省**） | 扩展包里的 WASM 组件，在产品进程的 wasmtime 里；`agent/` 装进产品的实例 | 清单，由原生扩展 `packages` 代为登记 | 清单申请 → 签名、披露、人同意 → 同意记录 | WASM 沙箱 |
| **WASM 进程**（模式 3，选用） | 同一个扩展包，在产品二进制的子命令 `ext-proc` 起的子进程里，连同它自己完整的 Agix；宿主只路由 | 同上；进程报上来的只用来核对 | 同上，产品侧复核 | WASM 沙箱 + 进程 + 操作系统沙箱 |

**原生打底。** 两种 WASM 载体**建在原生之上**：`packages` 是一个持能力 `extensions.manage` 的原生扩展，它照每个扩展包的清单与同意记录拼出一个描述，
经和原生扩展同一个登记口登记。在内核里一个扩展包就是一个扩展：同一种描述、同一张路由表、同一套授予与审计，诊断里它和原生扩展列在一起
（信任 `Consent`、载体 `wasm` 或 `process`）。原生扩展能做的是全集，扩展包是它的一个子集，子集之外的每一样都写明了理由（§4.5）。

**扩展不是 Agix 插件。** Agix 插件（QuickJS 脚本、skill、agent 类型）是引擎的包：包格式、取包、校验、能力声明、披露、沙箱、生命周期，整件事都在引擎那边；
它跑在实例里，够不到 Harnix 的方法面。Harnix 只经第一方扩展 `plugins` 把文件送过去、读它引擎不关心的那一段 `[[ui]]`（§4.7）。
扩展包的 Agent 部分就是一个 Agix 插件，由载体装进实例。

#### 2.2.1 只在 WASM 沙箱里执行包里的代码，QuickJS 按签名信任

> **Harnix 只在 WASM 沙箱里执行包里的代码。包里的 QuickJS 在引擎里跑，按签名信任。**

- **WASM**：扩展包的后端与工具是 WASM 组件，跑在 Harnix 自己的 wasmtime 里（`harnix-wasm`），模式 2 在产品进程里，模式 3 在扩展进程里，是同一份。
  它是隔离边界：内存安全，没有环境里的文件与网络，能碰到的只有宿主函数，而每个宿主函数都按同意记录查（`net` 精确主机、`env` 名单、`storage` 上限、
  能调的名字、`fs` 预开目录）。
- **QuickJS**：扩展包的 Agent 部分可以带 QuickJS 脚本，它们挂在 Agix 的扩展点上、在引擎里跑、没有 I/O。Agix 明说 QuickJS 只限资源、
  **不是隔离边界**，所以它的信任来自签名：商店审核时按「脚本即代码」对待。
- **不执行的**：原生动态库、包里的任意进程、Harnix 自己的脚本解释器。Harnix 侧没有一个能跑包里脚本的地方：扩展 Agent 的脚本是 Agix 的。
  模式 3 的扩展进程不是包里的进程：它是产品二进制自己（§4.6）。

由 `crates/harnix/tests/layering.rs` 盯着：整个 crate 树里不许出现任何解释器；wasmtime 只许出现在 `harnix-wasm` 里，外面经它的 API 碰组件，
那个 API 叫不出 wasmtime 的类型。

**为什么不是更宽的规则。** 早先有过一个例外：Agix 包的 `[[host]]` 段里的投影，一个折叠会话事件流的纯函数，由 Harnix 执行。它让规则必须写成
「Harnix 执行包里的代码，但只执行什么都做不了的那种」，而**一条带例外的规则是会被人加宽的**，所以它被撤掉了。今天的规则也不带例外：
包里的代码要在 Harnix 这边跑，只有一种跑法，就是 WASM 沙箱；要的每一项能力都在同意记录里、在宿主函数里查。原生扩展不受这条约束——
它不是包里的东西，是应用本身。

#### 2.2.2 为什么是这个形状

- **一个概念，而不是两个。** 编进来的代码与装上的包若是两个概念，就有两套登记、两条授权路径、两处决定「它能做什么」，它们会分叉，
  分叉之后往往只有一处是真正拦得住的。所以只有扩展：一个描述、一张路由表、一套授予；装上的包只是由 `packages` 代为登记的扩展。
- **应用的领域能力要原生。** 应用要在 Harnix 上做产品，就要能加后端方法、space、原生工具、场景、实例模板，这些运行期包给不了，也不该给。
  原生扩展是应用作者本人的源码，编译期链接；它能做的是全集。
- **第三方的后端逻辑要隔离。** 应用要让别人往产品里加东西，而第三方代码不能是内核级的。答案是 WASM：一个能对恶意代码也成立的
  边界，加上同意记录里逐项的能力。WASM 载体原来在 Agix 里，和脚本载体互斥；它搬到 Harnix 之后，Agix 只留 Rust 与 QuickJS 插件，
  WASM 只有一处，在 Harnix。
- **Agent 侧的扩展归引擎。** Harnix 不做 Agent 侧的第二套插件，Agix 插件的包方案、能力与披露都留在引擎；Harnix 只补引擎有意不做的那一步（收文件，§4.7）。
- **特权是有名字的能力，不是名单上的 id。** 一个按 id 给的特权（「`observability` 可以读任何会话的内部」）是骨架里的一个分支，换一个扩展就做不到同样的事。
  所以读会话内部的权力就是 `engine.inspect` 这一项能力，同样的授予给别的扩展就有同样的权力（§4.3）。

写下来是因为 §2.5：一份反复改过又没说为什么的设计，读的人无从判断哪一版是当前的。

### 2.3 信任按出身定，能力按授予定，声明只收窄

一个来自外面的扩展要撒谎，撒的正是「我需要什么」这种声明。所以级别由它**从哪儿来**决定：应用作者
编进来的扩展、运维本人写在项目里的东西、装上的扩展包、远端连上来的设备，天然不同级。声明的作用是在已定
的级别内**进一步收窄**，不是用来晋级的。

- **信任**写在扩展的登记里，两种：`Origin`（原生扩展：出身即信任，每一行由它自己的访问规则判）与 `Consent`（扩展包：只到同意记录里的 `calls`
  与它自己的名字，每一行再收窄到它自己的 space 与会话）。
- **能力**是有名字的特权（`instances.admin`、`engine.inspect`……），原生扩展的由产品在 `main.rs` 里显式授予，扩展包的来自人同意过的清单。
  没有按 id 给的特权，也没有「第一方」这一类：第一方只是出处。
- 扩展包的出身由签名定（商店副署、受信发布者、未签名），出身定了它的界面进页面还是进 iframe、能不能在非开发模式下跑；
  清单里的能力只在这个级别里收窄——一个清单写得再宽，也拿不到 WASM 沙箱之外的东西，也拿不到只给原生的能力。

### 2.4 失败只让它自己那份消失

抛异常、超时、配额耗尽、答出一个用不了的形状——这个点保持原样，别的什么都不受影响。每个适配器先把
改动完整算出来再施加，所以不存在「施加了一半」的状态。

这条对每一种扩展都成立：

- 一条界面贡献渲染出错，只有它消失；形状不对或 id 重复，这一条被拒，记进诊断。一个 UI 包的 `register` 抛错，只有它的注册不生效。
- 一个 Agix 插件的界面模块照别的贡献点 API 版本写的，**那一条**报「不生效」，包的其余部分照常（§5.8）。
- 一个原生扩展登记冲突、配置反序列化失败、`migrate` 或 `start` 失败，只停用这个扩展和它的方法、主题、路由、space、
  实例，进诊断页；别的扩展照常启动。
- 一个扩展包装到一半失败，整体回滚，只停这一个；它的后端超时只换掉它的 Store，反复崩溃就置于一旁（行留在表里，答 `EXTENSION_UNAVAILABLE`）；
  模式 3 的扩展进程崩了只影响它自己，按退避重起；它的一个界面面板崩了，外壳只在那一块画「出错了，重试」，连续失败的面被置于一旁。

而且**「它什么也没做」是可查询的**：哪个点、谁、什么原因，都记下来并且能问（`harnix.diagnostics`、`harnix.extensions`、
设置里的诊断）。否则「我的扩展为什么不工作」只能靠猜。扩展包的这些在设置 → 诊断的「扩展包运行状况」里，各扩展的日志在它下面（§5.5）。

### 2.5 每一条承诺都可检查

- **层次**：哪个 crate 能依赖哪个、哪里不许出现哪些名字（Agix 的方法名、第一方扩展的 id、按前缀分派），由 `crates/harnix/tests/layering.rs` 读
  `cargo metadata` 与源码断言，不由文档描述。界面一侧同样有规则（`tests/ui-layering.mjs`）：外壳核心不认识任何第一方 UI 包。
- **路由表**：产品缺省装配的每一行、它的所有者与访问写成一份快照，改了要在提交说明里写明；LIVE 再从运行中的进程读一遍比对。
- **扩展接口**：一个测试扩展只用 `harnix-ext` 的公开接口，把登记、上下文、调用的每一个函数各用一次；一个叫 `debugger` 的测试扩展被授予
  `instances.admin`、`engine.inspect`、`engine.control`、`process.observe`，声明一个 `cross_space()` 的 space，就能观看、操作任何 space 的会话，不授予就每一样都被拒。
- **Agix 接缝**：LIVE 的录像缺省**严格**回放，比对交给引擎的系统块、工具表与每条消息的摘要；接缝改了一个字节就红。
- **载体**：扩展包的套件在两种 WASM 载体下各跑一遍；模式 3 的沙箱有探针，读不该读的就失败。
- 贡献点目录由代码生成；性能预算进 CI 门禁；内建界面走的就是公开的那批贡献点，而且有测试盯着「外壳真的去问了」；
  功能覆盖表由用例标签生成，一行在某一层是零就失败。

**一份没人检查的承诺，下一次改动就变成谎话。**

## 3. 内核

骨架是四件事：装配、中枢、传输、路由与准入（§2.1）。先看它们管着的东西。

**运行时四层。** Harnix 里一切和 Agent 有关的东西都落在这四层之一：

```text
Harnix 进程
 ├─ 实例 main             （进程内）  ← 隔离单位：数据根、设置、provider、MCP、Agix 插件、场景
 │   ├─ 会话 a            ← 一条轮次循环；同一时刻至多一轮
 │   │   ├─ 后台任务：子 Agent "explore"     ← 属于会话，跟着会话的权限、项目根、生命周期
 │   │   ├─ 后台任务：后台 Bash `npm run dev`
 │   │   └─ 后台任务：模型建的定时 0 9 * * *
 │   └─ 会话 b
 ├─ 实例 helm-l1          （进程内，Helm 的扩展按自己的模板建的）
 ├─ 实例 ci-runner        （spawn 的 daemon，本机另一个进程）
 └─ 实例 proc.acme.notes  （收养的：模式 3 的扩展进程里它自己的引擎）
```

| 层 | 是什么 | 拥有什么 | 隔离到什么程度 | 谁建 | 身份 |
|---|---|---|---|---|---|
| **Harnix 进程** | 一个二进制，一个用户 | 中枢、路由表与准入、传输、实例登记表、扩展宿主、账本 | — | 运维 | — |
| **实例** | 一台 Agix 引擎，一个会话池 | 数据根（设置三层、transcript、记忆、技能、录像）、provider 路由与凭据、MCP 连接、Agix 插件、场景、引擎贡献 | **彼此完全隔离**。daemon 与收养的实例还隔离了崩溃和资源 | profile 声明；扩展、界面按模板建；宿主组件收养 | `instance` |
| **会话** | 实例里的一条轮次循环 | transcript、场景（创建时定，决定工具集）、项目根、模型、权限规则 | 共享所属实例的配置；彼此的上下文互不可见 | 客户端、扩展（无头）、模型（子 Agent 的侧链） | `(instance, session)` |
| **后台任务** | 属于某个会话、在会话之外继续跑的工作 | 子 Agent、团队成员、执行中的 Shell 与监视器、模型建的定时 | 跟着所属会话：同一套权限、项目根；会话删了，后台任务一起没 | 会话里的模型（经工具） | `(instance, session, task)` |

由这张表直接推出来的规则：

- **隔离只在实例这一层承诺。** 要两套互不相干的配置（不同的 MCP、凭据、场景），就建两台实例，不在
  一台实例里靠会话区分。进程内实例的隔离由 Agix 承诺（同一进程里的几台会话池互不可见，有守护测试；
  唯一共享的是 OTel 导出器）。
- **后台任务是 Agix 的东西，Harnix 只看、只转发停止。** 子 Agent 的侧链在 Agix 里也是一个会话，在 Harnix
  里它是父会话的后台任务，不出现在会话列表的顶层，不进中枢的键，不进账本。
- **会话不跨实例，也不跨 space。** 要跨就用 `@session` 引用或分叉（§5.4）；拥有它的扩展可以把它**展示**到另一个 space（§5.4），归属不变。
- **轮不一定由 Harnix 发起。** 模型建的定时会让一个会话自己开始一轮。实例在 `daemon.event` 上报每一轮的
  开始与结束（带 `initiator`），中枢据此知道，不假定「我没发起的轮就不存在」。

**结构。**

```text
 浏览器（同一份产物；Tauri 只是装它的窗口）
```

依赖是单向的，每一层不认识它上面那层的概念，由 `crates/harnix/tests/layering.rs` 断言：

| 层 | 不许知道 |
|---|---|
| 协议类型（`harnix-contract`） | 任何一层；不链异步运行时 |
| 内部接口（`harnix-kernel`） | Agix、HTTP |
| 传输 | 路由表、中枢、实例、引擎是什么 |
| 路由与准入 | 帧长什么样、走的哪条通道、实例在哪 |
| 中枢 | 实例层、HTTP、TLS、连接、拓扑、**实例载体与数据根**、**Agix 的任何方法名与事件种类** |
| 实例层 | 客户端面协议、space、扩展 |
| 引擎词汇（`harnix-engine-api`） | Agix（连可选依赖也没有） |
| 扩展接口（`harnix-ext`） | 中枢、引擎链接、路由表、授予表、Agix |
| 第一方扩展 | 除 `harnix-ext` 以外的任何 Harnix crate；宿主组件另可用 `harnix-host-api` |

第一方扩展只用公开的扩展接口，同一套规则盯着：`harnix-ext-observability` 只依赖 `harnix-ext`，不链它，内核一行不改，路由表只差它的行。
如果 Harnix 自己带的东西不能用公开契约写出来，这份契约就不值得相信。

**稳定层级。** 接口按承诺分四层，层次规则让每一层的变化落在一处：

| 层级 | 包含 | 承诺 |
|---|---|---|
| **S1 扩展接口** | Rust：`harnix-ext`、`harnix-engine-api`、`harnix_contract::s1` 的全部公开项（经 `harnix` 门面重导出；门面只依赖前两者）；包：清单、WIT `harnix:ext@1.0.0`、桥、`@harnix/ext-sdk`、`@harnix/ext-kit`；界面：`@harnix/react` 的公开导出 | 只做加法 |
| **S2 线上协议** | 方法、主题、通知、错误码、握手，**除了**随 Agix 变的两块（§9） | 只做加法；改形状升 `PROTOCOL_VERSION` |
| **S3 内核内部接口** | `harnix-kernel`、`harnix-engine-link`（引擎链接、操作、事件）、`harnix-host-api`、端口与扩展线 | 骨架与宿主组件之间的契约；本仓库内可改；普通扩展不许依赖 |
| **U 不稳定** | `harnix::testing`、`harnix_ext::http::axum`、事件负载与 `engine.*` 的答 | 不在任何承诺里，文档首句写明 |

「只做加法」靠的是机制，不是自觉：出现在 S1 签名里的类型住在 S1 的 crate 里（契约的在 `s1/`），S1 的 crate 不依赖 S3 的，所以写不出 S3 的名字；S1 的公开结构与枚举一律 `#[non_exhaustive]`、经构造函数与
builder 生成，加字段、加变体都是加法；cargo feature 只加函数与模块，不加字段与变体（feature 是合并的，一个下游开了它，别的下游的穷尽 `match` 不能因此坏）；
扩展接口里没有 `#[doc(hidden)]`。这几条都是层次规则。

### 3.1 装配：扩展宿主与启动顺序

装配（`harnix-assembly`）决定这个进程由哪些扩展组成、按什么顺序起来，并且就是**扩展宿主**：登记、迁移、启动、停用扩展，查授予，
把描述装进路由表、中枢的主题与 space 表、传输层的路由、界面板。内核自己的几行也在这里（`harnix.hello`、`harnix.diagnostics`、`harnix.audit`、
`harnix.extensions`、`harnix.ui`、`harnix.bulk.upload`）。

装配是**声明式的**，并且在启动时定：

> **装配在启动时定：有哪些原生扩展、各授予什么能力、有哪些模板、链了哪些载体。运行期能新建的只有会话、模板允许的实例，
> 以及由持 `extensions.manage` 的宿主组件登记的扩展包。模板与原生扩展本身不能在运行期新增或改写。**

本意是「运行期没有东西能决定这个进程是什么」。运行期建出来的每台实例，在启动时就已经能被枚举（模板 × 允许的参数）。运行期登记的扩展包
也不改写装配：它只在自己的 id 下（`<id>.*`，§3.4.1），照装前披露过、人同意过的清单，可撤；宿主对它的描述再查一遍结构（§4.4）。
不链 `packages`、或不授予它 `extensions.manage`，这条路就不存在，路由表就是启动时装配出来的那张。

**配置每一节一个所有者。** 装配读整份 profile，把每一节交给它的所有者；**没有所有者的节、节里不认识的键，都拒绝启动**并说是哪一行。
写了一个不存在的开关的 profile 启动失败，而不是被悄悄忽略。

| 节 | 所有者 |
|---|---|
| `[engine]`、`[[instances]]`、`[[instance_templates]]` | 实例层 |
| `[transport]` | 传输 |
| `[brand]`、`[shell]`、`[ui]`（`dir`、`runtime_modules`）、`[extensions]`（`off`、`default_space`） | 装配 |
| `[ext.<id>]` | 扩展 `<id>`：反序列化成它的配置类型，未知键由那个类型决定（第一方的一律拒绝未知键） |
| `[ext."<包 id>"]` | 那个扩展包：盖在它清单的 `[config]` 上，由 `packages` 交给它 |

启动顺序：

1. **分派子命令。** `daemon`、`ext-proc` 这类子命令在读 profile、拿状态锁、装配任何扩展**之前**就交给登记的入口（§4.6）。
2. 读 profile，把 `[ext.<id>]` 交给对应扩展（反序列化失败只停用它）。
3. **注册**：按顺序调每个扩展的 `manifest` 与 `register`；查授予（§4.3，违反拒绝启动）；把描述装进路由表、中枢、传输层、界面板。
   名字冲突时后来的那个停用，诊断写明。
4. **迁移**：按顺序调 `migrate`（它自己的数据），失败只停用这个扩展。
5. **建实例**：`main`（带上仍启用的扩展的引擎贡献）、profile 的 `[[instances]]`、账本里按模板建过的。
6. **启动**：按顺序调 `start`，失败只停用这个扩展和它的一切；它已经交给 `main` 的场景摘不掉，留到下次启动，诊断写明。
7. 开始服务。

引擎的根**显式传进去**，不改本进程的环境变量：那样一个进程才可能服务几台实例，状态也不会藏在调用者
看不见的地方。

#### 3.1.1 实例层：实例登记表、实例载体、模板、收养

**实例只从声明来**：profile 里声明的固定实例、按模板建的，或者宿主组件收养的扩展进程的引擎。实例登记表（`harnix-instance`）管建、确保、停、重启、
等就绪、模板、账本、拥有者，以及 `harnix.instances.*` 的行与主题。

| | 进程内 | spawn | attach | 收养 |
|---|---|---|---|---|
| 是什么 | Agix 的会话池经 `agix::embed` 起在本进程里，经内存双工上的 daemon 协议连 | Harnix 起的子进程，本二进制的 `harnix daemon`，经私有目录里的 unix socket | 连一台已经在跑、只给这个 Harnix 用的 daemon | 模式 3 扩展进程里它自己的 Agix，引擎线是继承的 socketpair |
| 引擎贡献 | 能：场景层、原生工具、`PromptGate`；在本进程执行，经链路登记给引擎 | 能，同进程内：登记在 daemon 的 socket 上，工具、钩子与门仍在本进程执行；另有那个 daemon 自己的配置与 Agix 插件 | 不能：别人的 daemon 不收这个进程的代码，登记时只记一条警告 | 不能：它是扩展自己的引擎（§4.6） |
| 隔离 | 状态隔离；崩溃与资源共用进程 | 状态、崩溃、资源都隔离；断了是「实例降级」，不是 Harnix 挂掉 | 同 spawn | 同 spawn，外加操作系统沙箱 |
| 版本 | 必然是这次构建链接的那版 Agix | 握手比对协议版本，不匹配就拒绝并说清楚 | 同左 | 扩展进程就是产品二进制，逐字相等才放行 |
| 实例的信任 | `Product` | `Product` | `Product` | `Extension(id)`（§3.1.2） |

spawn 的看护在 `harnix-supervise`：等它就绪；stdin 一断它就退出，所以随 Harnix 退出；意外退出按退避重启，连续几次刚起来就退出则不再重启
——重启循环只会掩盖问题。默认起本二进制，版本按构造就对得上。

**模板**（`InstanceTemplate`）是建实例的规格：实例载体、场景、数据根规则、允许调用方填的参数、能不能由
界面用（`ui`）、最多几台。profile 里的模板只能是 spawn 或 attach（profile 拿不出引擎贡献）；原生扩展经 `Registrar::template` 声明的进程内模板
可以带引擎贡献。**界面永远给不出二进制路径、命令行参数、环境变量、模型端点**——那些等于「装载子进程、改写模型端点」，不对设备开放（§3.4.5）。

每台实例有**拥有者**：内核（profile 声明的，含 `main`）、一个扩展（它按自己的模板建的，或收养的）、一个 space（界面建的，归发起时的前台 space）。
账本记按模板建的实例；**重启后一律由 Harnix 按账本重建**：模板还在、拥有者启用着就照建；否则这台实例显示为 `Down` 并写明原因，数据根不动。
扩展停用时，它拥有的实例停下、列成 `Down` 并写明原因，留在账本里，扩展重新启用时回来。删除实例删的是登记，数据根默认保留。
**拥有者检查用能力**：跨拥有者停、重启与按非 `ui` 模板建要 `instances.admin`；内核拥有的实例谁都不能停（按拥有者，不按 id）。
`harnix.instances.templates` 只列调用方能建的模板，所以设备看不到非 `ui` 的模板。

**中枢与实例之间只有一个接口：有类型的引擎链接**（`EngineLink`，§9）。登记表和中枢之间有三条不变量：

1. **可见晚于接管。** 一台实例在中枢接过它的链接、开始听它的事件**之后**，才进列表、`harnix.instances` 主题与按 `instance` 参数的路由。
   任何人能看到它时，中枢已经在听。建、停、重起在单独的任务里跑：调用方放弃了，也不会留下中枢读得到而没人列的引擎。
2. **链接只有中枢持有。** 登记表把整条链接交给中枢一次（加入、重起时），自己只留它的控制一半（状态、身份、进程号、停、重读设置），碰不到会话。
   没有公开的「取链接」，事件的接收端只有中枢取。
3. **锁序。** 中枢调登记表（例如首次在一个 space 里按模板建实例）时不持自己的任何锁；登记表回调中枢时不持自己的锁。两边在入口处断言对方的锁没被持着，
   有压力测试盯着。

中枢问登记表只经一个内部接口（`InstanceBook`），不持登记表本身；中枢的代码里不出现「是不是远程」的分支，`layering.rs` 在中枢的源码上断言它
不提实例载体、不打开数据根、不构造登记表与引擎贡献。载体之间不同的地方是实例层自己的事：spawn 出来的 daemon 要在它的 socket 上登记本进程的工具、
钩子与门（模板的原生贡献与扩展包的工具，工具集变了由 `ToolProvider::changes()` 通知，登记随连接，重连重登）；继承 provider 的模板要把 `main` 的 provider 写进新实例的
设置——这些都由实例层在建实例时写进它的数据根，之后集合变了也由它跟上。

**扩展拿不到引擎链接。** 扩展拿到的是一台实例的只读视图（`EngineView`：场景、模型、实例的信任，凭能力才有的读者；读者经引擎的协议读，不读文件），所有会话调用仍然经过中枢和路由表。
扩展要是能直接对一台实例发 `run_turn`，「中枢先订阅」这条不变量就有了旁路。

**daemon 的语义。** daemon 对一条通过认证的连接完全信任，没有逐方法授权。所以：

- **一台 daemon 只服务一个 Harnix。** spawn 的天然如此：它的 unix socket 放在只有本用户能打开的私有
  目录里；attach 的由运维保证。中枢的排队、结算、「先答者生效」都假定它是这台 daemon 上会话的唯一调用方。
- **daemon 的凭据不出 Harnix**：attach 要的 token 在 profile 里只写凭据名，值由产品的 `Credentials` 给，不发给任何客户端。
- 引擎直通的拒绝对每台实例都一样，改凭据、改端点这些对 daemon 实例同样拒绝（§3.4.5）。
- **断线**：实例变成 `Degraded`，daemon 那边的轮照跑。重连由实例层做（引擎的链接自己只说一条连接上的话），重连后中枢对每个在观看的会话重建缓冲，
  再推 `harnix.session_resync`，客户端照刷新那条路重新 attach；这期间的发送进队列，不拒绝。daemon 丢订阅走同一条路。
  这是中枢本来就有的恢复路径，不是新语义。

#### 3.1.2 实例的信任

收养的实例由第三方代码控制：它发给中枢的每一帧都可能是恶意的。所以每台实例带一个信任（`InstanceTrust`），中枢按它设限：

| 对产品的引擎（`Product`） | 对扩展的引擎（`Extension`） |
|---|---|
| `daemon.event` 广播给每个客户端（`harnix.host_event`） | **不转发**；用于中枢自己的轮次记账。它的轮开始、结束（`turn_started` / `turn_completed`）由中枢照读到的另发：字段由中枢重建（`session_id`、`turn_id`、`initiator` 只认引擎自己的词），标 `trust: "extension"`，计入它的帧上限 |
| 帧不设每实例的上限 | 每帧 ≤ 1 MiB；帧数按令牌桶限，持续每秒 200 帧、一次可突发 2000 帧，桶空就是超限；每会话的追赶缓冲 ≤ 4096 帧；超了丢弃、审计，实例列成 `Degraded{flooding}`；结束轮次的帧不丢，客户端要靠它落定，但照样取令牌、照样算超限、照样受大小上限与加固；连续 3 秒超限：收养的实例由它的载体结束扩展进程，不论它跑了多久都算一次崩溃（三次就置于一旁），实例留着、列成降级等下一次运行；不是收养的，登记表停掉它 |
| 谁都能点名它（照行的范围） | **点名它的调用**（建会话、挪会话、`engine.*` 直通、运行期 space 的缺省实例）只对它的扩展自己（含它的 iframe）、它声明的 space、跨 space 的调用开放；其余答 `SPACE_MISMATCH`，在唤醒之前判。所以模式 2 的扩展包把自己 `[[space]]` 的 `instance` 写成别人的 `proc.<id>` 也用不上它 |
| 会话列表的答直接进列表 | 标题截到 200 字，轮次状态只认枚举里的值；中枢自己的列表与直通的列表一样施行 |
| `engine.config.*`、`engine.plugin.*` 对内核与有能力的扩展开 | 到这台实例的这两族**谁都不行**，`engine.plugin.list` 也一样（它的配置由载体在拉起前写好） |
| 外壳照受信内容渲染 | 列表、`hello`、会话事件里给它的会话标 `trust: "extension"`；外壳按不受信内容渲染：HTML 只当文本显示、链接变成文字、图片只许 `data:` |

**归 space 的实例**照同一条规则：模板为某个 space 建的实例，点名它的调用（建会话、挪会话、全部 `engine.*` 直通，与 space 无关的行在内）只对它的 space、跨 space 的调用与内核开放，
在唤醒之前判；不声称 space、产品又没有缺省 space 的调用也答 `SPACE_MISMATCH`。不归任何 space 的实例（`main`、profile 的实例、扩展经 `harnix.instances.create` 建的）
照旧谁都能点名。原生扩展用归 space 的实例时也要声称 space（`cx.sessions().in_space(..)`），不开豁免；替设备读会话内部的扩展（`observability`）转过去的调用照设备声称的 space。

### 3.2 中枢

中枢是会话的持有者。它的存在理由是一条不变量：

> **中枢永远比任何客户端先订阅。**

会话第一次被打开时中枢立刻订阅并开始缓冲，此后任何观看者的追赶**只在中枢的缓冲区里进行**。由此得到：

1. **刷新页面不丢内容。** 一轮跑到一半刷新，前半段在缓冲里，不依赖引擎补发。
2. **turn 不挂在连接上。** 关掉标签页、切换设备、断网重连都不影响这一轮，最终结果广播给所有观看者。
3. **多设备一致。** 同一个会话可以被几个客户端同时看，任何一个都能回答权限提问，先答者生效。
4. **排队是产品行为，不是错误。** 引擎对同一会话同时刻只允许一个 turn；有 turn 在跑时新消息进中枢的
   队列，上一轮结束后自动发出，队列可撤销，整值快照推给所有客户端。

模式 3 的扩展在它自己引擎上的会话也由中枢持有：先订阅、给 `seq`、管队列，前端只和产品说话（§4.6）。

**中枢只认有类型的引擎操作与事件。** 它只依赖协议类型、内部接口与引擎词汇（`harnix-engine-api`）：一样操作一个方法（建、取、列、恢复、跑一轮、中断、
关、分叉、应答……），事件带中枢要用的那部分类型（片段、工具调用、提问、轮次完成、会话列表变了），旁边是引擎原样的 JSON 给观看者。
中枢不编译 Agix、不拼 Agix 的方法名、不认 Agix 的事件种类，测试可以全用假链接。

**turn 由中枢发起，调用方有两类：客户端和服务端（内核、扩展），语义相同**——排队、中断、结算、广播
都一样。服务端调用方经 `ExtensionContext::sessions()` 建、开、发、中断、关闭会话（**无头会话**），用
`OnBusy { Queue, Reject, Interrupt, Steer }` 说忙的时候怎么办；客户端的 `harnix.session.send` 和服务端的发送走
同一条路径。无头会话照样出现在它所属 space 的会话列表里，界面随时可以 attach 旁观。

为什么是两类调用方而不是只有客户端：无头会话必须和客户端共用排队与 `seq`——在中枢之外另做一份，就是第二份会话状态。
扩展包的后端驱动会话也走这一条（经 `host.call` 调 `harnix.session.create`、`harnix.session.send`，以 `ext:<id>` 准入，范围只限它自己的 space）。

**队列项带着调用链。** 一条消息排进队列时记下发它的那次调用的链；一轮由哪一项起，这一轮的链就是那一项的链，steer 进来的并进去。
工具在这一轮里回调扩展时，宿主核心据此认出重入（§3.4.3）。

**tap** 是服务端的观看者，和客户端观看者同一套语义，不是一条特殊的无损通道：有界、按 `seq` 投递、
**不在中枢的锁里等待**；满了就标成落后，它下一次读到 `Lagged { last_seq }`，按客户端追赶那条路补齐。
**中枢永远不会因为一个慢的 tap 卡住会话。**

**推送一律整值。** 队列、会话列表、实例树、引擎健康这类状态推的是完整快照，客户端不做增量合并——增量
合并的错误只在特定顺序下出现，而那个顺序在测试里不容易造出来。主题可以**带参数订阅**，值在有人
订阅时才算，短时间内的多次变化合成一次：

| 主题 | 参数 | 所有者 | 内容 |
|---|---|---|---|
| `harnix.instances` | — | 实例登记表 | 实例登记表：实例载体、模板、拥有者、信任、链接状态、版本、会话数 |
| `harnix.instances.sessions` | `instance` | 中枢 | 这台实例的顶层会话 |
| `harnix.session.tasks` | `instance`、`session_id` | 中枢 | 这个会话的后台任务 |
| `harnix.sessions.status` | — | 中枢 | 所有会话的运行状态 |
| `harnix.spaces` | — | 中枢 | 已声明的后端 space |
| `harnix.ui` | — | 装配 | 每个扩展的界面条目、Agix 插件的界面模块、扩展包的面（也是同名的方法） |
| `<扩展 id>.<主题>` | 扩展声明 | 那个扩展 | 它推的整值快照，例如 `observability.process`、`packages.list`；扩展撤下时订阅者收到 `harnix.topic_ended` |

**会话事件不是主题**：`harnix.session.attach` 之后经 `harnix.event` 帧来，带 `seq`。

**历史会变短。** 会话的历史只由引擎的日志投影出来，而日志只追加：压缩把视图换成摘要，**回退**（`harnix.session.rewind`，
[Harnix app](harnix-app.md) §5.1）在日志里追加一条作废标记，切点之后的轮从 `engine.session.history` 里消失（`total` 变小，`seq` 从切点接着编），
原样的行还在磁盘上。回退之后，中枢缓冲里画过的帧就不对了：中枢清掉这个会话的缓冲，向每个观看者推 `harnix.session_resync`，各台设备照刷新那条路
重新读历史——和重连之后是同一条恢复路径，中枢的 `seq` 照常往上数，不回头。中枢自己写进日志的条目（`harnix.changes`）同样不删，回退后追加一条
标记，列条目时把被撤掉的轮的那几条去掉。

中枢的状态与语义**不可替换**（§2.1）。

#### 3.2.1 往对话里写东西：扩展条目

扩展可以往会话时间线写**扩展条目**（例如「采集任务跑完，推一张任务卡」）：走 Agix 的扩展条目
（`harnix.session.entries.append`，底下是引擎的 `appendEntry` / `entries`），由 `flow.block` 画出来。条目进入会话日志，刷新、重放、
分叉都看得到；**只给人看，不给模型看**；命名空间由中枢定为写它的扩展的 id，扩展自己说不了算。
Harnix 不另存一份会话状态。

### 3.3 传输

传输是**一组通道语义**，不是一种连接拓扑。**语义写死，拓扑可选。**

理由很具体：不同的部署对连接的诉求不一样。边缘弱网下少开一条连接是省下的重连与心跳；放在反向代理后面
时，让请求走普通 HTTP 能直接吃到现成的中间件；一个只想看进度的只读客户端不该被迫开一条能发请求的
双向连接。**这些差异不该逼着中枢换一套语义。**

#### 3.3.1 五种通道语义

| 语义 | 干什么 | 谁发起 |
|---|---|---|
| **unary** | 一次请求一次应答的方法调用 | 客户端 |
| **会话事件流** | 某个会话的事件：流式正文、工具行、权限提问、子 Agent、扩展条目 | 服务端 |
| **宿主事件流** | 与具体会话无关的主题：实例树、会话状态、队列、扩展的主题 | 服务端 |
| **带外应答** | 对服务端发起的提问的回答（权限、澄清） | 客户端 |
| **大负载旁路** | 附件上传、导出下载 | 双向 |

会话事件与宿主事件从语义上就是两个订阅面：一个只看侧栏的客户端不该为了知道「哪个会话在跑」而接收所有
会话的正文。带外应答单列，是因为它在只下行的事件流拓扑里没有回程可用。

#### 3.3.2 三种参考拓扑

| 拓扑 | 映射 | 适合 |
|---|---|---|
| **单双向流** | 一条双向连接承载全部（大负载仍走旁路） | 单机、边缘弱网 |
| **分离流** | unary 与带外应答走 HTTP；两种事件流各一条只下行流 | 反向代理后面、多客户端、只读客户端 |
| **纯请求** | 只有 unary 与旁路，事件靠长轮询补上 | 脚本客户端、受限网络 |

三种拓扑的方法名、参数、错误码、事件形状完全一致。服务端配置支持哪几种，客户端在握手时选一种；不匹配
就拒绝并说清原因，不做静默降级。

分离流的一条事件流断了可以再开：再开就换掉前一个读者，浏览器的 `EventSource` 自己重连就能接上（断开期间的帧
不补发）。所以客户端库在两条流都重新开上之后，像重连之后那样追上：状态再报一次 `open`，看会话的重新 attach、
订阅的重新订阅。服务端拒了的流（不认识的凭据，比如进程重启过）浏览器不再重开：客户端重新握手，握手之前先取一次
当前的令牌，和单双向流重连失败时一样。两条流都关着、`/rpc` 也 5 分钟没来，这份握手就结束；在这之前它仍算一条
已连接的客户端——分离流的客户端走的时候什么也不说，关掉的流和正在重开的流看起来一样。每个客户端的出站队列都有界（4096
帧）：读者不读、队列满了，这个客户端就算走了，连接关掉，重连后从中枢的缓冲追上，而不是让内存跟着它涨。

#### 3.3.3 跨拓扑的不变量

拓扑可选，但下面这些在任何拓扑下都成立，它们是传输真正写死的部分：

1. **`seq` 是唯一的追赶锚。** 每条会话事件带 `(instance, session_id, seq, turn_id)`，`seq` 由**中枢**
   按会话分配，与连接、实例载体都无关。
2. **一次握手，一次协商。** 协议版本、贡献点 API 版本、拓扑、能力位在握手里一次谈完；后开的通道携带
   握手换来的凭据，不各自再谈。
3. **权限提问的语义与通道无关。** 广播给所有观看者，任一可答，先答者生效，第二个回答是静默成功。
4. **大负载永远走旁路。** 一次性凭据换 URL，落盘后以路径引用。
5. **中枢、路由与准入不感知拓扑。** 加一种拓扑不会改动这几层——**如果改动了，说明语义被拓扑污染了，那是要修的**。
   `layering.rs` 断言它们的源码里叫不出拓扑、连接、HTTP 的类型。

#### 3.3.4 只提供 RPC 的形态

传输可以不提供任何静态资源（`--headless`）。界面在别处，或者根本没有界面（§5.1、§7.1）。

#### 3.3.5 扩展的 HTTP 路由

一个原生扩展的前后端之间可以有自己的 HTTP 路由与 WebSocket，挂在 `/ext/<id>/<前缀>…` 下（`Registrar::route`），由
Harnix 的传输层发出，与界面**同源**，准入走同一套：传输层先准入，再问路由表这个主体能不能用 `route:<id>` 与这条路由的访问规则，再交给处理者；
有审计。只读的静态文件用 `static_dir`（不列目录，`..` 拒绝）。前端经宿主 API 的 `ext(id).fetch()` / `.socket()` 用它，扩展代码不自己拼地址。
它承载 Harnix 通道不适合的东西，代价是**不享受**拓扑无关和 `seq` 追赶这些保证——要这些保证，就用上面五种语义。

稳定的接口用 `http` 1.x 的类型，不让 axum 的大版本绑进扩展接口；要 WebSocket 或 axum 的中间件，开 feature `axum`（不稳定层）。
扩展包没有任意的 HTTP 处理者：它在 `/ext/<id>/` 下只有界面文件（`static_dir`）。

前后端之间用哪条：一问一答用 unary 调 `<id>.*`；状态更新用主题推整值快照；长任务返回任务 id，
进度作为带参数的主题；大文件走旁路；剩下的才用扩展的路由。**不为扩展加新的通道语义。**

### 3.4 路由与准入

**这个进程只有一张路由表、一个准入点。** 加一个方法，默认是谁都不能调。

#### 3.4.1 一张路由表

方法、主题、HTTP 路由都是一张表里的一行：名字（主题写作 `topic:<名>`，路由写作 `route:<扩展 id>`）、**所有者**、处理者、**谁能用**（访问）、
要什么能力、**范围**、说明。内核的行（中枢、实例登记表、装配、路由器自己的）、引擎直通的行、每个扩展的行都在这里，**没有第二张表、没有前缀分派、
没有散在各处的 `match`**：一次调用到了路由器，查一行，判定一次，审计一次，调那一行的处理者。

- **名字的所有者**是已登记的、与它整段前缀匹配的最长 id：内核（`harnix`）、引擎（`engine`）或某个扩展（`observability`、`acme.notes`……）。
  内核方法在 `harnix.*`（单数区域是对一个东西的操作，`harnix.session.send`；复数是集合，`harnix.sessions.list`）；引擎直通在 `engine.*`；
  扩展在 `<扩展 id>.*`。第一方扩展也只在自己的 id 下（`observability` 的方法是 `observability.*`，不在 `harnix` 名下），没有预留命名空间这种特权。
- **跨类的整段前缀重叠一律拒**：原生 `acme` 与扩展包 `acme.notes` 不能同时登记。冲突时原生优先，扩展包标 `namespace_taken`，诊断写明谁占了它——
  产品升级时新链进一个原生 `acme`，用户早先装的 `acme.notes` 不会被静默停掉。扩展包 id 的第一段（发布者）不许是保留字（`harnix`、`engine`、`agix`、`ext`、
  `topic`、`route`、`proc`、`ctl`；`agix` 是因为 Agix 拒 `agix.` 下的条目命名空间，而条目命名空间就是扩展 id），也不许是本产品链进的任何原生扩展 id（不论关没关），装的时候就拒；商店把第一方扩展的 id 保留成发布者名。
  这些规则只在一处（`router/src/names.rs`），只在装行时判，分派时不判。
- **按所有者原子地装与撤**：一个扩展的全部行一次装上，全有或全无；停用时一次撤下，之后这些名字答 `METHOD_NOT_FOUND`，和从没有过一样。
  只有扩展宿主装行，靠的是层次规则：只有装配依赖路由器。
- **`harnix.reachable`** 告诉调用方它能调什么，界面据此决定画什么；它答的就是 `decide()` 会放行的，没有另一份。

授权发生在**方法这一层**，不在连接那一层——多通道拓扑里同一个主体可能有好几条连接，把授权挂在连接上
会得到几份可能不一致的答案。

#### 3.4.2 一行对谁开放，作用在什么上

每一行有一个**访问**：只对设备（与内核）；对设备与扩展；只对扩展；只对某一个扩展（按 id，只给「一个扩展只给自己的另一个扩展调」这种少见的情况）；
只对内核与持有某项能力的扩展（设备永远不在里面）；或谁都不行、不能授予（绕过中枢的方法，**中枢独占**）。
另外可以要求一项能力、写明拒绝的理由。

- **人经界面做的决定只对设备开**（`Access::device()`，不含扩展）：批准与拒绝、授予与撤销、设置、设备、包与安装、会话内部的读取——第一方扩展的行（`observability.context`、`settings.*`、
  `packages.*`……）、`harnix.session.setModel`、`harnix.bulk.upload`。第一方扩展替设备去做时，用的是它自己被授予的能力。
- **扩展也要调的行明写 `Access::device().with_extensions()`**：中枢的会话行与主题、引擎直通、实例登记表、内核自述（`harnix.hello`、`harnix.ui`、`harnix.extensions`、
  `harnix.diagnostics`、`harnix.audit`、`harnix.reachable`）、扩展发布的主题（缺省）。`harnix.session.respond` 在里面：`flow` 按策略作答；扩展包被收窄到自己的 space，
  所以只能答自己 space 里会话的提示。方法表的 LIVE 测试守着：批准、拒绝、授予、撤销、安装、卸载、配对这类不要能力的行不许列扩展。
- 扩展包的同意（`calls`）与 iframe 都够不着不对扩展包开放的行；同意里列了这种行，登记时就拒（§4.4）——否则扩展包能借第一方扩展的能力做事。

每一行还有一个**范围**：`Open`（与 space、会话无关）、`Space`（作用在一个 space 上，例如 `harnix.sessions.list {space}`）、`Session`（作用在一个会话上）。
范围按调用方收窄：

| 调用方 | `Open` 行 | `Space` 行 | `Session` 行 |
|---|---|---|---|
| 设备（不经 iframe） | 照访问 | 不声称 space 时按缺省 space 检查（防误） | 会话不属于声称的 space → `SPACE_MISMATCH`（防误）；声称一个 `cross_space()` 的 space 可以跨（防误，写审计）；会话被它的扩展展示到声称的 space 时，能看、`interact` 时还能说（§5.4 第 6 条） |
| 原生扩展（`Origin`） | 照访问 | 声称了才检查（出身即信任，防误） | 同左；要读写**任何** space 的会话内部，用要 `engine.inspect` / `engine.control` 的行 |
| 扩展包（`Consent`） | 访问 ∩ 同意的 `calls` | **只限它自己的 space**（`<id>` 或 `<id>.<名>`）；调用不声称 space 就拒；订阅主题不声称 space 当作声称了 `<id>`，值裁到那个 space（全局的会话主题照订，只投它 space 的会话）；声称了却没有定义的 space，订阅与会话列表都看不到任何会话 | **只限绑在它自己 space 上的会话**；它的引擎自己建的会话（子 Agent 的）随父会话的 space；`engine.inspect` / `engine.control` 不对扩展包开放 |
| 扩展包的 iframe（设备，代那个扩展） | 设备的权力 ∩ 那个扩展清单的 `[interface] calls` ∩ 对扩展包开放的行；别的扩展包的名字一律拒 | 同上，再收窄到那个扩展的 space | 同上，再收窄到它 space 的会话 |

- **iframe 的调用在服务端可辨**：外壳的桥给代理的调用与订阅加一个保留参数，传输层把它取出来放进调用上下文（处理者看不到），路由器取交集，
  审计记 `device:<id> via ext:<id>`。所以 iframe 能调什么由服务端说了算，外壳只留界面层面的收窄（例如只能开前台 space 的会话）。
- **读别人的会话**这种权力不给扩展包：没有一项扩展包能申请的能力开它。要的产品写原生扩展。

#### 3.4.3 调用上下文与调用链

一次调用随身带一个有类型的**调用上下文**：主体、客户端（设备调用时那条连接）、代谁（iframe 的扩展）、调用 id、父调用、调用链、取消、截止时间。
扩展在处理一次调用的过程中再发出调用，就是一次**子调用**：新 id，父调用是这一次，取消是这一次的子令牌，截止时间继承，主体是这个扩展。
审计因此是一棵树：设备调了 `observability.context`，`observability` 以自己的身份调了 `engine.session.inspectContext`，两次判定各记一条，后者挂在前者下面。

- **取消与截止时间是合作式的**：路由器不丢弃处理者的 future（停在半路的处理者留下的状态没人能信），处理者在等的地方与它们赛跑。
  客户端协议里没有取消，设备调用没有截止时间。
- **调用链**是正等着这次调用的扩展与它们被占着的那次调用。一个扩展包的后端是串行的：它在等一次调用时，同一个后端再被调用就是死锁。
  宿主核心看到链里有「自己，并且那次调用此刻正占着自己的后端」，当场答 `EXTENSION_UNAVAILABLE{reentrant}`，而不是等到超时把后端换掉；
  后端早已答完、只是排了一轮的，不算重入。链经过一轮：存在队列项上（§3.2），工具调用时由引擎一侧的适配从这一轮的链里取；
  模式 3 由产品在起轮、结算时经扩展线推给进程。
- **宿主工具的调用带着会话**：引擎把工具调用经 daemon 链路交回本进程时说明是哪个会话（子 Agent 的调用按根会话取这一轮的链），所以 spawn 的 daemon 里的
  工具调用与进程内的一样查得到链，重入当场答。

#### 3.4.4 四种主体，一个准入点

| 入口 | 凭据 | 主体 | 谁发 | 什么时候作废 |
|---|---|---|---|---|
| `/ws`、`/rpc`、`/events/*`、`/respond`、`/ext/<id>/…` | 握手换来的凭据；回环上的进程令牌、启动链接 cookie；配对设备的挑战应答 | `device:<id>` | 传输层握手 / 配对 | 设备撤销、握手过期 |
| 扩展线（继承的 fd） | 无：连接本身就是身份 | `ext:<id>` | 宿主拉起扩展进程前把主体绑在产品这一端的流上 | 子进程退出、流关闭 |
| 内核内部 | — | `kernel` | — | — |

四种主体的准入状态都在 `harnix-authz` 一处：设备的配对存储由传输层问，扩展进程的绑定由宿主拉起它时建；一处发、一处撤、一处审计。原生扩展以自己的身份调用时（经 `ExtensionContext`）主体是 `ext:<id>`，
不过任何入口。没有第二个准入点：引擎不回头调本进程的 HTTP 端点（它要的工具经 daemon 链路到中枢这一侧），扩展进程**没有监听套接字**可连（§4.6）。`Subject::Engine` 只在审计里出现，用来记一台实例的引擎做的事，没有哪个入口发它。

- **扩展包的 iframe 不是主体**：它以页面的身份（一台设备）发出、带着它代的扩展，够得着的是设备能调的、又在清单里的那一小块（§3.4.2）。
- **Agix 插件不是这里的主体**——它跑在引擎里，受引擎的能力门控约束，够不到这个进程的方法面。

#### 3.4.5 引擎直通与拒绝

设备能调到的引擎方法，每一条是路由表里显式的一行：Harnix 的名字（`engine.<x>`）、访问、范围、之后的钩子（先答者、目标记账、列表刷新）。
处理者把 `<x>` 交给引擎，Agix 的方法名只在引擎的适配里。读的（`engine.session.history`、`engine.scene.list`、`engine.daemon.status`……）对设备开放；
读或改**任何**会话内部的要 `engine.inspect` / `engine.control`；改设置与 provider 的要 `engine.config.*`；装卸 Agix 插件的要 `engine.plugins`。

单用户系统里「这个人能不能做」的答案几乎总是「能」，所以这一层真正在守的是：

- **引擎那些等价于接管进程的方法一个都不出去。** 改凭据、装载子进程、改写模型端点的方法，永远不出现在
  任何设备的可用集里——不是「未实现」，是明确拒绝，并且错误里写清原因。中枢独占的方法
  （`run_turn`、`subscribe`、`engine.daemon.shutdown`……）谁都不能调，也不能授予。
- **设备建实例只能按模板。** 模板集合在启动时定死，设备只能选 `ui` 模板、填模板放开的参数（§3.1.1）。
- **加一个方法默认是谁都不能调。** 每一行的访问都写在它登记的地方，方法表的快照把它们全列出来。

#### 3.4.6 设备怎么用到特权

**设备自己永远没有能力。** 它调一个扩展的方法（`observability.context`），扩展以自己的身份、用自己被授予的能力去调内核或引擎；两次调用各判定一次，
审计里是一棵树。扩展的披露（`Manifest::disclosure`）写明它替设备做什么。这样「这个产品里设备能做什么」就是「设备能调的那些扩展方法做什么」，
而每个扩展的权力都是装配时写下的、看得见的几项能力。

## 4. 扩展模型

### 4.1 三种模式，缺省是模式 2

在 Harnix 上做应用有三种模式（[应用开发](app-development.md)），每一种的产品都是 Rust 写的：

| | 模式 1：纯 Rust 应用 | 模式 2：Rust + 同进程的扩展（缺省） | 模式 3：Rust + 每个扩展一个进程（选用） |
|---|---|---|---|
| 是什么 | 用 Rust 写原生扩展，把 Harnix 装配成一个产品；不装扩展包 | 再装扩展包：在产品进程里，每个包一台 WASM 虚拟机 | 再装扩展包：每个包一个扩展进程，产品二进制的子命令，关在操作系统沙箱里；给安全要求高的场景 |
| 用什么写 | 原生扩展（§4.2）、引擎贡献、编进外壳的 UI 包 | 同模式 1，加扩展包（§4.5） | 同模式 2，同一个包 |
| 构建 | 库 `harnix`，不开载体 | feature `wasm`（`harnix` 二进制缺省开） | feature `proc`（`harnix` 二进制缺省也开） |
| 运行时选 | — | `[ext.packages] carrier = "wasm"`（只链一个时不用写；两个都链又没写，取它） | `[ext.packages] carrier = "process"` |

**缺省是模式 2**：Harnix 发布的二进制 `harnix` 就是这样，要装扩展包的产品方也推荐同样的形状。模式 3 是选用的，不是缺省：
给第三方来源多、要进程与文件隔离的产品。

**模式 2 与模式 3 基本二选一，但不写死在代码里。** 两个载体可以同时链进来，`packages` 按名字取载体；骨架与宿主组件的代码里没有按 feature 的分支，
`cfg(feature = "proc")` 只在门面（登记子命令）与 `harnix-cli`。0.4.4 里一个产品的全部扩展包跟产品选的那一个载体；按扩展包选载体的位置留在安装记录里。
**包对载体中立**：同一个 `.hxext` 两种载体都装，商店只有一种包；作者要知道的差异只有一张表（[应用开发](app-development.md) §10）。

### 4.2 原生扩展

一个原生扩展实现 `Extension` trait，应用在 `main.rs` 里显式列出并授予能力，**顺序就是注册、迁移、启动的顺序**：

```rust
fn main() -> anyhow::Result<()> {
    harnix::App::builder()
        .profile_from_args()
        .extensions(harnix::first_party::standard())          // Harnix 带的那几个，连同它们的授予
        .extension(helm_home::Home::default())
            .grant([caps::TRANSCRIPTS_READ])
        .extension(helm_feeds::Feeds::default()).ungranted()
        .run()
}
```

`harnix::first_party::standard()` 的源码就是 Harnix 自己的授予清单：每个第一方扩展拿几项能力，一眼看得到，产品可以照抄、删减、换掉其中一个。

一个扩展有五个入口：`manifest`（id、版本、标题、披露、要的与可选的能力、它自己定义的能力）、`register`（在一个 `Registrar` 里说完它提供的一切）、
`migrate`（它自己的数据）、`start`、`stop`。`register` 里能声明的：

- 方法（`<id>.<名>`，带访问、schema、说明；缺省谁都不能调）与主题（缺省设备与任何扩展可订；推整值或有人订时才算）；
- 后端 space（`SpaceDecl`：缺省实例、场景、是不是缺省 space、是不是 `cross_space()`、收不收会话 `no_sessions()`）；
- 工具的规格（诊断里列得出一个扩展有哪些工具）；
- HTTP 路由与静态目录（`/ext/<id>/`，§3.3.5）；
- 界面的声明：它的 UI 包、它定义的贡献点（§5.6）；
- 引擎贡献：给 `main` 的（`engine()`）与给每台进程内实例的（`engine_everywhere()`）——场景层、原生工具与 `ToolProvider`、工具钩子、`PromptGate`；
- 实例模板（`<id>.<模板>`），可以带它自己的引擎贡献。

**引擎贡献只有两条路**：给 `main` 与每台进程内实例的走 `engine()` / `engine_everywhere()`，给自己实例的走进程内模板带的贡献。多个
扩展的贡献由 Harnix 按注册顺序组合，Agix 不用改。这些类型都是 Harnix 自己的（`harnix::engine`），扩展接口里没有 Agix 的类型（§9）。

`ExtensionContext` 给扩展：自己的配置节（profile 的 `[ext.<id>]`，密钥只写引用，值由 `Credentials` 提供）、自己的数据目录（`ext/<id>/data/`）、凭据、
以自己的身份调方法（和设备走同一张路由表）、服务端会话（§3.2）、实例（按自己的模板建、确保、等就绪、停）、发布与订阅主题、
一台实例的只读视图与凭能力才有的读者（录像、转录；经引擎的协议读，每台实例各一套）、进程信息（凭 `process.observe`）、大负载、运行期发布的界面条目，以及有名字的宿主服务（§4.4）。
**拿不到中枢、引擎链接、路由表、授予表，也拿不到数据根的路径。** 每一项服务在调用时查能力，缺了答 `REFUSED` 并写明缺哪一项。

迁移：Harnix 只管**什么时候迁、失败了怎么办**（按顺序、失败只停用这个扩展），不管**用什么迁**。数据库
选型、迁移工具都由扩展自己定；Harnix 自己的账本与扩展的数据分开。

版本：扩展接口的版本 `EXT_API_VERSION` 写进文档与 `--version`，不做编译期断言——兼容性靠 crate 的 semver，从 0.4.4 起扩展接口只做加法（§3 的稳定层级）。
**贡献点 API 版本**在握手与读包时检查（§5.8）。

### 4.3 能力与授予

**能力**是一项有名字的特权，目录分两层：

1. **内核目录**：名字都在内核的词里，只有骨架改它。
2. **扩展声明的能力**：原生扩展在 `manifest` 里声明 `<自己的 id>.<名>`，它自己的行要求它，授予照常在装配时写；扩展包只能申请声明方标了可给扩展包的项。
   例：IPDrun 的 `billing` 声明 `billing.charge`，只让持有它的扩展调某几个方法——不改 Harnix，也不退回按 id 绑定。
   Harnix 自己的例子是 `schedule` 声明的 `schedule.manage`：别的扩展持有它才能调 `schedule.*`（建、改、删、暂停、立即执行定时，读投递记录）；设备不需要它，人管自己的定时。它不在内核目录里，标准装配里谁都没有。

| 内核能力 | 意思 | 原生 | 扩展包 | Harnix 里谁有 |
|---|---|---|---|---|
| `instances.admin` | 停、重启任何不属于内核的实例；按任何模板建实例、列出全部模板 | ✔ | | —（应用自己的调试面要它） |
| `engine.inspect` | 读**任何**会话的内部：上下文、后台任务、后台任务的输出、目标、历史 | ✔ | | observability（会话的上下文、后台任务的输出）、flow、schedule（模型建的定时）、settings（会话的 MCP 上下文，可选） |
| `engine.control` | 改任何会话的内部：后台任务、消息、压缩、清空、模型、名字、目标；读、改项目的信任 | ✔ | | flow（给它开的会话改名）、schedule（删模型建的定时）、harnix-app（项目信任，可选） |
| `engine.config.read` / `engine.config.write` | 读 / 写引擎设置与 provider；后者含重读设置、交给继承 provider 的实例 | ✔ | | settings · settings |
| `engine.plugins` | Agix 插件的装、卸、启停、重读 | ✔ | | plugins、packages |
| `engine.export` | 导出、导入会话 | ✔ | | harnix-app |
| `engine.mcp` | 在引擎的任一层加、改、删、停用 MCP 服务器，重连它，登录远端的 | ✔ | | settings（可选） |
| `recordings.read` · `transcripts.read` | 录像与用量的读者 · 转录的读者；都经引擎的协议读（`session.calls`、`call`、`callBlob`、`search`），每台实例各有一套，实例连不上读者返回 `Unavailable` | ✔ | | observability · harnix-app |
| `process.observe` | 版本、运行时长、内存、线程、已连接的客户端；各扩展的日志 | ✔ | | observability（可选） |
| `devices.manage` | 配对码、列设备、撤销设备 | ✔ | | devices |
| `extensions.manage` | 拿宿主组件接口：运行期登记扩展、拉起扩展进程、收养扩展进程的引擎 | ✔ | | packages |
| `ui.page` | 进页面的 ES 模块 | ✔ | 只 `trusted` 发布者 | — |
| `events.all_tools` | 看到每个会话的每一次工具调用 | | ✔ | — |
| `feedback.read` | 收到人对回复的每一条反馈（评分、类别、备注原文，连同会话），主题 `harnix.feedback` | ✔ | | —（缺省谁都没有：反馈不出日志，除非产品授予某个扩展） |
| `net:<主机>` · `env:<名字>` · `storage:<MB>` · `fs:data` · `fs:project` | 扩展包的资源能力 | | ✔ | — |

**跨 space 不是一项能力。** 同页的代码能声称任何 space，所以「在一个 space 里看别的 space 的会话」只能防误。它是 space 声明上的标志 `cross_space()`，
只有原生扩展能声明；真正的跨 space 读写权力在 `engine.inspect`、`engine.control`、`instances.admin`，它们才是安全边界。

**启动时检查，违反就拒绝启动**（装配是声明式的，错在 `main.rs`），错误写明扩展与能力：

1. 扩展要的每一项都被授予；可选的可以不给（扩展照 `cx.grants()` 降级）。
2. 授予的必须是内核目录或某个已链进的扩展声明过的项，并且在这个扩展要的或可选的里——**多给的特权是看不见的特权**。
3. 扩展包的同意记录只含可给扩展包的项；`packages` 拼描述时查，宿主登记时再查一遍结构。

**能力只在三处查**，层次规则保证骨架里没有第四处按 id 查：路由器（行要求的能力）；`ExtensionContext` 的服务（调用时查）；实例登记表的拥有者检查。

### 4.4 宿主组件与运行期登记

`packages` 与两个载体是**宿主组件**：写成扩展的形状、经同一个登记口与授予进来，但要碰几样普通扩展不该看到的管道——运行期登记一个扩展、
拉起一个扩展进程、把扩展进程的引擎收养成实例。这几样在 S3 的 `harnix-host-api` 里，经
`cx.service::<HostServices>()` 拿，要能力 `extensions.manage`。放在单独的接口里，是为了以后改进程模型不破坏扩展接口。

**运行期登记走原生的那条宿主路径**：一个动态描述经 `DynamicRegistrar` 登记，全有或全无，和启动时的原生扩展同一张表、同一套审计。登记之后宿主组件
拿到一个把手：以被登记的扩展的身份调用、发布、订阅，标它的可用性（起来中、就绪、停了、置于一旁——行留在表里，答 `EXTENSION_UNAVAILABLE`），撤下它。

**宿主对动态描述只查结构**——同意记录的权威在 `packages`，宿主看不到它；违反就拒绝，什么都不写，记审计：

1. 信任是 `Consent`，id 是合法的扩展包 id（§3.4.1）。
2. 名字只在 `<id>.*`；space 只在 `<id>` 或 `<id>.<名>`，不 `cross_space()`。
3. 没有引擎贡献，没有实例模板。
4. HTTP 路由只有静态目录。
5. 能力只含可给扩展包的项；`calls` 里没有要能力的行，也没有不对扩展包开放的行（中枢独占的、只对设备开的第一方行）。
6. 进页面的模块要求 `ui.page`；不定义贡献点。
7. 工具名唯一，拼出的会话工具名不撞。

`packages` 自己是一个普通的原生扩展：它的权力就是装配时授予的那几项能力，不授予 `extensions.manage` 它什么也登记不了。

### 4.5 扩展包：WASM 扩展

一个扩展包（`.hxext`）是清单 `harnix-ext.toml`、至多一个预编译的 WASM 组件（`.cwasm`）、一个 Agix 插件（`agent/`）、界面（`ui/`）、签名（`SIGNATURES`），
各部分可选。怎么写见 [扩展包](harnix-ext-package.md)；这里讲它为什么是这个形状。

**`packages` 管与载体无关的一半**：安装记录与同意记录、商店、披露与同意、升级与回滚、启停、卸载、清数据，推送的主题 `packages.list`（载体报告状态变了才推，另有至多 10 秒一次的兜底）；
每次启动对盘上的包再验签、核清单的摘要。载体给的是描述里的**处理者**：方法转给后端，主题由后端推，界面文件是静态目录，工具经载体的 `ToolProvider`
进会话。清单用 `[[tool]]` 声明全部工具，两种载体都以它为准，运行期不首次采信组件报上来的东西。

**模式 2：一个扩展包一台虚拟机，只在主进程里。** 「虚拟机」是一个边界，不是一个进程：后端是一个常驻的 wasmtime `Store`（状态、订阅、定时器在这里，调用排队串行进入），
每次工具调用、每次事件另起一个调用 Store、用完即弃。spawn 出来的 daemon 不起虚拟机，它的会话里用到这个包的工具，由主进程在 daemon 的 socket 上提供、在那一台执行。
所以在任何拓扑下，一个扩展包只有一份状态。超时的调用被放弃、后端的 Store 换掉（停在半路的代码不能信它的状态）；反复崩溃就置于一旁；
`on-demand` 的后端闲置时卸下，下一次调用冷启动。要留下的状态放 kv。它的 `agent/` 装进 `install_into` 列出的**产品实例**，它的会话受产品的引擎策略约束。

**数据只走 Harnix 的通道。** 扩展包的界面和它的后端之间没有自己的连接：iframe 经外壳的桥、外壳经页面那一条 Harnix 连接，到中枢、到后端；
后端推的主题原路回来。准入与审计一处管；断线重连、远程与桌面拓扑都由外壳已有的连接处理；iframe 不能联网，界面就没有绕过能力声明的路。

**编译放在商店。** 产品构建不带编译器，只反序列化商店为每个引擎指纹编好的产物：二进制小、攻击面小。反序列化只用于可信的产物，
所以先验签、再按签名里的 sha256 比对读进来的字节，才反序列化。产物绑 wasmtime 的版本，Harnix 与 Agix 一一对应地发布，wasmtime 只在
Harnix 发布时变，商店为每个 wasmtime 版本编一遍。

**扩展包是原生的子集，子集之外的每一样有理由。** 每一条例外的形状都是「扩展包经同一个描述登记，但这一项描述里不许有」：

| 例外 | 理由 |
|---|---|
| 没有引擎贡献（场景层、`PromptGate`） | 引擎贡献在实例建起来时就定了，扩展包在运行期来去；这些是宿主的单槽契约，第三方代码不决定（§10）。模式 2 的扩展包进会话只经工具与钩子，经载体的一个 `ToolProvider`——它本身是原生的贡献，所以这条也是建在原生之上。模式 3 的扩展在它自己的引擎里有它自己的场景，那不是对产品引擎的贡献 |
| 没有实例模板 | 模板集合在启动时定死，是设备建实例的安全边界。收养的 `proc.<id>` 不是模板：只有宿主组件能收养，id 固定、一个扩展一台 |
| 没有任意 HTTP 处理者 | 扩展包的数据只走 Harnix 的通道；界面文件是静态目录 |
| 不能定义贡献点、能力，不能 `cross_space()` | 前两样是给别的扩展用的接缝与特权；后者是跨 space 的声明 |
| 处理者不是它自己的代码，是载体的转发 | 扩展包的代码只在 WASM 沙箱里执行（§2.2.1） |
| 信任是 `Consent`（`calls` 加范围） | 信任按出身（§2.3） |
| 没有编进外壳的 UI 包；进页面的模块只给 `trusted` | 编进外壳要重编译；进页面就是与页面同级（§5.8） |

**它在内核里是谁。** 扩展包不是一个新的主体，它以 `ext:<id>` 行事：它的方法、主题、space 照同意记录登记进路由表与中枢，停用时撤下；
它的后端 `host.call` / `host.subscribe` 以 `ext:<id>` 进同一张路由表，只到同意的 `calls` 与它自己的名字，再收窄到它自己的 space 与会话；被拒的记审计，
也显示在设置 → 诊断的「扩展包运行状况」里。它的工具在会话里叫 `ext__<id>__<工具>`（id 里的 `.` 换成 `_`，引擎的工具名收字母、数字、`_` 与 `-`），名字由内核拼；每次调用都先问人，能挡掉它的是 Agix 的权限。

### 4.6 模式 3：扩展进程

**扩展自己的 Agix 与 WASM 在它的进程里是完整的；宿主 Harnix 只路由**——方法、主题、事件、前端到它的会话——并负责准入、监护、同意。
进程是产品二进制自己的子命令 `ext-proc`，关在一个最小的操作系统沙箱里。

```text
浏览器 ──Harnix 协议──▶ 产品进程
                        ├─ 路由表：<id>.* 的行 → 进程载体的处理者 → 扩展线
                        ├─ 中枢：proc.<id> 上的会话也由中枢持有（先订阅、seq、队列），按扩展的信任防着它
                        ├─ 实例登记表：proc.<id> = 收养的引擎（接在继承的流上）
                        └─ packages + harnix-carrier-proc：记录、同意、复核、监护、出口代理
                            │ 建两对 socketpair、绑主体、套沙箱、fork + exec 本二进制
                ┌───────────┴────────────┐
                ▼ fd 3：扩展线            ▼ fd 4：引擎线（Agix daemon 协议）
          <产品> ext-proc（沙箱里，一个扩展包一个）
          ├─ 宿主核心 + 虚拟机（与模式 2 同一份）
          ├─ 产品的服务 = 线上的客户端；HTTP 出口 = 经产品代发
          └─ 它自己的 Agix（只在有 agent/ 或 [[space]] 时起）＋ 本地的工具
```

**没有第二个程序。** 扩展进程是产品二进制以子命令重新执行自己，同 `harnix daemon`：

- 装配的 `run()` 先分派子命令，在读 profile、拿状态锁、装配任何扩展**之前**；门面在 feature `proc` 下替产品登记 `ext-proc`。所以任何开了 `proc` 的模式 1
  产品不用另发一个二进制，`main.rs` 一行不改。分派只在第一个参数恰好是登记的名字时匹配。
- **只能 fork + exec**：异步运行时是多线程的，裸 `fork()` 之后只剩一个线程、锁的状态不定。产品可以用 `[ext.packages] proc_program` 指向另外构建的、
  更瘦的二进制，只要它也带 `proc`。
- **没有监听套接字。** 两条线都是继承的 socketpair，别的进程没有东西可以连；身份不靠凭据，它就是拉起时拿到 fd 3 的那个子进程。stdin 断了（产品没了）它就退出。
- **环境清空**，只留几个必需的变量（系统的 `PATH`、`LANG`，产品有时的 `RUST_LOG`）；`HOME`、`TMPDIR`、工作目录都在它自己的运行目录下。它不读 profile、不碰状态目录（沙箱也不让）。
- **沙箱在 exec 之前就套好**：由产品套（§6.6），进程自己不套、也跳不过；套不上就不拉起。
- **版本逐字相等**：进程的第一帧报它的版本、它链的 Agix 版本、虚拟机引擎的指纹，三样都必须与产品相同，否则拒绝，理由「不是同一次构建」。
  指纹单列，是因为版本串相同不保证产品预编译的 `.cwasm` 在这台引擎上能加载。

**产品从不信进程报上来的东西。**

- **登记的作者只有产品**：拉起之前，产品照同意记录拼好描述并登记（行标「起来中」）；进程报上来的登记只做「⊆」与摘要比对，不同说明它跑的不是记录里那个包
  ——拒绝、杀进程、审计。进程退出时产品不撤行，所以前端的订阅与 `harnix.reachable` 不随进程重启抖动。
- **线上来的元数据只是提示**：产品对进程发来的每个调用重签调用 id；父调用只接受这条连接上产品发给它、此刻仍在跑的调用；调用链按本地的父调用重算，
  从不取自线上（进程伪造不出一条让别的扩展拒绝服务的链）；截止时间取远端值、父调用的截止时间、方法上限中最早的那个。
- **签名只在产品验**；进程只核 `.cwasm` 的哈希等于产品给它的那个。`net` 在产品侧判：进程的 HTTP 出口经扩展线由产品代发。

**它的引擎与会话：宿主只路由。** 有 `agent/` 或 `[[space]]` 的扩展包，进程起它自己的 Agix；产品把它收养成实例 `proc.<id>`（实例的信任是 `Extension`，§3.1.2）。
它的 space 落在 `proc.<id>` 上；在它的 space 里建会话，中枢在 `proc.<id>` 上建、先订阅、给 `seq`、管队列。点名 `proc.<id>` 的调用只对它自己（含 iframe）、
它的 space 与跨 space 的调用开放（§3.1.2）；没有 `[[space]]` 的扩展包，它的实例只有它自己与跨 space 的调用够得着。
它的会话事件经中枢到观看者；它的引擎事件不转发，轮的开始与结束由中枢自建（§3.1.2）。

- **产品的引擎策略有意不进它的引擎**：产品的 `PromptGate`、工具钩子、原生工具、场景层只装在产品自己的实例上；扩展的 Agent 是扩展自己的，受它自己的场景与
  Agix 的权限约束，跑在它自己的沙箱进程里。这是写明的载体差异（[应用开发](app-development.md) §10）。
- **provider 继承自 `main`**：产品在拉起前把 `main` 的 provider 写进它引擎根的设置，变了之后推过去（休眠中的不唤醒，醒来时读）。这是它的引擎拿模型的唯一来源：
  进程的环境是清空的，产品环境里的 `ANTHROPIC_*` 不进它，只有设置页的 provider。**模型凭据因此在扩展进程里**（§6.6）。
- **它的工具到产品的每台进程内实例**（两个载体都一样，不只 `install_into` 点名的），工具调用经扩展线过去；产品 spawn 的 daemon 经它的 socket 把调用交回产品，再过线。
  `install_into` 只在安装时校验，在这个载体上此外不起作用。

**监护**：

| 事 | 规则 |
|---|---|
| 就绪 | 版本相符、登记复核通过、（有引擎时）引擎线接上，30 秒内；否则杀掉、按崩溃算 |
| 健康 | 每 15 秒问一次状态，5 秒不答算一次失败，连续 3 次就杀掉、按崩溃算 |
| 退避 | 1、2、4、8、16、30、60 秒；健康运行满 120 秒计数清零 |
| 致命退出 | 进程自己查出来的（fd 不对、虚拟机引擎建不起来、`.cwasm` 哈希不符）以退出码 78 退出，立即放弃、不退避；产品查出来的（版本不符、复核不过）先停再杀，同样不重试；沙箱套不上的根本不拉起 |
| 置于一旁 | 起来之后 60 秒内崩溃 3 次（它的引擎刷屏被杀，不论跑了多久都算一次）：不再拉起，扩展标 `faulted`，理由与 stderr 最后几行进 `packages` 的快照、每行也进产品日志；停用再启用会重来 |
| 闲置回收 | `on-demand`，满闲置时限，产品侧没有在途的调用，进程里的虚拟机自报休眠，它的引擎没人用（没有加载着的会话、观看者、在跑或排队的轮、后台任务、问题）：先存会话列表，再让进程停下退出，状态 `hibernating` |
| 唤醒 | 只有要它做事的调用唤醒：它的方法、它的工具（产品实例上的与 spawn 的 daemon 里的）、它的引擎上的会话调用；列表读（由产品侧存下的会话列表答）、`harnix.hello`、首页的全局统计、工具钩子、主题值都不唤醒它 |
| 产品退出 | 各包同时停：先请它停下、退出（各等 5 秒），关线，关 stdin、等 5 秒、TERM、1.5 秒、KILL；进程组里剩下的 TERM、1.5 秒、KILL |

**它挡住什么、挡不住什么**，见 §6.6。

### 4.7 Agix 插件：一个包，装到引擎里；Harnix 只收文件

一个 Agix 插件装的地方是 Agix（以 Agix 的 `plugin_packages.md`、`extending_quickjs.md`、`extension_points.md` 为准）。
Harnix 不定义它的包格式、不校验、不解包、不判定能力。第一方扩展 `plugins` 做两件事：

1. **把文件送过去。** 引擎的 `engine.plugin.install` 自己去取 URL，**没有上传通道**——这是引擎的选择，它在包已经躺在
   跑引擎那台机器上时完全够用；而当包在使用者的笔记本上、引擎在另一台机器上时，就没有路可走。那一步是
   宿主的活：`plugins.upload` 换一个一次性 URL（大负载旁路），`plugins.install` 把落盘路径交给引擎。扩展包的 `agent/` 由载体装进实例。
2. **读包里引擎不关心的那一段**——`[[ui]]`（§5.8）。**包在哪由引擎说**：`engine.plugin.list` 的条目带 `root`，
   Harnix 只读那下面的 `plugin.toml`，自己不拼任何路径，引擎的缓存布局因此仍然是引擎的。
   扩展包的 `agent/` 另有一个读者：装包之前，`harnix-package` 从它的 `plugin.toml` 读 `[plugin]` 的 `name` 和
   `version`，是要请引擎装成的名字，此外一个键也不读（`layering.rs` 查这两处）。

**生命周期走 `plugins.*`，引擎自己那几个名字不对设备开。** 装、卸、启、停都是引擎干的活，`plugins` 不加判断也不发明参数，以自己的身份、
凭 `engine.plugins` 调引擎；它加的是后面那一步：任何改变「装了什么」的调用之后重读一遍，因为它在服务每个包的 `ui/` 目录、并经 `harnix.ui` 对外公布
界面条目。直接透传 `engine.plugin.disable` 的后果是包停了而它的界面模块还在被服务，且没有任何一侧会发现。

**披露在装完之后，因为引擎是那个顺序。** 引擎装完才回 `disclosure`（这个包会往模型上下文里塞的文本）。界面上就是：装好了，这是它会放到
模型面前的东西，留还是删。想在装之前看，就得在这一侧读包，而那正是这一节要避免的事。**沙箱管得住插件执行什么，管不住它说什么**，所以模型
可见文本必须被人看见。界面贡献占了哪些点是 Harnix 知道的，安装完的那一屏把两半拼起来，否则用户看到的披露是不全的。（扩展包不同：它的
清单是 Harnix 的，披露在装之前，人同意了才装，§4.5。）

**装 Agix 插件是这个人自己的决定。** `plugins.*` 对设备开放：一个进程服务一个用户，设备就是这个人本人。真正的强制边界在引擎：能力门控、
沙箱、它自己回的那份披露。`engine.mcp.addServer`（以及改、删、停用、重连）要 `engine.mcp`，设备直接调永远被拒：它配出来的是一个能起子进程的工具，没有 manifest、
没有能力声明、没有任何披露。设备经设置页的 `settings` 扩展加、改、删、停用：那里持这项能力，披露写明它替设备做这件事，一次一个服务器、
一层一层地经引擎写，值不回显（[Harnix 扩展](harnix-ext.md) §22.9）。

**包方案不跟着载体走。** 引擎的载体今天是 QuickJS 脚本与编译进宿主的 Rust 插件，带 `[[wasm]]` 段的包拒装（WASM 在 Harnix，§2.2.2）。
读 manifest、校验、解包、披露、启停不需要任何运行时。一个不带包方案的构建仍然合法，所以 `PLUGINS_DISABLED` **如实透传，不包装成
「没有已安装的插件」**：「这个构建里没有插件子系统」和「一个都没装」是两件事。

### 4.8 不进 Harnix、由应用自己做的

按 §1.3，下面这些应用在扩展接口上就做得出来，不进 Harnix。做法写在 [原生扩展](harnix-ext.md)：

- **批准**（「这个业务动作要不要人确认」）：只许设备调的 `<id>.*` 方法收回答、带参数的主题推待批事项、
  扩展条目记下决定、`flow.block` 画卡片。引擎权限管「这个工具能不能跑」，批准管「这个业务动作要不要人
  确认」，后者的策略本来就归应用。要只让某个扩展调的方法，扩展声明自己的能力（§4.3）。
- **MCP 服务端与角色令牌**：应用要给外部 Agent 开 MCP，就在自己的扩展里起自己的路由或监听，它不在
  Harnix 的保证之内，由应用负责。
- **非 Rust 的 sidecar 服务**：走 Agix 的 MCP，或经扩展的路由转发。

### 4.9 流程：内置的应用开发工具链（`flow`）

流程是 Harnix 内置的应用开发工具链：让 Agent 按一套定义好的过程干活，判定只看结构化信号；流程本身也在它自己的对话里由 Agent 编写、试运行。
它不进骨架，是一个**只用公开扩展接口写的可选第一方扩展**（crate `harnix-ext-flow`，界面 `@harnix/flow`）：产品链它就有，不链什么都不变；
Harnix 自己的二进制 `harnix` 链了它。它被授予 `engine.inspect` 与 `engine.control`（给它开的会话改名）。它的界面是一个自己的
`flow` space：流程 space，入口在左栏底部（[Harnix app](harnix-app.md) §11）。

流程也在项目里跑：带 `project_root` 的运行是**项目任务**（界面上叫「任务」），主会话在项目（或它的一个 worktree）里干活，
交付物落在项目的**输出目录**，软件用的过程落在 `<项目>/.harnix/runs/<运行>/`。它从项目的「新任务」、项目里对话的 `/flow`、或一条定时起；
`flow` 拥有主会话，把它**展示**给发起的 space（§5.4），项目 space 在自己的中区打开它，右栏的「流程」页签跟着它走到哪一站。
项目还可以带自己的流程（`<项目>/.harnix/flows/`，项目受信才读）。见 [Harnix app](harnix-app.md) §3.2。

```
 流程包（内置层 + 可写层）     flows · skills · rules · policies · gates · hooks
          │ 校验、建运行时钉住定义与策略、门禁
          ▼
 内核（库 harnix-flow，纯）   站的有向无环图：进站、派工、租约、出站判定、返工、暂停；
          │                   只经宿主 trait 读写（RunStore、Packs、Authorizer、Tools）
          ▼ 工作项
 派工器（库 harnix-flow 的 runner）  会话工作项交给会话（主会话 = 主 Agent；子 Agent；独立会话），
          │                   答流程会话的权限询问，命令门禁去跑，钩子去投递，开、收 worktree；
          │                   会话只经 trait SessionHost 拿到
          ▼ 开、看、发、答
 宿主（harnix-ext-flow）      HarnixSessionHost：会话经中枢；程序与宿主门禁交给应用；
                              flow.* 方法与主题、作者场景、实例模板、流程 space
```

**分层**：流程的内核不建会话、不碰磁盘、不知道谁是用户——存储、授权、应用的程序与检查都由应用以 trait 交进来，
所以同一个内核也跑在试运行的沙箱里（外面的一切模拟）。派工器把内核交出的工作项做掉，它认识的会话只有 trait `SessionHost`
（开、看帧、发消息、打断、答权限）。内核、派工器连同存储、流程包、试运行是一个单独的库 `harnix-flow`（`crates/flow`），
不链 Harnix 也不链 Agix，别的宿主可以整个拷走，拿按脚本答话的 `ScriptedHost` 与一致性测试 `harnix_flow::conformance` 单独验证
（[嵌入指南](../crates/flow/docs/embed.zh-CN.md)）。库写在项目里的东西放哪由宿主以 `ProjectLayout` 交进来，库里不写死目录名。
扩展那一层是 Harnix 的宿主：用中枢实现 `SessionHost`、原生工具（`flow_submit`、
`flow_state`、`flow_propose`，用 `Tool` 写）、作者场景 `flow-author`（用 `SceneLayer` 包在一个底版场景上）、实例模板、方法与主题、流程 space。

**每个时间点只有一处能拦**：干活过程中是**权限**——流程会话对受限工具和权限提到的工具都 `ask`，`flow` 按这一轮所属
工作项的权限判（`deny` > `ask` > `allow`，作者写的 `ask` 留给人）；没有权限说话的，按流程的执行语义 `guard`：缺省 `auto` 不审批，
项目里放行、项目之外的路径拒绝，`strict` 受限工具拒绝、项目之外转给人。任务里的会话没有提问工具，要人拍板的地方写 `confirm` 站；出站时是**出口条件**——输出契约、门禁（`tool` / `command` /
`host`）、人的确认。**规则**与 skill 只告诉 Agent，不拦。**钩子**是旁观者：不写在流程里，从不阻塞运行。

**不进 Harnix 的**：审批策略（几个人批、批与做不能是同一人）归应用——流程把 `who` 交给应用的授权方。
对象与写法见流程 space 右栏的参考页（`crates/flow/docs/guide.*.md`）；构建器、方法与主题见 [原生扩展](harnix-ext.md)。

## 5. 界面

### 5.1 界面在二进制里，可以被换掉

**安装物是一个文件。** 界面编译在里面，所以不存在「页面和后端对不上」这种状态。

| 形态 | 怎么来 | 用在哪 |
|---|---|---|
| 内嵌（默认） | 编译进二进制 | 单机、边缘节点。装一样东西 |
| `--ui-dir <目录>` / `[ui] dir` | 从磁盘读，整套替换 | 做另一个产品；开发前端时改完刷新 |
| `--headless` | 一张都不发 | 纯 RPC 节点 |
| `ui export <目录>` | 把内嵌的那份写出来 | 让 CDN 或代理去发。仍然只有一个安装物 |

**为什么编进去，而不是一个独立的界面产物。** 分开的唯一硬理由是运行期要 import 别人的界面模块，而那件事由包自己的
`ui/` 目录满足（Agix 插件的界面模块、扩展包的页面都由后端从包里发出），不需要界面本身是分离的。编进去对二进制大小几乎没有影响；
换一整套界面仍然是一个参数，不是一次重编译。

没有界面产物就直接 `cargo build` 会**明确失败并说该跑什么**，不悄悄嵌一份空界面。

#### 5.1.1 版本协商仍然要，使用者变了

界面在握手时声明协议版本、贡献点 API 版本与拓扑，后端回自己支持的；不匹配就拒绝并说清哪一边旧了，**不做
静默降级**——一个半兼容的界面产生的 bug 报告是无法处理的。`hello.engine_protocol` 另报 Agix 的协议版本，`@harnix/core` 不认识的就拒绝并说明（§9）。

内嵌之后，内建界面不可能对不上，所以协商的使用者只剩这几个：`--ui-dir` 换进来的那一套；**包带的界面
模块**，在读包时逐条比对（§5.8）；扩展包的页面，它和外壳之间是另一份协议（桥 `harnix-ui-bridge@2`，§5.7）。界面**不假定拓扑**：它拿到的是一个客户端库，库把五种通道语义映射到
握手谈定的那种拓扑上。

### 5.2 技术栈与包

**React + TypeScript + Vite + Zustand，定死。** 用的人最多、后续好维护；Agent 类界面的生态基本都是 React 的；
IPDrun 已经有能对着 Harnix 协议跑的 React 对话组件，直接回流成了对话主干（`ChatPanel`）。

包的边界只画在「谁依赖谁」真正不同的地方：

| 包 | 依赖框架吗 | 职责 |
|---|---|---|
| `@harnix/core` | 否 | `/protocol`（从序列化到线上的 Rust 类型**生成**：`harnix-contract` 的帧与行、readers 的答、`packages.list` 的行；漂移就失败）、`/client`（握手、拓扑与回退、追赶）、`/state`（会话事件归约、实例树、每个 space 的当前会话）。**唯一认识 Agix 事件形状的解析层** |
| `@harnix/react` | React | 注册表（12 个内核点 + 扩展定义的点）、宿主 API `HostApi`/`useHost()`、i18n、令牌、图标、对话组件、对话框与菜单原语、不受信内容的渲染。**写界面只依赖它** |
| `@harnix/shell` | React | **外壳核心**（§5.3）。应用的入口，不被 import |
| `@harnix/harnix-app` | React | 首页、会话 space、项目 space、新会话与添加项目的对话框、`@` 文件候选、归档与导出；定义项目的条目与概况、待我处理、首页的区块等点 |
| `@harnix/settings` · `@harnix/plugins` · `@harnix/devices` | React | 设置节：模型、场景、MCP · Agix 插件 · 设备 |
| `@harnix/packages` | React | 设置节「扩展包」（装、升、卸、同意、清数据）；设置 → 诊断里「扩展包运行状况」 |
| `@harnix/observability` | React | 对话区的「轨迹」视图（`conversation.view`）、右栏的「上下文」（常驻）「用量」「输出」页签、首页的全局统计与用量、设置 → 诊断里的扩展日志 |
| `@harnix/flow` | React | 流程 space、项目里的任务、首页的最近任务；定义任务行的标记与另一种起法两个点 |
| `@harnix/schedule` | React | 定时：会话菜单「定时…」、项目概况与首页的区块、会话行与任务行的时钟、「定时运行这个流程…」；全经别的包定义的点 |
| `@harnix/ext-sdk` · `@harnix/ext-kit` | 否 | 扩展包的页面在 iframe 里的一侧：桥的客户端与 mock 宿主 · 外壳的令牌与几样基础部件 |
| `@harnix/testkit` | 否 | LIVE 测试的启动器、API 客户端、Playwright 夹具 |

框架只出现在 `@harnix/react` 及以上；`@harnix/core` 与后端一一对应（`/protocol` ↔ `harnix-contract`，
`/client` ↔ 传输，`/state` ↔ 中枢推的帧与快照），换框架也不动它。

**第一方 UI 包只用公开 API**，和后端「第一方扩展只用公开扩展接口」是同一条：它们只许 import `@harnix/react`、`@harnix/core` 的公开导出与 React；
外壳核心不 import 任何第一方 UI 包，源码里没有 `"home"`、`"sessions"`、`"flow"` 这样的 id。`tests/ui-layering.mjs` 查这几条。

第一方 UI 包与应用自己的 UI 入口一样，由构建脚本编进外壳的产物：`HARNIX_UI_FIRST_PARTY` 选编进哪几个第一方包（不设是全部，空串是一个也不要），
应用自己的入口经 `HARNIX_UI_MODULES`，排在第一方包之后；Harnix 自己的产物带全部第一方包。

### 5.3 外壳的框架

**外壳核心只留每个产品都要的**：外框、space 切换、三栏与窄屏抽屉；对话区（对话、输入框的 `@` 与 `/` 菜单、权限卡、队列、
会话菜单与标题栏的动作）；设置面板的框（内建节只有通用、连接、诊断、关于）；扩展包界面的运行时（iframe 面与桥、行内点、进页面模块的加载器）；
按 `hello` 激活编译进来的 UI 包。**它不认识任何第一方 UI 包**：没有一个 import，没有一个 id。

外框里固定的只有：

- 左栏顶上：品牌（`[brand]` 的图标和名字）、新建对话、搜索；
- 左栏底下：`place: "bottom"` 的 space 的入口（流程 space 就是这样放在那里的），以及**头像**。头像就是设置入口，外圈颜色表示连接状态
  （已连 / 重连 / 断开），悬停说连到了哪。

其余都由 space 给。**一个 space 是三栏合在一起**：

| 栏 | 由什么给 | 不给时 |
|---|---|---|
| 左栏中段 | `sidebar`：这个 space 的条目 | 这个 space 的会话列表 |
| 中区 | `center`：`chat`（默认）/ `minimized`（对话收成底部一条，可展开）/ `hidden`（用 `overview()` 画自己的视图） | 对话 |
| 右栏 | `details`：space 自己的一组页签，**可以是当前选中项的函数**，每次绘制时读；打开了会话时，同一条页签栏里还有**这个会话的停靠面**（`sidebar.tab` 的页签类型，§5.6；文件、改动、输出、流程进度都在这一侧） | 只有详情抽屉与会话的停靠面 |

左右两栏都能拖宽并记在本地；窄屏时先把左栏收成图标栏，再把两侧都变成抽屉。一个 space 可以 `within` 另一个：不列在左栏，
由代码进入，在前台时点亮外层的入口。

**UI 包怎么进来。** 一个 UI 包导出它是哪个后端扩展的界面（`extension`）与一个 `register(r, host)`。`hello` 带着启用了的扩展，外壳在握手之后、首屏之前
就对每个启用了的扩展的包调 `register`——**激活是同步的**，首屏不闪；之后 `harnix.ui` 推来变化：新启用的补调，被停用的扩展的注册按 owner 整批撤下、
外壳重画；`register` 可以返回一个函数，撤下时一起调（它订的主题、起的计时器随之停）。不写 `extension` 的入口（应用自己的）总是调。所以「这个产品有没有流程 space」只看后端有没有链 `flow`、有没有 `[extensions] off` 它，
界面一侧不另设开关。

**Harnix 自带的 space 都只是用例和默认值**，来自第一方 UI 包：

| space | 属于 | 左 | 中 | 右 | 后端 |
|---|---|---|---|---|---|
| **首页** | `harnix-app` | 只有「待我处理」的入口 | 首页的区块（`center: "hidden"`，`harnix-app.home.panels`），不持有对话 | — | `harnix-app` 声明的 `home` space（`no_sessions()`：不收会话） |
| **会话** | `harnix-app` | 全部会话，按时间分组（`sidebar.group`，应用可以换），带搜索 | 对话 | 详情 | `harnix-app` 声明的 `sessions` space，**缺省 space** |
| **项目** | `harnix-app` | 一棵树：项目（工作区）一次只展开一个，它的会话挂在下面 | 对话；新建的会话跑在展开的项目里 | 详情 | **同一个**后端 `sessions` space |
| **流程** | `flow` | 通用会话、流程与它们的运行 | 选中项的对话，旁边的二级栏是它的详情 | 流程、运行、参考 | `flow` 声明的 `flow` space（场景 `flow-author`）；入口在左栏底部 |

新开的页面（新标签页、重开应用）落在说自己是落地处的 space 上（`landing`：首页），同一个标签页里刷新留在原处。
不链一个扩展，它的 space 就不注册；不链 `harnix-app`，剩下的第一个成为默认；不链 `flow`，底部的入口和它的方法一起没了。Harnix app 怎么用框架
做出来的见 [Harnix app](harnix-app.md)。

**项目 space 是界面上的一个视图，不是第二个会话集合。** 「按时间看」和「按项目看」是同一批会话的两种排法；如果它们是两个后端 space，
同一个会话就得属于两个 space，而会话按 space 绑定是不变量（§5.4）。所以界面 space 可以用 `sessions` 指向另一个后端 space：两个界面视图，
一个后端归属。只有界面、没有后端的 space 不用在后端声明。

**新建对话的空页**：问候、这个 space 的建议，下面是 `home.card` 的卡片。

为什么外框只有这些：

- **外框只留真正每个产品都要的东西，其余都可去掉。** 外框里没有首页：新对话的空页（问候、问一句、`home.card` 的卡片）是外壳的，
  Harnix app 的首页是它自己的一个 space，外壳只知道哪个 space 说自己是落地处（`landing`）。
- **首页是看全局的，不是又一个聊天的地方。** 它的中区是区块；要在会话里继续说话，就到会话所属的 space 打开。它因此不收会话：
  后端的 `home` 声明 `no_sessions()`，在它里面建、导入、挪进会话都答 `SPACE_MISMATCH`。
- **外壳里写死的每一样只属于某个扩展的东西，都是一个缺的贡献点。** 标题栏、工具行上只属于某个扩展的动作，会话菜单里的归档与导出
  是同一种东西，所以有了 `session.action`（§5.6），外壳不再认识它们。

### 5.4 Space 模型

**space = 左栏 + 中区 + 右栏，一起注册，所以「成对」是原子的。** 一个 space 有三个**部分**，可以任意组合：

| 部分 | 在哪执行 | 来源 |
|---|---|---|
| 前端 | 浏览器 | 编进外壳的 UI 包；或扩展包的面（iframe）与进页面的模块。Agix 插件的界面模块只能给已有的贡献点做贡献，不能新增 space |
| 后端 | Harnix 进程内（模式 3 在扩展进程里） | 一个原生扩展的 `SpaceDecl`；或扩展包清单的 `[[space]]` |
| Agent | Agix 实例里 | 引擎贡献（原生扩展的 `engine()` 或模板）或 Agix 插件（也可以是扩展包的 `agent/`） |

**内核不认识任何 space id**：`sessions`、`home`、`flow` 都是各自的扩展声明的。会话与 space 的**绑定账本**是中枢的不变量，由中枢读写；声明来自扩展。

中区缺省是对话；space 可以在对话旁边开一个**二级栏**（`secondary()`：标题、正文、能拖宽、能最大化、能关），放它右栏里
选中那一项的详情——列表留在右栏，详情不挤在列表下面。会话还空着时，space 可以给一段说明（`emptyConversation`）。

**会话规则：**

| 规则 | 内容 |
|---|---|
| 绑定 | 一个会话在创建时绑定一个 space 和一台实例，**设备不能挪**（应用重整自己的 space 时，扩展可以经 `harnix.session.move` 把会话连同转录绑到另一个 space，目标要是这台实例能服务的、不跨 space 的 space）；建它的扩展可以把它**展示**到别的 space（`harnix.session.expose`，下面第 6 条），归属不变；要跨 space 延续，用 `@session` 引用（被引用会话说过的话作为附件交给这一轮——复制的是话，不是会话）或分叉。引擎自己建的会话（子 Agent 的）没有经过中枢的创建：引擎报了父会话就随父会话的 space，否则是它所在实例的 space（实例归 space 时），再否则是缺省 space；不放宽 |
| 多会话 | 一个 space 可以有多个会话，可以分布在它能用的几台实例上 |
| 缺省实例 | space 声明 `main`（默认）、一台固定实例，或 `template:<id>`（第一次在这个 space 里建会话时按模板建一台，之后复用，归这个 space）。这就是「一个 space 要一台自己的、隔离的 Agent」的写法；模式 3 的扩展包的 space 落在它自己的引擎 `proc.<id>` 上 |
| 缺省 space | 不声称 space 的设备调用按它检查；一个进程至多一个，由声明它的扩展说（Harnix app 的 `sessions`）。`hello.defaults` 告诉界面它是哪个，外壳与扩展都不写死 |
| 切换 | 离开一个 space 时记住它当前的会话，切回来时恢复；那个会话没了就退到这个 space 的列表，**不退到别的 space 的会话** |

**硬理由**：Agix 的会话在创建时就定了场景，场景决定工具集。不同 space 的工具不同，它们的会话本来就不能
共用。所以按 space 绑定不是界面偏好，是引擎语义的直接结果。绑定是 Harnix 自己的账本数据（引擎不知道 space）。

**前台 space 与它的会话：对应关系不能错。** 哪个 space 在前台，中区、输入框、右栏看到和操作的就只能是这个
space 自己的会话。这件事错一次就是把消息发进了别的产品面、别的实例、别的工具集，所以它是不变量：

1. **前端没有全局的「当前会话」。** 状态里记的是「每个 space 的当前会话」，切换 space 就是切换取哪一项。
2. **会话总是带着实例一起出现。** 草稿、滚动位置、权限卡、队列的键都是 `(instance, session)`。
3. **服务端也核对。** 会话调用带上调用方声称的 `space`，中枢对着账本核对，不属于就拒绝
   （`SPACE_MISMATCH`，错误里写明它属于哪个 space）。**声明了 `cross_space()` 的 space 是例外**（第一方里没有，留给应用自己的调试面）：声称它的调用可以观看、操作任何 space
   的会话，每一次跨 space 的操作都写审计。
4. **新建会话的去向只看前台 space。** 不存在「先建再挪」。
5. **在一个 `cross_space()` 的 space 里看别的 space 的会话是「观看」**，不改变归属，也不改写那个 space 记住的当前会话。
6. **展示（exposure）是第 3 条的另一个例外，由拥有者开**：建了会话的扩展可以把它展示到另一个 space（`harnix.session.expose {to, interact?}`，
   `cx.sessions().expose(&s, space, Exposure)`），声称那个 space 的调用就能够到它——`interact: false` 只能**看**（attach、history、entries、outline、tasks、
   skills、hooks、会话主题、`engine.session.get / resume`），`interact: true` 还能**说**（send、respond、队列、interrupt、rewind、feedback、扩展条目）；
   会话的**生命与身份**（close、delete、fork、rename、setModel、setPrompt、move）无论怎样展示都只能从它自己的 space 做，新加的方法没登记前也算这一类。
   归属、实例、谁启动的、审计都不变（展示不是跨 space，不写跨 space 审计：是拥有者开的门）；`harnix.sessions.list {space}` 和按 space 裁的会话主题里，
   被展示来的行带 `exposed_from: <它的 space>`，每一行都带 `exposed_to: [{space, interact}]`。展示记在账本里，随会话一起删，重启不丢；`unexpose` 收回。
   设备不能展示（会话在哪里出现是应用定的，同归属）；不是建它的扩展也不能；目标要是这个应用有的 space（只有界面的也算），不能是它自己的、
   关掉的或 `cross_space()` 的。用处：项目里的任务——主会话归 `flow`，展示到项目 space 列的 `sessions`，就能在项目 space 的中区打开、对话，
   项目 space 仍然不认识流程。

第 3 条是**防误，不是安全边界**：space 是调用方自己声称的，同页的任何代码都能声称任何 space，包括 `cross_space()` 的那个（§6.2）。真正的跨 space 权力是能力（§4.3）。

### 5.5 看得见：首页、上下文、诊断

**看进程的东西分给拥有它的扩展，放在人会去的地方**，不另设一个能看见一切的面：

| 在哪 | 看什么 | 谁的 |
|---|---|---|
| 首页 | 全局统计（版本、运行时长、内存、线程、连接、实例、Agent、运行中的会话与后台任务、等人处理的）、待我处理、最近的会话与任务、全部定时、30 天的用量 | `harnix-app` 定义的点 `harnix-app.home.panels`，各块由 `observability`、`harnix-app`、`flow`、`schedule` 的 UI 包注册 |
| 会话的右栏 | 下一次调用将要带的上下文（每个会话的页签栏末尾常驻）、用量、后台任务的输出 | `observability` |
| 会话的中区 | 轨迹：记录下来的每一次模型调用 | `observability` |
| 设置 → 诊断 | 引擎、界面模块、扩展与它们在本页上的面板、被拒的贡献、自检；扩展包运行状况；扩展日志 | 外壳；`packages`、`observability` 的区块（`settings.section` 的 `within: "diagnostics"`） |
| 流程 space | 应用的工具链：流程、运行、参考 | `flow` |

每一块、每个数据来源见 [Harnix app](harnix-app.md) §6.1、§10、§11、§12。都只用公开的扩展接口与贡献点，没有私有通道；首页不认识往里放东西的包，
挂在哪由点有没有定义决定，不按 id（§5.6）。

**设备够不着的引擎方法包在扩展后面。** 读会话的上下文与后台任务的输出要 `engine.inspect`，读进程信息与扩展日志要 `process.observe`；`observability`
被授予它们，把四样包成设备能调的方法：`observability.context`、`observability.tasks.output`、`observability.process`、`observability.extensions.log`。
设备调它，它以自己的身份、凭自己的能力调引擎或内核，两次判定都进审计（§3.4.6）。前两个按 `RowScope::Session` 判，只对设备声称的 space 的会话，
转过去的调用照设备声称的 space——**它不跨 space**；扩展日志只转 `extension`、`level`、`after`、`limit` 四个键，内核那一行不对设备与扩展包开放。

**录像里有完整的系统提示词，敏感级别和 transcript 相同**（§6.4），所以只能经要能力的方法读（`observability.*` 要 `recordings.read`），录像目录永不经 HTTP 暴露。
录像存哪由链路定：建会话时问引擎生效的 `recorder.root`（没配用 `<数据根>/recordings`），写进会话的 `recorder.dir`；整棵会话树在根会话的一份录像里。它只覆盖最近一次运行，所以用量也只算这次运行，读用量的结果标 `run`/`earlier_run`；休眠的模式 3 进程不为读用量叫醒，给旧数并标 `stale`。
产品不要这些，就不链 `observability`，或者 `[extensions] off = ["observability"]`：它的方法连同授予一起没有——**撤的是方法，不只是不画**。

**要一个观看、操作任何 space 的会话的调试面，应用自己写。** 一个原生扩展被授予 `engine.inspect`、`engine.control`（要管实例再加 `instances.admin`），
声明一个 `cross_space()` 的 space，就能看、能改任何 space 的会话，每一次跨 space 的操作都写审计；不授予就每一样都被拒（§2.5 的 `debugger`）。
骨架里没有一行认它，第一方里也没有这样的 space。

**Agix 没给的，不画假的。** 页签或按钮在 Agix 补上之前不出现，而不是做成灰的或者在 Harnix 侧模拟。

### 5.6 贡献点与宿主 API

**内核贡献点十二个**，数量本身是设计的一部分，再加一个是一个需要论证的决定。完整目录由代码生成，见 [contribution_points.md](contribution_points.md)。

| 贡献点 | 贡献什么 |
|---|---|
| `space` | 一个 space：图标、标题、放在哪，分四组——左栏（`sidebar`）、中区（`center`）、对话（`conversation`）、右栏（`details`）；可选一个 store，值变了不用记得重画 |
| `home.card` | 新对话空页上、输入框下的一张卡 |
| `tool.row` | 一次工具调用在流里的那一行 |
| `flow.block` | 流里的一种块（扩展条目就是用它画的） |
| `details.panel` | 右栏详情里的一页，由 `reveal(item)` 打开 |
| `sidebar.group` | 会话列表的分组与排序 |
| `command` | 一条 `/` 命令或 `@` 引用的补全候选（`trigger` 选哪个菜单） |
| `settings.section` | 设置里的一节 |
| `session.action` | 对一个会话、或它里面一次工具调用的动作；外壳在标题栏、会话菜单、工具行上问它 |
| `sidebar.tab` | 右栏的一种页签类型：认领 `harnix-resource://` 地址的资源页，或按 `kind` 打开的页；右栏是每个会话一个停靠面 |
| `shortcut` | 一条有快捷键的命令：按平台的缺省键、生效的地方（全局、输入框、右栏）、动作；人在设置里改的键存在浏览器里 |
| `conversation.view` | 中区画一个打开的会话的另一种画法（缺省是对话）；外壳在中区顶上画「对话 \| …」的切换，每个会话各记自己的选择 |

**这些是界面自己的接缝。** 它们存在的理由不是给第三方一个扩展面——扩展 agent 是引擎的事——而是让界面不是
一堆 switch：于是「换一整套界面」是换一批注册，而不是改一堆分支。**频率是约束**：没有一个点跟着流式分片求值。

**第九个的理由**：外壳里曾经写死几样只属于某个扩展的东西——标题栏、工具行上打开某个扩展的面的按钮，会话菜单里的归档与导出。
它们是同一种东西，没有现成的点能承载；有了 `session.action`，它们由各自的 UI 包注册（`@harnix/harnix-app` 的归档、导出、在预览中打开，
`@harnix/observability` 的查看输出），外壳只问。
外壳自己的菜单项（打开、分叉、关闭、删除、改名）只用内核方法，照旧由外壳画。

**第十个的理由**：右栏照 DSH 的架构做成每个会话一个停靠面之后，在里面打开的东西——文件预览、用量、流程进度、后台任务的输出——是同一种东西：
一种认领地址、或按名字打开的页签类型，记在会话名下。`details.tabs` 是 space 的，承载不了「这个会话开着哪几页」。于是有 `sidebar.tab`，
进右栏的每条路都走宿主 API 的 `host.sidebar`；`details.*` 与 `reveal` 原样保留，是同一条页签栏里 space 那一侧（[Harnix 扩展](harnix-ext.md) §22.7）。

**第十一个的理由**：外壳的三个键（新会话、收起左栏、聚焦输入框）是一个监听器里写死的三个分支；别的包要加键只能自己再挂监听器，
谁占了哪个键没有一处说得清，设置里也没法改。一条带按平台缺省键、生效地方和动作的命令是同一种东西，于是有 `shortcut`：外壳一个监听器按键找命令，
焦点所在处（输入框、右栏）的先于全局的；设置的「快捷键」列出全部命令、录键、查冲突、恢复缺省。`command` 是输入框里 `/`、`@` 的补全，承载不了它。

**第十二个的理由**：中区把一个会话画成对话，而轨迹（这个会话的调用按轮列成一张表）是同一个会话的另一种画法——它占对话的位置，不在对话旁边。
`space` 的 `center` 是整个 space 的、不是一个会话的，右栏的页签在对话旁边，都承载不了它；于是有 `conversation.view`，`@harnix/observability` 注册「轨迹」。

**扩展定义的贡献点。** 一个原生扩展的 UI 包可以定义自己的点（`r.definePoint("<自己的 id>.<名>", ..)`），别的包往里注册；后端在界面声明里写同一个点，
进生成的目录。注册进还没定义的点先挂着，全部注册完还没人定义就丢掉并记进诊断。要「接不上就自己来」，注册时给 `orElse`：点在全部注册结束时还没定义就调它。
首页就是这样拼起来的：`@harnix/observability`、`@harnix/flow`、`@harnix/schedule` 往 `harnix-app.home.panels` 里注册，`orElse` 什么都不做，
没有 Harnix app 的产品里它们悄悄不出现——这是「挂在哪由点有没有定义决定，不按 id」。扩展定义的点不算进十二个。

**外壳必须真的去问。** 一个没人问的贡献点等于只存在于目录里，产品照旧自己直接画，而所有测试都还是绿的。这件
事真的发生过一次，七个点里的五个。判据因此不是「注册了」，是「被问过」，并且由测试盯着——点的名单本身也从
生成的目录里读，因为手抄的那份也漂过一次。内建界面走的就是这些点，没有一样有私有通道：**如果连工具行都是
这样画出来的，这些接缝就不需要谁来相信。** 例外要说出来：`home.card` 没有内建注册，外壳照样在新对话的输入框下问它，`examples/hello-app` 注册了一张。

**令牌覆盖与语言包不是贡献点。** 注册表上的 `r.tokens({...}, owner)` 只许覆盖**已有的**令牌名，值只许是颜色或
长度；`r.strings(locale, {...}, owner)` 的 key 必须在 `<owner>.` 下面。不合规矩的那一条被拒并记进诊断。它们
不是点，因为它们不在任何时机被「问」——它们改的是主题和词典本身。

**宿主 API（`HostApi`，`useHost()`）** 是前端代码拿到的全部能力：`call`（只放行 `harnix.reachable` 里的）、`subscribe`（主题，可带参数）、
前台 space 的会话（自动绑定前台 space）、实例（按可达方法过滤）、会话事件（引擎原样的与 `@harnix/core` 解析过的两份，带会话的信任）、跨 space 导航
（`navigate.open`：把 space 带到前台，把选择交给它）、外壳的对话框与菜单（焦点、Esc、遮罩都是外壳的，扩展不自己造）、`composer.insert`、`reveal`、
`ext(id).fetch / socket`、`defaults`（缺省实例与缺省 space）、`t()`。**拿不到 Harnix 自己的连接**，所以同一份代码在任何拓扑下都能跑——这是
「语义写死、拓扑可选」在界面这一侧的体现。

### 5.7 扩展包的界面：面、桥、行内点

**受信的界面进页面，商店的界面进隔离的 iframe；外壳拥有一切，扩展包只能借外壳的手。** 会话、对话、连接、主题、快捷键、模态层都是外壳的；
扩展包的界面在外壳给的「面」里画自己的内容，所有数据经外壳那一条 Harnix 连接来回（§4.5）。两种载体的扩展包界面完全一样。

| 信任 | 界面怎么跑 |
|---|---|
| 商店副署（`store`）、未签名（`unsigned`，只在开发模式） | 隔离 iframe：清单的面与行内点；进页面的模块一个都不跑 |
| 受信发布者（`trusted`） | 可以带进页面的模块（要 `ui.page`），和 UI 包同权限；面照样进 iframe |

扩展包的界面全部是声明：`harnix.ui` 里它的条目带面、行内点、进页面的模块与基址 `/ext/<id>/ui/`。外壳核心照条目替它往内核点上注册（owner 是它的 id）。

**面与行内点分开。** iframe 适合整块的区域，不适合成百个的小部件（一个流块一个 iframe 养不起）。所以分成两类：

- **面**（space 的中区、左栏中段、右栏页签、二级栏，详情面板、设置节、新对话卡、模态框）给 iframe。外壳给每个面画外框（标题、加载、出错、
  重新加载），一个崩掉的扩展看起来是「这一块出错了，重试」，而不是半张白页；连续失败的面被置于一旁。
- **行内点**（工具行、流块卡片、命令、侧栏分组）是**声明式**的：清单写模板，外壳用自己的组件照画，不跑包里的代码。要比模板更多的样子，
  就做成一个面，而不是在流里塞 iframe。

**对话始终是外壳的。** 商店的扩展包不能替换对话的画法，只能经声明给某种块、某个工具指定样子。一个 space 的左栏也只有一种：外壳的会话列表
（可以声明分组），或扩展包自己的面。

**iframe 的边界**：页面是不透明源，读不到外壳页面的令牌、存储与 cookie；它不能联网，数据只走桥；它能把自己导航走，但出不了这个源。
这些靠的是 iframe 的沙箱属性与两层 CSP，属性与策略的原文、各自挡住什么，只写在 [扩展包](harnix-ext-package.md) 一处。

**桥**（`harnix-ui-bridge@2`）：外壳经 `MessageChannel` 交给 iframe 一个端口（不是 `window.postMessage` 广播），页面一侧用 `@harnix/ext-sdk`。
它能请外壳做的是宿主 API 的一个子集：调自己的 `<id>.*` 与清单 `[interface] calls` 列出的少数内核方法，开自己 space 的会话，
外壳的手（切 space、开右栏、二级栏、设置节、往输入框插字、角标、通知、复制、模态框、确认、外链、上传）。都是外壳去做：`confirm` 是外壳画的，
扩展造不出假的确认；外链每次问人。**它能调什么由服务端说了算**：桥给每个代理的调用与订阅标上它代的扩展，路由器取「设备的权力 ∩ 清单 `[interface] calls`」
并按范围收窄到它自己的 space 与会话（§3.4.2）；被拒的记审计，设置 → 诊断的「扩展包运行状况」里看得到。**拿不到的**：页面的令牌、连接本身、别的扩展的名字、DOM。

**看起来像原生的。** `@harnix/ext-kit` 是外壳的令牌加几样基础部件，主题与语言经桥推进来、即刻生效；外壳的快捷键在 iframe 里按下也交给外壳，
外壳的对话框开着时 iframe 收不到键：一个键只落在一处。

### 5.8 Agix 插件的界面模块

```toml
[[ui]]                          # 同源 ES 模块，浏览器 import
point       = "tool.row"
module      = "rows.js"         # 相对包里的 ui/，只在那底下解析
api_version = 4                 # 贡献点 API，与 [plugin] api_version 是两个数
```

**两个版本号，各由拥有它的一侧检查。** `[plugin] api_version` 是引擎的扩展 API，引擎校验；`[[ui]] api_version`
是贡献点 API，Harnix 校验。一个包可以在一边是新的、在另一边是旧的，所以它们不能是同一个数。

**模块是预编译好的 ES 模块**（JSX 已编译掉），**不带自己的 React**——页面上两份 React 会让 hooks 失效。
它按名字 import `react`、`react-dom`、`react-dom/client`、`react/jsx-runtime`、`@harnix/react`；外壳的构建
为这几个名字各出一个 facade，页面里一份**内联 import map** 把名字指到它们，外壳自己用的也是这几份，所以页面
上只有一个 React。React 的大版本因此是贡献点 API 的一部分，升 React 大版本就是升 `api_version`。

**import map 只能内联，而 CSP 是 `script-src 'self'`。** 办法是服务端在**发页面时**从要发的
`index.html` 算出 import map 的 `sha256`，写进这一页的 CSP：只放行这一段确定的文本，不算放宽，不需要
`unsafe-inline`、`unsafe-eval`。在发页面时算而不是构建时写死，是为了 `--ui-dir` 换进来的界面也对。

**照别的版本写的那一条不生效。** 版本不符（包括没声明 `api_version`，那被当作 1）的条目在读包时就被拒，
报「这一条不生效」并写明哪一边旧了，包的其余部分照常。在读包时拒而不是 import 进来再失败，是因为后者的症状
是一个悄悄不出现的面板（§2.4）。

`module` **只在 `ui/` 底下解析**——带 `..` 的直接拒，结构上就点不到包里别的文件。模块由 `plugins` 在它的路由下发出（`/ext/plugins/ui/<包>/<模块>`，要凭据），
条目经 `harnix.ui` 公布，外壳的模块加载器据此 import。

**产品可以整个关掉：`[ext.plugins] ui_modules = false`。** 关掉时既不提供、也不发任何 Agix 插件的界面模块，包就只剩引擎
那一半。需要「必须是人点的」的产品（例如交易）要关（§6.2）。

**信任级说清楚：界面模块与页面同级。** 它是同源模块，浏览器没有任何机制能把它关小；CSP 挡得住外部来源、
内联脚本与出网，挡不住一个已经被允许加载进来的同源模块去做页面本来就能做的事。所以这一层的约束是**披露、
准入检查、开关、可吊销与可审计**，不是强制隔离——一个被当成隔离来依赖的非隔离，比一个已知不隔离的地方危险
得多。一个界面模块能做的最坏的事，上限是「这个用户自己在这个页面上能做的事」。

受信发布者的扩展包带的进页面的模块是同一种东西，同样与页面同级；所以只给 `trusted`、要 `ui.page`，商店与未签名的扩展包只进 iframe（§5.7）。

### 5.9 界面产物的硬规矩

- **只用令牌，不写死颜色**——写死颜色的部件在另一种主题下不可读。
- **只用 key，不写死文案**——写死文案让整个界面在切换语言后变成两种语言。

由静态检查强制。**CSP 不放宽**：`script-src 'self'`（外加上面那一个 import map 的 hash）、`style-src 'self'`、
`connect-src 'self'`，无 `unsafe-inline`、无 `unsafe-eval`、无外部源。产物自包含，没有 CDN，没有运行期从网上拉
的依赖——所以断网时界面照常打开。

**出网是一项要披露的能力。** 界面这一侧没有第二条出网通道，CSP 挡住了。这是有意的：出网是一项要在安装时被
看见的能力，不该因为代码跑在浏览器里就绕过披露。要访问外部服务，走引擎侧声明了 `net` 能力的代码、原生扩展的后端，或扩展包
同意过 `net` 的后端。扩展包的 iframe 另有自己更严的 CSP（`connect-src 'none'`，§5.7）。

### 5.10 品牌与目录

profile 的 `[brand]`：`name`（页面标题、左栏产品名）、`icon`（SVG）、`product_id`。外观的其余部分（配色、文案）
由扩展经 `r.tokens` / `r.strings` 贡献。应用不 fork 界面就能拥有自己的外观。

**状态目录** `~/.<product_id>/`（不配就是 `~/.harnix/`；`HARNIX_STATE_DIR` 能挪）里每一处只有一个所有者：

| 位置 | 所有者 | 内容 |
|---|---|---|
| `token`、`devices.json`、`harnix.lock` | 装配、准入 | 进程令牌、配对的设备、进程锁 |
| `engine/`（`--engine-dir` 可挪走） | `main` 实例 | 它的引擎根：设置分层、transcript、记忆、技能、录像。Harnix 自己的，别的引擎客户端的目录（`~/.agix`）不读 |
| `kernel/spaces.json` | 中枢 | 会话与 space 的绑定、space 按模板建的实例、Harnix 起的会话 |
| `kernel/instances.json`、`instances/<数据根>/` | 实例层 | 实例账本、按模板建的实例的数据根 |
| `run/` | 实例层 | spawn 的 daemon 的私有套接字目录（只有本用户能进） |
| `uploads/<pid>/` | 装配 | 本进程的上传 |
| `ext/<id>/data/` | 原生扩展 `<id>` | 它的数据（例如 `ext/harnix-app/data/state.json`：工作区、归档、偏好） |
| `ext/<id>/install.json` | `packages` | 扩展包的安装记录与**同意记录**（扩展进程看不见它，§6.6） |
| `ext/<id>/<version>/` | `packages` | 解开、验过签的包 |
| `ext/<id>/run/` | 载体 | 扩展包的数据、kv，模式 3 里它自己 Agix 的根、它的会话的项目目录、`HOME`、`TMPDIR` |
| `ext/flow/data/worktrees/<运行>/` | 流程扩展 | worktree 任务的 worktree（分支 `harnix/flow/<运行>`），在项目之外 |

| 其余路径 | 是什么 |
|---|---|
| `~/Documents/`（`--data-dir` / `HARNIX_DATA_DIR`） | **只放项目**。选项目从这里开始，新建项目建在这里；里面没有隐藏目录 |
| `<项目>/.harnix/`（带品牌的应用 `.<product_id>/`） | 项目数据目录：项目自己的数据与配置，**一律**放这里，不另开：引擎的项目层（设置、agents、hooks、rules、memory、它的 worktree）与 Harnix 写的（流程的 `runs/`、项目的 `flows/`）同在一处。它是工具的，不是任务的：流程任务的会话写它算写项目之外，引擎沙箱让会话写的 `scratchpad/`、`memory/`、`worktrees/` 除外；流程往它的 `.gitignore` 里只加 `runs/` |

为什么这样分：状态目录按产品 id 命名，同一台机器上装两个产品不会抢令牌和账本；每一处一个所有者，一个扩展停用或卸载时清掉的就是它自己那一处；
Documents 是用户的，不该藏着程序的东西；项目里只有一个属于工具的目录，引擎与 Harnix 共用它（引擎启动时带 `project_dir = ".harnix"`、`product_name = "Harnix"`；带品牌的应用带 `.<product_id>` 与它的名字，二开的产品在用户的项目里留下的是自己的名字，不是 Harnix 的）。流程的 worktree 不在里面：引擎会清掉 `.harnix/worktrees/` 下它不认识的目录，所以它们在流程扩展的数据目录里。Harnix 只认这一种布局，不读、不迁移别的布局留下的文件。

### 5.11 桌面：Tauri 只是外壳

`templates/desktop` 是一个 Tauri 2 壳，任何 Harnix 应用都能套上，只换品牌。**webview 直接加载服务端发的 HTTP
页面**，所有业务走页面自己的 HTTP/WS，和在浏览器标签页里一模一样——在桌面窗口里和在浏览器里是同一个产品：同一份
界面、同一条准入路径、同一套测试。桌面壳与模式无关：模式 1、2、3 的产品都能套上它，它不是一种模式。壳连服务端有两种连法：

| 连法 | 壳做什么 |
|---|---|
| **本地** | 以子进程启动应用二进制：回环、`--launch-link`、`--exit-with-stdin`（壳退出，应用跟着退）；读状态目录里的令牌文件，`POST /auth/link` 换一条一次性链接，让窗口打开它，链接种下 `HttpOnly`、`SameSite=Strict` 的 cookie |
| **远程** | 打开配置好的 `https://` 地址，走 TLS 与设备配对 |

**没有业务 IPC**：没有命令、没有 invoke handler、不用自定义协议发界面、不用本地 socket；令牌只经过一个文件和
一次回环请求，窗口只见到一条用过即废的链接。`check-no-ipc.mjs` 在离线检查层盯着。连不上服务端时只显示壳里
打包的「无法连接」页，壳里不放业务界面。理由：一条 IPC 就是一条不经路由表、不进审计、浏览器里没有的通道，
桌面窗口与浏览器从此不是同一个产品。

唯一的例外属于窗口本身：macOS 上窗口没有标题栏（红绿灯浮在页面上），页面的顶栏就是拖窗口的地方，而网页自己
挪不动原生窗口。所以页面能对壳请求两件事——开始拖动、双击最大化——只给主窗口、只给回环上的页面
（`capabilities/window-drag.json`），`check-no-ipc.mjs` 对其余任何权限照样失败。它只动窗口，不经手应用的
任何数据。

## 6. 信任与安全

### 6.1 级别

| 级 | 是谁 | 信任从哪来 | 能做什么 | 挡它的是什么 |
|---|---|---|---|---|
| **内核** | 这个二进制自己 | — | 全部 | — |
| **原生扩展** | 应用编进来的扩展，含第一方扩展 | 出身：编进二进制 | 它被授予的能力之内的一切；它是内核级源码，真要绕可以 | 结构约束（拿不到中枢与链接、只经路由表）：防误，不防恶意 |
| **运维本人** | 写在项目 / 配置目录里的脚本与设置 | 出身 | 他本来就能亲手做的任何事 | 引擎判 |
| **扩展包，模式 2** | 装上的扩展包：后端与工具在产品进程的 WASM 里，以 `ext:<id>` 行事 | 签名 + 人同意 | 同意的 `calls`（只限自己的 space 与会话）与资源能力 | WASM 沙箱（宿主函数逐项按同意记录查）；wasmtime 或宿主函数的 bug 波及整个产品 |
| **扩展包，模式 3** | 同一个包，在它自己的扩展进程里，另有它自己完整的 Agix | 同上 | 同上 | WASM 沙箱 + 进程 + 操作系统沙箱（§6.6） |
| **扩展进程里的引擎** | `proc.<id>` | 第三方代码控制 | 它发给中枢的帧 | 实例的信任（§3.1.2）；外壳按不受信内容渲染 |
| **Agix 插件** | 装上的包的 Agent 段，含扩展包的 `agent/` | 签名与引擎的披露 | 默认什么也够不着；多要一分，安装时写下来一分 | 引擎判 |
| **页面** | 界面、UI 包、Agix 插件的界面模块、受信发布者进页面的模块 | 同源 | 这个用户在这个页面上能做的事 | — |
| **iframe** | 扩展包的界面 | 签名 | 设备的权力 ∩ 清单 `[interface] calls`，只限它的 space | 不透明源、CSP `connect-src 'none'`、服务端的交集（§3.4.2） |
| **设备** | 远端连上来的客户端 | 配对 / 本机令牌 | 路由表里对设备开放的行 | 准入、访问规则；设备永远不持有能力 |

级别按出身定（§2.3）。运维与 Agix 插件两级由**引擎**判定和强制——同一份 `.js`，放在项目里是运维本人写的，随包下载来的就是插件，
判据是规范化之后的路径，不是它自称什么。Harnix 判定的是设备、扩展与扩展包。

**扩展包的三个信任等级**由签名定，写进安装记录，每次启动对盘上的文件再验：

| 等级 | 什么时候 | 界面 |
|---|---|---|
| `store` | 商店副署对产品内置的商店公钥验得过 | iframe |
| `trusted` | 发布者签全了每个文件，且它的公钥是 profile 为这个发布者写的 | iframe；可以带进页面的模块 |
| `unsigned` | 没有签名；只在 `[ext.packages] dev = true` 时能装、能跑 | iframe |

### 6.2 强制、披露、防误

每一处约束标明是哪一种。**安全边界**对恶意代码也成立；**披露**是让人在装的时候看见；**防误**只防 bug、不防
恶意。后两种都是 §1.2 说的「明说不是强制的」那一类。不存在「大概安全」的地方。

| 约束 | 种类 | 防什么 | 不防什么 |
|---|---|---|---|
| 命令执行的权限判定与沙箱；出网策略 | **安全边界**（引擎的） | 插件、模型越权 | 运维配的端点不受出网策略约束 |
| 路由表：每一行写明谁能用、要什么能力，缺省谁都不能调；引擎的凭据 / 子进程 / 端点类方法不对设备开放；中枢独占的谁都不能 | **安全边界** | 未授权的主体调方法、访问扩展的路由；设备接管进程 | — |
| 能力：特权只来自装配时的授予或人的同意；启动时查少授、多授、未定义 | **安全边界**（对设备与扩展包） | 设备与扩展包拿到没给的特权 | 原生扩展是内核级源码（见下面「结构约束」那一行） |
| 设备配对与吊销；非回环必须 TLS + 配对 | **安全边界** | 网络上的其他人 | — |
| 设备建实例只能按启动时定下的 `ui` 模板、只能填模板放开的参数；跨拥有者与非 `ui` 模板要 `instances.admin` | **安全边界** | 设备装载子进程、改写模型端点、指定任意数据目录、停别人的实例 | — |
| daemon 的凭据不出 Harnix（spawn 的 socket 在私有目录里，attach 的 token 只在 Harnix 手里）；引擎直通的拒绝对每台实例一样 | **安全边界** | 设备经 Harnix 拿到 daemon 的完全信任 | 本机上能读 Harnix 进程内存或环境的人 |
| 一个扩展不链或关掉时它的行连同授予从路由表撤掉 | **安全边界** | 产品里有人用到它的方法（例如读录像、跨 space 操作） | — |
| 扩展包的范围：只在它自己的 space 与会话上，读不到别人的会话内部 | **安全边界** | 扩展包读写别的 space 的会话 | — |
| 扩展包的 WASM 沙箱：宿主函数逐项按同意记录查（`net` 精确主机、`env` 名单、`storage`、`calls`、`fs` 预开目录）；内存与单次调用时间封顶 | **安全边界** | 扩展包越权：联网到别处、读没给它的秘密或进程的环境变量、调没同意的方法、碰别的文件、吃光内存或 CPU | wasmtime 或宿主函数自己的 bug（模式 2 同一个进程，波及整个产品；模式 3 隔开，见 §6.6） |
| 扩展包的签名：解包前验，每次启动再验，`.cwasm` 按签名的 sha256 比对后才反序列化；未签名的只在开发模式 | **安全边界** | 被篡改的包、来路不明的编译产物 | 签了名的发布者本人写的坏代码（那是 WASM 沙箱与披露的事） |
| 扩展包的界面进隔离 iframe：不透明源、`connect-src 'none'`、只经桥；它能调什么在服务端取交集 | **安全边界** | 扩展包的界面读页面的令牌、自己联网、调清单之外的方法、伪造确认框 | 受信发布者进页面的模块（与页面同级）；iframe 自己导航外带数据（外壳当失败拆掉它，但挡不住那一次导航） |
| 模式 3 的进程与操作系统沙箱：读不到令牌、设备、别的扩展与产品引擎的数据，改不了自己的同意记录，没有可以连的套接字 | **安全边界**（§6.6） | 被攻破的扩展进程以设备身份调用、读别人的数据、给自己加能力 | **网络**：它可以直接连任何主机；**它自己引擎里的模型凭据**与它自己引擎的设置；内核或沙箱本身的漏洞 |
| 扩展进程里的引擎：引擎事件不转发、帧有上限、标题与状态截断、会话按不受信内容渲染 | **安全边界**（对中枢与外壳） | 第三方引擎刷屏、伪造状态、往外壳里塞会执行的内容 | 它会话里的话本身 |
| 「只有设备能回答」：权限提问，以及应用自己做的批准 | **安全边界，只对后端成立** | 引擎、扩展、内核替人回答 | **区分不了人和同页的界面模块**：进页面的模块能替人点。需要「必须是人点的」的产品，设 `[ext.plugins] ui_modules = false`，不信任发布者 |
| 扩展包里的 QuickJS | **不是隔离边界**（按签名信任） | — | 模式 2 里脚本在产品实例的 Agix 里跑，看得到那个实例里其它会话的事件 |
| 扩展包的能力、行内点会知道什么、界面能调的名字 | **披露**（装前，人同意才装；升级多要能力时只列多出来的） | 人不知道扩展包要什么 | 扩展包在给了的能力之内做什么 |
| 原生扩展的披露：它做什么、替谁做；诊断列出它的授予 | **披露** | 人不知道产品里的扩展替设备做什么 | 原生扩展在授予之内做什么 |
| Agix 插件的模型可见文本 | **披露** | 人不知道包往模型面前放了什么 | 文本本身的内容 |
| 界面模块占了哪些贡献点 | **披露** | 人不知道包改了界面哪里 | 模块在页面里做什么（§5.8） |
| 原生扩展拿不到中枢、引擎链接、路由表与授予表 | **结构约束**（可见性与层次规则） | 扩展不小心绕过中枢与判定 | 原生扩展是内核级源码，真要绕可以；这一条防的是误用 |
| `SPACE_MISMATCH`：会话与声称的 space、实例对不上就拒绝；`cross_space()`；展示（`harnix.session.expose`，只有建它的扩展能开） | **防误** | 界面或扩展的 bug 把消息发进别的 space、别的实例 | 同页的代码：space 是调用方自己声称的，任何设备代码都能声称任何 space。真正的跨 space 权力是能力 |

把这些讲清楚比藏起来有用。

### 6.3 远程访问

一个进程服务一个用户，但这个用户可能有几台设备。

- **配对**：一次性配对码换一份长期设备凭据（设备侧密钥对，挑战应答）。每台设备一条，可列出，可单独吊销。不需要
  CA，不需要身份提供方。配对过的设备存在状态目录的 `devices.json`（同令牌一样只有属主可读），重启后仍在。配对码与设备的管理是第一方扩展 `devices`
  （凭 `devices.manage`），配对的准入仍在骨架。
- **凭据绑主体，不绑连接。** 多通道拓扑里所有通道共用握手换来的那一份凭据，吊销一台设备立即断掉它的全部通道：
  它的凭据当场作废（分离流的请求得 401），单双向流的连接以 1008 关掉，事件流结束。
- **准入只给一个答案。** 未知或已吊销的设备、过期或用过的挑战、对不上的签名，拒绝的理由是同一句；令牌按恒定时间比较；
  `/challenge` 同时最多 1024 个未答的挑战，超了回 429。
- **非回环绑定必须同时有 TLS 与已配对设备。** 没有裸 HTTP 的远程——不是默认关闭，是没有这条路径。
- **启动链接**：本机打开页面时令牌可以不进页面，浏览器凭一次性链接换一个 `HttpOnly` cookie（桌面壳本地的连法就
  走这条，§5.11）。
- 回环绑定同时监听 IPv4 与 IPv6：`localhost` 在多数系统上先解析到 `::1`，只绑一边会出现「curl 通了但页面打不开」。
- Origin 校验按部署形态取值：本地放行本地来源，远程只放行配置里写明的来源，**不提供通配**。

### 6.4 敏感数据

transcript、会话记忆、录像（每次模型调用的完整输入，含系统提示词）都是同一批内容，**敏感级别相同**，落在同一个
实例数据根、同一套文件权限下。

三条规则：录像默认开，因为没有它就无法回答「模型到底看见了什么」（会话的「轨迹」视图就靠它）；录像目录
**永不经 HTTP 暴露**，只能经要 `recordings.read` 的读者读，转录只能经要 `transcripts.read` 的读者读；删除会话连带删除它的录像（侧链与分叉的也一起删），关闭会话不删——会话还能重开。
attach 的实例是别人的 daemon，不给目录、不删录像；回放不录。
扩展拿到的是读者，不是数据根的路径。

### 6.5 审计

路由器的每一次拒绝，以及设备配对与吊销、扩展的登记与撤下、扩展包的安装与同意、权限回答、每一次跨 space 操作、实例的新建停止重启、
扩展进程的复核不过、清数据，都记下来。每一条带主体、代谁（`via ext:<id>`）、方法、判定、理由、调用 id 与父调用：
设备调了一个扩展的方法、扩展再以自己的身份调内核，审计里是一棵树。
进程里有一个有界的环，`harnix.audit` 与诊断能读；能归到一个会话上的，另以扩展条目写进那个会话的时间线，与其余条目同序。
不是每次放行都记：一秒几次的只读放行会把真正有人会去找的条目埋掉。

复用引擎的扩展条目而不是另建一套日志，有一个具体好处：**未知命名空间必须可跳过**，所以卸载一个 Agix 插件或扩展包之后，它留下
的旧条目仍然能被加载，历史不会因为少了一个扩展而读不出来。

### 6.6 模式 3：同一个系统用户，加一层沙箱

扩展进程与产品是**同一个系统用户**。不加操作系统沙箱时，一个被攻破的扩展进程（wasmtime 逃逸、宿主函数的 bug）不需要过线，就能读产品的令牌成为设备、
读别的扩展与产品引擎的数据。所以模式 3 带着沙箱，并且没有任何监听套接字。

**沙箱**套在重新 exec 的那个子进程上，它 fork 出去的子进程（它自己 Agix 的 shell 工具）继承同一个沙箱。扩展进程只能读写它自己的运行目录、只读它的包、
执行本二进制与系统的几处只读路径、查 TLS 根证书与 DNS；回放录像时（`--replay-dir`）另只读放行那个目录，那是操作者显式给的。它看不见状态目录的其余部分、
别的扩展、产品的引擎根与 daemon、它自己的同意记录——一个能改自己同意记录的进程就能在下次启动时给自己加能力。**网络开着**。

**进程沙箱是唯一的边界。** Agix 自己的命令沙箱不另套在里面：macOS 不许嵌套（外层的沙箱里再套一层答 `Operation not permitted`，Agix 给 shell 命令套的那层起不来），
Linux 照同一条。所以沙箱开着时，产品收养它的引擎时在它引擎根的设置里关掉 Agix 自己的命令沙箱；`sandbox = "off"` 时不关，Agix 自己的命令沙箱照开。
代价（维护者定，接受）：模型的命令能改写这个扩展自己的引擎设置（含权限），但出不了进程沙箱；Agix 只在自己的沙箱兜着时才自动放行 shell 命令，所以无人值守的会话不再自动放行它。

- **macOS**：经系统的 `sandbox-exec` 执行，profile 按上面的路径生成，缺省拒绝一切。
- **Linux**：Landlock，同样由产品套：父进程先建好规则集，子进程在 exec 之前只设 `PR_SET_NO_NEW_PRIVS`、套上规则集，所以进程一条指令都没跑就已在沙箱里；
  内核支持时另限信号与抽象 unix 套接字；产品在拉起前查 `ptrace_scope ≥ 1`。
- **套不上时拒绝**：`[ext.packages] sandbox = "required"`（缺省）下，没有 Landlock、`ptrace_scope = 0`、没有 `sandbox-exec`、Windows，模式 3 一律拒绝拉起扩展进程，
  `packages` 的快照写明原因（`runtime.sandbox`）；不静默降级。`sandbox = "off"` 只给开发用：启动时警告，快照里每个进程标 `sandbox: off`。
  沙箱由宿主套，载体跳不过；`off` 只认 profile 里 `[ext.packages]` 写的。`off` 与套不上都在扩展的设置节与设置 → 诊断的「扩展包运行状况」顶上标红、写明原因，
  每一行标「无沙箱」。

**它挡住什么、挡不住什么**：

| 资产 / 能力 | 不加沙箱时同一用户拿得到 | 模式 2，被攻破（= 整个产品进程） | 模式 3，被攻破（沙箱生效） |
|---|---|---|---|
| `calls`（中枢的方法与主题） | 读令牌就是设备 | 不成立 | **成立**：读不到令牌，没有监听者，只有它自己的线 |
| 令牌、启动链接、`devices.json` | 能读 | 不成立 | **成立** |
| 别的扩展的数据、kv、引擎根、安装记录 | 能读写 | 不成立 | **成立** |
| `main` 引擎根（provider 密钥、转录、录像） | 能读 | 不成立 | **成立** |
| 产品 spawn 的 daemon 的套接字 | 能连、能读 | 不成立 | **成立** |
| 别的扩展进程的引擎 | — | — | **成立**：继承的 fd，没有套接字文件 |
| 自己的同意记录 | 能改 | 不成立 | **成立**：不在它看得见的地方 |
| `net` | — | 不成立 | **不成立**：网络开着，它可以直接连任何主机，包括回环上别的服务 |
| 模型凭据 | 能读 `main` 的 | 不成立 | **不成立**：产品把 provider 写进了它自己的引擎根（只有设置页的 provider；产品环境里的 `ANTHROPIC_*` 不进它） |
| `env` 秘密 | 能读 profile | 不成立 | 只有给它的那些；别人的读不到 |
| `storage` | — | 虚拟机配额 | 只靠产品的兜底：快照时量它的运行目录，超上限 10% 就停掉它 |
| CPU、内存 | — | 虚拟机 | 虚拟机之外只有 Linux 上的地址空间上限；macOS 不设 |
| 对产品进程 ptrace、发信号 | 能 | — | macOS：沙箱挡住；Linux：要 `ptrace_scope ≥ 1`（拉起前查），信号只在 Landlock ABI ≥ 6 的内核上挡，否则**不成立** |
| 内核或沙箱本身的漏洞 | — | — | **不成立** |

一句话：**模式 3 隔开故障、资源与文件**；被攻破的扩展进程读不到产品的令牌、设备、别的扩展与产品引擎的数据，也没有可以连的东西，所以 `calls` 与数据这几行对它也成立。
**它挡不住网络，也挡不住它拿着的模型凭据**——诚实的进程的 `net` 在产品侧判（出口经扩展线由产品代发），被攻破的进程可以绕过它直接联网，并带着产品写给它的 provider。

**不防的**：模式 3 的网络、它自己引擎里的模型凭据、它自己引擎的设置（见上：出不了进程沙箱）、旧内核上的信号、内核与沙箱的漏洞；模式 2 里 wasmtime 与宿主函数的 bug；原生扩展的恶意。
要让网络与凭据也成为边界，要的是模型调用经产品中继、沙箱里断网；出口已经只在产品侧判，provider 只是交给进程的一个字段，所以这两步不改线、不改包。

## 7. 边缘部署

### 7.1 形态

**一个进程、一个用户、多个会话、一个后端二进制、无运行时依赖。** 没有包管理器，没有 `node_modules`。安装物是这一个
文件；运行时不从安装目录读任何东西，状态在状态目录，所以升级就是换掉那个文件。要隔离崩溃与资源的那部分 Agent，
用 daemon 实例放到另一个进程里；要隔离的扩展包，用模式 3——两者都是同一个二进制的子命令（`daemon`、`ext-proc`），不另外分发。

| 形态 | 后端 | 界面 | 传输拓扑 |
|---|---|---|---|
| 单机 / 桌面 | 本机，回环 | 后端提供（桌面壳加载它） | 单双向流 |
| 边缘节点 + 远程使用 | 节点上，TLS + 配对 | 后端提供 | 单双向流 |
| 反向代理后面 | 内网，代理终结 TLS | 独立静态服务（`ui export`） | 分离流 |
| 一堆节点 / 自动化 | 每节点一个进程，`--headless` | 无，或一份共用界面 | 纯请求 |

缺省的模式 2 就是为这一节做的：扩展包不多一个进程，每个包一台虚拟机，常驻开销是它常驻 Store 的线性内存（清单的 `memory_mb` 封顶，通常几 MB），
整个进程共用一个 wasmtime 引擎；`on-demand` 的后端闲置时卸下。产品构建不带编译器，只反序列化商店编好的产物，所以带载体的二进制只比不带的大几 MB
（模式 1 的构建不开载体，没有 wasmtime）。
资源与安全的取舍见 [应用开发](app-development.md) §3–§4。

### 7.2 预算

**一个不被测量的性能目标只是一句话。** 下面这些数进 CI 门禁（`tests/budget.mjs`），回归即失败。初值按「4 核 8G
小主机，也要能在 2 核 2G 的 arm64 单板上跑」定：

| 指标 | 上限 |
|---|---|
| 后端二进制大小（`harnix` 的缺省构建：两个载体，带 wasmtime） | ≤ 104 MB（实测 52.9 MB；带的是 wasmtime 的运行时，不带编译器） |
| 界面产物（gzip 后） | ≤ 600 KB（含 React） |
| 冷启动到可服务 | ≤ 600 ms |
| 空载常驻内存（只有 `main` 一台实例） | ≤ 160 MB |
| 每个空闲会话的内存增量 | ≤ 8 MB |
| 每多一台空载的进程内实例 | ≤ 8 MB（实测约 0.1–0.2 MB） |
| 一次 unary 往返 p99（同机） | ≤ 30 ms |
| 每条空闲连接的常驻开销（预热后的边际值） | ≤ 128 KB |
| 握着 100 条连接时的常驻内存 | ≤ 240 MB |
| 完全空闲时 CPU | < 1% |
| 模式 3：每个扩展进程（带它自己的 Agix）的空载常驻 | ≤ 80 MB（实测 25.4 MB，开一个会话 28.8 MB；代码页与产品共享同一个文件映射） |
| 模式 3：扩展进程启用到能答（3 次取中位） | ≤ 4 s（实测约 44–47 ms） |
| 模式 3：`on-demand` 的扩展进程被一次调用唤醒（3 次取中位） | ≤ 4 s（实测 31–35 ms） |

**「每条空闲连接」测的是预热之后的边际值。** 冷测时头一百条连接看起来每条 145 KB；开完关掉再开一百条，边际不到
1 KB——差别是分配器第一次向操作系统要页然后一直留着。对冷数字设门禁等于对 malloc 设门禁。所以两个数都测：
**再开一条要多少**，以及**握着一百条时一共多少**；后者也是前者不能被悄悄换掉的原因。daemon 实例与扩展进程是另外的进程，不计入
产品进程的内存预算，扩展进程另有自己的行。

调整这些数的前提是把新的数写进这张表并说明理由，不是让门禁静默放宽。上一次调整：维护者定，引擎增长不卡门，上限翻倍（2026-11-15）；不带编译器由结构检查守，不靠体积数。

四个已知的取舍，摆在这里，不藏在实现里：

1. **QuickJS 每次调用建一个全新运行时**，这是「调用之间什么都不留」这条安全承诺的实现方式。是否为某些点复用
   运行时，是一个会削弱那条承诺的决定，要显式做。
2. **进程内实例意味着崩溃不隔离。** 换来的是没有 socket、没有握手、可以带原生工具。补偿措施是轮次级的故障隔离、
   随发布物提供的进程守护单元，以及需要时把那台实例换成 daemon——是可选的，不是默认把进程拆开。
3. **拓扑的成本不一样，所以它是配置而不是常量。** 分离流在代理后面更好用，代价是多一条连接；单双向流在弱网下
   更省，代价是所有流量共享一条连接的队头。**边缘默认单双向流**，因为那里连接比中间件贵。
4. **模式 3 的每个扩展进程重新执行整个产品二进制。** 换来的是没有第二个程序要分发、版本按构造就对得上；代价是每个进程都映射一个大二进制
   （代码页共享，常驻只算它自己的那部分）。嫌重的产品用 `proc_program` 指向一个更瘦的构建。

### 7.3 离线

- 模型走本地端点（OpenAI 兼容协议直连本地推理服务），并按任务分路由：主循环用大模型，压缩、子代理、记忆检索
  用小模型——这几类调用次数多、对质量要求低，是边缘设备上最值得省的地方。
- 界面产物自包含，无 CDN（§5.9），所以断网时界面照常打开。
- 安装可以完全离线：一个 Agix 插件是一个文件，从本地路径装与从市场装走同一条披露流程；扩展包也是一个文件，签了名的经
  `packages.installFile` 照样验签，商店也可以是本机的 `file://` 目录。
- 构建也能离线：Agix 随 `harnix/` 子仓一起检出，作为路径依赖，不经 git 源。

### 7.4 故障

- 引擎的持久化是 append-only 的日志，进程消失后重启即恢复到最后落盘的那一轮；按模板建的实例照账本重建。
- 被取消的轮次**不写终止标记**——取消是被打断，不是到达终点，所以会话必须保持可续。
- **断线不动 turn。** 任何通道断开只影响观看，中枢照跑；重连后按 `seq` 追赶。多通道拓扑里一条通道断了不牵连另一条。
- **daemon 断了是降级，不是挂掉**：那边的轮照跑，重连后 resync（§3.1.1）。
- **扩展包的陷阱、超时、内存超限被接住**，只动这一个扩展（换 Store、重建、反复崩溃置于一旁）；健康运行一段时间后出错计数清零。
  wasmtime 或宿主函数自己的 bug 在模式 2 里会波及整个进程；模式 3 里只波及那一个扩展进程，按退避重起，`proc.<id>` 上的会话靠 Agix 的持久化回来。
- **产品重启**：扩展进程随 stdin 断而退出；产品起来后按安装记录重新拉起。
- 上游长时间无响应要在界面上表现为可脱出的状态，不是无限「运行中」。

## 8. 改造它的层次

| 层次 | 做什么 | 代价 |
|---|---|---|
| **换 profile** | 一份声明式配置：引擎、实例与模板、拓扑、关掉哪些链进来的扩展、各扩展的配置节、品牌、是否加载 Agix 插件的界面模块、扩展包用哪个载体 | 不写代码 |
| **装 Agix 插件** | 引擎的脚本、skill、agent 类型改 agent 的行为；包的界面模块给已有的贡献点做贡献 | 不重编译 |
| **装扩展包**（模式 2 / 3） | 一个 `.hxext`：后端方法、主题、space、给 Agent 的工具、Agix 插件、隔离的界面，照同意记录拿能力 | 不重编译；产品要链 `packages` 与一个载体 |
| **换界面** | 换掉 `--ui-dir` 指的那份产物，或者只换其中几个注册 | 不重编译后端 |
| **做一个应用：原生扩展**（模式 1） | 以子仓引入 Harnix，写自己的扩展（后端方法、主题、路由、实例模板、引擎贡献、自己的能力）和 UI 包，挑第一方扩展，`App::builder()` 装起来、写下授予 | 重编译；不 fork Harnix |

最后一层是 §1.2 第一条目标真正落地的地方：一个形态完全不同的产品（Helm 的交易面板、IPDrun 的流程）不需要 fork，而是 Harnix 之上的一组扩展。
应用仓库里只有一个子仓 `harnix/`，Agix 由它带进来（`harnix/agix`，版本就是 Harnix 钉的那一版）。应用只认 Harnix：代码只依赖 crate `harnix`，
扩展接口经 `harnix::ext`、引擎词汇经 `harnix::engine` 取，里面没有 Agix 的类型；问题与需求只提 Harnix 的 issue，落在哪一层由 Harnix 决定——这样应用只有一个版本
要跟，Harnix 也能改动自己与引擎之间的分界而不牵动应用。没有 Agix 类型的逃生口：要引擎做的事，经 daemon 协议与引擎词汇说（§9）。公共改动在应用的 `harnix/` 子仓里开分支回推上游，**应用里不许有长期补丁**
（`check-pins` 检查子仓指针只指向上游存在的提交）。怎么做见 [原生扩展](harnix-ext.md)，从 `templates/app` 起步。

配套的两样，缺一不可：

- **贡献点目录由代码生成**，并有测试盯着它与代码一致。一份会过期的清单比没有更糟——它会被当成事实引用。
- **功能测试对着真的二进制跑（LIVE）**：后端走 API，前端走 Playwright 真浏览器，同一个运行器、同一套夹具；模型缺省严格回放引擎的录像，
  所以工具调用、权限提问、子 Agent 每次都一样，不花钱也不等网络；另有连真实模型的 live 模式刷新录像。覆盖表由用例标签生成，一个功能在
  某一层是零就要补或写明为什么。见 [testing.md](testing.md)。

为什么不用假 DOM、假后端：假后端还返回旧形状时，界面测试全绿而功能是坏的。在有录像回放之前，权限那条路**一次都没被真正跑到过**——
配置的模型不肯调工具，测试轮轮报「不确定」，而一切看上去是绿的。所以测试的结果有三种，不是两种：通过、失败、没结论。

## 9. 与 Agix 的边界

**依赖方式：**

> **引擎经 `agix::embed` 起，一律经 Agix 的 daemon 协议连接：进程内的实例是一条内存双工，spawn 与 attach 的是 socket。每种实例载体对中枢是同一条有类型的引擎链接，
> 会话语义不因载体改变；一台 daemon 只服务一个 Harnix，中枢仍是它上面会话的唯一持有者。**

这条原则的本意是两件事：中枢是会话的唯一持有者；Harnix 不因为连接方式不同而改变会话语义。一律走协议保住了这两件事：进程内与 daemon 是同一条路径（同一份翻译、同一套
宿主工具与钩子的登记），载体之间只差崩溃与资源的隔离。Harnix 交给引擎的只有它的设置；扩展的贡献（工具、钩子、门）登记在链路上、在本进程执行。

**接缝只有一处，在两个 crate 里；直接用 Agix 的代码只有一个文件。** 「只有一处」在两个意义上都成立——谁 `use` Agix，谁**知道** Agix 的名字：
`crates/engine/src/embed.rs` 是唯一直接用 Agix（`agix::embed`）的地方，其余都是协议上的 JSON。

| crate | 是什么 | 谁用 |
|---|---|---|
| `harnix-engine-api` | **没有 Agix 依赖的引擎词汇，扩展的一半**（S1，整个 crate 就是 `harnix::engine`）：`Tool`、`ToolSpec`、`ToolProvider`、`ToolHook`、`SceneLayer`、`SceneBase`、`PromptGate`、`EngineContribution`、模板声明、录像与转录的读者 | 扩展（经 `harnix::engine`）、中枢、实例层、引擎 |
| `harnix-engine-link` | **引擎词汇的骨架一半**（S3）：引擎链接（控制的一半与整条）、一样一个方法的引擎操作、有类型的引擎事件、场景层的展开、调用链的来源、一台实例的两个读者。依赖 `harnix-engine-api`，不被扩展接口、门面、宿主组件依赖 | 中枢、实例层、引擎、装配、扩展进程 |
| `harnix-engine` | **唯一依赖 Agix 的 crate**：Agix 的 JSON-RPC 与有类型的操作、事件之间的翻译（Agix 的方法名与事件种类只在这一份）；daemon 链路（进程内的内存双工与 socket 同一份）与回放链路；`embed.rs` 里经 `agix::embed` 起引擎与 daemon 的服务；链路上登记的宿主工具、钩子与门；读者的实现（经协议读，不解析录像文件，也不依赖 transcript 存储）；provider 的校验 | 实例层、扩展进程 |

- **中枢只认引擎词汇**：不编译 Agix，不拼 Agix 的方法名，不认 Agix 的事件种类（层次规则从翻译里的常量生成名单去查中枢的源码）。
- **扩展只见 Harnix 的工具与场景类型。** `SceneLayer` 只说要改的几样（追加的系统块、工具、交互方式、是否要项目、命名），其余照底版；
  场景层**由中枢在建会话时展开**：会话建在层的基场景上，再由中枢补上提示词的追加、这个会话自己的宿主工具、`attended`、`auto_name` 与权限规则。
  `ToolProvider` 是 Agix 插件的 Harnix 形状：工具集是实例级的（连接时问一次、`changes()` 响了再问），经链路登记，每个会话（含子 Agent、团队成员、后台任务）都有。
  宿主工具与 hook 的调用经链路交回本进程：工具的权限由链路按 `Tool::permission` 代答，`ToolHook` 在引擎的权限检查之前看到调用，
  `AddContext` 的话在模型下一步之前作为 system-reminder 交给它。Agix 取消一次工具调用时，链路取消工具的取消令牌，载体据此通知后端。
- **没有逃生口。** 没有 Agix 自己的值进得来的那一格：要引擎做的事，缺的就补 Agix（下文）。
- **严格回放是这一层的守护。** 翻译要逐字节复现交给引擎的系统块与工具表：LIVE 的录像在严格回放下全过，接缝改了一个字节就红。
  Agix 的协议改了方法名或字段，翻译旁边的测试比对它们，红在这里。
- **线上仍有两块是 Agix 的形状**，协议明说它们随 Agix 变：`harnix.event` 帧里的事件负载就是 Agix 的会话事件；`engine.*` 直通的答是 Agix 的形状。
  它们不在 `PROTOCOL_VERSION` 的加法承诺里，由 `hello.engine_protocol`（Agix 的协议版本）标明；`@harnix/core` 只在它的解析层认识 Agix 的事件形状，
  不认识的 `engine_protocol` 拒绝并说明。其余（内核的方法、主题、通知、错误码）都是 Harnix 自己的、只做加法的协议。

**Harnix 一侧永远不做的事**：实现或复制任何引擎逻辑；绕过引擎直接操作 transcript；在引擎之外维护第二份会话状态
（中枢维护的是**观看状态**与队列，账本记的是会话归属，都不是会话本身；会话标题只在引擎）。

**Agix 必选，不做引擎可替换。** 抽象一层「任意引擎」，代价是每一处都只能用所有引擎的交集，而 Harnix 的价值恰恰在于把这一台引擎的语义完整地
交给应用。引擎词汇是 Harnix 的类型，不是「任意引擎」的抽象：它的用处是让 Agix 的类型变化只落在一个 crate 里。

**Agix 缺的，去补 Agix。** 缺口写成 Agix 的 issue，由它驱动 Agix 开发；Harnix 侧不绕过、不模拟（界面上「Agix 没给的不画假的」是同一条，§5.5）。
**Harnix 跟着 Agix 持续升级**：`agix/` 子仓的钉就是 Harnix 验证过的那一版，每个 Harnix 发布对应一个 Agix 发布；Agix 改自己的类型，对一个
不实现引擎逻辑的宿主不该有代价，而接缝只有一处正是为了让这个代价落在一处。

**WASM 在这一侧。** Agix 只留编译进宿主的 Rust 插件与 QuickJS 脚本，带 `[[wasm]]` 段的包拒装；扩展包的 WASM 组件跑在 Harnix 的 `harnix-wasm` 里，
经载体的 `ToolProvider` 进会话（模式 3 进的是它自己的引擎）。所以 WASM 只有一处，Agent 侧的扩展也只有一处。

Harnix 依赖 Agix 提供的、并且已经由它提供的：

| Harnix 用来做什么 | Agix 给的 |
|---|---|
| 实例装配 | `agix::embed`：在本进程起一台引擎，接在一条现成的流上；同一进程里几台会话池互不可见 |
| daemon 与收养的实例 | daemon 服务的入口（接在 socket 或一条现成的流上）、协议版本与能力位、`subscription_dropped`、spawn 的就绪 |
| 中枢知道每一轮 | 会话与轮的生命周期进 `daemon.event`（带 `initiator`）；订阅冷会话 |
| 会话列表、改名、换模型 | 列表条目带场景与项目根；`engine.session.rename`、`engine.session.setModel` |
| 会话的内部（右栏的上下文与输出、轨迹、用量） | 上下文可查看；会话的后台任务可列、输出可读；录像 |
| 扩展条目 | 引擎的 `appendEntry` 与 `entries`（Harnix 这边是 `harnix.session.entries.append` 与 `engine.session.entries`）、`extension_entry` 帧；分叉带上条目 |
| Agix 插件 | 包方案与载体解耦；`engine.plugin.list` 带包的 `root`、`script_faults`；装不上的包不会假装装上；manifest 里不认识的段只告警 |
| 工具与场景进会话 | 连接级登记的宿主工具与 hook（引擎回调本进程执行）；会话选项里的 `host_tools`、`skill_dirs`、`attended`、`prompt` 与会话的 `setPrompt`；内置场景 |

这些曾经一条条是给 Agix 提的 issue。

## 10. 明确不做的

| 不做 | 理由 |
|---|---|
| 多租户 | 一个进程一个用户。硬塞进来会让授权模型对单用户场景过度复杂 |
| 可替换的会话中枢、可替换的引擎 | §2.1、§9 |
| 让拓扑或载体差异渗进中枢、路由与准入 | 传输可以有几种拓扑、实例与扩展各有几种载体，但只能有一套语义 |
| 运行期新增或改写模板、原生扩展 | 等于让别的东西决定这个进程是什么（§3.1）。运行期登记的扩展包在自己的 id 下、照同意记录、可撤 |
| 按 id 给的特权；骨架里认某个扩展的分支 | 特权是有名字的能力，产品授予或人同意（§2.3、§4.3） |
| 编进来的代码与装上的包是两个概念 | 两套登记、两条授权路径会分叉（§2.2.2） |
| Agent 侧的第二套插件体系 | 同一件事两处真相，且只有一处真拦得住；Agix 插件的包方案、能力与披露留在引擎（§2.2） |
| 在 WASM 沙箱之外执行包里的代码 | 原生动态库、包里的进程、Harnix 侧的脚本解释器都不要；规则不需要例外才守得住（§2.2.1） |
| 给 Agix 插件贡献的 Harnix 方法 | 它需要回调能力，给出能力就是在 Harnix 长出第二个能力模型。要后端方法，写原生扩展或扩展包 |
| 扩展包贡献内核方法、往别人的 space 加东西、读别的 space 的会话 | 它的方法、主题、space、面都在它自己的 `<id>.*` 下，范围只限它自己的 space（§3.4.2） |
| 扩展包改宿主的单槽契约（权限判定、预算、提示组装器、场景） | Agix 也只给 Rust；第三方代码不决定这些（§4.5） |
| Agix 插件新增 space、往别的 space 加页签 | 要 space 的第三方代码写成扩展包 |
| dylib 形式的 Rust 扩展；扩展包里的原生二进制 | 运行期的后端只有 WASM；原生代码只走编译进来的原生扩展。模式 3 有进程，也不放原生二进制：放了包就不能在模式 2 里跑，签名、审核与跨平台都要另起一套 |
| 扩展进程的监听套接字、第二个扩展进程程序 | 继承的 fd 就是身份；没有可以连的东西，也没有要另发的二进制（§4.6） |
| 界面的运行期外部依赖（CDN、远程 import） | 断网即坏，且把供应链面开到系统之外 |
| 桌面壳的私有通道（IPC、自定义协议） | 一条不经路由表、不进审计、浏览器里没有的通道（§5.11） |
| 把引擎的凭据 / 子进程 / 端点类方法开放给设备或扩展包 | 它们等价于接管这个进程 |
| 批准原语、角色令牌、MCP 服务端进内核 | 应用在扩展接口上做得出来（§4.8）；两个应用的实现形状一致后再收 |
| 跨机器的 daemon 实例与扩展进程；几个宿主共用一台 daemon | 前者只做本机；后者破坏中枢的唯一持有（§3.1.1） |
| 宿主主题的「追加模式」 | 整值快照够用；出现真实的高频增量需求再说 |
| 迁移的备份钩子、`--dry-run` | Harnix 只管迁移的顺序与失败隔离（§4.2） |
| 读取或迁移别的布局留下的状态 | Harnix 只认一种状态布局（§5.10）；一份「顺便也认旧格式」的代码会永远留着 |
| 协议层的投影子系统 | 派生视图不属于协议 |

这些里有「以后可能做」的，前提都是真实需求加 §1.3 的判据。

## 11. 与业界的位置

这一节说明哪些决定是共识、哪些是这套设计的选择。

近两年出现的几个 agent 宿主（DeepSeek Harness / dsh，以及围绕 MCP 生态生长出来的若干 IDE 与桌面宿主）在几件事上
给出了同样的答案，Harnix 也照做：**一切能力以扩展形式接入**、**模型是可换的类别而不是硬编码**、**会话是可追加、
可回放的事件流**、**界面与内核分层**、**请求与事件流分开承载**、**界面用 React**。这些不是差异点，是这类系统的形状。

传输拓扑上没什么可争的：那类系统普遍采用「一条 unary 端点 + 若干只下行事件流 + 一条带外应答端点」的分法。Harnix
的做法是把这套分法**上升成语义、把连接数下降成配置**——同一套语义在边缘设备上更适合收敛成一条连接，在代理后面
更适合摊开成几条，这两种部署都在目标之内。

分歧在四处：

**一、内核边界。** 那类系统多把「一切皆插件」推到底——agent 循环、会话持久化、审批逻辑本身也是可换插件。代价是
这个系统不再保证任何东西：当循环本身可换时，「一轮是什么」没有答案。Harnix 反过来，骨架写死、判断开放（§2.1）；连 Harnix 自己带的功能
也都是骨架之外、只用公开接口的扩展。这牺牲了一部分灵活性，换来的是可以对用户做出承诺。

**二、扩展的运行方式与隔离。** 以 Node 为宿主的方案里，插件与内核同进程同权限，JS 的对象级隔离不是隔离；其沙箱通常只覆盖文件系统的几档模式。
这套设计里只有一个扩展概念，信任按出身、能力按授予：应用自己的代码是原生扩展，权力是装配时写下的几项能力；第三方的扩展包只跑在 WASM 里，
那是一个对恶意代码也成立的边界，它要的每一项能力人同意过、在宿主函数里逐项查，模式 3 再加一层进程与操作系统沙箱，并明说它挡不住网络与它拿着的模型凭据；
Agent 侧的扩展在引擎里（QuickJS 没有 I/O、限内存限时；它限的是资源，不是对恶意代码的隔离边界，信任来自签名与安装时的披露）。
界面一侧，商店的扩展包进隔离的 iframe，受信的才能进页面、与页面同级，这一点明说，并且产品可以整个关掉（§5.7、§5.8）。差别不在
「更安全」这个形容词上，在于每一处都标明了自己是哪一种。

**三、模型可见文本的处理。** 这一类攻击面在多数方案里没有专门位置：沙箱管执行，而一段进入系统提示词的文字既不越权
也不出网。引擎把它当作一等的披露对象，从安装里回出来；宿主的活是把它摆到人面前，而不是自己再算一遍（§4.7）。会话右栏常驻的上下文
页签与轨迹视图让人随时看到每一次调用实际带了什么（§5.5）。

**四、部署形态。** 以 Node 或容器为前提的宿主，安装物是一棵依赖树，冷启动以秒计，常驻内存以百兆计。Harnix 的后端
是一个二进制，预算写进 CI（§7.2）；体积上限按带载体的构建定，一个扩展包的常驻开销是它常驻 Store 的线性内存，模式 3 的扩展进程也还是这同一个二进制。
这条不是性能偏好，它决定了这个系统能不能装在一台边缘设备上。

值得从那些系统里继续借的，是它们对**分层配置**的处理（插件 → 打包 → profile → 覆盖层，让「换一个形态」变成一次
配置而不是一次 fork）。Harnix 的改造层次（§8）就是这条思路，加上一层编译进来的原生扩展。
