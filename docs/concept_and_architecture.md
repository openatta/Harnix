## 1. 定位

**Harnix 是 Agix 应用的公共底座。**

引擎负责「跑一个 agent 会话」：装配提示词、调模型、执行工具、管理上下文与历史。Harnix 负责把一台或
几台引擎变成一个**应用**：会话的持有与追赶、实例的组织、界面的外壳、身份与授权、部署形态，以及让
应用作者把自己的代码接进来的契约。一个应用（Helm、IPDrun，或者 Harnix 自己发布的空应用）是一个
二进制加一份编在里面的界面产物，由 `harnix::App::builder()` 加上应用自己的模块组成，不 fork、不留补丁。

这条分工是硬的，两个方向都是：

- **Harnix 不含任何引擎逻辑。** 会话怎么跑、工具怎么派发、上下文什么时候压缩，一律是 Agix 的事。
  缺的能力去给 Agix 提，不在这边补一个平行实现——一个平行实现意味着同一件事有两处真相，而它们会分叉。
- **Agix 不知道有界面、space、应用这回事。** 客户端面的协议、贡献点、身份、space，全部止步于 Harnix。

### 1.1 它不是什么

| 不是 | 因为 |
|---|---|
| 一个 agent 框架 | 框架是 Agix。Harnix 是它的宿主 |
| 一个多租户服务 | 一个进程服务一个用户（多个会话、多台设备、可以多台实例）。多租户是另一个系统，不是这个系统的配置项 |
| 一个「什么都能换」的内核 | 骨架不可插拔，见 §2.1 |
| 应用的功能仓库 | 应用独有的东西（领域服务、产品面板、批准策略）不进 Harnix，见 §1.3 |

### 1.2 三个目标，按优先级

1. **可定制。** 不 fork 就能做出一个形态不同的产品。这是首要目标，其余两条服务于它。
2. **可在边缘部署。** 一个后端二进制，无运行时依赖，冷启动以毫秒计，空载内存以十兆计。
3. **安全边界清楚。** 每一处约束要么是强制的，要么被明说成不是强制的。没有第三种。

0.4 落地它们的方式：应用以子仓引入 Harnix 和 Agix、用编译期模块装配（目标 1）；一个 Harnix 可以组织
多台互相隔离的实例，进程内的、独立 daemon 进程的都行（目标 1、2）；自带一个能看见一切的系统 space
（目标 3：看得见才谈得上清楚）；每个功能都对着真的二进制测（§8）。

### 1.3 什么进 Harnix：判据

> **只有在公开契约之上做不出来，或者做出来会破坏 Harnix 不变量的东西，才进 Harnix。**

满足下面任一条才进：

- 它要碰中枢、授权、传输、装配的内部（例如无头会话：要和客户端共用排队与 `seq`）；
- 应用各写一份会破坏一条不变量（例如会话与 space 的对应关系）；
- 它本身就是契约的一部分（模块 trait、贡献点、宿主 API）。

「第二个应用也会要」不够：那样几乎什么都能塞进来。其余的，即使两个应用都要，也先由应用在模块契约上
实现；等两份实现证明是同一个形状，再考虑收进来。Helm、IPDrun 的需求是**输入**，不是必须满足的清单。

背后是维护者定下的一条：**Harnix 自己保持薄、容易改造。** 一个什么都带的底座，每个应用都要先学会
关掉它不要的那些；一个薄的底座，应用只学它要的那些。内建的东西因此也都做成可以去掉的（§5.3 的三个
内建 space、§5.5 的系统 space、§5.7 的运行期界面模块都有开关）。

## 2. 设计原则

### 2.1 骨架不可插拔

Harnix 的骨架是四件事：**传输、授权、中枢、装配**。它们不是扩展点，没有替换入口。

理由和引擎把轮次循环的步骤顺序写死是同一个：**顺序与所有权本身就是定义**。一个能被插件换掉的会话
中枢等于没有中枢——追赶不变量一旦可以被第三方重写，「打开一个跑到一半的会话会看到什么」就不再有
答案，而这是产品最基本的动作。

骨架之上的每一个判断都可插拔。分界线画在「这件事的形状」和「这件事怎么做」之间。

**「不可插拔」约束的是语义，不是实现形式。** 传输承载什么、保证什么是写死的，用几条连接承载不是
（§3.3）；中枢的语义是写死的，它对面的实例在本进程里还是在另一个进程里不是（§3.1.1）。

### 2.2 插件只属于 Agix；模块不是插件

**插件装到 Agix，不装到 Harnix。** 包格式、取包、校验、缓存、manifest、能力声明、安装期披露、沙箱、
载体、生命周期——整件事都在引擎那边。Harnix 没有、也不会有自己的插件体系：一件事有两处真相，它们就会
分叉；而分叉之后往往只有一处是真正拦得住的，另一处是装饰。**「插件」这个词只指 Agix 的包。**

0.4 多了一种扩展的来源：**编译期模块**（`Module`）。它是应用作者链接进来的 Rust 源码，和内建模块
同级，不是包，所以不叫插件。三种来源各自的信任与能力：

| 来源 | 什么时候进来 | 谁写的 | 信任级 | 能加 space | 能加后端方法 |
|---|---|---|---|---|---|
| **编译期模块** | 应用构建时链接 | 应用作者本人 | 内核级 | 能 | 能，在 `app.<id>.*` 命名空间 |
| 运行期包 · Agent 段 | 安装时 | 第三方 | 插件级：能力门控 + 披露，引擎管 | — | 不能 |
| 运行期包 · `[[ui]]` 段 | 安装时 | 第三方 | 页面级（§5.7） | 不能 | 不能 |

一个包里可以有 Harnix 关心的一段（界面模块），但那不构成第二个体系——**一个包、一份 manifest、
一次安装、一次披露**。Harnix 只是多读一段引擎不关心的配置，然后把一个目录发出去。

#### 2.2.1 Harnix 不执行包里的任何东西

包里的界面模块是**浏览器**加载的静态资源，不是 Harnix 跑的代码。这一侧读一段配置、发一个目录，仅此
而已。

曾经有过一个例外：`[[host]]` 段里的**投影**，一个折叠会话事件流的纯函数，由 Harnix 执行。它没有能力
可谈，所以并没有引入第二个「扩展能做什么」的答案——但它让这条规则必须写成「Harnix 执行包里的代码，
但只执行那种什么都做不了的」，而**一条带例外的规则是会被人加宽的**。所以它被撤掉了：

> **Harnix 不执行包里的任何东西。**

编译期模块不受这条约束——它不是包里的东西，是应用本身。这条规则和「不给插件贡献 `harnix.*`
方法」（§10）一样，**对运行期包照旧成立**，0.4 没有推翻它们，只是写清了适用范围。

由 `crates/harnix/tests/layering.rs` 盯着：manifest 读取结构体只许有 `ui` 一个字段，整个 crate 树里
不许出现任何解释器。Agix 把载体的脚本引擎交出来了（`script_host::bindings::engine()`），宿主可以把自己
的扩展点绑到同一个载体上——**Harnix 有意不用**，用了就是第二个「扩展能做什么」的答案。

#### 2.2.2 这一节改过三次方向，原因写在这里

1. **第一版**把宿主侧和界面侧的贡献都算作 Harnix 的插件模型。
2. **第二版**全部撤掉，理由是插件体系是 Agix 的。这次撤销基于一个当时以为成立的前提：Agix 的插件
   体系在跑。后来发现出厂构建里它是关着的（脚本载体与 WASM 载体互斥，我们发脚本构建，于是
   `plugin.*` 一律 `PLUGINS_DISABLED`）。当时的选择是在 Agix 修，不是在 Harnix 另起一套；Agix 0.2.4
   把包方案与载体解耦（§4.5），出厂构建装得了包。
3. **第三版**（0.3）回到「包是 Agix 的，Harnix 读其中一段」。这中间短暂有过 `[[host]]` 投影，撤掉的
   理由见 §2.2.1。
4. **0.4** 加上编译期模块。应用要在 Harnix 上做产品，就要能加后端方法、space、原生工具，这些运行期包
   给不了，也不该给（给出能力就是在 Harnix 长出第二个能力模型）。答案不是放宽包，而是**另开一种出身**：
   应用作者本人的源码，信任级与内核相同，编译期链接，没有运行期加载。插件这个词因此只留给 Agix 的包。

写下来是因为 §2.5：一份反复改过又没说为什么的设计，读的人无从判断哪一版是当前的。

### 2.3 信任按出身定，不按声明定

一个来自外面的扩展要撒谎，撒的正是「我需要什么」这种声明。所以级别由它**从哪儿来**决定：应用作者
编进来的模块、运维本人写在项目里的东西、装上的插件、远端连上来的设备，天然不同级。声明的作用是在已定
的级别内**进一步收窄**，不是用来晋级的。

### 2.4 失败的扩展只让它自己那份贡献消失

抛异常、超时、配额耗尽、答出一个用不了的形状——这个点保持原样，别的什么都不受影响。每个适配器先把
改动完整算出来再施加，所以不存在「施加了一半」的状态。

这条对每一种出身都成立：

- 一条界面贡献渲染出错，只有它消失；形状不对或 id 重复，这一条被拒，记进诊断。
- 一个包的界面模块照旧版贡献点 API 写的，**那一条**报「不生效」，包的其余部分照常（§5.7）。
- 一个编译期模块注册冲突、`migrate` 或 `start` 失败，只停用这个模块和它的方法、主题、路由、space、
  实例，进诊断页；别的模块照常启动。

而且**「它什么也没做」是可查询的**：哪个点、谁、什么原因，都记下来并且能问（`harnix.diagnostics`、
设置与系统 space 的诊断）。否则「我的插件为什么不工作」只能靠猜。

### 2.5 每一条承诺都可检查

贡献点目录由代码生成；层与层之间的依赖方向由测试断言而不是由文档描述；性能预算进 CI 门禁；内建界面
走的就是公开的那批贡献点，而且有测试盯着「外壳真的去问了」；功能覆盖表由用例标签生成，一行在某一层是
零就失败。**一份没人检查的承诺，下一次改动就变成谎话。**

## 3. 内核

骨架是四件事：装配、中枢、传输、授权（§2.1）。先看它们管着的东西。

**运行时四层。** Harnix 里一切和 Agent 有关的东西都落在这四层之一：

```text
Harnix 进程
 ├─ 实例 system           （进程内）  ← 隔离单位：数据根、设置、provider、MCP、插件、场景
 │   ├─ 会话 a            ← 一条轮次循环；同一时刻至多一轮
 │   │   ├─ 任务：子 Agent "explore"     ← 属于会话，跟着会话的权限、项目根、生命周期
 │   │   ├─ 任务：后台 Bash `npm run dev`
 │   │   └─ 任务：定时任务 0 9 * * *
 │   └─ 会话 b
 ├─ 实例 helm-l1          （进程内，Helm 的模块按自己的模板建的）
 └─ 实例 ci-runner        （daemon，本机另一个进程）
```

| 层 | 是什么 | 拥有什么 | 隔离到什么程度 | 谁建 | 身份 |
|---|---|---|---|---|---|
| **Harnix 进程** | 一个二进制，一个用户 | 中枢、授权、传输、实例登记表、账本 | — | 运维 | — |
| **实例** | 一台 Agix 引擎，一个会话池 | 数据根（设置三层、transcript、记忆、技能、录像）、provider 路由与凭据、MCP 连接、插件、场景、原生扩展 | **彼此完全隔离**。daemon 载体还隔离了崩溃和资源 | profile 声明；模块、界面按模板建 | `instance` |
| **会话** | 实例里的一条轮次循环 | transcript、场景（创建时定，决定工具集）、项目根、模型、权限规则 | 共享所属实例的配置；彼此的上下文互不可见 | 客户端、模块（无头）、模型（子 Agent 的侧链） | `(instance, session)` |
| **任务** | 属于某个会话、在会话之外继续跑的工作 | 子 Agent、团队成员、执行中的 Shell 与监视器、定时任务 | 跟着所属会话：同一套权限、项目根；会话删了，任务一起没 | 会话里的模型（经工具） | `(instance, session, task)` |

由这张表直接推出来的规则：

- **隔离只在实例这一层承诺。** 要两套互不相干的配置（不同的 MCP、凭据、场景），就建两台实例，不在
  一台实例里靠会话区分。进程内实例的隔离由 Agix 承诺（同一进程里的几台会话池互不可见，有守护测试；
  唯一共享的是 OTel 导出器）。
- **任务是 Agix 的东西，Harnix 只看、只转发停止。** 子 Agent 的侧链在 Agix 里也是一个会话，在 Harnix
  里它是父会话的任务，不出现在会话列表的顶层，不进中枢的键，不进账本。
- **会话不跨实例，也不跨 space。** 要跨就用 `@session` 引用或分叉（§5.4）。
- **轮不一定由 Harnix 发起。** 定时任务会让一个会话自己开始一轮。实例在 `daemon.event` 上报每一轮的
  开始与结束（带 `initiator`），中枢据此知道，不假定「我没发起的轮就不存在」。

**结构。** 相对 0.3 变了三处：装配拆成实例层与应用装配两层（§3.1）；中枢下面不再是「一个引擎」，而是
一张实例登记表，中枢只认 `EngineLink`（§3.1.1）；内建功能全部改成内建模块。

```text
 浏览器（同一份产物；Tauri 只是装它的窗口）
 ┌──────────────────────────────────────────────────────────────────┐
 │ @harnix/shell  外壳：固定外框、space 切换、设置；内建 space（会话 / 项目 / 系统）│
 │ 应用的 space    应用自己的 React 组件，只依赖 @harnix/react              │
 │ @harnix/react  贡献注册表、useNest()、i18n、令牌；对话组件 ChatPanel 等     │
 │ @harnix/core   不依赖框架：协议类型（生成）、协议客户端、会话状态            │
 └──────────────────────────────┬───────────────────────────────────┘
                                │ 五种通道语义（拓扑可选）· /apps/<id>/ 自有链接
 ┌──────────────────────────────▼───────────────────────────────────┐
 │ harnix 进程（应用的二进制 = App::builder() + 模块）                      │
 │  传输 harnix-transport  通道、TLS、静态面、模块路由、启动链接              │
 │  授权 harnix-authz      唯一准入点：主体 × 方法 / 路由，默认拒绝            │
 │  中枢 harnix-hub        会话持有者：订阅、缓冲、turn、队列；两类调用方      │
 │  实例 harnix-instance   模板、两种载体，一个 EngineLink                   │
 │  模块 harnix-module     编译期模块契约、注册表、贡献点目录                  │
 │  装配 harnix-app        App::builder()、profile、启动顺序、诊断            │
 └────────────┬──────────────────────────────┬──────────────────────┘
              │ 进程内调用                     │ JSON-RPC（unix socket / 回环 ws）
      ┌───────▼────────┐             ┌───────▼──────────────────┐
      │ Agix 实例       │  ……         │ Agix daemon 进程          │ ……
      │（作为库链接）    │             │（由 Harnix spawn 或 attach）│
      └────────────────┘             └──────────────────────────┘
```

依赖是单向的，每一层不认识它上面那层的概念，由 `crates/harnix/tests/layering.rs` 断言：

| 层 | 不许知道 |
|---|---|
| 传输 | 会话、实例是什么 |
| 授权 | 帧长什么样、走的哪条通道、实例在哪 |
| 中枢 | HTTP、TLS、连接、拓扑、**实例的载体** |
| 实例层 | 客户端面协议、space、模块 |
| 模块契约 | 中枢、`EngineLink` |
| 协议类型（`harnix-contract`） | 任何一层 |

内建功能（工作区、文件、搜索、设置、插件包、设备、系统 space、录像）全部是**内建模块**，只走公开的
模块 API，同一个测试盯着。如果内建的东西不能用公开契约写出来，这份契约就不值得相信。

### 3.1 装配：应用装配与实例层

装配拆成两层：**应用装配**（`harnix-app`：这个进程由哪些模块组成、按什么顺序起来）和**实例层**
（`harnix-instance`：怎么建或连上一台引擎）。

装配是**声明式的**，并且在启动时定：

> **装配在启动时定：有哪些模块、哪些模板、哪些载体。运行期能新建的只有会话，以及模板允许的实例。
> 模板本身不能在运行期新增或改写。**

0.3 的原则是「运行期没有东西能改写装配」，0.4 允许运行期建实例，字面上冲突。原则的本意是「运行期没有
东西能决定这个进程是什么」，修订后的写法保住了它：运行期建出来的每台实例，在启动时就已经能被枚举
（模板 × 允许的参数）。

启动顺序：

1. 读 profile。
2. **注册**：按顺序调每个模块的 `manifest` 与各注册函数。模块 API 版本不符**编译不过**；id、方法、路由
   冲突时后注册的那个停用。
3. **迁移**：按顺序调 `migrate`，失败只停用这个模块。
4. **建实例**：`system`（带上仍启用的模块给它的原生贡献）、profile 的 `[[instances]]`、账本里按模板建过的。
5. **启动**：按顺序调 `start`，失败只停用这个模块和它的一切；它已经交给 `system` 的场景摘不掉，留到下次
   启动，诊断页写明。
6. 开始服务。

引擎的根**显式传进去**，不改本进程的环境变量：那样一个进程才可能服务几台实例，状态也不会藏在调用者
看不见的地方。

#### 3.1.1 实例层：载体、模板、EngineLink

**实例只从声明来**：profile 里声明的固定实例，或者按模板建的。

| | 进程内 | daemon |
|---|---|---|
| 是什么 | Agix 的会话池建在本进程里 | 本机另一个 Agix daemon 进程，经 JSON-RPC（unix socket 优先，其次回环 ws） |
| 怎么来 | Harnix 建 | **spawn**：Harnix 起子进程并做最小看护（等它开始监听；stdin 一断它就退出，所以随 Harnix 退出；退出了就重启，连续几次刚起来就退出则不再重启——重启循环只会掩盖问题），默认起本二进制的 `harnix daemon`，版本按构造就对得上；**attach**：连一台只给这个 Harnix 用的 daemon |
| 原生 Rust 贡献 | 能：场景、原生工具、`SessionCustomizer`、凭据源 | 不能，只有那个 daemon 自己的配置与插件 |
| 隔离 | 状态隔离；崩溃与资源共用进程 | 状态、崩溃、资源都隔离；断了是「实例降级」，不是 Harnix 挂掉 |
| 版本 | 必然是这次构建链接的那版 Agix | 握手比对协议版本，不匹配就拒绝并说清楚 |

**模板**（`InstanceTemplate`）是建实例的规格：载体、场景、数据根规则、允许调用方填的参数、能不能由
界面用（`ui`）、最多几台。profile 里的模板只能是 spawn 或 attach（profile 拿不出原生贡献）；模块在
`templates()` 里声明的进程内模板可以带原生贡献。**界面永远给不出二进制路径、命令行参数、环境变量、
模型端点**——那些等于「装载子进程、改写模型端点」，不对设备开放（§3.4）。

每台实例有**拥有者**：`kernel`（profile 声明的）、`module:<id>`、`space:<id>`（界面建的，归发起时的前台
space）。账本记按模板建的实例；**重启后一律由 Harnix 按账本重建**：模板还在、拥有者启用着就照建；
否则这台实例显示为 `Down` 并写明原因，数据根不动。模块停用时，它拥有的实例和它的模板建出的实例一起停。
删除实例删的是登记，数据根默认保留。

**中枢与实例之间只有一个接口：`EngineLink`。** 一次调用、全部异步帧、一个屏障标记（中枢结算一轮前
在已收到的帧后面放一个标记，等它从事件流里出来——等的是「已经路由」，不只是「已经收到」，否则
`turn_settled` 会超车本轮最后的事件）、链接状态（`Starting / Ready / Degraded / Down`）。三种实现：
进程内、daemon、`DownLink`（建不起来的实例）。中枢的代码里不出现「是不是远程」的分支。

**`EngineLink` 不对模块开放。** 模块拿到的是只读的 `InstanceHandle`，所有会话调用仍然经过中枢和授权。
模块要是能直接对一台实例发 `session.run_turn`，「中枢先订阅」这条不变量就有了旁路。

**daemon 的语义。** daemon 对一条通过认证的连接完全信任，没有逐方法授权。所以：

- **一台 daemon 只服务一个 Harnix。** spawn 的天然如此：它的 unix socket 放在只有本用户能打开的私有
  目录里；attach 的由运维保证。中枢的排队、结算、「先答者生效」都假定它是这台 daemon 上会话的唯一调用方。
- **daemon 的凭据不出 Harnix**：经回环 TCP attach 时要的 token 在 profile 里只写凭据名，值由凭据源给，
  不发给任何客户端。
- 透传白名单对每台实例都一样，`config.setProvider`、`mcp.addServer` 这些对 daemon 实例同样拒绝。
- **断线**：实例变成 `Degraded`，daemon 那边的轮照跑。中枢重连后对每个在观看的会话重建缓冲，再推
  `harnix.session_resync`，客户端照刷新那条路重新 attach；这期间的发送进队列，不拒绝。daemon 丢订阅
  （`subscription_dropped`）走同一条路。这是中枢本来就有的恢复路径，不是新语义。

### 3.2 中枢

中枢是会话的持有者。它的存在理由是一条不变量：

> **中枢永远比任何客户端先订阅。**

会话第一次被打开时中枢立刻订阅并开始缓冲，此后任何观看者的追赶**只在中枢的缓冲区里进行**。由此得到：

1. **刷新页面不丢内容。** 一轮跑到一半刷新，前半段在缓冲里，不依赖引擎补发。
2. **turn 不挂在连接上。** 关掉标签页、切换设备、断网重连都不影响这一轮，最终结果广播给所有观看者。
3. **多设备一致。** 同一个会话可以被几个客户端同时看，任何一个都能回答权限提问，先答者生效。
4. **排队是产品行为，不是错误。** 引擎对同一会话同时刻只允许一个 turn；有 turn 在跑时新消息进中枢的
   队列，上一轮结束后自动发出，队列可撤销，整值快照推给所有客户端。

**turn 由中枢发起，调用方有两类：客户端和服务端（内核、模块），语义相同**——排队、中断、结算、广播
都一样。服务端调用方经 `ModuleContext.sessions` 建、开、发、中断、关闭会话（**无头会话**），用
`OnBusy { Queue, Reject, Interrupt, Steer }` 说忙的时候怎么办；客户端的 `harnix.send` 和服务端的发送走
同一条路径。无头会话照样出现在它所属 space 的会话列表里，界面随时可以 attach 旁观。

0.3 写的是「turn 由客户端发起」。0.4 改成两类调用方，因为无头会话必须和客户端共用排队与 `seq`——
在中枢之外另做一份，就是第二份会话状态。

**tap** 是服务端的观看者，和客户端观看者同一套语义，不是一条特殊的无损通道：有界、按 `seq` 投递、
**不在中枢的锁里等待**；满了就标成落后，它下一次读到 `Lagged { last_seq }`，按客户端追赶那条路补齐。
**中枢永远不会因为一个慢的 tap 卡住会话。**

**推送一律整值。** 队列、会话列表、实例树、引擎健康这类状态推的是完整快照，客户端不做增量合并——增量
合并的错误只在特定顺序下出现，而那个顺序在测试里不容易造出来。宿主主题可以**带参数订阅**，值在有人
订阅时才算，短时间内的多次变化合成一次：

| 主题 | 参数 | 内容 |
|---|---|---|
| `harnix.instances` | — | 实例登记表：载体、模板、拥有者、链接状态、版本、会话数 |
| `harnix.instances.sessions` | `instance` | 这台实例的顶层会话 |
| `harnix.sessions.tasks` | `instance`、`session_id` | 这个会话的任务 |
| `harnix.sessions.status` | — | 所有会话的运行状态 |
| `app.<id>.<主题>` | 模块声明 | 模块推的整值快照 |

中枢的状态与语义**不可替换**（§2.1）。

#### 3.2.1 往对话里写东西：扩展条目

模块可以往会话时间线写**扩展条目**（例如「采集任务跑完，推一张任务卡」）：走 Agix 的扩展条目
（`session.appendEntry` / `session.entries`），由 `flow.block` 画出来。条目进入会话日志，刷新、重放、
分叉都看得到；**只给人看，不给模型看**；命名空间由中枢定为 `app.<模块 id>`，模块自己说不了算。
Harnix 不另存一份会话状态。

### 3.3 传输

传输是**一组通道语义**，不是一种连接拓扑。**语义写死，拓扑可选。**

理由很具体：不同的部署对连接的诉求不一样。边缘弱网下少开一条连接是省下的重连与心跳；放在反向代理后面
时，让请求走普通 HTTP 能直接吃到现成的中间件；一个只想看进度的只读客户端不该被迫开一条能发请求的
双向连接。**这些差异不该逼着中枢换一套语义。**

#### 3.3.1 五种通道语义

| 语义 | 干什么 | 谁发起 |
|---|---|---|
| **unary** | 一次请求一次应答的方法调用 | 客户端 |
| **会话事件流** | 某个会话的事件：流式正文、工具行、权限提问、子 Agent、扩展条目 | 服务端 |
| **宿主事件流** | 与具体会话无关的主题：实例树、会话状态、队列、模块主题 | 服务端 |
| **带外应答** | 对服务端发起的提问的回答（权限、澄清） | 客户端 |
| **大负载旁路** | 附件上传、导出下载 | 双向 |

会话事件与宿主事件从语义上就是两个订阅面：一个只看侧栏的客户端不该为了知道「哪个会话在跑」而接收所有
会话的正文。带外应答单列，是因为它在只下行的事件流拓扑里没有回程可用。

#### 3.3.2 三种参考拓扑

| 拓扑 | 映射 | 适合 |
|---|---|---|
| **单双向流** | 一条双向连接承载全部（大负载仍走旁路） | 单机、边缘弱网 |
| **分离流** | unary 与带外应答走 HTTP；两种事件流各一条只下行流 | 反向代理后面、多客户端、只读客户端 |
| **纯请求** | 只有 unary 与旁路，事件靠长轮询补上 | 脚本客户端、受限网络 |

三种拓扑的方法名、参数、错误码、事件形状完全一致。服务端配置支持哪几种，客户端在握手时选一种；不匹配
就拒绝并说清原因，不做静默降级。

#### 3.3.3 跨拓扑的不变量

拓扑可选，但下面这些在任何拓扑下都成立，它们是传输真正写死的部分：

1. **`seq` 是唯一的追赶锚。** 每条会话事件带 `(instance, session_id, seq, turn_id)`，`seq` 由**中枢**
   按会话分配，与连接、载体都无关。
2. **一次握手，一次协商。** 协议版本、贡献点 API 版本、拓扑、能力位在握手里一次谈完；后开的通道携带
   握手换来的凭据，不各自再谈。
3. **权限提问的语义与通道无关。** 广播给所有观看者，任一可答，先答者生效，第二个回答是静默成功。
4. **大负载永远走旁路。** 一次性凭据换 URL，落盘后以路径引用。
5. **中枢与授权不感知拓扑。** 加一种拓扑不会改动这两层——**如果改动了，说明语义被拓扑污染了，那是要修的**。
   `layering.rs` 断言这两层的源码里叫不出拓扑、连接、HTTP 的类型。

#### 3.3.4 只提供 RPC 的形态

传输可以不提供任何静态资源（`--headless`）。界面在别处，或者根本没有界面（§5.1、§7.1）。

#### 3.3.5 模块自有链接

一个模块的前后端之间可以有自己的 HTTP 路由与 WebSocket，挂在 `/apps/<id>/` 下，由
Harnix 的传输层发出，与界面**同源**，准入走同一套（同一份凭据、按「主体 × 模块路由」判定、默认拒绝、有
审计）。前端经宿主 API 的 `space(id).fetch()` / `.socket()` 用它，模块代码不自己拼地址。它承载 Harnix
通道不适合的东西，代价是**不享受**拓扑无关和 `seq` 追赶这些保证——要这些保证，就用上面五种语义。

前后端之间用哪条：一问一答用 unary 调 `app.<id>.*`；状态更新用宿主主题推整值快照；长任务返回任务 id，
进度作为带参数的主题；大文件走旁路；剩下的才用自有链接。**不为模块加新的通道语义。**

### 3.4 授权

**这个进程只有一个准入点。** 加一个方法，默认是拒绝。

主体有三类：**内核**（这个二进制自己）、**模块**（`Module(id)`，一个编译期模块）、**设备**（配对过的
客户端，或本机带令牌的页面，代表一个人）。每个方法、每条模块路由声明给哪类主体用，进授权表。装上的
**插件不是这里的主体**——它跑在引擎里，受引擎的能力门控约束，够不到这个进程的方法面；在这一层再放一个
「插件」主体，就是第二处决定扩展能做什么的地方。

单用户系统里「这个人能不能做」的答案几乎总是「能」，所以这一层真正在守的是：

- **引擎那些等价于接管进程的方法一个都不出去。** 改凭据、装载子进程、改写模型端点的方法，永远不出现在
  任何设备的可用集里——不是「未实现」，是明确拒绝，并且错误里写清原因。中枢独占的方法
  （`session.run_turn`、`session.subscribe`）同样拒绝，模块也不能 grant。
- **设备建实例只能按模板。** 模板集合在启动时定死，设备只能选模板、填模板放开的参数（§3.1.1）。
- **加一个方法默认是拒绝。** 设备能调到的引擎方法是一张透传白名单。

授权发生在**方法这一层**，不在连接那一层——多通道拓扑里同一个主体可能有好几条连接，把授权挂在连接上
会得到几份可能不一致的答案。`harnix.reachable` 告诉调用方它能调什么，界面据此决定画什么。

## 4. 扩展模型

### 4.1 编译期模块

一个模块实现 `Module` trait，应用在 `main.rs` 里显式列出，**顺序就是注册、迁移、启动的顺序**：

```rust
fn main() -> anyhow::Result<()> {
    harnix::App::builder()
        .profile_from_args()
        .with_builtins()
        .module(helm_home::Module::default())
        .run()
}
```

一个模块可以贡献：给 `system` 实例的原生贡献（`engine()`）、自己的实例模板（`templates()`）、后端侧的
space 声明（`spaces()`：默认实例、场景）、`app.<id>.*` 方法（带 schema 与主体声明）、宿主主题、
`/apps/<id>/` 路由，以及 `migrate` / `start` / `stop`。完整的接口见 [SDK 参考](harnix-sdk-reference.md)。

**原生贡献只有两条路**：给 `system` 的走 `engine()`，给自己实例的走进程内模板带的 `EngineContrib`。多个
模块的 `SessionCustomizer` 由 Harnix 按注册顺序组合，Agix 不用改。

`ModuleContext` 给模块：自己的配置段（profile 的 `[modules.<id>]`，密钥只写引用，值由凭据源提供）、自己
的数据目录、凭据、发布主题、以 `Module(<id>)` 身份调方法（和设备走同一个准入点）、服务端会话（§3.2）、
按自己的模板建实例。**拿不到中枢的内部状态，也拿不到 `EngineLink`。**

迁移：Harnix 只管**什么时候迁、失败了怎么办**（按顺序、失败只停用这个模块），不管**用什么迁**。数据库
选型、迁移工具都由模块自己定；Harnix 自己的账本与模块数据分开。

两个版本号各由拥有它的一侧检查：**模块 API 版本**在编译期检查，不匹配编译不过（模块是源码，错配在
运行期才发现没有任何好处）；**贡献点 API 版本**在握手与读包时检查（§5.7）。0.4.z 内协议与模块 API
只做加法。

### 4.2 运行期包：一个包，装到引擎里；Harnix 只收文件

一个插件是一个 Agix 插件，装的地方也是 Agix（以 Agix 的 `extending_wasm.md`、`extending_quickjs.md`、
`extension_points.md` 为准）。Harnix 不定义包格式、不校验、不解包、不判定能力。它做两件事：

1. **把文件送过去。** `plugin.install` 自己去取 URL，**没有上传通道**——这是引擎的选择，它在包已经躺在
   跑引擎那台机器上时完全够用；而当包在使用者的笔记本上、引擎在另一台机器上时，就没有路可走。那一步是
   宿主的活：`harnix.plugins.upload` 换一个一次性 URL（大负载旁路），`harnix.plugins.install` 把落盘路径
   交给引擎。
2. **读包里引擎不关心的那一段**——`[[ui]]`（§5.7）。**包在哪由引擎说**：`plugin.list` 的条目带 `root`，
   Harnix 只读那下面的 `plugin.toml`，自己不拼任何路径，引擎的缓存布局因此仍然是引擎的。

**生命周期走 `harnix.plugins.*`，引擎自己那几个名字不开。** 装、卸、启、停都是引擎干的活，这一层不加判断
也不发明参数；它加的是后面那一步：任何改变「装了什么」的调用之后重读一遍，因为 Harnix 在服务每个包的
`ui/` 目录、并对外公布贡献集合。直接透传 `plugin.disable` 的后果是包停了而它的界面模块还在被服务，且没有
任何一侧会发现。

### 4.3 披露在装完之后，因为引擎是那个顺序

引擎装完才回 `disclosure`（这个包会往模型上下文里塞的文本）。
界面上就是：装好了，这是它会放到模型面前的东西，留还是删。想在装之前看，就得在这一侧读包，而那正是这一节
要避免的事。**沙箱管得住插件执行什么，管不住它说什么**，所以模型可见文本必须被人看见。界面贡献占了哪些点
是 Harnix 知道的，安装完的那一屏把两半拼起来，否则用户看到的披露是不全的。

### 4.4 装插件是这个人自己的决定

`harnix.plugins.*` 对设备开放：一个进程服务一个用户，设备就是这个人本人。
真正的强制边界在引擎：能力门控、沙箱、它自己回的那份披露。`mcp.addServer` 保持拒绝，差别正在这里：它配出来
的是一个能起子进程的工具，没有 manifest、没有能力声明、没有任何披露。

### 4.5 一个构建只带一种载体，包方案不跟着走

引擎带一种扩展载体或一种都不带（脚本与 WASM 在上游互斥：两个解释器是两倍的攻击面）。
互斥的理由只对载体成立，对包方案不成立——读 manifest、校验、解包、披露、启停不需要任何运行时。Agix 0.2.4
起两者分开，出厂的二进制能装包。一个不带包方案的构建仍然合法，所以 `PLUGINS_DISABLED` **如实透传，不包装
成「没有已安装的插件」**：「这个构建里没有插件子系统」和「一个都没装」是两件事。

### 4.6 不进 Harnix、由应用自己做的

按 §1.3，下面这些应用在模块契约上就做得出来，不进 Harnix。做法写在[二开指南](harnix-sdk.md)：

- **批准**（「这个业务动作要不要人确认」）：只许设备调的 `app.<id>.*` 方法收回答、带参数的主题推待批事项、
  扩展条目记下决定、`flow.block` 画卡片。引擎权限管「这个工具能不能跑」，批准管「这个业务动作要不要人
  确认」，后者的策略本来就归应用。
- **MCP 服务端与角色令牌**：在那之前应用要给外部 Agent 开 MCP，就在自己的模块里起自己的监听，它不在
  Harnix 的授权与保证之内，由应用负责。
- **非 Rust 的 sidecar 服务**：走 Agix 的 MCP，或经模块路由转发。

## 5. 界面

### 5.1 界面在二进制里，可以被换掉

**安装物是一个文件。** 界面编译在里面，所以不存在「页面和后端对不上」这种状态。

| 形态 | 怎么来 | 用在哪 |
|---|---|---|
| 内嵌（默认） | 编译进二进制 | 单机、边缘节点。装一样东西 |
| `--ui-dir <目录>` / `[ui] dir` | 从磁盘读，整套替换 | 做另一个产品；开发前端时改完刷新 |
| `--headless` | 一张都不发 | 纯 RPC 节点 |
| `ui export <目录>` | 把内嵌的那份写出来 | 让 CDN 或代理去发。仍然只有一个安装物 |

**这一节改过一次方向。** 原来是「后端不含界面，界面是独立产物」，最硬的论据是插件的界面模块要在运行期
import 进来——而那件事由引擎的插件目录提供，不需要界面本身是分离的。编进去对二进制大小几乎没有影响。
换一整套界面仍然是一个参数，不是一次重编译。

没有界面产物就直接 `cargo build` 会**明确失败并说该跑什么**，不悄悄嵌一份空界面。

#### 5.1.1 版本协商仍然要，使用者变了

界面在握手时声明协议版本、贡献点 API 版本与拓扑，后端回自己支持的；不匹配就拒绝并说清哪一边旧了，**不做
静默降级**——一个半兼容的界面产生的 bug 报告是无法处理的。

内嵌之后，内建界面不可能对不上，所以协商的使用者只剩两个：`--ui-dir` 换进来的那一套，以及**包带的界面
模块**——后者在读包时逐条比对（§5.7）。界面**不假定拓扑**：它拿到的是一个客户端库，库把五种通道语义映射到
握手谈定的那种拓扑上。

### 5.2 技术栈与包

**React + TypeScript + Vite + Zustand，定死。** 用的人最多、后续好维护；Agent 类界面的生态基本都是 React 的；
IPDrun 已经有能对着 Harnix 协议跑的 React 对话组件，直接回流成了对话主干（`ChatPanel`）。代价是旧的原生 JS
界面整个换掉，以及运行期包的 v1 界面模块不再生效（§5.7）。

只分 4 个包，边界只画在「谁依赖谁」真正不同的地方：

| 包 | 依赖框架吗 | 职责 |
|---|---|---|
| `@harnix/core` | 否 | `/protocol`（从 `harnix-contract` 用 `ts-rs` **生成**的类型，漂移就失败）、`/client`（握手、拓扑与回退、追赶）、`/state`（会话事件归约、实例树、每个 space 的当前会话） |
| `@harnix/react` | React | 贡献注册表、`useNest()`、i18n、令牌、图标；对话组件。**应用写 space 界面只依赖它** |
| `@harnix/shell` | React | 外框、space 切换、设置、内建 space。应用的入口，不被 import |
| `@harnix/testkit` | 否 | LIVE 测试的启动器、API 客户端、Playwright 夹具 |

框架只出现在 `@harnix/react` 及以上；`@harnix/core` 与后端一一对应（`/protocol` ↔ `harnix-contract`，
`/client` ↔ 传输，`/state` ↔ 中枢推的帧与快照），换框架也不动它。**内建 space 只用公开 API**：外壳里画
内建 space 的代码只许 import `@harnix/react`、`@harnix/core` 的公开导出——和后端「内建模块只用公开模块
API」是同一条。

应用的界面入口由构建脚本生成成一个虚拟模块，和外壳一起由 Vite 打成一份产物，顺序与 `main.rs` 里的模块
顺序一致。

### 5.3 外壳的框架

**固定外框，加上 space。** 外框里固定的只有：

- 左栏顶上：品牌（`[brand]` 的图标和名字）、新建对话、搜索；
- 左栏底下：系统 space 的入口（保留它时）和**头像**。头像就是设置入口，外圈颜色表示连接状态
  （已连 / 重连 / 断开），悬停说连到了哪。

其余都由 space 给。**一个 space 是三栏合在一起**：

| 栏 | 由什么给 | 不给时 |
|---|---|---|
| 左栏中段 | `sidebar()`：这个 space 的条目 | 这个 space 的会话列表 |
| 中区 | `center`：`chat`（默认）/ `minimized`（对话收成底部一条，可展开）/ `hidden`（用 `overview()` 画自己的视图） | 对话 |
| 右栏 | `tabs`：一组页签，**可以是当前选中项的函数**，每次绘制时读 | 只有详情抽屉 |

左右两栏都能拖宽并记在本地；窄屏时先把左栏收成图标栏，再把两侧都变成抽屉。

**Harnix 内建三个 space，都只是示例和默认值**，产品用 profile 的 `[shell] spaces` 选留哪几个（默认三个都留）：

| space | 左 | 中 | 右 | 后端 |
|---|---|---|---|---|
| **会话** | 全部会话，按时间分组（`sidebar.group`，应用可以换），带搜索 | 对话 | 详情 | 后端的 `sessions` space |
| **项目** | 一棵树：项目（工作区）一次只展开一个，它的会话挂在下面 | 对话；新建的会话跑在展开的项目里 | 详情 | **同一个**后端 `sessions` space（`SpaceContribution.sessions = "sessions"`） |
| **系统** | 实例列表 | 控制台（`center: "hidden"`），不持有对话 | 选中项的检查器 | 后端的 `system` space（§5.5） |

去掉一个 space，它的入口就不注册；去掉「会话」，剩下的第一个成为默认；去掉「系统」，底部的入口和它的方法
一起没了。

**项目 space 是界面上的一个视图，不是第二个会话集合。** 「按时间看」和「按项目看」是同一批会话的两种
排法；如果它们是两个后端 space，同一个会话就得属于两个 space，而会话按 space 绑定是不变量（§5.4）。所以
界面 space 可以用 `sessions` 指向另一个后端 space：两个界面视图，一个后端归属。

**新建对话的空页**：问候、这个 space 的建议，下面是 `home.card` 的卡片。

这一节在 0.4 里改过一次。M5 的内建 space 是「会话」「HOME」「系统」：HOME 是一个仪表盘（问候、问一句、
卡片网格），对话最小化在底部；系统 space 的中区是选中会话的对话；开关是 `[system_space] enabled`。M8 照
维护者的框架设计改成上面这样，理由：

- **外框只留真正每个产品都要的东西，其余都可去掉。** HOME 的问候、问一句、卡片，和新对话的空页是同一件
  事的两个入口；把卡片放到新对话的输入框下面，HOME 就不需要是一个 space 了。`home.card` 这个点保留。
- **系统 space 是看进程的，不是又一个聊天的地方。** 它的中区换成控制台；要在会话里继续说话，就「到所属
  space 打开」。这也让它不再需要自己的会话。
- **一个开关管一个内建 space 不够。** 换成 `[shell] spaces` 一张表，三个内建 space 同等对待。旧的
  `[system_space]` 段已不认识——profile 每一段都拒绝未知键，写了会启动失败并说哪一行，而不是被悄悄忽略。

### 5.4 Space 模型

**space = 左栏 + 中区 + 右栏，一起注册，所以「成对」是原子的。** 一个 space 有三个**部分**，可以任意组合：

| 部分 | 在哪执行 | 来源 |
|---|---|---|
| 前端 | 浏览器 | 编译期（打进应用的界面产物）。运行期包只能给已有的贡献点做贡献，不能新增 space |
| 后端 | Harnix 进程内 | **只有编译期**：一个模块 |
| Agent | Agix 实例里 | 原生 Rust（模块的 `engine()` 或模板）或运行期 Agix 插件包 |

只有前端与 Agent 部分的 space 不用在后端声明，取默认（`system` 实例、实例的默认场景）。

**会话规则：**

| 规则 | 内容 |
|---|---|
| 绑定 | 一个会话在创建时绑定一个 space 和一台实例，**不能挪**；要跨 space 延续，用 `@session` 引用（被引用会话说过的话作为附件交给这一轮——复制的是话，不是会话）或分叉 |
| 多会话 | 一个 space 可以有多个会话，可以分布在它能用的几台实例上 |
| 默认实例 | space 声明 `instance = "system"`（默认）、一台固定实例，或 `"template:<id>"`（第一次在这个 space 里建会话时按模板建一台，之后复用，归这个 space）。这就是「一个 space 要一台自己的、隔离的 Agent」的写法 |
| 切换 | 离开一个 space 时记住它当前的会话，切回来时恢复；那个会话没了就退到这个 space 的列表，**不退到别的 space 的会话** |

**硬理由**：Agix 的会话在创建时就定了场景，场景决定工具集。不同 space 的工具不同，它们的会话本来就不能
共用。所以按 space 绑定不是界面偏好，是引擎语义的直接结果。绑定是 Harnix 自己的账本数据（引擎不知道 space）。

**前台 space 与它的会话：对应关系不能错。** 哪个 space 在前台，中区、输入框、右栏看到和操作的就只能是这个
space 自己的会话。这件事错一次就是把消息发进了别的产品面、别的实例、别的工具集，所以它是不变量：

1. **前端没有全局的「当前会话」。** 状态里记的是「每个 space 的当前会话」，切换 space 就是切换取哪一项。
2. **会话总是带着实例一起出现。** 草稿、滚动位置、权限卡、队列的键都是 `(instance, session)`。
3. **服务端也核对。** 会话调用带上调用方声称的 `space`，中枢对着账本核对，不属于就拒绝
   （`SPACE_MISMATCH`，错误里写明它属于哪个 space）。**系统 space 是唯一的例外**，它可以观看、操作任何 space
   的会话，每一次跨 space 的操作都写审计。
4. **新建会话的去向只看前台 space。** 不存在「先建再挪」。
5. **在系统 space 里看别的 space 的会话是「观看」**，不改变归属，也不改写那个 space 记住的当前会话。

第 3 条是**防误，不是安全边界**：space 是调用方自己声称的，同页的任何代码都能声称任何 space，包括 `system`（§6.2）。

### 5.5 系统 space

开发调测用的基础面：**按四层（§3）看到这个 Harnix 管着的一切，并且能操作。** 它是内建模块，只用公开 API，
没有私有通道——这也让它成了「space 模型真能承载复杂面板」的第一个内建证明。

| 栏 | 是什么 |
|---|---|
| 左 | 实例列表：状态点（Ready / Degraded / Down）、载体 |
| 中（控制台） | 顶上一条：应用、Harnix、Agix 的版本，运行时长，内存，已连接的客户端（来自 `harnix.process`）；**运行中**：实例 → 运行中的会话 → 运行中的任务，实时变化，结束的淡出；**诊断**：模块、贡献、界面模块的状态、被拒的令牌 |
| 右（检查器） | 只出现适用于选中项的页签。实例：**概况**（事实、它的会话、重启、停止、按模板新建）。会话：**概况**（事实、操作、到所属 space 打开）/ **调用** / **上下文** / **任务** / **原始帧**；选中的是一个任务时，同一组页签从「任务」开始 |

| 页签 | 看什么 | 从哪来 | 能做什么 |
|---|---|---|---|
| 调用 | 这个会话**每一次记录下来的模型调用的输入与输出**：系统块、工具目录、消息区间、配置、输出与用量；相邻两次的差异 | 录像，经 `harnix.system.trace` / `.trace.call` | — |
| 上下文 | 下一次调用**将要**带的上下文：每块的来源、tokens 与正文，工具表，合计与压缩阈值 | `harnix.system.context`（底下是 `session.inspectContext`） | 删除、改写消息 |
| 任务 | 子 Agent、后台 Shell、定时任务……的状态与细节 | `harnix.sessions.tasks` | 停止 |
| 原始帧 | 会话的帧，实时 | 会话事件流 | — |

会话的操作（压缩、清空、分叉、换模型、中断、改名、关闭、删除）与实例的操作（新建、停止、重启——重启一台
attach 的实例就是重新连上）**全部写审计**。

**设备够不着的引擎方法包在系统模块后面。** `inspectContext`、`dropMessages`、`editMessage`、`stopTask`、`taskOutput`、
`compact` 这些引擎方法不在设备的透传白名单里；系统模块把它们包成 `harnix.system.*`：设备调它，它以 `system`
模块的身份经授权调引擎，两次判定都进审计。其余（`session.history`、`fork`、`interrupt`……）设备直接调，带上
`space: "system"`。

**录像里有完整的系统提示词，敏感级别和 transcript 相同**（§6.4），所以只能经授权过的方法读，录像目录永不
经 HTTP 暴露。产品不要系统 space，就从 `[shell] spaces` 里去掉：系统模块不注册，它的方法连同授权一起没有，
声称来自 `system` 的调用一律 `SPACE_MISMATCH`——**撤的是方法，不只是不画**。

**Agix 没给的，不画假的。** 页签或按钮在 Agix 补上之前不出现，而不是做成灰的或者在 Harnix 侧模拟。

### 5.6 贡献点与宿主 API

八个贡献点，数量本身是设计的一部分，加第九个是一个需要论证的决定。完整目录由 `harnix_module::catalog`
生成，见 [contribution_points.md](contribution_points.md)。

| 贡献点 | 贡献什么 |
|---|---|
| `space` | 一个 space：图标、标题、`sidebar()`、`center`、`overview()`、`tabs`、`sessions`、建议与提示 |
| `home.card` | 新对话空页上、输入框下的一张卡 |
| `tool.row` | 一次工具调用在流里的那一行 |
| `flow.block` | 流里的一种块（扩展条目就是用它画的） |
| `details.panel` | 右栏详情里的一页，由 `reveal(item)` 打开 |
| `sidebar.group` | 会话列表的分组与排序 |
| `command` | 一条斜杠命令及其补全候选 |
| `settings.section` | 设置里的一节 |

**这些是界面自己的接缝。** 它们存在的理由不是给第三方一个扩展面——扩展 agent 是引擎的事——而是让界面不是
一堆 switch：于是「换一整套界面」是换一批注册，而不是改一堆分支。**频率是约束**：没有一个点跟着流式分片求值。

**外壳必须真的去问。** 一个没人问的贡献点等于只存在于目录里，产品照旧自己直接画，而所有测试都还是绿的。这件
事真的发生过一次，七个点里的五个。判据因此不是「注册了」，是「被问过」，并且由测试盯着——点的名单本身也从
生成的目录里读，因为手抄的那份也漂过一次。内建界面走的就是这些点，没有一样有私有通道：**如果连工具行都是
这样画出来的，这些接缝就不需要谁来相信。** 例外要说出来：去掉 HOME 之后 `home.card` 没有内建注册了，外壳
照样在新对话的输入框下问它，`examples/hello-app` 注册了一张。

**令牌覆盖与语言包不是贡献点。** 注册表上的 `r.tokens({...}, owner)` 只许覆盖**已有的**令牌名，值只许是颜色或
长度；`r.strings(locale, {...}, owner)` 的 key 必须在 `<owner>.` 下面。不合规矩的那一条被拒并记进诊断。它们
不是点，因为它们不在任何时机被「问」——它们改的是主题和词典本身，所以点仍然是八个。

**宿主 API（`useNest()`）** 是前端代码拿到的全部能力：`call`（只放行 `harnix.reachable` 里的，包括
`app.<id>.*`）、`subscribe`（宿主主题，可带参数）、前台 space 的会话（`current / context / list / open /
create`，自动绑定前台 space）、实例（列、建、停，按可达方法过滤）、`composer.insert`、`reveal`、
`space(id).fetch / socket`、`t()`。**拿不到 Harnix 自己的连接**，所以同一份代码在任何拓扑下都能跑——这是
「语义写死、拓扑可选」在界面这一侧的体现。

### 5.7 运行期包的界面模块

```toml
[[ui]]                          # 同源 ES 模块，浏览器 import
point       = "tool.row"
module      = "rows.js"         # 相对包里的 ui/，只在那底下解析
api_version = 2                 # 贡献点 API，与 [plugin] api_version 是两个数
```

**两个版本号，各由拥有它的一侧检查。** `[plugin] api_version` 是引擎的扩展 API，引擎校验；`[[ui]] api_version`
是贡献点 API，Harnix 校验。一个包可以在一边是新的、在另一边是旧的，所以它们不能是同一个数。

**v2 的模块是预编译好的 ES 模块**（JSX 已编译掉），**不带自己的 React**——页面上两份 React 会让 hooks 失效。
它按名字 import `react`、`react-dom`、`react-dom/client`、`react/jsx-runtime`、`@harnix/react`；外壳的构建
为这几个名字各出一个 facade，页面里一份**内联 import map** 把名字指到它们，外壳自己用的也是这几份，所以页面
上只有一个 React。React 的大版本因此是贡献点 API 的一部分，升 React 大版本就是升 `api_version`。

**import map 只能内联，而 CSP 是 `script-src 'self'`。** 办法是服务端在**发页面时**（`page_csp`）从要发的
`index.html` 算出 import map 的 `sha256`，写进这一页的 CSP：只放行这一段确定的文本，不算放宽，不需要
`unsafe-inline`、`unsafe-eval`。在发页面时算而不是构建时写死，是为了 `--ui-dir` 换进来的界面也对。

**照别的版本写的那一条不生效。** 版本不符（包括没声明 `api_version`，那被当作 v1）的条目在读包时就被拒，
报「这一条不生效」并写明哪一边旧了，包的其余部分照常。在读包时拒而不是 import 进来再失败，是因为后者的症状
是一个悄悄不出现的面板（§2.4）。0.3 的 v1 模块是直接操作 DOM 的函数，换成 React 外壳之后没有办法让它们继续
工作，所以 v1 一律不生效，而不是拒装整个包。

`module` **只在 `ui/` 底下解析**——带 `..` 的直接拒，结构上就点不到包里别的文件。

**产品可以整个关掉：`[ui] runtime_modules = false`。** 关掉时既不提供、也不发任何包的界面模块，包就只剩引擎
那一半。需要「必须是人点的」的产品（例如交易）要关（§6.2）。

**信任级说清楚：界面模块与页面同级。** 它是同源模块，浏览器没有任何机制能把它关小；CSP 挡得住外部来源、
内联脚本与出网，挡不住一个已经被允许加载进来的同源模块去做页面本来就能做的事。所以这一层的约束是**披露、
准入检查、开关、可吊销与可审计**，不是强制隔离——一个被当成隔离来依赖的非隔离，比一个已知不隔离的地方危险
得多。一个界面模块能做的最坏的事，上限是「这个用户自己在这个页面上能做的事」。

### 5.8 界面产物的硬规矩

- **只用令牌，不写死颜色**——写死颜色的部件在另一种主题下不可读。
- **只用 key，不写死文案**——写死文案让整个界面在切换语言后变成两种语言。

由静态检查强制。**CSP 不放宽**：`script-src 'self'`（外加上面那一个 import map 的 hash）、`style-src 'self'`、
`connect-src 'self'`，无 `unsafe-inline`、无 `unsafe-eval`、无外部源。产物自包含，没有 CDN，没有运行期从网上拉
的依赖——所以断网时界面照常打开。

**出网是一项要披露的能力。** 界面这一侧没有第二条出网通道，CSP 挡住了。这是有意的：出网是一项要在安装时被
看见的能力，不该因为代码跑在浏览器里就绕过披露。要访问外部服务，走引擎侧声明了 `net` 能力的代码，或模块的
后端。

### 5.9 品牌与目录

profile 的 `[brand]`：`name`（页面标题、左栏产品名）、`icon`（SVG）、`product_id`。外观的其余部分（配色、文案）
由模块经 `r.tokens` / `r.strings` 贡献。应用不 fork 界面就能拥有自己的外观。

| 路径 | 是什么 |
|---|---|
| `~/.<product_id>/`（不配就是 `~/.harnix/`；`HARNIX_STATE_DIR` 能挪） | 程序自己的配置与状态：令牌、设备、工作区与偏好、space 账本、实例账本、按模板建的实例的数据根、各模块的数据目录、上传 |
| `~/.agix/`（`--agix-dir` / `AGIX_CONFIG_HOME`） | `system` 实例的引擎根：设置分层、transcript、记忆、技能、录像 |
| `~/Documents/`（`--data-dir` / `HARNIX_DATA_DIR`） | **只放项目**。选项目从这里开始，新建项目建在这里；里面没有隐藏目录 |
| `<项目>/.agix/` | 项目自己的数据与配置，**一律**放这里，不开 `<项目>/.harnix/` 之类 |

为什么这样分：状态目录按产品 id 命名，同一台机器上装两个产品不会抢令牌和账本；Documents 是用户的，不该
藏着程序的东西；项目里只有一个属于工具的目录，而它属于引擎。0.4 之前状态放在 `~/Documents/.harnix`，**旧目录
不迁移、不读**（维护者定）：升级后令牌、工作区分组、实例账本从空开始。

### 5.10 桌面：Tauri 只是外壳

`templates/desktop` 是一个 Tauri 2 壳，任何 Harnix 应用都能套上，只换品牌。**webview 直接加载服务端发的 HTTP
页面**，所有业务走页面自己的 HTTP/WS，和在浏览器标签页里一模一样——桌面版和浏览器版是同一个产品：同一份
界面、同一条准入路径、同一套测试。

| 模式 | 壳做什么 |
|---|---|
| **本地** | 以子进程启动应用二进制：回环、`--launch-link`、`--exit-with-stdin`（壳退出，应用跟着退）；读状态目录里的令牌文件，`POST /auth/link` 换一条一次性链接，让窗口打开它，链接种下 `HttpOnly`、`SameSite=Strict` 的 cookie |
| **远程** | 打开配置好的 `https://` 地址，走 TLS 与设备配对 |

**没有业务 IPC**：没有命令、没有 invoke handler、不用自定义协议发界面、不用本地 socket；令牌只经过一个文件和
一次回环请求，窗口只见到一条用过即废的链接。`check-no-ipc.mjs` 在离线检查层盯着。连不上服务端时只显示壳里
打包的「无法连接」页，壳里不放业务界面。理由：一条 IPC 就是一条不经授权表、不进审计、浏览器版没有的通道，
两个版本从此不是同一个产品。

唯一的例外属于窗口本身：macOS 上窗口没有标题栏（红绿灯浮在页面上），页面的顶栏就是拖窗口的地方，而网页自己
挪不动原生窗口。所以页面能对壳请求两件事——开始拖动、双击最大化——只给主窗口、只给回环上的页面
（`capabilities/window-drag.json`），`check-no-ipc.mjs` 对其余任何权限照样失败。它只动窗口，不经手应用的
任何数据。

## 6. 信任与安全

### 6.1 级别

| 级 | 是谁 | 能做什么 |
|---|---|---|
| **内核** | 这个二进制自己，**以及应用编进来的模块** | 全部（模块经授权表，但它是内核级的源码） |
| **运维本人** | 写在项目 / 配置目录里的脚本与设置 | 他本来就能亲手做的任何事 |
| **插件** | 装上的包的 Agent 段 | 默认什么也够不着；多要一分，安装时写下来一分 |
| **页面** | 界面与包的界面模块 | 这个用户在这个页面上能做的事 |
| **设备** | 远端连上来的客户端 | 授权表上的方法 |

级别按出身定（§2.3）。运维与插件两级由**引擎**判定和强制——同一份 `.js`，放在项目里是运维本人写的，随插件
下载来的就是插件，判据是规范化之后的路径，不是它自称什么。Harnix 判定的是设备与模块。

### 6.2 强制、披露、防误

每一处约束标明是哪一种。**安全边界**对恶意代码也成立；**披露**是让人在装的时候看见；**防误**只防 bug、不防
恶意。后两种都是 §1.2 说的「明说不是强制的」那一类。不存在「大概安全」的地方。

| 约束 | 种类 | 防什么 | 不防什么 |
|---|---|---|---|
| 引擎侧 WASM 组件的能力门控；命令执行的权限判定与沙箱；出网策略 | **安全边界**（引擎的） | 插件、模型越权 | 运维配的端点不受出网策略约束 |
| 授权表：主体 × 方法 / 路由，默认拒绝；引擎的凭据 / 子进程 / 端点类方法不对设备开放 | **安全边界** | 未授权的主体调方法、访问模块路由；设备接管进程 | — |
| 设备配对与吊销；非回环必须 TLS + 配对 | **安全边界** | 网络上的其他人 | — |
| 设备建实例只能按启动时定下的模板、只能填模板放开的参数 | **安全边界** | 设备装载子进程、改写模型端点、指定任意数据目录 | — |
| daemon 的凭据不出 Harnix（spawn 的 socket 在私有目录里，attach 的 token 只在 Harnix 手里）；透传白名单对每台实例一样 | **安全边界** | 设备经 Harnix 拿到 daemon 的完全信任 | 本机上能读 Harnix 进程内存或环境的人 |
| 系统 space 去掉时它的方法从授权表撤掉 | **安全边界** | 产品里有人读录像、跨 space 操作 | — |
| 「只有 `Device` 能回答」：权限提问，以及应用自己做的批准 | **安全边界，只对后端成立** | 引擎、模块、内核替人回答 | **区分不了人和同页的界面模块**：装进来的包能替人点。需要「必须是人点的」的产品，设 `[ui] runtime_modules = false` |
| 插件的模型可见文本 | **披露** | 人不知道包往模型面前放了什么 | 文本本身的内容 |
| 界面模块占了哪些贡献点 | **披露** | 人不知道包改了界面哪里 | 模块在页面里做什么（§5.7） |
| 模块拿不到 `EngineLink` 和中枢内部状态 | **结构约束**（编译期可见性） | 模块不小心绕过中枢 | 模块是内核级源码，真要绕可以；这一条防的是误用 |
| `SPACE_MISMATCH`：会话与声称的 space、实例对不上就拒绝 | **防误** | 界面或模块的 bug 把消息发进别的 space、别的实例 | 同页的代码：space 是调用方自己声称的，任何设备代码都能声称任何 space，包括 `system` |
| 设备在系统 space 之外只能用 `ui = true` 的模板 | **防误**（保留系统 space 时） | 界面 bug 在普通 space 里建出调试用的实例 | 声称 `system` 的设备代码能用任何模板（仍然只能是启动时定下的模板，上面那条安全边界不变）。要让 `ui` 标记成为边界，就去掉系统 space |

把这些讲清楚比藏起来有用。

### 6.3 远程访问

一个进程服务一个用户，但这个用户可能有几台设备。

- **配对**：一次性配对码换一份长期设备凭据（设备侧密钥对，挑战应答）。每台设备一条，可列出，可单独吊销。不需要
  CA，不需要身份提供方。
- **凭据绑主体，不绑连接。** 多通道拓扑里所有通道共用握手换来的那一份凭据，吊销一台设备立即断掉它的全部通道。
- **非回环绑定必须同时有 TLS 与已配对设备。** 没有裸 HTTP 的远程——不是默认关闭，是没有这条路径。
- **启动链接**：本机打开页面时令牌可以不进页面，浏览器凭一次性链接换一个 `HttpOnly` cookie（桌面壳的本地模式就
  走这条，§5.10）。
- 回环绑定同时监听 IPv4 与 IPv6：`localhost` 在多数系统上先解析到 `::1`，只绑一边会出现「curl 通了但页面打不开」。
- Origin 校验按部署形态取值：本地放行本地来源，远程只放行配置里写明的来源，**不提供通配**。

### 6.4 敏感数据

transcript、会话记忆、录像（每次模型调用的完整输入，含系统提示词）都是同一批内容，**敏感级别相同**，落在同一个
实例数据根、同一套文件权限下。

三条规则：录像默认开，因为没有它就无法回答「模型到底看见了什么」（系统 space 的「调用」页签就靠它）；录像目录
**永不经 HTTP 暴露**，只能通过授权过的方法读；删除会话连带删除它的录像，关闭会话不删——会话还能重开。

### 6.5 审计

授权的拒绝、设备配对与吊销、扩展的安装、权限回答、系统 space 的每次跨 space 操作、实例的新建停止重启，都记下来。
进程里有一个有界的环，`harnix.audit` 与诊断能读；能归到一个会话上的，另以扩展条目写进那个会话的时间线（目前是
`system` 实例上的会话），与其余条目同序。不是每次放行都记：一秒几次的只读放行会把真正有人会去找的条目埋掉。

复用引擎的扩展条目而不是另建一套日志，有一个具体好处：**未知命名空间必须可跳过**，所以卸载一个插件之后，它留下
的旧条目仍然能被加载，历史不会因为少了一个插件而读不出来。

## 7. 边缘部署

### 7.1 形态

**一个进程、一个用户、多个会话、一个后端二进制、无运行时依赖。** 没有包管理器，没有 `node_modules`。安装物是这一个
文件；运行时不从安装目录读任何东西，状态在状态目录，所以升级就是换掉那个文件。要隔离崩溃与资源的那部分 Agent，
用 daemon 载体放到另一个进程里（默认就是同一个二进制的 `daemon` 子命令，不另外分发）。

| 形态 | 后端 | 界面 | 传输拓扑 |
|---|---|---|---|
| 单机 / 桌面 | 本机，回环 | 后端提供（桌面壳加载它） | 单双向流 |
| 边缘节点 + 远程使用 | 节点上，TLS + 配对 | 后端提供 | 单双向流 |
| 反向代理后面 | 内网，代理终结 TLS | 独立静态服务（`ui export`） | 分离流 |
| 一堆节点 / 自动化 | 每节点一个进程，`--headless` | 无，或一份共用界面 | 纯请求 |

### 7.2 预算

**一个不被测量的性能目标只是一句话。** 下面这些数进 CI 门禁（`tests/budget.mjs`），回归即失败。初值按「4 核 8G
小主机，也要能在 2 核 2G 的 arm64 单板上跑」定：

| 指标 | 上限 |
|---|---|
| 后端二进制大小（默认构建） | ≤ 48 MB |
| 界面产物（gzip 后） | ≤ 300 KB（含 React） |
| 冷启动到可服务 | ≤ 300 ms |
| 空载常驻内存（只有 `system` 一台实例） | ≤ 80 MB |
| 每个空闲会话的内存增量 | ≤ 4 MB |
| 每多一台空载的进程内实例 | ≤ 4 MB（实测约 0.1–0.2 MB） |
| 一次 unary 往返 p99（同机） | ≤ 15 ms |
| 每条空闲连接的常驻开销（预热后的边际值） | ≤ 64 KB |
| 握着 100 条连接时的常驻内存 | ≤ 120 MB |
| 完全空闲时 CPU | < 0.5% |

**「每条空闲连接」测的是预热之后的边际值。** 冷测时头一百条连接看起来每条 145 KB；开完关掉再开一百条，边际不到
1 KB——差别是分配器第一次向操作系统要页然后一直留着。对冷数字设门禁等于对 malloc 设门禁。所以两个数都测：
**再开一条要多少**，以及**握着一百条时一共多少**；后者也是前者不能被悄悄换掉的原因。daemon 实例是另一个进程，不计入
Harnix 的内存预算。

调整这些数的前提是把新的数写进这张表并说明理由，不是让门禁静默放宽。

三个已知的取舍，摆在这里，不藏在实现里：

1. **QuickJS 每次调用建一个全新运行时**，这是「调用之间什么都不留」这条安全承诺的实现方式。是否为某些点复用
   运行时，是一个会削弱那条承诺的决定，要显式做。
2. **进程内实例意味着崩溃不隔离。** 换来的是没有 socket、没有握手、可以带原生工具。补偿措施是轮次级的故障隔离、
   随发布物提供的进程守护单元，以及需要时把那台实例换成 daemon 载体——是可选的，不是默认把进程拆开。
3. **拓扑的成本不一样，所以它是配置而不是常量。** 分离流在代理后面更好用，代价是多一条连接；单双向流在弱网下
   更省，代价是所有流量共享一条连接的队头。**边缘默认单双向流**，因为那里连接比中间件贵。

### 7.3 离线

- 模型走本地端点（OpenAI 兼容协议直连本地推理服务），并按任务分路由：主循环用大模型，压缩、子代理、记忆检索
  用小模型——这几类调用次数多、对质量要求低，是边缘设备上最值得省的地方。
- 界面产物自包含，无 CDN（§5.8），所以断网时界面照常打开。
- 插件安装可以完全离线：一个插件是一个文件，从本地路径装与从市场装走同一条披露流程。
- 构建也能离线：Agix 作为平级的路径依赖，不经 git 源。

### 7.4 故障

- 引擎的持久化是 append-only 的日志，进程消失后重启即恢复到最后落盘的那一轮；按模板建的实例照账本重建。
- 被取消的轮次**不写终止标记**——取消是被打断，不是到达终点，所以会话必须保持可续。
- **断线不动 turn。** 任何通道断开只影响观看，中枢照跑；重连后按 `seq` 追赶。多通道拓扑里一条通道断了不牵连另一条。
- **daemon 断了是降级，不是挂掉**：那边的轮照跑，重连后 resync（§3.1.1）。
- 上游长时间无响应要在界面上表现为可脱出的状态，不是无限「运行中」。

## 8. 改造它的层次

| 层次 | 做什么 | 代价 |
|---|---|---|
| **换 profile** | 一份声明式配置：场景、provider、实例与模板、拓扑、留哪几个内建 space、品牌、是否加载包的界面模块 | 不写代码 |
| **装运行期包** | 引擎的脚本或插件改 agent 的行为；包的界面模块给已有的贡献点做贡献 | 不重编译 |
| **换界面** | 换掉 `--ui-dir` 指的那份产物，或者只换其中几个注册 | 不重编译后端 |
| **做一个应用：编译期模块** | 以子仓引入 Harnix 和 Agix，写自己的模块（后端方法、主题、路由、实例模板、原生工具）和 space 界面，`App::builder()` 装起来 | 重编译；不 fork Harnix |

最后一层是 0.4 加的，也是 §1.2 第一条目标真正落地的地方：一个形态完全不同的产品（Helm 的交易面板、IPDrun 的
流程）不再需要 fork，而是 Harnix 之上的一个应用。应用仓库里 `harnix/` 与 `agix/` 是两个**平级**的子仓：应用发现
Agix 的问题，直接在自己的 `agix/` 里开分支回推，不用先改 Harnix 再升 Harnix。公共改动在应用的 `harnix/` 子仓里开
分支回推上游，**应用里不许有长期补丁**（`check-pins` 检查子仓指针只指向上游存在的提交）。怎么做见
[二开指南](harnix-sdk.md)，从 `templates/app` 起步。

配套的两样，缺一不可：

- **贡献点目录由代码生成**，并有测试盯着它与代码一致。一份会过期的清单比没有更糟——它会被当成事实引用。
- **功能测试对着真的二进制跑（LIVE）**：后端走 API，前端走 Playwright 真浏览器，同一个运行器、同一套夹具；
  模型默认按位置回放引擎的录像，所以工具调用、权限提问、子 Agent 每次都一样，不花钱也不等网络；另有连真实模型的
  live 模式刷新录像。覆盖表由用例标签生成，一个功能在某一层是零就要补或写明为什么。见 [testing.md](testing.md)。

**LIVE 取代了 0.3 的「界面的测试不需要浏览器：一套假 DOM 里跑真模块」。** 那时的教训是：假后端还返回旧形状，
界面测试全绿而功能是坏的。更早一次的教训同样在这里：在有录像回放之前，权限那条路**一次都没被真正跑到过**——
配置的模型不肯调工具，测试轮轮报「不确定」，而一切看上去是绿的。所以测试的结果有三种，不是两种：通过、失败、
没结论。

## 9. 与 Agix 的边界

**依赖方式：**

> **进程内实例以库链接；daemon 实例经本机 JSON-RPC。两种载体对中枢是同一个 `EngineLink`，会话语义不因载体改变；
> 一台 daemon 只服务一个 Harnix，中枢仍是它上面会话的唯一持有者。**

0.3 写的是「以库链接，不起子进程、不走 socket」。daemon 载体字面上违反它，但那条原则的本意是两件事：中枢是会话
的唯一持有者；Harnix 不因为连接方式不同而改变会话语义。修订后的写法保住了这两件事，换来了崩溃与资源的隔离。

**Harnix 一侧永远不做的事**：实现或复制任何引擎逻辑；绕过引擎直接操作 transcript；在引擎之外维护第二份会话状态
（中枢维护的是**观看状态**与队列，账本记的是会话归属，都不是会话本身）。

**Agix 必选，不做引擎可替换。** 抽象一层「任意引擎」，代价是每一处都只能用所有引擎的交集，而 Harnix 的价值恰恰
在于把这一台引擎的语义完整地交给应用。

**Agix 缺的，去补 Agix。** 缺口写成 issue（放在 `.local/`），由它驱动 Agix 开发；Harnix 侧不绕过、不模拟（系统
space 的「Agix 没给的不画假的」是同一条）。**Harnix 跟着 Agix 持续升级**：`agix/` 子仓的钉就是 Harnix 验证过的
那一版；Agix 改自己的类型，对一个不实现引擎逻辑的宿主不该有代价。

Harnix 依赖 Agix 提供的、并且已经由它提供的：

| Harnix 用来做什么 | Agix 给的 |
|---|---|
| 实例装配 | 装配的函数入口（`daemon::assemble::pool`）；同一进程里几台会话池互不可见 |
| daemon 载体 | `DaemonServer` 的库入口、协议版本与能力位、`subscription_dropped`、spawn 的就绪 |
| 中枢知道每一轮 | 会话与轮的生命周期进 `daemon.event`（带 `initiator`）；订阅冷会话 |
| 会话列表、改名、换模型 | 列表条目带场景与项目根；`session.rename`、`session.setModel` |
| 系统 space | 会话的任务可列、可停；上下文可查看、去掉或改写消息；录像 |
| 扩展条目 | `session.appendEntry` / `session.entries` / `extension_entry` 帧；分叉带上条目 |
| 包 | 包方案与载体解耦；`plugin.list` 带包的 `root`、`script_faults`、`component_faults`；装不上的包不会假装装上；manifest 里不认识的段只告警 |

这些曾经一条条是给 Agix 提的 issue，记录在 [0.4 设计](harnix-0.4-design-and-plan.md) §17 与 `.local/` 里。

## 10. 明确不做的

| 不做 | 理由 |
|---|---|
| 多租户 | 一个进程一个用户。硬塞进来会让授权模型对单用户场景过度复杂 |
| 可替换的会话中枢、可替换的引擎 | §2.1、§9 |
| 让拓扑或载体差异渗进中枢、授权 | 传输可以有几种拓扑、实例可以有两种载体，但只能有一套语义 |
| 运行期新增或改写模板、模块 | 等于让别的东西决定这个进程是什么（§3.1） |
| Harnix 侧的第二套插件体系 | 同一件事两处真相，且只有一处真拦得住（§2.2） |
| 在 Harnix 侧执行包里的任何代码 | 包括没有能力的纯函数。规则不需要例外才守得住（§2.2.1） |
| 给运行期包贡献的 `harnix.*` / `app.*` 方法 | 它需要回调能力，而给出能力就是在 Harnix 长出第二个能力模型。要后端方法，写编译期模块 |
| 运行期包新增 space、往别的 space 加页签 | 0.4 不做；有真实需求时和运行期后端模块一起考虑 |
| 运行期后端模块、dylib 形式的 Rust 模块 | 后端模块只有编译期的。以后的方向参照 Agent 侧（WASM / QuickJS / 原生） |
| 界面的运行期外部依赖（CDN、远程 import） | 断网即坏，且把供应链面开到系统之外 |
| 桌面壳的私有通道（IPC、自定义协议） | 一条不经授权、不进审计、浏览器版没有的通道（§5.10） |
| 把引擎的凭据 / 子进程 / 端点类方法开放给设备或插件 | 它们等价于接管这个进程 |
| 批准原语、角色令牌、MCP 服务端进内核 | 应用在模块契约上做得出来（§4.6）；两个应用的实现形状一致后再收 |
| 跨机器的 daemon 实例；几个宿主共用一台 daemon | 前者 0.4 只做本机；后者破坏中枢的唯一持有（§3.1.1） |
| 宿主主题的「追加模式」 | 整值快照够用；出现真实的高频增量需求再说 |
| 迁移的备份钩子、`--dry-run` | Harnix 只管迁移的顺序与失败隔离（§4.1） |
| 协议层的投影子系统 | 派生视图不属于协议 |

这些里有「以后可能做」的，排在 [roadmap](roadmap.md) 的「0.4 之后」，前提都是真实需求加 §1.3 的判据。

## 11. 路线与改过的方向

### 11.1 路线

0.4 把 Harnix 从「一个产品」变成「应用的公共底座」：M0–M9 依次立起引擎基线与构建方式、LIVE 测试、模块契约与
应用装配、实例层与服务端会话、React 外壳、space 模型、系统 space、模块的对话与链接能力、运行期界面模块 v2 与
品牌、桌面壳。每个里程碑交付完整的功能模块（后端、前端、两层测试各一块）。里程碑、任务、验收与「0.4 之后」
排什么，见 [roadmap](roadmap.md)；做到哪了见 [status](status.md)。

**0.4.z 内协议与模块 API 只做加法**：协议形状（`instance` 字段、会话键）在 0.4.0 定下，之后不改已有的形状。
0.4 的最后一条验收是：**照二开指南从模板做出一个换了品牌的应用，不问作者**。

### 11.2 改过方向的地方

每一处都在正文里写了理由，这里汇总，让人知道哪一版是当前的：

| 什么 | 原来 | 现在 | 为什么 |
|---|---|---|---|
| 定位 | 把 Agix 装配成一个产品（「浏览器里的 Agix」） | Agix 应用的公共底座（§1） | Helm、IPDrun 要在上面做各自的产品，而它们只能 fork 或抄装配 |
| 扩展模型 | 三次：Harnix 的插件模型 → 全撤 → 包是 Agix 的、读一段 | 再加编译期模块，插件一词只属于 Agix（§2.2.2） | 应用要加后端方法、space、原生工具，运行期包给不了也不该给 |
| 运行期装配 | 运行期不改装配 | 装配在启动时定，运行期只能按模板建实例（§3.1） | 多实例；本意「这个进程是什么在启动时定」不变 |
| 与引擎的连接 | 以库链接，不起子进程 | 两种载体，一个 `EngineLink`（§9） | 崩溃与资源隔离；本意「中枢唯一持有、语义不变」不变 |
| turn 的发起方 | 客户端 | 客户端与服务端，同一语义（§3.2） | 无头会话要和客户端共用排队与 `seq` |
| 授权主体 | 内核、设备 | 内核、模块、设备（§3.4） | 模块有自己的方法要声明主体，也要以自己的身份调别的方法 |
| 界面与后端 | 分离的产物 | 编进二进制，可整套替换（§5.1） | 分离的唯一硬理由由引擎的插件目录满足了 |
| 界面技术 | 无构建的原生 JS 模块 | React + TS + Vite + Zustand（§5.2） | 生态与回流 IPDrun 的对话组件；v1 包因此不生效 |
| 内建 space | 会话、HOME、系统；`[system_space]` | 会话、项目、系统，都可去掉；`[shell] spaces`；`home.card` 到新对话下（§5.3） | 外框只留每个产品都要的，HOME 与新对话重复 |
| 系统 space 的中区 | 选中会话的对话 | 控制台；右栏检查选中项，含每次调用的输入输出（§5.5） | 它是看进程的；对话到所属 space 打开 |
| 状态目录 | `~/Documents/.harnix` | `~/.<product_id>`，旧的不读（§5.9） | 两个产品不抢令牌；Documents 只放项目 |
| 包的界面模块 | v1：没声明 `api_version` 的照装并提醒 | v2：预编译、共享页面的 React；没声明即 v1，不生效（§5.7） | React 外壳里 v1 无法工作；在读包时拒比悄悄不出现好 |
| 测试 | 假 DOM 跑真模块，不需要浏览器 | LIVE：对着真二进制，API 与 Playwright（§8） | 假后端返回旧形状，测试全绿而功能坏 |

## 12. 与业界的位置

这一节说明哪些决定是共识、哪些是这套设计的选择。

近两年出现的几个 agent 宿主（DeepSeek Harness / dsh，以及围绕 MCP 生态生长出来的若干 IDE 与桌面宿主）在几件事上
给出了同样的答案，Harnix 也照做：**一切能力以插件形式接入**、**模型是可换的类别而不是硬编码**、**会话是可追加、
可回放的事件流**、**界面与内核分层**、**请求与事件流分开承载**、**界面用 React**。这些不是差异点，是这类系统的形状。

有一处形状不同：那类宿主自己长着一套插件系统。Harnix 没有，因为它下面已经有一个——Agent 的扩展整件事在引擎里，
宿主只补引擎有意不做的那一步；应用自己的代码则是编译期模块，不走插件。

传输拓扑上没什么可争的：那类系统普遍采用「一条 unary 端点 + 若干只下行事件流 + 一条带外应答端点」的分法。Harnix
的做法是把这套分法**上升成语义、把连接数下降成配置**——同一套语义在边缘设备上更适合收敛成一条连接，在代理后面
更适合摊开成几条，这两种部署都在目标之内。

分歧在四处：

**一、内核边界。** 那类系统多把「一切皆插件」推到底——agent 循环、会话持久化、审批逻辑本身也是可换插件。代价是
这个系统不再保证任何东西：当循环本身可换时，「一轮是什么」没有答案。Harnix 反过来，骨架写死、判断开放（§2.1）。
这牺牲了一部分灵活性，换来的是可以对用户做出承诺。

**二、插件的运行方式与隔离。** 以 Node 为宿主的方案里，插件与内核同进程同权限，JS 的对象级隔离不是隔离；其沙箱
通常只覆盖文件系统的几档模式。这套设计里插件跑在引擎侧，两档载体（QuickJS 的无 I/O 运行时、WASM 的能力门控）都是
真约束，而宿主这一侧根本没有插件在跑——**没有需要被相信的隔离，是因为没有那个位置**。界面一侧的包模块与页面同级，
这一点明说，并且产品可以整个关掉（§5.7）。差别不在「更安全」这个形容词上，在于每一处都标明了自己是哪一种。

**三、模型可见文本的处理。** 这一类攻击面在多数方案里没有专门位置：沙箱管执行，而一段进入系统提示词的文字既不越权
也不出网。引擎把它当作一等的披露对象，从安装里回出来；宿主的活是把它摆到人面前，而不是自己再算一遍（§4.3）。系统
space 让人随时看到每一次调用实际带了什么（§5.5）。

**四、部署形态。** 以 Node 或容器为前提的宿主，安装物是一棵依赖树，冷启动以秒计，常驻内存以百兆计。Harnix 的后端
是一个二进制，预算写进 CI（§7.2）。这条不是性能偏好，它决定了这个系统能不能装在一台边缘设备上。

值得从那些系统里继续借的，是它们对**分层配置**的处理（插件 → 打包 → profile → 覆盖层，让「换一个形态」变成一次
配置而不是一次 fork）。Harnix 的改造层次（§8）就是这条思路，加上一层编译期的应用。
