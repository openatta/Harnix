# grabix-04：同一主题退订后立刻再订阅，服务端可能后执行退订，订阅从此丢失

类型：缺陷｜优先级：中

## 现象

`ui/packages/shell/src/topics.ts` 的 `Topics` 按 `(topic, params)` 计数：最后一个订阅者离开时发 `harnix.unsubscribe`（第 84–86 行，
不等结果），下一个订阅者到来时因为条目已删，新建条目、发 `harnix.subscribe`（第 65、95–105 行）。两帧走同一条连接，但服务端每帧各起一个任务处理
（`crates/transport/src/ws.rs` 第 340 行 `tokio::spawn`），两次调用的执行顺序不保证：

1. 客户端：`unsubscribe(k)` 发出 → `subscribe(k)` 发出；
2. 服务端：`subscribe(k)` 先执行（返回当前值，客户端照常交付）→ `unsubscribe(k)` 后执行，这条连接上 `k` 的订阅被删；
3. 客户端条目 `held = true`，不会再订阅；之后 `k` 的推送一条也收不到，直到断线重连。

触发条件是「订阅数掉到 0 再回来」，在同一个事件循环轮次或很短的间隔里：切换页签、条件渲染的组件卸载又挂载、React 严格模式的双挂载都会遇到。
表现是界面停在旧值上（例如刚建的条目不出现在列表里）。

## 建议

客户端修，协议与服务端不动：

- 每个 key 记一个「退订在途」的 promise。新订阅者到来时，如果同一 key 的退订还在途，`hold` 等它完成后再发 `subscribe`（这期间新条目照常收
  监听者、`held = true`）。
- 可选：最后一个订阅者离开时延迟一个宏任务再退订，期间又有人订阅就取消退订、沿用原条目（省掉切页签时的一来一回）。

两条都只改 `Topics` 内部，`subscribe(topic, params, fn) => unsubscribe` 的签名与语义不变。

## 兼容性

- 公开接口、协议帧、服务端行为不变。
- 行为改动只在这一处：退订与紧随其后的再订阅不再可能以「最终无订阅」告终。
- 贡献点 API 版本不用升。

## 验收

- `ui/packages/shell` 单元测试：用假 client，让 `harnix.unsubscribe` 的处理延迟、`harnix.subscribe` 立即完成，模拟服务端乱序；
  订阅 → 退订 → 同一轮再订阅之后，假 client 上最后一次生效的操作是 `subscribe`，推送仍能交付给新订阅者。
- 若做了延迟退订：同一轮内退订再订阅不发任何帧；超过延迟后才发 `harnix.unsubscribe`。
- 现有 host.spec 的订阅用例不变通过。

## 依赖

无。与 ipdrun-16（退订计数）是同一个类的另一种情况：那条修了「一个订阅者退订会影响另一个」，这条是「计数归零再回来」的窗口。

## 来源
