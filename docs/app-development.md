# 在 Harnix 上开发应用：三种模式

> 状态：**模式 1 已有应用在用**（IPDrun、Grabix）；**模式 2 在开发与测试中**（开关 `apps` 关着时构建与今天一样）；**模式 3 只有设计**，还没有代码。
> 用词照 [术语](glossary.md)：「应用」是在 Harnix 上做出来的产品；装进应用里的叫**运行期应用**（常说的「插件 APP」——「插件」在这里只指 Agix 的包，所以文档里不用这个词称呼它）。模式 1 的接口在 [二开指南](harnix-sdk.md)、[SDK 参考](harnix-sdk-reference.md)、[贡献点](contribution_points.md)。

## 0. 一句话

**一种用 Rust 做产品，两种往产品里装运行期应用。**
- 模式 1（单一应用）：用 Rust 把 Harnix 装配成一个产品，IPDrun、Grabix 就是这样做的。
- 模式 2 和模式 3（运行期应用）：同一种应用包（`.hxapp`：WASM + QuickJS + 界面），装进一个模式 1 的产品里跑。
  - 模式 2：嵌入的，同一个进程，资源受限。
  - 模式 3：每个应用一个独立进程，资源宽松，适合桌面与云。
- 一个产品要么开模式 2，要么开模式 3，二选一；应用包两边一样，不用改。

## 1. 三种模式

| | 模式 1：单一应用 | 模式 2：运行期应用（嵌入） | 模式 3：运行期应用（独立进程） |
|---|---|---|---|
| 状态 | 已有应用在用 | 开发与测试中 | 只有设计 |
| 谁写 | 产品方 | 应用作者（第三方也可以） | 同模式 2 |
| 用什么写 | Rust：编译期模块、Agix 原生工具与场景、前端的编译期 space | WASM 组件（WIT `harnix:app`）+ Agix 包（QuickJS、skill、agent 类型）+ 界面（iframe 页面与声明式行内点） | 同模式 2，**同一个包** |
| 跑在哪 | 产品的二进制里 | 产品进程里：每个应用一台 WASM 虚拟机；Agent 用产品实例的 Agix | 每个应用一个进程：应用宿主 + WASM 虚拟机 + 应用自己的 Agix，经 RPC 连产品 |
| 隔离 | 无：这就是产品本身，按「出身」信任 | 弱：WASM 沙箱隔开代码与能力，授权表隔开权限；故障与资源只隔到一台虚拟机，宿主出 bug 会拖垮整个进程 | 强：进程级。崩溃、内存、CPU、文件系统、网络各自独立，可以再套 cgroup 或容器 |
| 资源 | 产品自己的 | 省：一个 `Engine`，每个常驻实例几到十几 MB，可以闲置休眠 | 宽：每个应用一份 Agix 与进程开销 |
| 分发 | 产品的发布 | 应用商店：签名 + 商店副署，预编译 `.cwasm` | 同模式 2 |
| 例子 | IPDrun、Grabix；Harnix 自己的二进制（[空应用](glossary.md)，只带内建模块的模式 1 产品） | 样例 `examples/apps/showcase` | — |

## 2. 三者的关系

```
            ┌──────────────── 模式 1：一个 Rust 产品（Harnix 装配起来的） ────────────────┐
            │  编译期模块 · Agix 原生工具与场景 · 编译期 space · 品牌 · profile              │
            │                                                                              │
            │  可选，二选一（构建时定）：                                                    │
            │   ├─ 模式 2 宿主：进程内跑运行期应用（feature `apps`）                          │
            │   └─ 模式 3 宿主：把运行期应用拉成独立进程，Harnix 只做通道与旁路管理（设计）   │
            └──────────────────────────────────────────────────────────────────────────────┘
                                   ▲ 同一种 .hxapp，两种宿主都装
```

- **模式 1 是产品，模式 2 和 3 是产品的能力。** 运行期应用不是产品：它总是装进某个模式 1 的产品里，哪怕那个产品就是 Harnix 自己的二进制。
- **模式 1 同时具备 2 或 3。** 模式 1 的产品只是在 Rust 层面扩展 Harnix，开一个构建开关就能接运行期应用，自己的编译期模块照常。
  - 比如 IPDrun 可以既有自己的 Rust 模块，又从商店装别人的应用。
- **2 和 3 对一个产品二选一。**
  - 理由一：两种宿主对「应用的 Agent 在哪」答案不同（§5、§6），一个产品里混着跑，同一个应用就会有两种行为。
  - 理由二：模式 2 的宿主要链 wasmtime，模式 3 的宿主不链（虚拟机在应用进程里）。
  - 落法：两个互斥的 cargo feature，同时开就 `compile_error!`；profile 不能切换。
- **应用包对模式中立。** 清单、WIT、界面、签名在两种宿主里含义相同；作者能观察到的不同只有 §7 那几条。
  - 所以商店里只有一种包，作者也只写一遍。
- **原生代码只走模式 1。** 运行期应用在两种模式里都只有 WASM 与 QuickJS。
  - 模式 3 有了进程隔离，看起来可以放原生二进制，但不放：放了包就不能在模式 2 里跑，而且签名、审核与跨平台都要另起一套。

## 3. 模式 1：用 Rust 做产品

已有，接口在 [二开指南](harnix-sdk.md)、[SDK 参考](harnix-sdk-reference.md)、[贡献点](contribution_points.md)。要点：

- 应用仓库 = 自己的 crate 加 `harnix` 依赖，`AppBuilder` 装配：编译期模块（trait `Module`：方法、主题、路由、数据迁移）、给 `system` 加原生工具与场景、给 space 一台独立实例、前端的编译期 space 与贡献点、品牌与 profile。
- 信任按出身：编进二进制的都是内建，全部贡献点、全部宿主 API。
- 要装运行期应用时开 feature `apps`（模式 2）；模式 3 的 feature（设计中）与 `apps` 互斥。开了之后 profile 的 `[apps] enabled` 等照模式 2 配。
- 产品可以给自己的应用商店换公钥与地址（`[apps] store`、受信发布者），也可以不开商店，只用 `installFile`（开发模式）。

## 4. 运行期应用：两种模式共用的开发方式

### 4.1 包与清单

`.hxapp`（zip）里有：

| 部分 | 作用 |
|---|---|
| `harnix-app.toml` | 清单 |
| `wasm/<组件>.<指纹>.cwasm` | 后端或工具组件：商店预编译，指纹含 `cpu=baseline` |
| `agent/` | Agix 包：QuickJS 脚本、agent 类型、skill |
| `ui/` | iframe 页面与资源；受信发布者可以带进页面的模块 |
| `SIGNATURES` | 每个文件的 sha256，发布者签名加商店副署 |

清单各节（只增不改；未知的节与字段按名拒）：

| 节 | 内容 |
|---|---|
| `[app]` | id、version、`harnix_api`、title、publisher |
| `[capabilities]` | `net`（精确主机）、`env`、`storage_mb`、`fs`（`${project}` 只读、`${data}`）、`hub`（以 `module:<id>` 能调的方法与 `topic:` 主题） |
| `[[component]]` | world `tools-app` 或 `backend-app`；`memory_mb`、`timeout_ms` |
| `[backend]` | `resident = "always" \| "on-demand"`、`idle_secs`（闲置休眠） |
| `[[method]]` / `[[topic]]` / `[[space]]` | 后端的方法（`subject`、内联 params schema）、主题、space |
| `[config]` | 缺省配置，profile 的 `[apps.config."<id>"]` 可以盖过 |
| `[interface]`、`[[surface]]` | iframe 的面（8 个点）、界面能调的 `harnix.*`/`session.*`（`hub`）、`links`、`isolate` |
| `[inline]` | 声明式行内点：`tool_row`、`flow_block`、`command`、`sidebar_group` |
| `[[ui]]` | 进页面的模块，只对受信发布者生效 |
| `[agent]` | `install_into`：§7 说明两种模式里的含义 |

### 4.2 后端：WIT `harnix:app@0.1.0`

- **world `tools-app`**：
  - `list-tools`、`call-tool`、事件钩子；
  - 每次工具调用一个临时实例，用完即弃。
- **world `backend-app`**：
  - 生命周期：`init`、`handle`、`on-topic`、`on-timer`、`stop`；
  - 一个常驻实例，调用串行排队；
  - 超时会换掉实例，`init` 重跑；
  - 崩溃重建一次，再崩就停用。
- **宿主函数**：
  - `call`、`publish`、`subscribe` / `unsubscribe`；
  - `set-timer`、kv、`http-request`、`secret`、`config`；
  - 每项都在调用时按清单的能力检查。
- **规矩**：
  - `handle` 要快，慢活拆成「发起」加「定时器或主题回报」；
  - 要保留的状态放 kv，内存里的状态随时可能因为换实例或休眠而丢；
  - 记录类型冻结，只增函数。

### 4.3 Agent 部分

- Agix 包：QuickJS 脚本挂在 Agix 的扩展点上，没有 I/O，信任来自签名，不来自沙箱；另有 agent 类型与 skill。
- 应用的工具在会话里叫 `app__<id>__<tool>`；经 MCP 时叫 `mcp__app-<id>__<tool>`。

### 4.4 界面

- **面**：space 中区、左栏中段、右栏页签、二级栏、设置节、新对话卡、模态框、`details.panel`。
  - 每个面一个 iframe：`sandbox="allow-scripts allow-forms"`，不透明源，CSP 带 `connect-src 'none'`。
  - 外壳给每个面画外框，并处理失败。
- **桥 `harnix-ui-bridge@1`**：经 `MessageChannel` 只调自己的 `app.<id>.*`，加 `[interface] hub` 列出的少数名字。
  - 外壳动作（打开会话、通知、确认、复制、打开链接、上传）都由外壳去做；`confirm` 画在外壳里，应用伪造不了。
- **SDK 与组件**：`@harnix/app-sdk`（连接、心跳、自动高度、mock 宿主）；`@harnix/ui-kit`（外壳的令牌加基础组件，主题与语言实时跟随）。
- **行内点**：只靠声明，外壳照着画，不跑应用的代码。

### 4.5 信任、分发与开发流程

- trust：
  - `store`：商店副署；
  - `trusted`：profile 里配的受信发布者签全了；
  - `unsigned`：只在 `[apps] dev = true` 时跑。
- 签名在解包前验，每次启动时对盘上的文件再验一次；`.cwasm` 读入时按签名里的 sha256 比对，通过后才反序列化。
- 安装两步：第一次返回披露与 digest，人同意后带着 digest 再调一次。升级时只列多出来的能力。
- 工具 `harnix-app`：`new`、`build`（基线 CPU）、`keygen`、`sign`、`verify`、`pack`、`fingerprint`；商店侧用 `countersign`、`index`。
- 测试：
  - 界面：`@harnix/app-sdk` 的 mock 宿主做单测；
  - 后端：在开发模式下 `installFile`，再写 LIVE；
  - showcase 是什么都有的样例。

## 5. 模式 2 的运行时（开发与测试中）

- 进程模型：
  - 一个产品进程；每个应用一台 WASM 虚拟机，只在主进程里，每进程一台；
  - 所有虚拟机共用一个 `Engine`。
- Agent：
  - 应用的 Agix 包装进 `install_into` 列出的产品实例；
  - 子 Agent 与产品的其它会话共用实例的 Agix，只靠上下文隔离；
  - spawn 出来的 daemon 不起虚拟机，经 `/apps/<id>/mcp` 回到主进程执行，应用的状态只有一份。
- 闲置休眠：`on-demand` 的应用满足以下条件后卸下后端，下次调用冷启动：
  - 没有订阅、没有定时器、没有在途调用；
  - 闲置满 `idle_secs`。
- 适合：单机、嵌入、资源受限的部署；应用之间协作方便，同一个会话可以同时用几个应用的工具。

## 6. 模式 3 的运行时（只有设计，单独立项）

### 6.1 结构

```
前端（外壳 + 应用 iframe） ──Harnix 协议──▶ 产品（Harnix：通道 + 旁路管理）
                                              │  每个应用一条链接（以 module:<id> 连上来）
                                              ▼
                                  应用进程 app-proc（每个应用一个）
                                  ├─ 应用宿主核心（与模式 2 同一份）
                                  ├─ harnix-wasm（同一份）
                                  └─ 应用自己的 Agix（装它的 Agix 包、工具）
```

### 6.2 产品的职责：通道与旁路管理

- **通道**：
  - 前端对 `app.<id>.*` 的调用与订阅，以及应用 space 里的 `session.*`，产品都转给应用进程。
  - 应用调 `harnix.*` 时反向走，主体是 `module:<id>`，授权与审计都在产品里做。
- **旁路管理**（不在数据路径上）：
  - 安装、验签、披露与同意（与模式 2 同一份代码）；
  - 起停与监护：拉起、健康检查、退避重启、闲置回收；
  - 配额与计量，以及密钥与环境变量的注入；
  - 出口规则：`net` 能力落成规则；
  - 系统 space 的「应用」页签。
- 产品自己不跑应用的代码，也不跑应用的 Agent。

### 6.3 应用进程 app-proc

- 一个二进制，由应用宿主核心、harnix-wasm、Agix 和端口的 RPC 适配器组成。
- 启动参数：包目录、链接地址与令牌、数据目录、已经同意过的能力。
- 产品里其它实例的会话要用这个应用的工具时，经 MCP 到这个进程。

### 6.4 链接与失败

- 链接用 Harnix 现有协议（模块自有链接）：同机走 Unix 套接字，跨机走 TLS 加配对（复用 remote 层）。
- 应用进程崩了，只有这个应用的方法答 `unavailable`；它的会话随进程恢复（Agix 的持久化）。产品按退避重启，连续失败就把它置于一旁。
- 产品重启后，应用进程重连，重新登记（登记是幂等的）。

### 6.5 立项时再定

1. 编排：先做本机监护器，还是直接接容器编排；冷启动预算。
2. 云上部署（多租户）：租户、计量、配额怎么接进授权表。桌面版不需要这一层。
3. 应用的 Agix 用谁的模型、谁付费。
4. 应用之间的协作：经产品转的 RPC，还是 MCP。
5. 应用数据与 kv 放本地盘还是对象存储；备份与迁移。

## 7. 应用作者在 2 和 3 之间能观察到的不同

| 方面 | 模式 2 | 模式 3 |
|---|---|---|
| `[agent] install_into` | 把 Agix 包装进列出的产品实例；那些实例的会话直接用它的工具 | Agix 包装在应用进程里；列出的实例经 MCP 用它的工具 |
| 应用自己的会话（它的 space 里的） | 在产品实例里 | 在应用进程里，产品负责路由 |
| 崩溃的影响 | 宿主 bug 可能波及产品进程；WASM 陷阱不会 | 只影响这个应用 |
| 资源上限 | 每台虚拟机记账（内存、时间、存储） | 每个进程记账，可以加 cgroup |
| 延迟 | 进程内调用 | 每次跨进程多一跳 RPC |

其余方面（清单、WIT、宿主函数、界面、桥、签名、商店）完全相同。应用作者的规矩只有一条：**不依赖两种模式之间的差异**。比如不要假设自己的会话和产品的其它会话在同一个 Agix 里。

## 8. 共享代码与边界

| 层 | crate | 模式 1 | 模式 2 | 模式 3 |
|---|---|---|---|---|
| 内核与模块 | `harnix`、`harnix-module`、hub、authz… | ✔ | ✔ | ✔（产品侧） |
| 分发与信任 | `harnix-app-package` | | ✔ | ✔（产品侧） |
| 边界 | `harnix-app-port`：`Platform`（应用宿主要外面做的）/ `Control`（外面要应用宿主做的），可以搬上 RPC 的形状 | | ✔ | ✔ |
| 虚拟机 | `harnix-wasm` | | ✔ | ✔（应用进程侧） |
| 应用宿主核心 | `harnix-app-host`：生命周期、注册表、健康、休眠、分派 | | ✔ | ✔（应用进程侧） |
| 粘合 | `harnix-apps`：端口的进程内实现、Agix 插件、`/apps/<id>/ui`、`/mcp` | | ✔ | |
| 粘合（模式 3，设计） | `harnix-app-proc` 加产品侧的端口服务与监护器 | | | ✔ |
| 前端 | 外壳、桥、`@harnix/app-sdk`、`@harnix/ui-kit`、行内点 | ✔ | ✔ | ✔（完全一样） |

约束（layering 测试守着）：
- 分发与信任、边界、应用宿主核心三层不依赖内核、hub、Agix 和 HTTP 框架；
- 只有 `harnix-wasm` 链 wasmtime；
- 端口经 JSON 回环测试，证明能搬上 RPC。

## 9. 怎么选

- **产品方**：
  - 要做自己的领域能力，用模式 1。
  - 要让别人往产品里加东西：资源紧、单机或嵌入的，开模式 2；桌面资源宽、要强隔离、要上云的，等模式 3。
  - 二者择一，构建时定。
- **应用作者**：
  - 只写运行期应用，不用关心宿主是模式 2 还是 3（§7 那条规矩除外）。
  - 需要原生代码、或者要进内核的能力，就不是运行期应用该做的事：去找产品方做成模式 1 的模块，或者给 Harnix 提 issue。
