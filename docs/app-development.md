# 在 Harnix 上开发应用：三种模式与产品形态

> 三种模式都已实现。**缺省、也是 Harnix 自己的配置是原生扩展 + 模式 2**；模式 3 是选用的。
>
> 用词照 [术语](glossary.md)：「应用」是在 Harnix 上做出来的产品；往产品里登记方法、主题、space、界面、工具的东西都叫**扩展**，
> Rust 写、编进二进制的是**原生扩展**，装上的 `.hxext` 是**扩展包**。Agix 的包叫 **Agix 插件**，它可以是扩展包的一部分。
>
> 这是总览。原生扩展怎么写（模式 1）在 [原生扩展](harnix-ext.md)；扩展包怎么写（模式 2 / 3 共用）在 [扩展包](harnix-ext-package.md)；
> 为什么是这个形状在 [概念与架构](concept_and_architecture.md) §2.2、§4；Harnix 自带的 Harnix app 与系统 space 在 [Harnix app](harnix-app.md)、[系统 space](system-space.md)。

## 0. 一句话

**用 Rust 写原生扩展做产品（模式 1），再选一种方式往产品里装扩展包：在产品进程里（模式 2，缺省），或者每个扩展包一个扩展进程（模式 3，选用）。**

Harnix 本身是**框架 + 第一方扩展**：Harnix app（会话 space、项目 space）、系统 space、设置、Agix 插件、观测、设备、流程，都是用框架的公开扩展接口写的原生扩展；
管扩展包的 `packages` 也是。Harnix 自己发布的二进制 `harnix` 就是全部第一方扩展加 `packages` 与模式 2 的载体——它本身就是「原生 + 模式 2」的一个应用。

## 1. 三种模式

| | 模式 1：原生扩展 | 模式 2：扩展包，同进程（缺省） | 模式 3：扩展包，扩展进程（选用） |
|---|---|---|---|
| 是什么 | 用 Rust 写扩展，把 Harnix 装配成一个产品 | 扩展包跑在产品进程里，每个包一台 WASM 虚拟机 | 每个扩展包一个进程：产品二进制以子命令 `ext-proc` 重新执行自己，里面是宿主核心、虚拟机与它自己完整的 Agix，关在操作系统沙箱里；产品只路由 |
| 谁写 | 产品方 | 扩展包作者（第三方也可以） | 同模式 2 |
| 用什么写 | Rust：`Extension`、引擎贡献（场景层、原生工具、`PromptGate`）、编进外壳的 UI 包 | 扩展包 `.hxext`：WASM 组件（WIT `harnix:ext`）+ Agix 插件（QuickJS、skill、agent 类型）+ 界面（iframe 页面与声明式行内点） | 同模式 2，**同一个包** |
| 能力从哪来 | 产品在 `main.rs` 里授予 | 清单申请，签名、披露、人同意，记在同意记录里 | 同模式 2，产品侧复核 |
| 构建 | 库 `harnix` | feature `wasm`（`harnix` 二进制缺省开） | feature `proc` |
| 运行时 | — | `[ext.packages] carrier = "wasm"`（只链了它时不用写） | `[ext.packages] carrier = "process"` |
| 分发 | 随产品发布 | 商店：发布者签名 + 商店副署，预编译 `.cwasm` | 同模式 2 |

两种 WASM 载体都**建在原生之上**：`packages` 是一个原生扩展，它把每个装上的包照清单与同意记录登记成一个扩展，和原生扩展同一个描述、同一张路由表、同一套审计。
所以在内核里，扩展包就是一个扩展，只是信任是「同意」、能做的是原生的一个子集（[概念与架构](concept_and_architecture.md) §4.5）。

## 2. 产品形态

| 形态 | 组成 | 一句话 |
|---|---|---|
| **应用**（IPDrun、Grabix…） | 自己的原生扩展 + 挑选的第一方扩展，一般再开模式 2 | 产品方用 Rust 做领域能力，再让精选的扩展包在进程内扩展它。**推荐的形状** |
| **Harnix**（二进制 `harnix`） | 全部第一方扩展 + `packages` + 模式 2 | Harnix 自己的缺省：一个进程，省内存，装少量受控的扩展包；也适合资源紧的设备与边缘部署 |
| **要进程隔离的产品** | 自己的原生扩展 + 模式 3 | 开放的商店、扩展包来自许多发布者、可信度参差：每个扩展包一个沙箱里的进程，一个崩了拖不垮整个产品 |

两条约束：

- **模式 2 与模式 3 基本二选一，但不写死在代码里。** 两个载体可以同时链进来，`packages` 按 `[ext.packages] carrier` 的名字取载体（两个都链又没写，取 `wasm`）；
  骨架与宿主组件的代码里没有按 feature 的分支。这一版里一个产品的全部扩展包都跟产品选的那一个载体走；按扩展包选载体的位置已经留在安装记录里。
  「扩展包的 Agent 在哪」（§10）是载体的属性，作者不该依赖它。
- **扩展包对载体中立。** 同一个 `.hxext` 在各个产品、两种载体下都能装。商店只有一种包，作者只写一遍。

## 3. 资源使用

| | 模式 1 | 模式 2 | 模式 3 |
|---|---|---|---|
| 二进制 | 不带载体 ≤ 48 MB（`budget` 层的上限） | 加载体后 ≤ 52 MB：只有 wasmtime 的运行时，没有编译器 | 同模式 2：**同一个二进制也是扩展进程**，产品里同样链着 wasmtime；没有第二个程序要分发 |
| 每个扩展包的常驻开销 | — | 常驻 Store 的线性内存：以清单的 `memory_mb` 封顶，通常几 MB；整个进程共用一个引擎，`.cwasm` 代码按文件映射 | 一个进程：虚拟机、异步运行时、有 `agent/` 或 `[[space]]` 时它自己的一台 Agix。代码页与产品共享同一个文件映射，空载常驻估计 20–40 MB |
| 工具调用 | 进程内 | 每次一个调用 Store，用完即弃 | 它自己引擎里的会话在进程里本地调；产品实例的会话经扩展线过去，多一跳 |
| 闲着的时候 | — | `resident = "on-demand"` 的扩展包闲置后卸下后端，下一次调用冷启动（毫秒级） | 同样闲置后连进程一起停，下一次要它做事时再拉起（冷启动预算 ≤ 2 s）；只读的列表由产品侧缓存答，不唤醒它 |
| 上限与记账 | 产品自己的 | 每台虚拟机：内存、单次调用时间（epoch 中断）、存储（kv + `/data`）；一个工具连续出错只停那个工具，后端反复崩溃就置于一旁 | 进程里同样的虚拟机记账；另有进程级的：Linux 上的地址空间上限，存储由产品在快照时量，超上限 10% 停掉它 |
| 规模感 | — | 几个到二十来个扩展包，合计几十到一两百 MB | 每个扩展包一个进程，内存随扩展包数线性增长 |

## 4. 安全性

谁在什么边界里，能碰到什么：

| | 模式 1 | 模式 2 | 模式 3 |
|---|---|---|---|
| 信任来源 | 出身：编进二进制，产品方负责审查；特权只是装配时授予的那几项能力 | 签名：商店副署（store）、受信发布者（trusted）；未签名只在开发模式跑。能力来自人同意的清单 | 同模式 2 |
| 后端代码 | 原生 Rust：内核级源码，结构约束只防误 | WASM 沙箱：内存安全；没有环境里的文件与网络，`net` 精确主机、`env` 名单、`fs` 预开目录、`storage` 上限，逐项在宿主函数里查 | 同模式 2，外加进程边界与操作系统沙箱（macOS `sandbox-exec`、Linux Landlock） |
| 对 Harnix 的调用 | 以 `ext:<id>` 进路由表，按每行的访问与它被授予的能力判 | 以 `ext:<id>` 进同一张路由表，只到同意的 `calls` 与自己的名字，再收窄到自己的 space 与会话；被拒的记审计 | 同模式 2；调用经扩展线进产品，元数据只是提示，产品重签调用 id、重算调用链 |
| Agent 部分（QuickJS、skill） | 原生，可信 | **弱点**：Agix 插件装进产品的实例，QuickJS 在实例共用的 Agix 里跑，看得到那个实例里其它会话的事件；它的信任来自签名，不来自沙箱 | 在扩展自己的 Agix 里跑，只看得到这个扩展自己的会话；**产品的引擎策略（`PromptGate`、工具钩子、场景层）也不进它的引擎** |
| 界面 | 编进外壳的 UI 包，可信 | 进隔离的 iframe（不透明源、`sandbox`、CSP `connect-src 'none'`），只经桥；它能调什么由服务端取「设备的权力 ∩ 清单」；受信发布者可以带进页面的模块 | 同模式 2，前端完全一样；它的会话内容外壳按不受信内容画 |
| 故障 | 产品自己的 | 虚拟机的陷阱、超时、内存超限被接住，只停这一个扩展包；**但** wasmtime 或宿主函数的 bug、Agix 插件里的问题会波及整个产品进程 | 只影响这个扩展进程；监护器退避重起，反复崩溃就置于一旁 |
| 文件与数据 | 产品自己的 | 每个扩展包自己的 kv 与 `/data`；同一个进程，靠代码边界分开 | 沙箱里只看得见自己的运行目录与包：读不到令牌、设备、别的扩展、产品引擎的数据、自己的同意记录 |
| **网络与模型凭据** | 产品自己的 | `net` 在产品侧判，对 WASM 是边界 | **挡不住**：沙箱里网络开着，被攻破的进程可以直接连任何主机，包括回环上别的服务；它的引擎用的是产品写给它的 provider，模型凭据在它手里 |

**一句话**：模式 2 的隔离靠 WASM 沙箱、路由表、同意与签名，挡得住「扩展包越权」，挡不住「宿主出 bug」，也不隔开 Agent 部分；
模式 3 加上进程边界与操作系统沙箱，隔开故障、资源与文件，Agent 部分也是它自己的——**但不隔开网络，也不藏住模型凭据**。
逐项的表与理由见 [概念与架构](concept_and_architecture.md) §6.6。

## 5. 目标市场

| 形态 | 给谁 | 典型场景 | 为什么是这个模式 |
|---|---|---|---|
| **应用**（1 + 2） | 做垂直产品的团队（ISV、企业内部平台） | 领域产品（如 IPDrun、Grabix），产品方自己定、自己审的一批扩展包，或者自己的商店 | 领域能力要原生 Rust（模式 1）；扩展是精选的、可信度高，进程内最省、协作最方便（模式 2） |
| **Harnix**（1 + 2） | 个人与团队用户，设备与边缘的集成方 | 通用的 Agent 工作台；工控机、边缘盒子、一体机与展示终端、离线现场，单租户 | 内存与盘紧、常常只有一个进程的预算；扩展包少而受控，弱隔离的风险可以接受 |
| **要进程隔离的产品**（1 + 3） | 面向开放商店的产品，以及给它写扩展包的第三方开发者 | 资源宽的桌面或服务器，扩展包来自许多发布者 | 来源参差，一个扩展崩了不能拖垮产品，文件与令牌要隔开；网络与模型凭据仍要靠发布者的信任与审核 |

云端多租户不在这个系统里：一个进程服务一个用户（[概念与架构](concept_and_architecture.md) §1.1）。

## 6. 怎么选

- **做产品的**：
  - 领域能力写成原生扩展。
  - 要让别人往产品里加东西：扩展包由你挑选、资源要省，用模式 2（缺省）；面向开放商店、要隔开故障与文件，用模式 3。
  - 构建时链哪个载体、profile 里选哪个；模式 3 的平台要能套上沙箱（macOS，或有 Landlock 的 Linux），套不上就拒绝拉起。
- **写扩展包的**：
  - 只写一个扩展包，不用关心宿主是哪个产品、哪种载体，只有 §10 那张表例外。
  - 要原生代码、引擎贡献（场景、提示的闸门、凭据源）、实例模板、任意 HTTP 处理者，就不是扩展包该做的事：找产品方做成原生扩展，或者给 Harnix 提 issue。
- **原生代码只走模式 1。** 扩展包在模式 2 和 3 里都只有 WASM 与 QuickJS。
  - 模式 3 有了进程，看起来可以放原生二进制，但不放：放了包就不能在模式 2 里跑，而且签名、审核与跨平台都要另起一套。

## 7. 模式 1：原生扩展

接口在 [原生扩展](harnix-ext.md)、[贡献点](contribution_points.md)。要点：

- 应用仓库就是自己的 crate 加上 `harnix` 依赖，用 `App::builder()` 装配。能装配的有：
  - 原生扩展（trait `Extension`）：方法、主题、space、HTTP 路由、工具、界面的声明、数据迁移；
  - 引擎贡献：给 `main` 实例与每台进程内实例的场景层、原生工具、`ToolProvider`、工具钩子、`PromptGate`、凭据源；
  - 实例模板：给一个 space 一台独立的实例；
  - 自己定义的能力与贡献点；
  - 第一方扩展：`harnix::first_party::standard()` 整套，或挑几个；
  - 前端的 UI 包、品牌与 profile。
- **信任按出身，特权按授予。** 编进二进制的扩展都是可信的源码，但它能做的特权只是 `main.rs` 里写下的那几项能力；少授、多授、授了没定义的都拒绝启动。
  第一方扩展也一样，没有「内建」这种特权。
- 要装扩展包时开 feature `wasm`（模式 2）或 `proc`（模式 3），链上 `packages` 并授予它 `extensions.manage`；profile 的 `[ext.packages]` 照 [扩展包](harnix-ext-package.md) 配。
- 产品可以给自己的商店换公钥与地址（`[ext.packages] store`、受信发布者），也可以不开商店，只用 `installFile`（开发模式）。

## 8. 扩展包：两种载体共用的写法

在 [扩展包](harnix-ext-package.md)：包与清单的每一节（含 `[[tool]]`）、WIT 与宿主函数、Agent 部分、界面（面、桥、`@harnix/ext-sdk`、`@harnix/ext-kit`、行内点）、
信任等级、签名、商店与同意、`harnix-pack` 工具、测试，以及它们的接口清单。两种载体下这些完全一样；作者能观察到的不同只在 §10。

## 9. 两种载体的运行时

### 9.1 模式 2：同进程

- **虚拟机**：每个扩展包一台 WASM 虚拟机，只在主进程里，共用一个引擎。
- **扩展包的 Agent**：Agix 插件装进 `install_into` 列出的产品实例。子 Agent 与产品的其它会话共用那个实例的 Agix，只靠上下文隔离；
  它的会话受产品的引擎策略约束。
- **工具**：载体的一个 `ToolProvider` 经每台进程内实例进每个会话；spawn 出来的 daemon 不起虚拟机，经 `/ext/<id>/mcp` 回到主进程执行。这样扩展包的状态只有一份。
- **闲置休眠**：`[backend] resident = "on-demand"` 的扩展包同时满足下面几条，就卸下后端，下一次调用时冷启动（`init` 重跑，状态从 kv 回来）：
  - 没有订阅；
  - 没有定时器；
  - 没有排队的投递（主题值、定时器的触发）；
  - 没有在途的调用：方法调用、工具调用、事件钩子都算；
  - 闲置满 `idle_secs`（缺省 600 秒，60–86400）。

  工具调用跑在自己的调用 Store 里，不唤醒后端，除非它 `host.call` 后端。

### 9.2 模式 3：结构

```
前端（外壳 + 扩展包的 iframe） ──Harnix 协议──▶ 产品进程（路由、中枢、准入、监护、同意）
                                                  │  每个扩展包一对继承的 socketpair：
                                                  │  fd 3 扩展线（harnix-ext-wire@1） · fd 4 引擎线（Agix daemon 协议）
                                                  ▼
                                   <产品> ext-proc（每个扩展包一个，在沙箱里）
                                   ├─ 宿主核心（与模式 2 同一份）
                                   ├─ harnix-wasm（同一份）
                                   └─ 它自己的 Agix：装它的 Agix 插件和工具；产品收养成实例 proc.<id>
```

### 9.3 产品的职责：路由与旁路管理

- **路由**：
  - 前端对 `<id>.*` 的调用与订阅是路由表里的行，处理者经扩展线转给扩展进程。
  - 扩展进程调 `harnix.*` 时反向走，主体是 `ext:<id>`，判定与审计都在产品里做；它发来的调用 id、父调用、调用链、截止时间都只是提示，由产品重签、重算。
  - **它 space 里的会话**落在它自己的引擎 `proc.<id>` 上，但仍由产品的中枢持有：先订阅、给 `seq`、管队列；前端只和产品说话。
    中枢按「扩展的信任」防着这台引擎：不广播它的引擎事件、限它的帧、截断它报的标题与状态。
- **旁路管理**（不在数据路径上）：
  - 安装、验签、披露与同意：与模式 2 同一份代码（`packages`）。
  - 登记：产品照同意记录自己拼描述、自己登记；进程报上来的只做「⊆」与摘要比对，不同就杀掉。
  - 拉起与监护：建 socketpair、绑主体、套沙箱、fork + exec 本二进制；就绪、健康检查、退避重起、置于一旁、闲置回收与唤醒。
  - provider：把 `main` 的 provider 写进它引擎根的设置，变了推过去。
  - 秘密：只把同意过的 `env` 名字的值交给它。
  - 出口：`net` 在产品侧判，HTTP 请求经扩展线由产品代发。
  - 系统 space 控制台的「扩展」页签。
- 产品不跑扩展包的代码，也不跑它的 Agent。

### 9.4 扩展进程、扩展线与失败

- **`ext-proc` 是产品二进制的子命令**：
  - 没有第二个程序。门面在 feature `proc` 下替产品登记这个子命令，产品的 `main.rs` 一行不改；`[ext.packages] proc_program` 可以指向另外构建的、更瘦的二进制。
  - 子命令在读 profile、拿状态锁、装配任何扩展之前就分派：它不读 profile、不碰状态目录。
  - 启动时拿到：继承的 fd、包目录、运行目录；环境清空，`HOME`、`TMPDIR`、工作目录都在运行目录下。
  - 第一帧报它的版本、它链的 Agix 版本、虚拟机引擎的指纹，三样与产品逐字相等才放行。
- **扩展线**：继承的流上的 NDJSON JSON-RPC 2.0，双向；进程发的方法是 `proc.*`，产品发的是 `ctl.*`。**没有监听套接字**：别的进程没有东西可以连，
  身份就是拉起时拿到 fd 3 的那个子进程。**只做同机**：端口上的路径照路径传（解包后的包、运行目录都由进程自己读），所以两边必须在同一台机器上。
- **调用链随调用过线**：宿主核心发出的调用把它正在服务的那次入站调用当父调用；后端经产品回调自己时，产品算出的链里已经有这个扩展，
  进程里的宿主核心当场拒绝（`EXTENSION_UNAVAILABLE{reentrant}`），而不是等到超时把后端换掉。取消是调用的一部分（`$/cancel`），截止时间在接收方也执行。
- **扩展进程崩了**：
  - 它的方法答 `EXTENSION_UNAVAILABLE{starting}`（退避中）或 `{faulted}`（置于一旁）；`proc.<id>` 答 `INSTANCE_UNAVAILABLE`。
  - 产品不撤它的行，前端的订阅不随进程重启抖动；它的会话靠 Agix 的持久化回来，重新接上后 resync。
  - 起来之后 60 秒内崩溃 3 次就置于一旁；停用再启用会重来。进程自己查出的致命错（沙箱套不上、`.cwasm` 哈希不符）以退出码 78 退出，不重试。
- **产品重启了**：扩展进程随 stdin 断而退出；产品起来后照安装记录重新拉起、重新登记。

### 9.5 这一版没有的

- **按扩展包选载体**：一个产品的扩展包都跟产品选的那一个载体。
- **跨机的扩展进程、进程池与预热**：线是流上的 NDJSON，换成别的流不改协议，但这一版只做本机、按需拉起。
- **扩展进程的断网与模型中继**：网络开着、模型凭据在它的引擎里（§4）。出口已经只在产品侧判，provider 只是交给进程的一个字段，所以补上这两样不改线、不改包。

## 10. 作者在两种载体之间能观察到的不同

**包对载体中立——除了下面这几条。** [扩展包](harnix-ext-package.md) 列同一张表：

| | 模式 2（同进程，缺省） | 模式 3（进程） |
|---|---|---|
| `agent/` 装在哪 | `install_into` 列出的产品实例 | 它自己进程里的 Agix |
| 它 space 里的会话跑在哪 | 产品的实例（清单的 `instance`，缺省 `main`） | 它自己的引擎 `proc.<id>` |
| 产品的引擎策略（`PromptGate`、工具钩子、原生工具、场景层） | **生效** | **不生效**（有意：它的 Agent 是它自己的） |
| `install_into` 的产品实例 | 装 agent 包，会话直接用它的工具 | 只拿到它的工具（过线） |
| `fs:project` | 有 | **没有**：项目在沙箱外；工具调用里没有 `/project`，披露写明 |
| 它自己会话的项目目录 | 产品的项目 | 只能在它运行目录的 `work/` 下 |
| 它的会话内容在外壳里 | 受信内容 | 不受信内容：不执行 HTML、链接不自动打开、图片只许 `data:` |
| 崩溃、资源、文件 | 波及整个产品；虚拟机记账 | 只影响它；进程记账；沙箱（§4） |
| 延迟 | 进程内 | 每次多一跳 |

其余方面完全相同：清单、WIT、宿主函数、界面、桥、签名、商店、同意。作者只要守一条规矩：**不依赖两种载体之间的差异**。比如，不要假设自己的会话和产品的其它会话在同一个 Agix 里，
也不要假设产品的提示闸门或工具钩子会替你挡住什么。

**各载体能做什么**（扩展包是原生的子集，理由见 [概念与架构](concept_and_architecture.md) §4.5）：

| | 原生 | WASM 同进程 | WASM 进程 |
|---|---|---|---|
| 方法、主题、space、工具规格、iframe 面、行内点 | ✔ | ✔（清单） | ✔（清单） |
| 编译进外壳的 UI 包 | ✔ | ✗ | ✗ |
| 进页面的 ES 模块 | ✔ | 只 `trusted`（`ui.page`） | 只 `trusted` |
| 工具的实现 | `Tool`、`ToolProvider` | 组件的 `tools`，经载体的 `ToolProvider` | 同，在它自己的引擎里本地调；给产品实例的过线 |
| 工具钩子 | ✔ | ✔（`events`：观察与否决） | ✔（在它自己的引擎里；产品实例上的过线） |
| 场景层、`PromptGate`、凭据源、`admit_everywhere` | ✔ | ✗ | ✗（它自己的引擎用它自己的场景） |
| 实例模板 | ✔ | ✗ | ✗（它的引擎是收养的，不是模板） |
| 任意 HTTP 处理者 | ✔ | ✗（只有界面文件与载体的工具端点） | ✗ |
| 定义贡献点、定义能力、`cross_space()` | ✔ | ✗ | ✗ |
| 能力 | 内核目录与扩展声明的，装配时授予 | 可给扩展包的项，经同意 | 同，产品侧复核 |
| 范围 | 照每行的访问 | 只限自己的 space 与会话 | 同 |

## 11. 共享代码与分层

| 层 | crate | 管什么 | 模式 1 | 模式 2 | 模式 3 |
|---|---|---|---|---|---|
| 骨架 | `harnix-contract`、`harnix-kernel`、`harnix-authz`、`harnix-router`、`harnix-transport`、`harnix-hub`、`harnix-instance`、`harnix-engine-api`、`harnix-engine`、`harnix-supervise`、`harnix-assembly` | 协议、内部接口、准入、路由表、传输、中枢、实例登记表、Agix 接缝、子进程看护、装配与扩展宿主 | ✔ | ✔ | ✔（产品侧） |
| 扩展接口 | `harnix-ext`；门面 `harnix` | 扩展接口（S1）；`harnix::ext`、`harnix::engine`、`App`、`first_party`、`carriers` | ✔ | ✔ | ✔ |
| 第一方扩展 | `harnix-ext-{system,harnix-app,settings,plugins,observability,devices,flow}` | 各一个原生扩展，只依赖 `harnix-ext` | ✔ | ✔ | ✔ |
| 宿主组件接口 | `harnix-host-api` | 运行期登记、拉起扩展进程、给 daemon 配工具端点、收养（S3，凭 `extensions.manage`） | | ✔ | ✔ |
| 扩展包的管理 | `harnix-ext-packages` | 安装记录与同意、商店、升级与回滚、按名字选载体、把包登记成扩展 | | ✔ | ✔ |
| 载体 | `harnix-carrier-wasm` · `harnix-carrier-proc` | 模式 2 的载体 · 模式 3 载体的产品侧（拉起、复核、扩展线的产品一端、`proc.<id>` 的收养） | | ✔ · | · ✔ |
| 分发与信任 | `harnix-package` | 清单 `harnix-ext.toml`、包 `.hxext`、签名、商店与下载、披露、出口策略；打包工具 `harnix-pack` | | ✔ | ✔ |
| 端口与线 | `harnix-wasm-port` | 宿主核心要外面做的（`Kernel`：产品的；`Agent`：引擎的）与外面要它做的（`Control`），每个调用带 `CallMeta`；feature `socket` 是流上的扩展线 | | ✔ | ✔ |
| 宿主核心 | `harnix-wasm-host` | 生命周期、注册表、健康、分派、进度、休眠 | | ✔ | ✔（扩展进程侧） |
| 虚拟机 | `harnix-wasm` | wasmtime 的引擎、Store、健康、记账、休眠；feature `compile` 带 Cranelift | | ✔ | ✔（扩展进程侧） |
| 扩展进程的入口 | `harnix-proc`（库） | `ext-proc` 子命令跑的那一份：宿主核心 + 虚拟机 + 线的客户端 + 它自己的 Agix；Linux 上自己套 Landlock | | | ✔ |
| 前端 | 外壳核心、第一方 UI 包、桥、`@harnix/ext-sdk`、`@harnix/ext-kit`、行内点 | | ✔ | ✔ | ✔（完全一样） |

feature 的链：库 `harnix` 的缺省不带载体，应用自己选；`harnix-cli` 缺省开 `wasm`、`flow`。`wasm` 链进 `harnix-ext-packages` 与 `harnix-carrier-wasm`；
`proc` 链进 `harnix-ext-packages`、`harnix-carrier-proc` 与 `harnix-proc`，并登记子命令 `ext-proc`。两个都不开的构建里这些 crate 一个都不链，二进制里没有 wasmtime。

- **编译器**：产品构建不带 Cranelift。`harnix-package` 的 `compile` 拉上 `harnix-wasm/compile`，只给打包工具 `harnix-pack` 和测试用。
- **HTTP 出口**：扩展包的 HTTP 请求在产品侧按 `net` 判，由产品发出；模式 3 经扩展线（`proc.fetch`）交给产品。

这些边界由 `crates/harnix/tests/layering.rs` 守着：

- 分发与信任、端口、宿主核心这三层，不依赖骨架的内部（kernel、router、hub、instance、authz、transport、assembly）、扩展接口、HTTP 框架、wasmtime 和 Agix 的任何 crate；
  `harnix-package` 对 `harnix-wasm` 的依赖必须是可选的，`harnix-wasm-port` 的外部依赖不超出 async-trait、serde、serde_json（tokio 只在 `socket` 下）。
- 只有 `harnix-wasm` 链 wasmtime；它自己不依赖任何 Harnix crate，也不依赖 Agix。`harnix-wasm` 只被宿主核心、扩展进程的入口与 `harnix-package`（可选）依赖；
  宿主核心只被模式 2 的载体与扩展进程的入口依赖。
- `harnix-ext-packages` 不依赖任何载体与虚拟机；模式 3 载体的产品侧不链虚拟机与宿主核心，也不链扩展进程的入口；扩展进程的入口不链骨架的内部与扩展接口。
- 只有 `harnix-engine` 依赖 Agix；第一方扩展只依赖 `harnix-ext`，宿主组件另可依赖 `harnix-host-api`；`harnix-host-api` 只被装配与宿主组件依赖。
- 骨架、扩展接口、宿主组件的代码里没有按 feature 选载体的分支；只有门面与 `harnix-cli` 可以有。
- 端口要过一遍线（`UnixStream::pair` 上跑同一份代码：每个方法往返、取消、截止时间、伪造的元数据被纠正、背压、超长帧断开），证明两种载体是同一套语义。
