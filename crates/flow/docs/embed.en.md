# Embedding guide: `harnix-flow`

[中文](embed.zh-CN.md)

`harnix-flow` is the flow library: it reads flow definitions (flow packs) and run state (run
records), moves a run through its stations, and — with the runner — drives a host's sessions
through the flow and its skills. It links no Harnix crate and no Agix, and the directory can be
copied whole into another workspace. Harnix's own host is the extension `harnix-ext-flow`
(`crates/ext/flow`), which re-exports the library whole (`pub use harnix_flow::*`), gives the
runner Harnix's sessions, and connects runs to Harnix's methods and topics.

What a flow is and how one is written (stations, executors, exit conditions, rules, policies and
permissions, gates, hooks…) is the [flow guide](guide.en.md); this document is about how a host
uses the library.

## 1. What you get

```text
crates/flow/
  Cargo.toml           every dependency's version written here, none inherited from a workspace
  src/lib.rs           FLOW_API_VERSION, DEFINITION_FORMAT, RUN_FORMAT, the names at the root
  src/kernel/          the kernel: definitions, validation, references, run records, the engine,
                       parts and judging a call, the protocol layer
  src/store.rs         MemStore, FileStore, Hooked
  src/packs.rs         MemPacks, DirPacks, ProjectPacks
  src/dryrun.rs        dry runs: the kernel in a sandbox, everything outside it mocked
  src/wire.rs          the library's own rows (DefRow, defs_list)
  src/runner/          the runner (feature `runner`): a run's work carried out in a host's sessions
    host.rs            SessionHost — what the runner asks of the host — and what crosses it
    mod.rs             Runner, RunnerConfig, Changed, CatalogPacks
    testing.rs         ScriptedHost: a host played from a script
    …                  dispatch, sessions, turns, the main session, gates, hooks, worktrees, git,
                       the process directory, trust, the flow's tools
  src/conformance.rs   what every SessionHost must do, checked against a live one
  packs/examples/      an example pack (example-review): a host that copies the library can load,
                       validate and run it; Harnix builds it into its app
  docs/guide.*.md      the flow guide (it is GUIDE_EN, GUIDE_ZH)
  docs/embed.*.md      this document
  tests/               the kernel's tests; runner.rs (the runner end to end over ScriptedHost);
                       conformance.rs; the two guards surface.rs and deps.rs; golden.rs with its
                       golden runs in tests/golden/
  examples/flowctl.rs  the library from the command line: validate, schema, dry-run, run, show
  examples/demo_seed.rs  the real kernel drives a few demo flows into a few states, into a FileStore
```

Features:

| feature | on by default | brings |
|---|---|---|
| `runner` | yes | the runner, `ScriptedHost`, the conformance suite (`tokio-util`, `futures`; tokio's `time`, `process`, `macros`, `io-util`) |
| `webhooks` | yes | `Webhooks`, the hooks' HTTP transport (`reqwest` over rustls); off, a host gives its own `HookTransport` or no hook is delivered |
| `ts` | no | TypeScript declarations of the definitions, run records and the like (`ts-rs`), generated by the host |

With `default-features = false` the crate is the kernel alone, as it was before the runner.

## 2. What the host provides

The kernel does not know where runs are stored, who the users are, who may do what, or how a gate
runs: those are the traits in `kernel::host`, and the host hands them in.

| trait | does | ready in the library |
|---|---|---|
| `RunStore` | reads and writes run records and their history; `commit` is atomic and compares revs | `MemStore`, `FileStore::new(dir)`; `Hooked` wraps one, to change ids or refuse commits in tests |
| `Packs` | the flow pack: flows, skills, rules, policies, gates, hooks, and the catalog (`Catalog`: the scenes, programs, gates, tools… known here) | `MemPacks` (given in code), `DirPacks` (layered directories, `with_builtin`, `with_writable`), `ProjectPacks` (a project's own pack, read only when the project is trusted) |
| `Authorizer` | who may do what (confirm, claim, hand in, edit flows…); the host interprets `Actor` | `AllowAll` |
| `Tools` | the read-only tools `tool` gates call | `NoTools` |
| `Gates` | `host` gates: the application's own checks, by name | — |
| `Programs` | `kind: program` tasks: the application's code | — |
| `Clock` | what time it is | `SystemClock`, `FixedClock`, `ManualClock` (tests) |

`Engine::new(store, packs)` builds the engine; `with_authorizer`, `with_tools`, `with_clock`,
`with_lease_ms`, `with_retries`, `with_guarded`, `with_submit_scenes`, `with_main_scene`,
`with_workspaces` and `with_layout` configure it. Each operation (`create`, `submit`, `confirm`, `tick`…) loads,
computes and commits against revs, and only after the commit returns an
`Outcome { value, events, work, bookkeeping }`:

- `events`: what happened (`EVENT_KINDS` lists every kind), for the host to pass to its subscribers;
- `work`: the `WorkItem`s for the host to carry out after the commit — `Task` (a session, sub-agent
  or program task, already claimed by `flow:dispatch`, with its token), `Gate` (run a `command` or
  `host` gate and hand the result back through `gate_result`), `CloseSession` (a session a
  cancelled task used);
- `bookkeeping`: only a lease moved on; nothing in the run's summary changed, so the host need not
  publish its list of runs again.

Carrying the work out — `WorkItem::Task` (opening a session, sending the skill, taking the
hand-in, answering permission asks), `WorkItem::Gate`, hooks, worktrees, the process directory —
is the runner's (`harnix_flow::runner::Runner`, below). A host that uses the kernel alone does it
itself, calling `Gates` and `Programs` when it carries a work item out; they are not given to
`Engine`.

### The runner and the host's sessions: `SessionHost`

`Runner::new(engine, host, RunnerConfig)` makes the runner; `start()` takes up the work the store
says was handed out and not answered, opens or watches again every active run's main session, and
looks for expired leases; `stop(grace)` tells its tasks to stop waiting (runs are not cancelled —
the next start recovers their work). Every outcome of an engine call goes through `apply`
(`apply_for(run, ..)` when the outcome names no run, `settle(result)` for the whole result): its
events are broadcast (`events()`), the runs it touched are projected into their process
directories and told to the host (`changes()` → `Changed { runs, substantive }`, for a host that
publishes them), the hooks are told, and each work item is started on a task of the runner's own.
`start_run(input, by)` starts a run as the runner does (trust heard, worktree made, output
directory claimed); `end_worktree`, `ensure_main`, `hook_status`, `agents_of`, `run_of_session`,
`set_trust`, `hear` are the rest a host's methods call.

`RunnerConfig` is what the host offers sessions and hands in: `profiles` (the scene names
definitions write, which the catalog offers), `submit_profiles` (those whose sessions hand in with
`flow_submit`), `main_profile`, `project_profiles` (whose sessions need a project: a run of none
works in a directory of its own), `guarded` (`DEFAULT_GUARDED`), `command_gates`, `lease_ms`,
`tick_ms`, `hook_headers` (the prefix of a delivery's headers; Harnix: `X-Harnix`), `recording`
and `main_recording` (hosts that replay), `programs`, `gates`, `hook_transport`, and `trust` (an
`Arc<ProjectTrust>` shared with the packs). `CatalogPacks::new(&cfg, templates)` wraps the host's
packs with what the runner adds to the catalog (the profiles, the guarded tools, whether command
gates run, the host's own templates) and gives each project its view (`set_layout` first).

The runner knows sessions only through the trait `SessionHost` (`runner::host`): the host opens
them, sends to them, streams their frames, answers their questions. Everything that crosses it is
in the flow's words — a session is an opaque `SessionId` the host gives back from `open` and the
runner keeps in run records:

| method | the host does |
|---|---|
| `open(OpenSpec) -> Opened { id, existed }` | opens the session the spec describes, or answers the one its `key` already names |
| `lookup(id) -> Option<SessionInfo>` | whether a session a record names is still there (brought back when it was only on disk) |
| `watch(id) -> Watch { frames, info }` | its frames from now on, and whether a turn runs now |
| `send(id, text)` | a message, queued behind a turn that is running |
| `interrupt(id)`, `close(id)` | |
| `answer(id, ask, Decision)` | a permission question: `Allow`, or `Deny { reason }` |
| `note(id, Note)` | a card for people in the session's record (`flow_propose`'s proposal) |
| `project_trusted(root)` | whether the project is trusted (Harnix asks its engine) |
| `run_over(run)` | the run is over: what the host made for it alone can go (default: nothing) |

`OpenSpec` carries the `key` (`flow:<run>/<station>/<task>@<token>` for a task's own session,
`flow:<run>#<key>` for a shared one, `flow:<run>@main` for the main session), the `run`, `main`,
the `profile`, the main session's `title`, the `project_root`, the `Placement` (model, provider,
`effort`, and `instance`/`template`/`params`/`space` — names the host interprets, and refuses
rather than ignores when it does not know them), `asks` (tool patterns each call of which must come
as `Frame::Asked`), `output_schema` (with `Delivery::StructuredOutput`), `delivery`, `shown_in`,
`recording`, and `tools` (the flow's tools to register, §4). It is `#[non_exhaustive]`: fields
are added, never removed.

`Frame` is what the host reports of a session: `TurnStarted { turn, text }`, `ToolCall`,
`ToolResult`, `Asked { turn, ask, call, tool, paths, agent }`, `AgentStarted`, `AgentEnded`,
`TurnSettled { turn, end: TurnEnd, output, usage }` and `Lagged`. `TurnEnd` is `Done`,
`Interrupted` or `Error { retryable, kind, message }` — a turn that failed for good (no
credentials) fails the attempt at once; one that may go through again (a rate limit) is treated as
a turn that handed in nothing. `HostError` is `Gone` (the attempt fails: "the session went away"),
`Refused` (the attempt fails with the reason), `Unavailable` (the runner gives up without a
failure; the lease lapses and the next start recovers) or `Other` (logged, as `Unavailable`).

**The contract** (what the runner relies on; the conformance suite checks it, §5):

- Frames arrive in order: `TurnStarted(t)` before anything of `t`, `TurnSettled(t)` last. A host
  that falls behind may drop frames in between and say so with `Lagged`; it never drops a
  `TurnSettled`.
- `open` is idempotent: the same `key` again answers the same id with `existed: true`; the same
  key with another spec is `Refused`. A host that can (Harnix, with an id derived from the key)
  keeps that across its own restarts; one that cannot keeps it at least within a process.
- `send` queues: a running turn is not cut off, and one send starts exactly one turn, whose
  `TurnStarted.text` is the text sent (the runner tells its own turns in the main session by it).
- `interrupt` on an idle session is `Ok`; on a running turn a `TurnSettled { end: Interrupted }`
  follows. `answer` for a question whose turn is over is `Ok` or `Gone`. After `close`, the
  watchers' streams end and `send` is `Gone`.
- Only permission questions come as `Asked`; a question for words (the model's, an MCP server's)
  is a person's. The host sends `Asked` for the tools the spec's `asks` named, and for what it
  holds back on its own (a write outside the project, into a reserved directory).
- The runner stops only by not waiting; it never asks the host to cancel. A task that is over
  while its turn runs is interrupted and waited for (30 s) before its session serves the next.

`ScriptedHost` (`runner::testing`) is a `SessionHost` played from scripts of turns
(`Turn::{Ends, Runs, Asks, Errors}`), by station, for the main session, or for a shared key: with
it the runner drives a whole pack from start to finish with no model (`tests/runner.rs`,
`examples/flowctl.rs`).

### Where it writes for a project: `ProjectLayout`

The library has no name of its own for a project's data directory, and no place for worktrees: the
host says, with `ProjectLayout { dir, worktrees_root, branch_prefix, agent_dirs }`
(`Engine::with_layout`; there is no default). Harnix gives `.harnix`, its flow extension's data
directory's `worktrees`, `harnix/flow`, and `scratchpad`, `memory`, `worktrees` as the directories
of `.harnix/` its engine's sandbox lets a session write (`with_agent_dirs`).

```text
<project>/<dir>/flows/        the project's own pack, committed with it (ProjectPacks::new takes the
                              layout; read only while the project is trusted)
<project>/<dir>/runs/<run>/   a run's process directory; `<dir>/.gitignore` gets the one line `runs/`
<worktrees_root>/<run>/       a run's worktree, outside every project, on <branch_prefix>/<run>
```

The data directory may be shared with others — Harnix shares `.harnix` with its engine, which keeps
its settings, memory and its own worktrees there — so the library uses `flows/` and `runs/` in it
and nothing else, adds only its own line to the `.gitignore`, and keeps its worktrees out of it.

Judging a call (`judge_under`) takes the directories that count as outside the project although
they are in it (`Call::reserved`; `ProjectLayout::reserved(root)` gives the data directory): a
task's tools may not touch them unless an `allow` whose own `paths` point into one says so —
`${workspace}/**` does not. The directories in it the host names as its sessions' own
(`Call::agent_dirs`; `ProjectLayout::agent_dirs_in(root)`) are judged as any path in the project.
Whatever the host writes there itself (a flow saved by its authoring tool, the process
directories) is not judged.

### What a session is opened with

A session task's `WorkItem::Task` carries a `Placement`: model, provider, `effort` (how hard the
model reasons, one of `EFFORTS`; the host's settings when absent), and where the session goes
(`instance`, `template`, `params`, `space` — names the host interprets; a host that does not
know one refuses the session rather than ignore it). The host opens the session with them and tells
the kernel what it opened it with: `attach_session(.., session_key, opened_with, ..)` and
`attach_main(run, session, opened_with)`. The run keeps it on the key (`BoundSession { id,
opened_with }`): a later task of the same key is checked against it before it works in that
session. `opened_with` is the host's own JSON; the kernel only keeps it.

`CreateIn::shown_in` is where else the host shows the run's main session — a place the host names
(Harnix: a space besides the flow's); the kernel records it on the run.

## 3. Storage, packs and what is written for a project

- **Runs**: a `RunStore` — `FileStore::new(dir)` keeps `<id>.json`, `<id>.history.jsonl`,
  `ids.json` and `FORMAT` in `dir`; `MemStore` for tests and dry runs.
- **Packs**: a `Packs` — `DirPacks::new([dirs…])` reads `flows/*.yaml`, `skills/<name>/SKILL.md`,
  `rules/*.md`, `policies/*.yaml`, `gates/*.yaml`, `hooks/*.yaml` from layered directories
  (`with_writable` for one that is saved into, `with_builtin` for a `MemPacks` underneath,
  `with_catalog` for the names the host knows); `CatalogPacks` over it for the runner.
- **Runs of no project**: `Engine::with_workspaces(dir)` — a run of no project that needs a
  directory (a session on a `project_profiles` profile, a gate, its output directory) gets
  `<dir>/<run>`.
- **In a project** (`ProjectLayout`, above): its own pack in `<project>/<dir>/flows/`, read while
  trusted; each run's process directory `<project>/<dir>/runs/<run>/` — `task.json` (the run as
  it stands, rewritten after each change), `flow.yaml` (the definition and parts pinned at start),
  `stations/<station>/` with each hand-in (`output.json`, or `<task>.json` each), a command gate's
  `context.json` and `gate-<gate>.log`; `<dir>/.gitignore` gets the one line `runs/`. A run's
  output directory (the start's `output_dir`, the flow's, or `flows/${flow}-${date}${seq}`) is
  made at start, inside the project (inside its worktree for a worktree run).
- **Worktrees** (`workspace: worktree`): `<worktrees_root>/<run>` on `<branch_prefix>/<run>` from
  the project's `HEAD`, made at start; once the run is over, `Runner::end_worktree(run, how, by)`
  merges the branch into the project's current branch (fast-forward or a merge commit; a conflict
  is `EndError::Conflict { files, .. }` with the project untouched), keeps it, or discards it. The
  project's data directory in the worktree is not committed, but for its `flows/`.
- **Hooks**: each event of a run goes to the hooks of the pack (and of the project's) that want it,
  as `POST`s through the `HookTransport` with the headers `<prefix>-Event`, `-Delivery`,
  `-Timestamp` and, with `secret_env`, `-Signature` (HMAC-SHA256 of `<timestamp>.<body>`);
  `Runner::hook_status()` lists each hook with its last delivery.

## 4. The flow's tools and the questions it answers

Every flow session has three tools of the flow's own — `flow_state`, `flow_submit {output}`,
`flow_propose {kind, to?, reason}` — which the host registers to the session (`OpenSpec::tools`
carries their specs; `runner::tool_specs()` gives them without a runner) and answers by routing
each call to `Runner::tools().call(session, tool, input)` with the session's id: the runner finds
the task the session serves and answers in text (`ToolReply { text, is_error }`). Harnix wraps
each of its scenes as `flow-<scene>` with the three tools added; a host over an engine's RPC
registers them as the session's host tools and answers each call the same way.

A task's permission questions are the runner's to answer: the host opens the session so that each
call of the tools in `OpenSpec::asks` (every guarded tool and every tool a permission of the
flow names: `ask_rules(&asks)` is the rule list Harnix hands its engine) comes as `Frame::Asked`,
and the runner answers through `SessionHost::answer` from the permissions of the task the turn
works on — `allow` permitted, `deny` refused with the reason, `ask` left to a person (the run
waits for `approval`; the host shows the question to people as it would any other). A question of
a turn no task owns (a person talking to the main Agent) is not answered by the runner.

## 5. Dry runs, `flowctl` and the conformance suite

A dry run (`Sandbox::new(packs, config)`) needs only the flow pack: the real kernel runs in memory
(`MemStore`), and no session, program, gate or tool is called — the caller mocks their results
(`Mocks`), or the contract's examples stand in.

`examples/flowctl.rs` is the library from the command line, with nothing of any host:

```text
cargo run -p harnix-flow --example flowctl -- validate <pack-dir> [--catalog catalog.json]
cargo run -p harnix-flow --example flowctl -- schema definition|run|tools|policy|gate|hook
cargo run -p harnix-flow --example flowctl -- dry-run <pack-dir> <flow> [--inputs '{}'] [--mocks '{}']
cargo run -p harnix-flow --example flowctl -- run <pack-dir> <flow> --script script.yaml [--state <dir>] [--project <dir>]
cargo run -p harnix-flow --example flowctl -- show <state-dir> <run>
```

`run` drives the flow with the runner over a `FileStore` and sessions played from a YAML script
(the main session's turns, each station's, each shared key's), printing each event; it ends when
the run is over or waits for a person. A host that copied the library runs it unchanged: that is
the check that the copy loads, validates and runs the example pack.

`harnix_flow::conformance::run_all(&Subject)` is what every `SessionHost` must do, checked against
a live one: a key opens once; a send starts exactly one turn, which settles; an idle interrupt is
`Ok`; a question comes and is answered; a closed session is gone; a note and the trust question are
answered. A host gives its `Subject` — itself, a profile, a message that makes a session answer and
stop, and (when it can) one that makes it call a guarded tool — and asserts the failures are none.
`ScriptedHost` runs it with a script (`tests/conformance.rs`), which keeps the suite itself honest;
Harnix runs it against its hub with a recording.

## 6. Versions and formats

| number | now | where | goes up when |
|---|---|---|---|
| `FLOW_API_VERSION` | `1` | `src/lib.rs` | the library's Rust interface changes in a way that breaks a host: the traits a host implements (`SessionHost` among them), the types they hand over and take, the names at the root, how the stores and packs are built, what the runner offers. `tests/surface.rs` keeps those tables |
| `DEFINITION_FORMAT` | `1` | `src/lib.rs` | the meaning of the definition and part formats changes. Adding a field with a default does not raise it (definitions refuse unknown fields, so an older library reading a newer field says so clearly) |
| `RUN_FORMAT` | `1` | `src/lib.rs` | the format of run records, histories and run ids changes. `tests/golden.rs` keeps the records and histories of a few runs, which move with it |

Where they are written:

- a definition and each part may say `format: N` (absent: 1, and 1 is not written back). One whose
  number is greater than `DEFINITION_FORMAT` is refused whole — validation says which format it
  needs, before any field this library does not know — and `0` or a word is no format;
- every run record says its `format`. A `FileStore` writes the file `FORMAT` (`1`) into its
  directory with the first run, and refuses — every call, with why — a directory whose `FORMAT` is
  greater than `RUN_FORMAT`, or one that holds runs and no `FORMAT` (written before formats were
  kept); a record of a greater format is refused on its own. Nothing is read in part.

The promise:

1. The public surface only grows; each addition gets a line in the version section below and goes
   into the tables of `tests/surface.rs`.
2. Only a removal, a rename or a changed signature raises `FLOW_API_VERSION`, and the version
   section then says what a host changes.
3. Within one format number fields are only added, each with a default; a rename or a removal
   raises it. A format number that goes up comes with which fields changed and what the host does
   about it, and the golden runs change with it; no migration code is provided (a host clears the
   old data, or migrates it itself).

## 7. Copying it

1. Copy the whole `crates/flow` directory into your workspace and list it in `members`. It reads
   neither `[workspace.dependencies]` nor `[workspace.package]`, so its `Cargo.toml` needs no
   change; to share a version your workspace already has, compare with the table above.
2. `cargo test -p harnix-flow`: the kernel's and the runner's tests, and two guards —
   - `tests/deps.rs` reads `cargo metadata` in your workspace: nothing of Harnix, nothing of Agix
     and no crate by local path in what it compiles, and nothing inherited from the workspace in
     its `Cargo.toml`;
   - `tests/surface.rs` parses the source and checks the public surface against its tables. When
     you change the library it says which change breaks hosts and which addition to write down.
3. Harnix's `scripts/check-flow-copy.sh` does exactly this: it copies the directory into a
   temporary workspace of its own, with no `Cargo.lock`, then builds and tests it there.

## 8. Versions and migrations

One section per `FLOW_API_VERSION`, newest first.

### `FLOW_API_VERSION = 1`

The library's first version: the kernel, stores, packs and dry runs move out of `harnix-ext-flow`;
`DEFINITION_FORMAT = 1`, `RUN_FORMAT = 1`. Within it, before it was first released:

- **The runner** (`runner`, feature `runner`, on by default): `Runner`, `RunnerConfig`, `Changed`,
  `CatalogPacks`, `FlowTools`/`tool_specs`, `DEFAULT_GUARDED`, `withheld`, `worktree_info`,
  `EndError`, `redact_url`; the trait **`SessionHost`** with `OpenSpec`, `Opened`, `SessionInfo`,
  `Watch`, `Frame`, `TurnEnd`, `Decision`, `Note`, `HostError`, `ToolSpec`, `SessionId`;
  `HookTransport` and `Webhooks` (feature `webhooks`); `ScriptedHost` and `Turn`;
  `conformance::{Subject, Failure, run_all}`; `wire::defs_list`.
- **`ProjectLayout`** (new, at the root): the project's data directory, the worktrees' root and
  their branch prefix, given by the host — `Engine::with_layout`, `Engine::layout` (in place of the
  fixed `kernel::refs::worktree_dir` and `worktree_branch`, both removed); `project_pack_dir(root,
  &layout)` and `ProjectPacks::new(base, root, &layout, trusted)` take it. The `.gitignore` line is
  `runs/` alone; worktrees are no longer in the project.
- **`ProjectLayout::agent_dirs`** (`with_agent_dirs`, `agent_dirs_in`) and **`Call::agent_dirs`**:
  the directories of the data directory a task's session writes as its own.
- **`Call::reserved`**: directories inside the root that count as outside it when a call is judged.
- **Formats written**: `format` on `FlowDef`, `PolicyDef`, `GateDef`, `HookDef` and `RunRecord`; the
  `FORMAT` file of a `FileStore`, which no longer reads a directory of runs without one.
- **`shown_in`** in place of `show_in_space` (`CreateIn`, `RunRecord`, `RunSummary`).
- **`BoundSession { id, opened_with }`** (new, at the root): what `RunRecord::session_keys` maps a
  key to, in place of the bare session id; `attach_session` and `attach_main` take `opened_with`.
- **`effort`** on a session executor, `MainSession` and `Placement`; `EFFORTS` (new, at the root).
- The example pack (`packs/examples`) and the golden runs (`tests/golden.rs`).

Migration: a host that used the kernel from `harnix-ext-flow` keeps `harnix_ext_flow::X` (it
re-exports the whole library); one that depends on the library directly writes `harnix_flow::X`.
Run state written before these changes is not read: `show_in_space` and the bare session ids are
gone, and a store directory without `FORMAT` is refused — clear it, or migrate it by hand.
