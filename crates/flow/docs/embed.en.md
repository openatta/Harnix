# Embedding guide: `harnix-flow`

[中文](embed.zh-CN.md)

`harnix-flow` is the flow library: it reads flow definitions (flow packs) and run state (run
records), and moves a run through its stations. It links no Harnix crate and no Agix, and the
directory can be copied whole into another workspace. Harnix's own host is the extension
`harnix-ext-flow` (`crates/ext/flow`), which re-exports the library whole
(`pub use harnix_flow::*`) and connects runs to Harnix's sessions, methods and topics.

What a flow is and how one is written (stations, executors, exit conditions, rules, policies and
permissions, gates, hooks…) is the [flow guide](guide.en.md); this document is about how a host
uses the library.

## 1. What you get

```text
crates/flow/
  Cargo.toml           every dependency's version written here, none inherited from a workspace
  src/lib.rs           FLOW_API_VERSION, DEFINITION_FORMAT, RUN_FORMAT, the names at the root
  src/kernel/          the kernel: definitions, validation, references, run records, the engine,
                       parts and judging a call, the protocol layer
  src/store.rs         MemStore, FileStore, Hooked
  src/packs.rs         MemPacks, DirPacks, ProjectPacks
  src/dryrun.rs        dry runs: the kernel in a sandbox, everything outside it mocked
  src/wire.rs          the library's own rows (DefRow)
  docs/guide.*.md      the flow guide (it is GUIDE_EN, GUIDE_ZH)
  docs/embed.*.md      this document
  tests/               the kernel's tests, and the two guards surface.rs and deps.rs
  examples/demo_seed.rs  the real kernel drives a few demo flows into a few states, into a FileStore
```

Features: only `ts` (off by default) — TypeScript declarations of the definitions, run records and
the like (`ts-rs`), generated by the host.

## 2. What the host provides

The kernel does not know where runs are stored, who the users are, who may do what, or how a gate
runs: those are the traits in `kernel::host`, and the host hands them in.

| trait | does | ready in the library |
|---|---|---|
| `RunStore` | reads and writes run records and their history; `commit` is atomic and compares revs | `MemStore`, `FileStore::new(dir)`; `Hooked` wraps one, to change ids or refuse commits in tests |
| `Packs` | the flow pack: flows, skills, rules, policies, gates, hooks, and the catalog (`Catalog`: the scenes, programs, gates, tools… known here) | `MemPacks` (given in code), `DirPacks` (layered directories, `with_builtin`, `with_writable`), `ProjectPacks` (a project's own pack, read only when the project is trusted) |
| `Authorizer` | who may do what (confirm, claim, hand in, edit flows…); the host interprets `Actor` | `AllowAll` |
| `Tools` | the read-only tools `tool` gates call | `NoTools` |
| `Gates` | `host` gates: the application's own checks, by name | — |
| `Programs` | `kind: program` tasks: the application's code | — |
| `Clock` | what time it is | `SystemClock`, `FixedClock`, `ManualClock` (tests) |

`Engine::new(store, packs)` builds the engine; `with_authorizer`, `with_tools`, `with_clock`,
`with_lease_ms`, `with_retries`, `with_guarded`, `with_submit_scenes`, `with_main_scene` and
`with_workspaces` configure it. Each operation (`create`, `submit`, `confirm`, `tick`…) loads,
computes and commits against revs, and only after the commit returns an
`Outcome { value, events, work, bookkeeping }`:

- `events`: what happened (`EVENT_KINDS` lists every kind), for the host to pass to its subscribers;
- `work`: the `WorkItem`s for the host to carry out after the commit — `Task` (a session, sub-agent
  or program task, already claimed by `flow:dispatch`, with its token), `Gate` (run a `command` or
  `host` gate and hand the result back through `gate_result`), `CloseSession` (a session a
  cancelled task used);
- `bookkeeping`: only a lease moved on; nothing in the run's summary changed, so the host need not
  publish its list of runs again.

In this version, carrying out `WorkItem::Task` (opening a session, sending the skill, taking the
hand-in, answering permission asks), running `command` gates and delivering hooks are still the
host's; Harnix does it in `crates/ext/flow/src/module/`. The host calls `Gates` and `Programs`
itself when it carries out a work item; they are not given to `Engine`.

A dry run (`Sandbox::new(packs, config)`) needs only the flow pack: the real kernel runs in memory
(`MemStore`), and no session, program, gate or tool is called — the caller mocks their results
(`Mocks`), or the contract's examples stand in.

## 3. Versions and formats

| number | now | where | goes up when |
|---|---|---|---|
| `FLOW_API_VERSION` | `1` | `src/lib.rs` | the library's Rust interface changes in a way that breaks a host: the traits a host implements, the types they hand over, the names at the root, how the stores and packs are built. `tests/surface.rs` keeps those tables |
| `DEFINITION_FORMAT` | `1` | `src/lib.rs` | the meaning of the definition and part formats changes. Adding a field with a default does not raise it (definitions refuse unknown fields, so an older library reading a newer field says so clearly) |
| `RUN_FORMAT` | `1` | `src/lib.rs` | the format of run records, histories and run ids changes |

The two format numbers are only declared in this version, not yet written into a definition or a
record; one without a number is format 1.

The promise:

1. The public surface only grows; each addition gets a line in the version section below and goes
   into the tables of `tests/surface.rs`.
2. Only a removal, a rename or a changed signature raises `FLOW_API_VERSION`, and the version
   section then says what a host changes.
3. A format number that goes up comes with which fields changed and what the host does about it;
   no migration code is provided (a host clears the old data, or migrates it itself).

## 4. Copying it

1. Copy the whole `crates/flow` directory into your workspace and list it in `members`. It reads
   neither `[workspace.dependencies]` nor `[workspace.package]`, so its `Cargo.toml` needs no
   change; to share a version your workspace already has, compare with the table above.
2. `cargo test -p harnix-flow`: the kernel's tests, and two guards —
   - `tests/deps.rs` reads `cargo metadata` in your workspace: nothing of Harnix, nothing of Agix
     and no crate by local path in what it compiles, and nothing inherited from the workspace in
     its `Cargo.toml`;
   - `tests/surface.rs` parses the source and checks the public surface against its tables. When
     you change the library it says which change breaks hosts and which addition to write down.
3. Harnix's `scripts/check-flow-copy.sh` does exactly this: it copies the directory into a
   temporary workspace of its own, with no `Cargo.lock`, then builds and tests it there.

## 5. Versions and migrations

One section per `FLOW_API_VERSION`, newest first.

### `FLOW_API_VERSION = 1`

The library's first version: the kernel, stores, packs and dry runs move out of `harnix-ext-flow`,
with their interface and behaviour as they were; `DEFINITION_FORMAT = 1`, `RUN_FORMAT = 1`.

Migration: none. A host that used them from `harnix-ext-flow` keeps `harnix_ext_flow::X` (it
re-exports the whole library); one that depends on the library directly writes `harnix_flow::X`.
